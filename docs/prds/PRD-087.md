# PRD-087: Identity and Event-Sequence Invariants

## Objective

The bug ledger runs to dozens of entries and the bugs are not typos:
identity taken from the wrong worktree, checkpoint event identifiers
colliding across occurrences, review recovery refusing its own
pre-migration rows. Almost all were found by running the product, which
speaks well of the dogfooding and badly of the design-time reasoning. The
shape they share is an invariant that exists only in prose — which
worktree is authoritative for identity, how an event identifier is
minted, what a row written before a migration is permitted to look like.
Prose invariants are rediscovered in production; enforced ones are not.

## Design

- **One minting site per identity family.** Repository identity, and
  checkpoint or occurrence event identity, each get a single enforced
  home. Every other caller goes through it. Concurrency and worktrees
  stop being places where identity can be derived differently.
- **Migration tolerance is explicit.** A recovery path either accepts the
  schema its own rows were written under or the rows are migrated with a
  record. Refusing your own history is neither.
- **Invariants run in the gate.** Each is a check that fails loudly when
  violated and fails when deleted, so the enforcement cannot rot into a
  comment.
- **The ledger is the coverage list.** Every past entry in these families
  points at the invariant that now covers it. Uncovered is a recorded
  state, not an absence.

## Scope

The single minting sites for repository identity and checkpoint or
occurrence event identity; worktree-origin resolution; pre-migration row
tolerance in the recovery paths that own those rows; gate-resident
invariant checks with mutation regressions; ledger-to-invariant linkage;
regressions in a dedicated test file.

Out of scope: the remaining ledger families that are not identity or
event sequencing, verification truth (PRD-067), integration and
admission (PRD-077), and any schema redesign beyond the migrations these
invariants require.

## Assumptions (recorded at specification time, 2026-09-04)

- The three named families cover the majority of the fundamental ledger
  entries; the linkage criterion will show whether that is true, and a
  large uncovered remainder is a finding this PRD is expected to surface
  rather than hide.
- Enforcing an invariant may expose existing durable rows that violate
  it; those are migrated with a record, never deleted.
