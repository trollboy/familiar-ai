# PRD-111: Verification Checks Are Named Definitions

## Objective

The verification checks are the most repeated thing in the settings form. On
this repository the global file carries six `[[review.verification]]` entries,
each with the same Docker argv prefix, the same `PATH` environment and the
same working directory, differing in `check_id`, the command tail and the
timeout. The form can only render an anonymous array as `review.verification.0`
through `.5`, each with its own `environment` sub-section, so one repository's
Settings tab shows twelve boxes for what is one list of six names. A project
can inherit the whole array or replace it wholesale; it cannot say "the same
checks, but `clippy` is optional here".

The owner's read on seeing it: *"these look like several different verification
items — once again it calls for a Verification factory model."* This is the
same shape as PRD-110: a definition made once at global scope, referenced by
name wherever it is needed, with a per-project list and per-project overrides
of the fields that legitimately vary.

## Design

### Checks: defined once, by name

```toml
[checks.fmt]
argv = ["/usr/bin/docker", "compose", "-p", "familiar-ai-verify", "run", "--build", "--rm", "test",
        "sh", "-c", "rustup component add rustfmt >/dev/null 2>&1; cargo fmt --all -- --check"]
required = true
timeout_ms = 900000
working_directory = "."
environment = { PATH = "/usr/local/bin:/usr/bin:/bin" }

[checks.clippy]
argv = ["/usr/bin/docker", "compose", "-p", "familiar-ai-verify", "run", "--build", "--rm", "test",
        "sh", "-c", "cargo clippy --workspace --all-targets --no-default-features -- -D warnings"]
required = true
timeout_ms = 900000

[checks.tests-green-crates]
argv = ["/usr/bin/docker", "compose", "-p", "familiar-ai-verify", "run", "--build", "--rm", "test",
        "sh", "-c", "cargo test --workspace --no-default-features"]
required = true
timeout_ms = 1200000
```

A check's name is today's `check_id`; the fields are today's fields. Nothing a
check can express changes. What changes is that it is defined once and
referenced.

### Assignment: which checks, in what order

```toml
[assignments]
verification = ["fmt", "clippy", "tests-green-crates"]

[repositories."/home/trollboy/Projects/spectra".assignments]
verification = ["spectra-lint", "spectra-test"]     # replaces the list

[repositories."/home/trollboy/Projects/spectra".checks.spectra-test]
timeout_ms = 1800000                                 # overrides one field of a named check
```

The `assignments` table is the one PRD-110 introduces for workers; this PRD
adds the `verification` key to it. If PRD-110 has not landed, this PRD
introduces the table with only that key and PRD-110 adds the rest. The review
runs the effective list in order and records each check under its name, as it
does today under `check_id`.

A repository override of a named check may change `required`, `timeout_ms`,
`working_directory` and `environment`. It may not change `argv`: a different
command is a different check and gets its own name. This keeps "the same
check" meaning the same thing across repositories in the accounting and the
session report.

### Rewrite on load

Each `[[review.verification]]` entry, global or per repository, becomes
`[checks.<check_id>]` and the array becomes the corresponding `verification`
list, in the array's order. Two entries with the same `check_id` and
different argv are a load error naming the id, since they were already
ambiguous in the session report. One log line per rewrite names the old
position and the check it became. The old key is documented as deprecated;
removing it is a later PRD.

### The settings surface

- **Global page, Checks pane**: one section per named check, with argv,
  required, timeout, working directory and environment. Add, rename, remove.
- **Project page, Verification row**: the effective ordered list, its origin
  (global or override), a picker of defined check names to add, remove and
  reorder, and beneath each name the fields a repository may override with
  their origin. The `review.verification.N` and `.N.environment` sections are
  gone.

Every save runs the daemon's own loader (FAM-BUG-094).

## Scope

In scope: the `checks` table, the `verification` assignment, per-repository
field overrides of a named check, the in-memory rewrite of the legacy arrays,
the review running the effective list, the contract document, the Tauri and
GTK settings surfaces.

Out of scope: changing what a check can do or how its verdict is recorded;
the preflight commands, which are a different list with a different job;
removing the legacy key from the schema.

## Assumptions (recorded at specification time, 2026-09-24)

- `check_id` values are unique per file today; the rewrite treats a
  duplicate with differing argv as an error rather than guessing.
- Environment for a check is a flat string map, as today.
- The order of checks matters to the operator reading the report, so the
  list is ordered and the rewrite preserves the array order.
