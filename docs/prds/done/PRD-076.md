# PRD-076: Scope Modularization for Parallel Authoring

## Objective

Make waves real. The owner's definition — and the correct one — is that a
wave is a batch of PRDs runnable simultaneously: dependency-ready AND
mutually scope-disjoint. Under today's file layout the remaining backlog
satisfies only the first half: computed against the scheduler's own
conflict rules it partitions into roughly twenty-three width-one rounds,
a chain, because four shared surfaces sit in nearly every PRD's declared
scope — the monolithic `config.rs`, the single `providers.md` contract
document, the CLI binary source, and whole shared test directories. This
PRD is pure file organization: split the hot surfaces into per-feature
files so pending PRDs can declare disjoint scopes, amend those
declarations, and regenerate the execution plan as computed true rounds.
No behavior changes; concurrency is recovered from layout alone. After
this PRD the same backlog partitions into on the order of nine rounds
with widths of two to five.

## Design

- **Config module tree.** `config.rs` becomes `config/` with per-feature
  modules (providers, registry/workers, driver, review, delivery,
  accounting, compression, context service, credential store…), re-
  exported so every existing consumer compiles unchanged. The equivalence
  oracle is a pinned fixture configuration resolving to an identical
  effective configuration before and after — behavior is proven
  preserved, not asserted.
- **Per-domain contracts.** the former providers contract (index now at `docs/contracts/providers-index.md`) splits by
  domain (inference providers, billing sources, deploy targets,
  credential authentication, registry migration) with an index document;
  existing text moves verbatim. Each pending PRD then owns its contract
  file instead of a section of a shared one.
- **Dispatch-only CLI binary.** `bin/familiar-ai.rs` keeps argument
  parsing and dispatch; subcommand bodies live in per-domain `cli/`
  modules (the `config_cli.rs` pattern, completed). Pending PRDs
  extending the CLI declare their module, not the binary.
- **Declaration amendment.** With the surfaces split, every pending PRD's
  `expected_files` narrows to the per-feature files it genuinely touches
  (shared test directories become dedicated per-PRD test files; storage
  repositories become per-feature repository files; the migrations
  directory stays as-is — PRD-066's number allocation already handles
  it). This PRD's approval is the recorded owner authorization for
  amending those signed-off contracts, and fixture pins update
  accordingly.
- **The plan tells the truth.** The execution plan's wave rows regenerate
  as computed rounds from the amended declarations using the scheduler's
  conflict rules — the same computation PRD-066's authoring-time
  validation performs — and the plan states the wave definition
  explicitly so the term cannot drift again.

## Scope

The three mechanical splits with behavior-preservation proof, the
backlog-wide expected_files amendment with fixture updates, and the plan
regeneration. Explicitly a refactor: no new features, no semantic
changes, no migrations.

Out of scope: splitting `billing.rs` per provider (PRD-052/054 may do so
themselves if they want to co-run), any change to scheduler or conflict
semantics (PRD-065/066 own them), and legacy-format PRDs' body prose
(032 and 038 get amended Expected Files sections only).

## Assumptions (recorded at specification time, 2026-08-31)

- Rust re-exports make the config split invisible to consumers; no call
  site outside the config module tree needs to change for the refactor
  itself.
- Amending pending PRDs' expected_files under this PRD's authorization is
  compatible with the content-hash discipline: each amended PRD's new
  hash reconciles as a normal document update since all are `pending`.
