# PRD-017: Backlog Driver Loop

**Status:** Ready for implementation
**Date:** 2026-08-04
**Depends on:** PRD-011, PRD-012, PRD-016
**Architectural direction:** Autonomy Fails Closed; Determinism Before Intelligence; Memory Must Be Durable
**Delivery boundary:** Independently mergeable unattended loop over the existing single-PRD run workflow

## Objective

Add `familiar-ai drive`: execute eligible backlog PRDs one after another through the existing, unchanged single-PRD run workflow until the backlog is empty, nothing is eligible, or a global budget warrant is exhausted — recording a durable driver-session audit that says exactly what ran, what stopped, why, and what it cost.

The loop adds no new execution semantics. Each iteration is precisely today's `familiar run` workflow: admission, claim, implementation, verification, isolated review, fail-closed completion or retained `in_progress`. The driver contributes only deterministic selection, a budget warrant, loop-termination rules, and durable session records.

## Motivation

Familiar can execute one PRD end-to-end but a human must relaunch it for each entry. The north star's Stage 1 requires "run until backlog empty, budget exhausted, or nothing eligible" under a global overnight warrant. Every building block exists — eligibility selection (`BacklogManager::next`), fail-closed completion (PRD-011), audited recovery for retained entries (PRD-012), review on Linux (PRD-016). The driver composes them into an unattended loop whose failure mode is a precise, durable account rather than a stalled terminal.

## Scope

This PRD includes:

1. A `drive` CLI subcommand executing the loop with the same composition-root agent construction as `run`.
2. Deterministic selection: each iteration picks the next eligible PRD exactly as `familiar-ai next` does; a PRD attempted in this session is never attempted again in the same session regardless of its resulting status.
3. A typed budget warrant in configuration — maximum PRDs per session, maximum known cost, maximum wall-clock duration — where at least one finite ceiling is required for `drive` to start, and CLI flags may only lower configured ceilings, never raise them.
4. Fail-closed cost accounting: per-run cost comes from the existing execution-history estimation; when a cost ceiling is configured and a run's cost is unknown, the session stops after that run with a distinct `cost_unknown` reason — unknown is never treated as zero.
5. Loop termination reasons as closed typed values: `backlog_empty`, `nothing_eligible`, `budget_prds_exhausted`, `budget_cost_exhausted`, `budget_duration_exhausted`, `cost_unknown`, `storage_failure`, `interrupted`.
6. Durable session records: a driver-session row (start, end, warrant snapshot, termination reason) and one row per attempt (PRD identity, execution id, outcome, retained reason when applicable, known cost/duration) written through a new additive storage migration; records are written before and after each attempt so an interrupted session is reconstructible.
7. A one-line-per-attempt stderr narration consistent with the existing `backlog:` lines, and a session-summary line at termination.
8. Focused unit, storage round-trip, and integration tests using fake agents and temporary repositories only.

## Non-goals

This PRD does not:

- change admission, claim, completion, recovery, review, verification, scope authorization, accounting, or any single-run semantics;
- retry, release, or recover a retained `in_progress` entry automatically — PRD-012 recovery remains explicit and human-driven;
- execute anything in parallel, create worktrees or branches, or continue a dependency chain past its failed prerequisite (ineligibility already excludes dependents);
- add scheduling, daemonization, cron, or watch behavior — `drive` is one foreground invocation;
- invoke any model for selection or termination decisions;
- generate reports (PRD-018 reads the records this PRD writes); or
- modify prior PRDs, architecture documents, ADRs, contracts, or philosophy.

## Behavior

`drive` resolves the repository and agents exactly as `run`, validates the warrant, opens one driver session, then loops:

1. Reconcile and select the next eligible PRD; none → terminate `backlog_empty` (no entries pending) or `nothing_eligible` (pending entries exist but none eligible, e.g. dependents of a retained entry).
2. If the PRD was already attempted this session → treat as ineligible for selection.
3. Check the warrant before launching: PRD-count, accumulated known cost, and elapsed duration; exhaustion terminates with the specific reason before any claim.
4. Record the attempt as started; execute the unchanged single-PRD workflow; record the attempt outcome (completed, or retained with the exact existing retained-reason string).
5. A failed attempt does not stop the session (its dependents simply become ineligible); a storage failure writing session records does stop it, fail-closed, with `storage_failure`.

Interruption (signal, crash) leaves the session row without an end timestamp; the next `drive` invocation opens a new session and never resumes or reinterprets the old one. Attempted-set state is session-scoped and derived from the session's own attempt rows.

Configuration, canonical shape:

```toml
[driver]
max_prds_per_session = 0        # 0 = unlimited; at least one ceiling below must be finite
max_session_cost_microusd = 0   # 0 = no cost ceiling
max_session_duration_ms = 0     # 0 = no duration ceiling
```

Validation is fail-closed: all three at zero rejects `drive` startup with a diagnostic naming the warrant requirement.

## Acceptance Criteria

1. `familiar-ai drive` executes successive eligible PRDs through the byte-identical single-run workflow and stops only for a closed, recorded termination reason.
2. Selection matches `next` semantics exactly, never selects a PRD twice in one session, and never bypasses admission or claim.
3. The warrant requires at least one finite ceiling; each ceiling terminates the session with its distinct reason; CLI flags can only tighten configured values.
4. With a cost ceiling configured, an unknown-cost run terminates the session with `cost_unknown`; unknown cost is never coerced to zero and never silently accumulated.
5. Session and per-attempt records are durable, written around each attempt, and sufficient to reconstruct what ran, in what order, with what outcome, retained reason, cost, and duration — including for interrupted sessions.
6. A retained `in_progress` entry stops nothing except its own dependents; recovery remains exclusively the explicit PRD-012 commands.
7. Existing `run`, `next`, `history`, `usage`, and `backlog` behavior is unchanged; with review disabled `drive` retains every entry exactly as `run` does today.
8. The storage change is one new additive migration; existing migrations are untouched.
9. All tests use fake agents, fake executables, and temporary repositories; formatting, focused Clippy, focused tests, and the full workspace suite pass, with demonstrably pre-existing failures reported separately with exact evidence.
10. The change is confined to the expected files and is independently mergeable.

## Test Strategy

- Warrant validation: all-zero rejected; each ceiling triggers its exact termination reason; CLI tightening honored, loosening rejected.
- Loop selection: multi-PRD temp repositories proving order, dependency skipping after a retained entry, no-repeat within a session, and both empty/none-eligible terminations.
- Cost semantics: known costs accumulate and terminate at the ceiling; an unknown-cost attempt with a cost ceiling terminates with `cost_unknown`.
- Storage: migration and session/attempt round-trip tests; interrupted-session reconstruction; injected storage failure stops the session fail-closed.
- Integration: a temp-repo backlog driven end-to-end with fake agents through completion and through retained outcomes, asserting narration lines and durable records.

- `crates/familiar-ai-storage/migrations/` — the next unused additive migration for driver sessions and attempts
- `crates/familiar-ai-storage/src/` — migration registration and the driver-session repository
- `crates/familiar-ai-storage/tests/` — migration and round-trip coverage
- `crates/familiar-ai-daemon/tests/` — driver integration coverage

No new crate or third-party dependency is expected. Changes outside this list require explicit pull-request justification.

## Definition of Done

PRD-017 is done when a single `familiar-ai drive` invocation works an eligible backlog unattended under a required finite warrant, stops only for closed recorded reasons, leaves retained entries untouched for explicit recovery, writes durable session and attempt records that survive interruption, changes no single-run semantics, and passes the full verification pipeline with only evidenced pre-existing failures.
