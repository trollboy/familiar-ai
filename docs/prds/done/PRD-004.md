# PRD-004: Execution History for `familiar run`

**Status:** Ready for implementation  
**Date:** 2026-08-03  
**Delivery boundary:** Standalone CLI execution observability

## Objective

Make every invocation of `familiar run <prd-path>` leave one durable, truthful execution record and expose that record through two small CLI reads:

```text
familiar history
familiar usage
```

The record must describe when the run occurred, what repository, worktree, Git commit, and PRD it targeted, which agent ran, any model and token usage that Codex reported deterministically, any cost that Familiar can calculate from explicit pricing, and how the child process ended.

This PRD extends the existing standalone `familiar` CLI and its direct `codex exec -` child-process boundary. It does not turn execution into a daemon-owned command, warrant, task, scheduler, or multi-provider subsystem. Repository and Git observations remain authoritative; Codex output is authoritative only for fields Codex explicitly reports about its own execution.

## Scope

This PRD includes:

1. One additive execution-history table in Familiar's existing SQLite database.
2. Creation of one execution record before each attempted Codex launch.
3. Finalization of that same record when Familiar observes child exit, launch failure, prompt-feed failure, or another handled terminal runner error.
4. Deterministic repository, worktree, `HEAD` commit, and canonical repository-relative PRD identity capture.
5. Invocation of Codex's structured `codex exec --json -` mode and bounded parsing of its JSONL stdout events.
6. Continued live forwarding of Codex output and stderr to the invoking terminal.
7. Extraction of model and token fields only from supported structured Codex events.
8. Optional deterministic cost estimation from explicitly configured per-model token rates.
9. `familiar history` for a bounded recent-execution listing.
10. `familiar usage` for aggregate known token and estimated-cost totals plus explicit unknown counts.
11. Unit and fake-executable integration coverage without invoking real Codex.

### Selected persistence boundary

Execution history must use the existing `familiar-storage` crate, migration mechanism, SQLite connection configuration, and default database path from `AppPaths` and Familiar configuration. It must not create a second database, embed a private storage format in the CLI, or require the daemon to be running.

The migration is additive. Based on the repository at PRD authoring time, the expected filename is `005_execution_history.sql`; if another migration has claimed that number before implementation begins, the implementation must use the next available migration number without changing this PRD's schema semantics.

This table is operational CLI history. It is not the canonical task, command, audit-event, warrant, verification, or execution-attempt state planned by later milestones, and it must not claim those semantics.

### Execution record

Each record has a stable generated execution ID and the following logical fields:

| Field | Required representation |
|---|---|
| `started_at` | UTC timestamp captured immediately before the durable pre-launch insert. |
| `ended_at` | UTC timestamp captured when Familiar observes a terminal result; nullable only when the runner was interrupted before finalization. |
| `duration_ms` | Non-negative monotonic elapsed milliseconds measured by the parent; nullable when no terminal boundary was observed. It is not derived by subtracting wall-clock timestamps. |
| `agent` | Stable value `codex` for this PRD. |
| `agent_version` | Version parsed from a successful bounded `codex --version` probe when available; otherwise null with a reason. |
| `model` | Exact model identifier from a supported Codex JSON event, if emitted; otherwise null with a reason. Familiar must not infer it from user configuration, pricing configuration, cached sessions, or model-dependent behavior. |
| `input_tokens` | Exact structured count reported by Codex; otherwise null with a reason. |
| `output_tokens` | Exact structured count reported by Codex; otherwise null with a reason. |
| `cached_tokens` | Exact structured cached-input count reported by Codex; otherwise null with a reason. Absence is not zero. |
| `total_tokens` | Checked sum of `input_tokens + output_tokens` when both are known. Cached tokens are a subset of input tokens and are not added again. Otherwise null with a reason. |
| `estimated_cost_microusd` | Deterministically calculated integer millionths of a US dollar when all required usage and pricing inputs are known; otherwise null with a reason. |
| `outcome` | Stable terminal or incomplete classification described below. |
| `exit_code` | Child exit code when the operating system reports a normal exit; otherwise null with a reason. |
| `signal` | Terminating signal when the platform reports one; otherwise null. |
| `repository` | Canonical absolute path of Git's common directory, obtained from Git. This identifies the local repository shared by linked worktrees. |
| `git_commit` | Exact `HEAD` object ID resolved before launch; null with a reason for an unborn or otherwise unavailable `HEAD`. |
| `worktree` | Canonical absolute path returned by Git for the current worktree root. |
| `prd_path` | Canonical repository-relative slash-separated path already validated by `familiar run`. |
| `unavailable_fields` | Deterministically serialized map from nullable logical field name to one stable missing-value reason. |

The record must not store the generated execution prompt, PRD body, Codex transcript, stdout, stderr, credentials, environment variables, or repository source content.

### Missing-value semantics

Familiar must never substitute zero, an empty string, a configured default, or a guessed value for an unavailable field. A missing value is stored as SQL `NULL`; `unavailable_fields` must contain exactly one of these stable reasons for that field:

- `agent_not_reported`: Codex's supported structured events did not report the field.
- `usage_not_reported`: Codex produced no supported terminal usage object or omitted the token field.
- `git_unavailable`: the bounded Git query failed or returned no value, including unborn `HEAD` for `git_commit`.
- `version_probe_failed`: `codex --version` could not be executed or parsed.
- `pricing_not_configured`: no price exists for the exact reported model.
- `pricing_rate_incomplete`: pricing exists but a required input, cached-input, or output rate is absent.
- `usage_incomplete`: cost or total tokens cannot be calculated because a required token count is null.
- `arithmetic_overflow`: checked token or cost arithmetic could not be represented.
- `no_normal_exit_code`: the child was signaled or otherwise ended without a normal exit code.
- `runner_interrupted`: Familiar did not observe and persist the terminal boundary.

`history` renders a null value as `—` and, when verbose detail is requested, its reason code. `usage` excludes null numeric values from arithmetic and reports how many selected executions have unknown values. It must never count an unknown as zero.

### Terminal outcome semantics

At minimum, execution outcomes are:

- `running`: the durable pre-launch record exists and no terminal result has been persisted;
- `succeeded`: Codex exited normally with code zero;
- `failed`: Codex exited normally with a non-zero code;
- `signaled`: the operating system reports signal termination;
- `launch_failed`: Familiar could not start Codex;
- `input_failed`: Familiar started Codex but could not fully feed the prompt and no more specific child outcome supersedes it; and
- `history_finalize_failed`: reserved for an error reported to the caller when execution ended but terminal persistence could not commit. The pre-launch row remains non-terminal and must not be rewritten as success.

On the next `history`, `usage`, or `run` command, previously non-terminal rows from another process invocation are displayed as `running/incomplete`; the CLI must not invent an end time, duration, exit code, or terminal outcome. This PRD does not add process recovery, liveness inference, or a scheduler.

### Structured Codex output

The runner must request `codex exec --json -`. It must parse JSONL one line at a time without retaining an unbounded transcript. Supported event types and field paths must be explicitly enumerated in code and fixtures.

- Known model and usage fields are accepted only from their documented supported JSON event and exact typed field path.
- The final supported usage observation for the execution supplies the stored counters; counters from different events must not be summed unless Codex's event contract explicitly identifies them as disjoint increments.
- Unknown event types and unknown fields are ignored for metrics and remain forward-compatible.
- Malformed JSON is forwarded or diagnosed without crashing the reader, but it cannot supply metrics.
- Codex stderr remains streamed directly.
- Structured stdout must be rendered incrementally into a usable terminal stream using only supported human-visible message/output fields. Unknown JSON events may be omitted from normal rendering but remain eligible for a concise diagnostic in verbose mode.
- The integration test must prove that output becomes visible before the fake child exits; collecting all output and printing it afterward is not streaming.

If the installed Codex version does not support `--json`, the child failure is recorded normally and token, model, and cost fields remain null with the applicable reason codes. Familiar must not fall back to scraping human-readable terminal output.

### Pricing and cost

Pricing is optional and local. The existing Familiar configuration may gain one execution-history pricing section keyed by exact model identifier. No provider abstraction or remote price lookup is permitted.

Each model entry may configure integer rates in micro-USD per one million tokens for:

- uncached input;
- cached input; and
- output.

When `input_tokens`, `cached_tokens`, and `output_tokens` are all known, `cached_tokens <= input_tokens`, and all three rates exist, cost is:

```text
uncached_input = input_tokens - cached_tokens
numerator = uncached_input * input_rate
          + cached_tokens * cached_rate
          + output_tokens * output_rate
estimated_cost_microusd = round_half_up(numerator / 1_000_000)
```

All operations use checked integer arithmetic. The exact price values used for a run must be copied into that execution record so later configuration changes do not rewrite historical estimates. If model, usage, or any required rate is unavailable, estimated cost is null with the appropriate reason. Familiar must not assume cached tokens are zero, apply an uncached rate to cached tokens, select a similar model, or retroactively reprice old records.

## Requirements

### R1: Durable pre-launch record

After repository and PRD validation but before probing or launching Codex, `familiar run` must open the configured existing Familiar database, apply additive migrations, and insert exactly one `running` execution row. Failure to insert prevents Codex launch and returns a non-zero CLI result.

Retries are separate user invocations and therefore create separate execution IDs. One invocation must never create more than one record.

### R2: Repository and target capture

The runner must use bounded Git commands, without shell interpolation, to resolve the canonical worktree root, Git common directory, and `HEAD` object ID. The validated PRD must be inside the resolved worktree's `docs/prds` directory and stored as canonical repository-relative identity.

Git query failure must stop before launch when worktree or repository identity cannot be established. An unavailable `HEAD` alone does not prevent a run; it produces null `git_commit` with `git_unavailable`.

### R3: Timing

The runner must capture UTC wall-clock start and end timestamps and use a monotonic clock for duration. The pre-launch row contains the start time. A handled terminal path atomically writes end time, duration, outcome, exit information, metrics, pricing inputs, estimated cost, and missing-value reasons.

### R4: Codex execution and streaming

The child command remains local Codex with prompt over stdin and repository worktree as its working directory. It adds only the structured-output option necessary for metrics. Stderr is inherited or streamed without buffering. Stdout JSONL is parsed and rendered incrementally. The runner returns the child exit status when one exists.

### R5: Deterministic metric extraction

Metric parsing must use typed or explicitly validated JSON fields with non-negative integer bounds. Duplicate terminal usage events must resolve through a documented deterministic rule. Invalid, negative, fractional, overflowing, text-scraped, or unknown values are unavailable rather than coerced.

### R6: Finalization on every handled path

Every handled path after successful pre-launch insertion must attempt to finalize that record, including version-probe failure, child launch failure, prompt-feed failure, stdout-read failure, normal exit, and signal termination. Storage finalization failure must be reported separately and must not be hidden by a successful Codex status.

### R7: `familiar history`

`familiar history` lists executions newest first with a default limit of 20 and a bounded `--limit` option from 1 through 100. Each row shows at least execution ID, start time, duration or `—`, agent, model or `—`, outcome/exit status, repository/worktree identification, and PRD path.

The command is read-only, performs no Codex or Git mutation, and returns an empty-state message with success when there are no records. It must use a deterministic tie-breaker after start time.

### R8: `familiar usage`

`familiar usage` summarizes all stored executions by default and displays:

- execution count;
- executions with complete usage;
- executions with unknown usage;
- known input tokens;
- known output tokens;
- known cached tokens;
- known total tokens;
- executions with a known cost;
- executions with unknown cost; and
- summed known estimated cost in micro-USD and a stable human-readable USD rendering.

Each token aggregate includes only records where that specific field is known. The output must label partial aggregates as known totals and show unknown counts. Cost addition uses checked integer arithmetic and fails explicitly on overflow.

### R9: Storage isolation and compatibility

Execution records are append-oriented after terminal finalization. Finalization may update only the matching `running` record and must be transactionally guarded against a second terminal write. Foreign keys and indexes must support bounded recent-history reads without changing existing project, summary, lifecycle, decision, or rollup data.

The schema and repository API must remain usable without the daemon. Concurrent daemon access relies on the existing SQLite WAL and busy-timeout configuration; this PRD adds no second writer service or authority claim.

### R10: Configuration

The CLI uses Familiar's existing default configuration and database-path resolution. The only new configuration is optional exact-model execution pricing. Missing configuration is valid and results in null estimated cost with `pricing_not_configured`.

Tests must be able to inject a temporary database path and explicit pricing without reading or modifying the user's Familiar data. No credentials or Codex configuration are read into execution history.

### R11: Compatibility with existing `run`

Existing repository-root resolution, PRD validation, prompt construction, direct ADR/contract inclusion, fixed execution constraints, stdout/stderr visibility, and child status propagation remain covered by regression tests. History persistence must not cause PRD-003 implementation or add content to the execution prompt.

## Acceptance Criteria

1. Each valid `familiar run` invocation that reaches the execution boundary creates exactly one durable execution record before Codex is launched.
2. Invalid repository or PRD arguments launch no child and create no execution record.
3. A fake successful Codex process produces one `succeeded` record with start, end, monotonic duration, `agent = codex`, repository, worktree, commit when available, PRD path, exit code zero, and every deterministically reported metric.
4. A fake non-zero Codex process produces one `failed` record, preserves the exact exit code, and the CLI returns that code.
5. A fake signaled process is recorded as `signaled`, with null normal exit code and `no_normal_exit_code`.
6. Launch and prompt-input failures finalize the pre-created record with their explicit outcome and return failure.
7. Supported JSONL events are rendered while the child is still running; stderr remains visible; no transcript is persisted.
8. Unknown or malformed JSONL cannot fabricate model or usage fields and does not prevent recording the child outcome.
9. Model is stored only when the supported event explicitly reports it; otherwise it is null with `agent_not_reported`.
10. Missing input, output, or cached counts are individually null with `usage_not_reported`; cached-token absence is never represented as zero.
11. Total tokens equal input plus output when both are known and exclude cached tokens from a second addition.
12. Complete exact-model pricing produces the specified checked, round-half-up micro-USD estimate and preserves the applied rates in the row.
13. Missing model, usage, cached usage, or required pricing makes cost null with the correct stable reason and no guessed partial cost.
14. `familiar history` returns the newest 20 records by default, supports limits 1 through 100, uses deterministic ordering, and handles an empty database successfully.
15. `familiar history` displays missing values as `—` and never renders null numeric metrics as zero.
16. `familiar usage` reports known token/cost sums and unknown execution counts without treating unknowns as zero.
17. Repeated `history` and `usage` calls do not mutate execution records or launch Codex.
18. Existing migrations upgrade additively and repeated migration execution is idempotent.
19. Existing `familiar run` prompt, path-validation, streaming, and exit-code tests continue to pass using a fake executable.
20. No architecture document, ADR, contract, prior PRD, dashboard, daemon orchestration, provider abstraction, warrant, task, or analytics capability is changed or introduced.

## Test Strategy

### Unit tests

- Repository, worktree, Git common-directory, commit, and PRD identity validation using temporary Git repositories and linked-worktree fixtures where supported.
- JSONL parsing fixtures for known events, unknown events, malformed lines, missing fields, duplicate terminal usage, negative/fractional values, and overflow.
- Exact model extraction and explicit absent-model handling.
- Input, output, cached, and total-token missing-value semantics.
- Checked cost arithmetic, cached-token subtraction, round-half-up behavior, missing rate, unknown model, incomplete usage, and overflow.
- Start/end serialization, monotonic duration conversion, outcome mapping, normal exit, non-zero exit, and signal termination.
- CLI parsing for `history`, `history --limit`, invalid limits, and `usage`.
- Stable history ordering, display of nulls, empty state, aggregate known totals, and unknown counts.

### Storage integration tests

- Fresh migration, upgrade from the immediately previous schema, and migration idempotency.
- Pre-launch insert and guarded single finalization.
- Exact nullable values and `unavailable_fields` reason validation.
- Applied-price snapshot preservation after configuration changes.
- Bounded newest-first history query with deterministic tie-breaking.
- Usage aggregation across complete, partial, failed, interrupted, and unpriced records.
- Existing project, summary, reconciliation, lifecycle, decision, and rollup rows remain unchanged.

### CLI integration tests

- Use a fake `codex` executable; never invoke real Codex.
- Verify exact `exec --json -` arguments, working directory, prompt input, incremental stdout rendering, stderr forwarding, normal and non-zero exit propagation, launch failure, malformed events, and metrics persistence.
- Use a temporary Familiar configuration and database path; never access the user's database.
- Run `familiar history` and `familiar usage` against the resulting temporary history and assert stable output.
- Preserve the existing fake-executable regression proving prompt construction and direct document inclusion.

### Verification commands

Implementation must run:

- formatting checks;
- focused unit and integration tests for the CLI and storage history repository;
- focused static analysis with warnings denied; and
- an attempted full workspace test suite, distinguishing implementation-caused failures from pre-existing failures.

## Definition of Done

PRD-004 is done when:

1. `familiar run` durably creates and finalizes exactly one execution record per valid invocation.
2. Every requested field is stored from deterministic evidence or represented as SQL `NULL` with an exact stable reason; no value is guessed.
3. Repository, worktree, commit, and PRD identities are captured through bounded Git and canonical path validation.
4. Codex structured output is parsed incrementally, terminal output remains live, and no prompt or transcript is persisted.
5. Child normal exit, non-zero exit, signal termination, launch failure, input failure, and incomplete finalization remain distinguishable.
6. Token totals and optional cost estimates follow the specified checked arithmetic and preserve the pricing snapshot used.
7. `familiar history` provides a bounded deterministic recent list with truthful missing values.
8. `familiar usage` provides known token and cost totals together with explicit unknown counts.
9. The existing SQLite database and migration framework are reused without changing unrelated records or introducing another database.
10. Unit, storage integration, and fake-Codex CLI tests cover success, failure, partial metrics, missing values, streaming, ordering, aggregation, and migration compatibility.
11. Formatting and focused static analysis pass, and the workspace suite is attempted with unrelated failures identified separately.
12. No PRD-003 implementation, daemon orchestration, provider abstraction, dashboard, analytics, task, warrant, audit-event, or later-milestone capability is included.
13. The work remains one independently mergeable change with any expected-file deviation explicitly justified.
