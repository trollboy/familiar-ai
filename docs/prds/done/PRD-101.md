# PRD-101: No Vendor CLI Required

## Objective

The owner's ask, stated directly: *"I'd love it if codex/claude weren't
required to use this."*

PRD-100 makes Familiar's own loop **selectable**. This PRD makes the
vendor CLIs **optional** — a different claim, and the one a stranger
actually experiences. Today the requirement is documented as a
requirement:

> **Requirements:** Rust (stable), Docker (for the test environment),
> Linux with kernel ≥ 5.13 or macOS, and at least one coding agent CLI on
> `PATH` (`claude` or `codex`).

That line is honest about the current state. The goal is to delete it.

## What makes them required

Three mechanisms, in increasing order of how hard they are to see:

1. **The documented prerequisite.** A reader installs a CLI because the
   README tells them to. Cheapest to fix, and worthless on its own.
2. **`#[default] Codex`.** `AgentAdapterKind`'s default means a
   configuration that declares no worker resolves to the Codex CLI.
   Absence of a choice is a choice, and it is currently a vendor's.
3. **The silent fallback.** `as_agent_entry()` maps every unrecognised
   `runtime` to `AgentAdapterKind::Codex`. A user who configures a
   raw-API worker does not get an error; they get a Codex worker. PRD-100
   removes this one, which is why this PRD depends on it rather than
   racing it.

There is also a shape worth naming before it bites: **preflight must not
treat a missing CLI as a session failure.** FAM-BUG-020 was exactly this
class — a single registered-but-unrouted provider with an absent
credential gated every healthy worker and burned eleven silent minutes.
A host with a perfectly good API key must not be stopped because `codex`
is not installed.

## What "not required" means precisely

Not "the raw loop becomes the default." Not "the CLIs are deprecated."
Those are separate decisions, and PRD-100 deliberately defers them until
`apply-edit` has a measured success rate. This PRD means:

**A host with one API key and no vendor CLI is a supported,
first-class installation that completes a PRD end to end.**

A host that has a CLI keeps using it, unchanged, and keeps preferring it
where it is declared. Both configurations are supported; neither is
mandatory. The requirement changes from *"install one of these two
vendors' products"* to *"have one reachable worker, by whatever means."*

## Design

- **Resolve the default from the host, not from a constant.** With no
  declared worker, ask what is actually available — a credentialled
  provider, a reachable local endpoint, a CLI on `PATH` — and say so.
  A fixed default that names an absent executable is a worse outcome
  than no default at all.
- **When nothing is available, name every road in.** The diagnostic
  lists the ways to get a working worker rather than the one it happened
  to try. This is the PRD-083 lesson — the failure a stranger hits first
  must be decidable from its own message.
- **Onboarding writes a config that works on this box.** PRD-036 already
  generates policy; generating a worker declaration naming an executable
  that is not installed is the specific failure to prevent.
- **A missing CLI is a per-worker fact.** Preflight reports it against
  the candidate that needs it and nothing else.
- **Documentation states the real requirement.** One reachable worker.
  The check exists because the CLI prerequisite crept into the README
  once and would again.

## Scope

Host-derived worker resolution when nothing is declared; the
nothing-available diagnostic; onboarding generating a host-valid worker
declaration; per-worker rather than session-level treatment of a missing
executable in preflight; the README and provider-setup guide; the check
forbidding a mandatory-CLI install instruction; regressions in a
dedicated test file covering the four host shapes (key only, local
endpoint only, CLI only, nothing).

Out of scope: making the owned loop the default or preferred worker, and
retiring either vendor CLI — both wait on PRD-100's measured edit-success
number, and taking either here would be steering ahead of measurement.
Also out of scope: the `RawAgent` bridge, factory registration, and the
`AgentAdapterKind`/`as_agent_entry` corrections, all of which belong to
PRD-100 and are its dependency relationship with this PRD; credential
storage (PRD-074); and packaging or release artifacts, which remain
unowned by any PRD.

## Assumptions (recorded at specification time, 2026-09-17)

- PRD-100 lands first. Without its bridge there is no non-CLI worker for
  this PRD to resolve to, and its `as_agent_entry` fix is what stops a
  raw declaration becoming a Codex worker. If PRD-100's measured edit
  success turns out to be poor, this PRD still stands — "supported" does
  not mean "best", and a user with only an API key is better served by a
  mediocre worker than by an install that refuses to run.
- One provider API key plus the existing credential-store descriptors is
  enough to reach a hosted model. No new credential handling is
  introduced here.
- Verification and review do not themselves require a vendor CLI. Review
  routing resolves through the registry like any other stage, so a
  CLI-less host reviews through a raw worker; if any non-configurable
  path is found to require a CLI, that dependency is a defect to report
  rather than to design around.
- Docker remains a documented requirement for the test environment. This
  PRD narrows the *worker* prerequisite only, and says nothing about the
  verification gate's own dependencies, which are PRD-092's and PRD-099's.
