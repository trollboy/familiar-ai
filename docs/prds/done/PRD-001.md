# PRD-001: Canonical File Identity Boundary

**Status:** Completed
**Date:** 2026-08-03  
**Roadmap milestone:** M1 — Repository Identity and Reconciliation  
**Epic:** EPIC-M1-01 — Canonical File Identity and Compatibility  
**Backlog source:** PRD-TBD-M1-01

## Objective

Establish one deterministic, project-scoped, repository-relative identity for every file summary read and write in Familiar.

After this PRD, the watcher, initial scan, summary worker, storage boundary, lazy file-summary lookup, and module-summary lookup must converge on the same identity for the same repository entry. New records must no longer use machine-specific absolute paths. Existing legacy records must remain untouched and safely readable through bounded compatibility behavior.

This is the first implementation PRD because repository file identity is the earliest unresolved dependency in the delivery backlog. It is required by legacy reconciliation, delete and rename handling, complete scans, content hashing, branch and worktree intelligence, context compilation, diff verification, and isolated execution. Establishing it before those capabilities prevents each from inventing incompatible path semantics.

## Scope

This PRD includes:

1. A shared canonical file-identity contract used by all current file-summary producers and consumers.
2. Deterministic conversion from an observed host path plus canonical project root to a repository-relative identity.
3. Deterministic validation and normalization of caller-supplied repository-relative file and module paths.
4. Physical containment checks for existing paths, including protection against traversal and symbolic-link escape.
5. Canonical identity enforcement at the file-summary persistence boundary so new uncanonical writes fail rather than create competing identities.
6. Adoption by daemon watcher-event handling, initial scan, summary deduplication, staleness lookup, summary generation, and summary write paths.
7. Adoption by lazy file-summary lookup and regeneration.
8. Adoption by module-prefix lookup and counting.
9. Canonical repository-relative paths in newly produced file-summary responses and generated summary text.
10. Bounded read compatibility for pre-existing absolute-path summary records, without rewriting, deleting, or merging them.
11. Deterministic diagnostics for rejected paths and canonical-versus-legacy conflicts.
12. Unit and integration coverage across the affected subsystem boundaries.

### Canonical file identity

A canonical file identity is the pair:

```text
(project_id, repository_relative_path)
```

The `repository_relative_path` must satisfy all of the following:

- It is relative to the canonical root of the identified project.
- It identifies a repository entry, not the host location of the repository.
- It is non-empty for a file.
- It has no root, volume, or host-specific absolute-path prefix.
- It contains no parent traversal component.
- Redundant current-directory components and separators do not produce distinct identities.
- Its logical component separator is `/` on every supported host.
- It preserves component spelling and does not apply Unicode normalization or case folding.
- It is losslessly representable; lossy path conversion is prohibited.
- It is stable when the repository moves to another host location.
- It is scoped by `project_id`; identical relative paths in different projects remain different identities.

The logical identity follows the repository entry path. Physical resolution is a separate containment check and must not silently replace the logical identity with a symbolic-link target path.

### Module identity

A module path is a canonical repository-relative directory prefix. The empty module path means the bounded root of one project. A non-empty module path uses the same component rules as file identity and is normalized to a directory boundary for lookup. For example, `src` may match `src/a.rs` and `src/sub/b.rs` but not `src_other/c.rs`.

## Non-goals

This PRD does not:

- rewrite, delete, merge, or deduplicate existing absolute-path records;
- implement the legacy summary identity reconciliation assigned to the next PRD;
- persist file deletion or rename lifecycle;
- make initial scans resumable or complete under queue saturation;
- introduce content hashes, Git object identity, branch identity, or worktree identity;
- change summary quality, extraction, ranking, token packing, or search algorithms;
- introduce the future daemon command/query runtime or local IPC boundary;
- remove existing direct client persistence paths; that cutover belongs to M2;
- implement audited command and event infrastructure beyond preserving compatibility with the approved contracts;
- change project identity or project-root registration semantics;
- support cross-project queries or identity;
- add semantic indexes or embeddings;
- broaden supported host platforms;
- follow symbolic links outside the project root;
- infer or fabricate identity for a path that cannot be represented losslessly; or
- introduce a destructive data migration.

## Functional Requirements

### FR-1: One shared identity operation

Familiar must expose one shared, deterministic operation for deriving a canonical file identity from:

- a stable `project_id`;
- the project's canonical repository root; and
- an observed or caller-supplied path.

The operation must be reusable by daemon, storage, and current client-facing summary paths. Subsystems must not retain independent normalization algorithms that can produce different identities.

### FR-2: Host-path conversion

For an observed host path, Familiar must:

1. establish the canonical project root;
2. establish that the observed path is lexically within that project scope;
3. for an existing path, verify physical containment without changing the logical repository-entry identity;
4. remove the project-root prefix;
5. normalize accepted relative components and separators; and
6. return the project-scoped canonical identity.

Paths outside the project, paths associated with the wrong project, and paths that require lossy conversion must be rejected explicitly.

### FR-3: Caller-supplied relative paths

Caller-supplied file paths must be interpreted only as repository-relative paths for the declared project. Familiar must reject absolute paths, root-prefixed paths, parent traversal, empty file paths, and paths whose existing physical target escapes the project.

Equivalent accepted spellings must converge on one identity. Validation must occur before cached lookup, disk access, summary generation, or persistence.

### FR-4: Repository entry and symbolic-link semantics

Canonical identity must preserve the logical repository-entry path. Resolving an existing symbolic link must not substitute its target as the stored identity.

- A link whose resolved target remains within the project may retain the link's repository-relative identity.
- A link whose resolved target escapes the project must be rejected before content is read or summarized.
- A missing path must still pass lexical containment validation; missing-path handling remains distinct from traversal rejection.

### FR-5: Daemon summary production

Every daemon-originated summary request must retain enough project-root context to derive canonical identity deterministically.

The daemon must use the canonical repository-relative identity for:

- pending-work deduplication;
- existing-summary lookup;
- staleness comparison;
- generated summary path display;
- persistence; and
- diagnostic attribution.

The host path may remain available transiently for filesystem access. It must not become the new summary's stored identity.

### FR-6: Initial scan and watcher convergence

An initial scan and a subsequent watcher change for the same repository entry must produce the same canonical identity and converge on one new canonical summary record.

Repeated events using equivalent accepted path spellings must deduplicate as the same pending file. The same relative path in two projects must not deduplicate across projects.

### FR-7: Lazy file-summary lookup

Lazy file-summary lookup must normalize and validate the requested relative path before any lookup or regeneration.

The same canonical identity must be used for:

- canonical cache lookup;
- safe host-path resolution;
- freshness evaluation;
- summary generation; and
- persistence of a regenerated summary.

The returned path for a newly generated or canonical cached record must be the canonical repository-relative path.

### FR-8: Module-prefix lookup

Module-summary input must use the shared relative-path rules. Prefix construction must be component-boundary safe.

Module counting and listing must:

- remain scoped to one project;
- use the same normalized prefix;
- produce deterministic path ordering;
- return canonical repository-relative paths for canonical records; and
- preserve `src` versus `src_other` separation.

### FR-9: Persistence-boundary enforcement

The file-summary persistence boundary must reject every new record whose path is not already a valid canonical repository-relative file identity for its declared project.

Validation at producers is not sufficient by itself. No current write path may persist a new absolute, traversing, empty, lossy, or otherwise noncanonical file-summary path after this PRD.

The existing uniqueness of project plus path remains the identity constraint. This PRD must not add a second competing canonical identifier.

### FR-10: Canonical read selection

For a canonical file request, lookup must select the canonical project-relative record first. If both canonical and legacy absolute records describe the same physical repository entry, the canonical record wins.

The existence of a legacy record must not cause a canonical write to reuse its absolute identity.

### FR-11: Legacy read compatibility

This PRD must not modify legacy records. A bounded compatibility read may locate an existing absolute-path record only by deriving the exact contained legacy path from the requested canonical project and relative identity.

Compatibility behavior must:

- remain project-scoped;
- never scan or match arbitrary host paths;
- never accept caller-supplied absolute paths as canonical input;
- never silently rewrite or delete the legacy record;
- identify the result as legacy-derived where the current response contract can do so compatibly; and
- report a canonical-versus-legacy conflict deterministically when both exist.

Full legacy enumeration, collision resolution, reversible mapping, and data reconciliation are deferred to the next PRD.

### FR-12: Lossless representation

Path conversion must never use lossy string conversion to form canonical identity. When an observed repository entry cannot be represented losslessly by the current file-summary identity format, Familiar must skip or reject it with an explicit diagnostic rather than persist a colliding or corrupted identity.

### FR-13: Error distinctions

The boundary must distinguish at least:

- invalid absolute input;
- parent traversal;
- project-root mismatch;
- lexical containment failure;
- physical symbolic-link escape;
- missing file after valid containment;
- non-file target;
- lossless-representation failure;
- canonical-versus-legacy conflict; and
- internal filesystem or persistence failure.

Current external response shapes may map these to existing compatible error categories, but logs and tests must preserve the underlying distinction. Missing content must not be reported as traversal, and traversal must not be reported as an ordinary cache miss.

### FR-14: No implicit data repair

Reading, normalizing, or writing a canonical identity must not implicitly migrate, deduplicate, delete, or rewrite any legacy row. Detection may emit diagnostics; repair is outside this PRD.

## Non-functional Requirements

### Determinism

Identical project identity, canonical root, and path input must produce the same result across repeated runs. Equivalent accepted input forms must converge on the same identity. Deterministic test fixtures must cover every normalization and rejection rule.

### Safety and isolation

Path handling must fail closed on ambiguity. No read, summary, or write may escape the declared project root. The same repository-relative path in different projects must remain isolated throughout lookup, deduplication, and persistence.

### Portability

Canonical identities must not embed machine-specific repository roots and must use `/` as the logical separator on macOS and Linux. Host-specific path handling may differ internally, but stored identity semantics and observable results must remain equivalent.

### Compatibility

Existing canonical relative records must remain readable without change. Existing absolute-path records must not be destroyed or made less recoverable. Current file-summary and module-summary behavior must remain available for valid relative inputs.

### Bounded behavior

Normalization and containment checks must be bounded by input path length and component count. The implementation must not introduce project-wide scans for ordinary single-file lookup or write validation.

### Observability

Rejected paths, legacy fallbacks, and canonical-versus-legacy conflicts must produce structured, project-scoped diagnostics without exposing unrelated host paths or project data.

### Performance

Canonicalization must not introduce a project tree walk per file-summary operation. The initial scan and watcher must retain existing bounded-channel behavior. Repeated root resolution may be cached only if the cache is invalidated when project-root identity changes.

### Architectural compatibility

The boundary must remain usable by the future Repository Identity and Reconciliation subsystem and future protocol-neutral command and query layers. It must not depend on a specific current interface, model, or inference implementation.

## Acceptance Criteria

1. A daemon initial scan stores `src/main.rs`, not an absolute host path, for a repository entry at `<project-root>/src/main.rs`.
2. A watcher change for that same file updates the same project/path record rather than creating a second new canonical record.
3. Lazy lookup for `src/main.rs` reads or regenerates the same canonical record created by the daemon.
4. Module lookup for `src` returns canonical records below `src/` and excludes `src_other/`.
5. Newly generated summary text does not expose the absolute repository root.
6. New file-summary writes reject absolute paths, parent traversal, empty file identity, wrong-project paths, and lossy path representations.
7. Existing paths whose resolved symbolic-link target escapes the project are rejected before content read or summary generation.
8. An in-project symbolic link retains its logical repository-relative entry identity rather than being stored under its target path.
9. Two projects may each store `src/main.rs` without collision or cross-project reads.
10. Equivalent accepted path spellings converge on one canonical identity and one new canonical record.
11. Canonical records take precedence when both canonical and legacy records are present.
12. An exact, contained legacy absolute record remains readable through compatibility behavior and is not modified.
13. No test or implementation path uses lossy conversion to construct a canonical identity.
14. No migration rewrites, deletes, or merges legacy file-summary data.
15. All existing valid relative-path file-summary and module-summary tests continue to pass or are updated only to reflect the canonical identity contract.
16. Targeted unit and integration suites pass on supported macOS and Linux behavior fixtures.
17. The full workspace test suite passes.
18. A deterministic inspection of newly written test records finds no absolute path in the file-summary identity field.

## Test Strategy

### Unit tests: canonical identity

Add table-driven fixtures for:

- root-level and nested files;
- repeated separators and current-directory components;
- parent traversal at beginning, middle, and end;
- absolute and root-prefixed inputs;
- similarly prefixed project roots;
- trailing separators and empty file paths;
- spaces, Unicode, punctuation, and literal platform-valid special characters;
- stable `/` output across supported host conventions;
- case preservation without case folding;
- same relative identity under different host roots;
- non-lossless path input on hosts where it can be represented in a fixture;
- in-project and escaping symbolic links; and
- missing but lexically contained paths.

The unit suite must prove idempotence: normalizing an already canonical identity returns that identical identity.

### Storage integration tests

Verify:

- valid canonical writes and reads;
- rejection of uncanonical new writes at the persistence boundary;
- project-scoped uniqueness;
- canonical-first lookup;
- exact bounded legacy fallback;
- canonical/legacy conflict behavior;
- deterministic module prefix counting and ordering; and
- no mutation of legacy rows during read or canonical write.

### Daemon integration tests

Using temporary repositories, verify:

- initial scan writes repository-relative identity;
- watcher and initial-scan events converge;
- pending-work deduplication uses canonical identity;
- staleness lookup finds the canonical record;
- generated text uses repository-relative path;
- escape and representation failures do not write summaries; and
- two projects with identical relative paths remain isolated.

### Current client-boundary integration tests

Verify:

- valid relative file lookup returns the daemon-created canonical record;
- lazy regeneration writes canonical identity;
- traversal and absolute caller inputs fail before lookup or disk access;
- module lookup normalizes boundaries consistently;
- `src` does not match `src_other`;
- canonical paths appear in search and packed context when those surfaces consume newly written records; and
- legacy compatibility does not expose an unrelated absolute path.

### Deterministic verification

The implementation pull request must record:

- focused test results for core identity, storage, daemon, and current client-boundary suites;
- the full workspace test result;
- formatting and static-analysis results under the repository's existing validation commands;
- a fixture inspection showing that initial scan and lazy lookup produce the same project/path identity; and
- a fixture inspection showing that no newly written file-summary identity is absolute.

No model judgment may substitute for these deterministic checks.

## Rollback Strategy

This PRD has a code-only rollback boundary and no destructive data migration.

If the new identity boundary causes regressions:

1. Revert the canonical-write selection and shared-normalization integration as one pull-request rollback.
2. Retain the existing legacy read behavior.
3. Leave newly created repository-relative records in place; they are valid under the existing project/path uniqueness model and must not be deleted automatically.
4. Do not attempt to merge canonical and legacy rows during rollback.
5. Run the existing summary lookup and daemon tests to confirm the prior supported behavior is restored.
6. Record any canonical/legacy duplicates for the later reversible reconciliation PRD.

Rollback must not delete user data, rewrite legacy paths, broaden path acceptance, or weaken containment checks. If rollback exposes mixed identities again, that state is accepted only as the pre-existing behavior and must remain observable.
