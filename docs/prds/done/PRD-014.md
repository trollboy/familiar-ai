# PRD-014: Claude Code Agent Adapter

**Status:** Completed
**Date:** 2026-08-03
**Depends on:** PRD-008, PRD-011
**Architectural direction:** Agents Are Replaceable; Determinism Before Intelligence; Stewardship Over Control
**Delivery boundary:** Independently mergeable addition of one coding-agent adapter and deterministic agent selection

## Objective

Add Claude Code as a first-class Familiar `CodingAgent` implementation so Familiar can use the locally installed `claude` CLI for implementation and review execution.

A new `ClaudeCodeAgent` implements the existing `CodingAgent` trait, invokes Claude Code non-interactively with `claude --print --output-format stream-json`, streams human-readable assistant output through Familiar as it arrives, and maps Claude's structured result, usage, cost, model, session, exit, and error information into Familiar's existing execution accounting. Deterministic configuration selects which adapter constructs the implementation agent and which constructs the reviewer agent, independently. The existing Codex adapter, orchestration behavior, execution history, usage accounting, backlog lifecycle, review isolation, context budgeting, and CLI behavior are preserved.

## Motivation

Familiar's philosophy requires coding agents to be interchangeable workers. Today the abstraction exists — `familiar run` orchestrates through `&dyn CodingAgent` — but only one production adapter exists (`CodexAgent`), and the CLI hardcodes `CodexAgent::new("codex")`. Familiar therefore cannot yet demonstrate its central architectural claim: that the steward outlives and freely exchanges its summoned daemons.

Claude Code is the first proof. Its non-interactive `--print` mode with `--output-format stream-json` provides a line-delimited structured event stream directly analogous to Codex's `--json` stream: assistant text events for human-visible progress, an init event carrying model and session identity, and a terminal result event carrying usage, cost, and error state. This maps onto the existing `ExecutionRequest`/`ExecutionResult` contract with only a minimal additive extension.

Selection must be deterministic configuration, not inference. This PRD adds a typed `[agents]` configuration section with independent implementation and reviewer entries and a deterministic constructor in the CLI composition root. It deliberately excludes automatic provider routing, capability scoring, Cursor, Ollama, and MCP integration.

## Scope

This PRD includes:

1. A `ClaudeCodeAgent` in `familiar-agent` implementing the existing `CodingAgent` trait.
2. Non-interactive invocation of the configured Claude executable with `--print` and `--output-format stream-json`, with the Familiar-compiled prompt delivered through stdin.
3. Line-by-line stream-json parsing that forwards human-readable assistant output as it arrives and captures structured metadata without fabricating unknown values.
4. Mapping of Claude-reported usage, cost, model, session, exit, and error information into `ExecutionResult`, with a minimal backward-compatible additive extension for session identity and reported cost.
5. Typed `[agents.implementation]` and `[agents.reviewer]` configuration with adapter, executable, model, effort, permission mode, maximum budget, and additional arguments, validated fail-closed.
6. Deterministic agent construction in the CLI composition root replacing the hardcoded Codex constructor, defaulting to today's exact behavior when no `[agents]` configuration is present.
7. Independent implementation and reviewer agent instances threaded through the existing run orchestration without making orchestration adapter-aware.
8. Reviewer execution through a fresh isolated Claude process honoring the existing `denied_read_path` isolated review workspace contract.
9. Timeout, process-group kill, and error taxonomy behavior equivalent to the existing Codex adapter.
10. Focused adapter, configuration, construction, and run-integration tests using fake executables and temporary repositories only.

## Non-goals

This PRD does not:

- remove, rewrite, or change the observable behavior of the Codex adapter beyond extracting shared helpers with byte-identical behavior;
- add automatic provider routing, capability-based agent selection, health probing, fallback between adapters, or per-task model choice heuristics;
- add Cursor, Ollama, OpenCode, or any other adapter;
- add MCP integration, `--mcp-config`, or agent-side tool servers;
- resume, fork, or reuse prior Claude sessions, or add `--resume`/`--continue` support;
- pass `--dangerously-skip-permissions` by default or provide any implicit permission escalation;
- redesign the `CodingAgent` trait, `ExecutionRequest`, or the error taxonomy beyond the minimal additive extensions defined below;
- change prompt compilation, prompt bytes, context budgeting, review coordination logic, reviewer-independence policy, verification, backlog admission/claim/completion/recovery semantics, execution-history schema semantics, or pricing-based cost estimation;
- add daemon, MCP, dashboard, tray, watcher, or network behavior; or
- modify prior PRDs, architecture documents, ADRs, contracts, or philosophy.

## Architecture

The adapter lives entirely inside `familiar-agent` beside `CodexAgent`. Orchestration (`familiar-daemon/src/run.rs`) continues to operate exclusively on `&dyn CodingAgent` and remains agent-neutral: it must not name, downcast, or branch on any concrete adapter.

Composition happens in exactly one place — the CLI composition root (`familiar-daemon/src/bin/familiar.rs`) — which reads validated configuration and constructs two agents:

```text
Config [agents.implementation] ──► build_agent() ──► Box<dyn CodingAgent>  (implementation)
Config [agents.reviewer]       ──► build_agent() ──► Box<dyn CodingAgent>  (reviewer)
                                          │
                          "codex"       ──► CodexAgent
                          "claude-code" ──► ClaudeCodeAgent
```

`run::execute` gains a reviewer agent alongside the existing implementation agent (as a second parameter or a small `AgentSet` struct, per repository convention). The implementation agent performs PRD implementation and remediation (`CodingRemediationAdapter`); the reviewer agent backs `StructuredReviewAdapter`. All existing review coordination, independence checks, evidence budgeting, verification, and stopping behavior are unchanged and see only the trait.

Shared subprocess mechanics currently private to `codex.rs` — the macOS `sandbox-exec` denied-read-path isolation helper and, where practical, the line-oriented stream loop — are extracted into a shared module within `familiar-agent` so both adapters use one audited implementation. Extraction must leave Codex behavior byte-identical.

## Adapter Contract

`ClaudeCodeAgent` implements the existing trait exactly:

- `execute(&self, request: ExecutionRequest<'_>, output: &mut dyn io::Write) -> Result<ExecutionResult, AgentExecutionError>` — one fresh child process per call; no shared state between calls beyond immutable construction-time configuration.
- `isolation_capability()` returns `IsolationCapability::FreshProcessPerExecution`.

`ExecutionRequest` semantics are honored as-is:

- `working_directory` — child process current directory.
- `denied_read_path` — when `Some`, the child must be unable to read that tree (isolated review execution); on hosts without an enforcement mechanism the launch fails closed exactly as Codex does today.
- `prompt` — written to child stdin, never interpolated into argv or a shell.
- `filesystem` — mapped to Claude permission behavior per the Permissions section.
- `model` — when `Some`, overrides the adapter's configured model for this execution.
- `timeout_ms` — enforced by the existing process-group watchdog pattern.

Minimal backward-compatible extensions, permitted because the requirement to parse session and Claude-reported cost cannot be met otherwise:

1. `ExecutionResult` gains two additive optional fields, defaulting to `None` for every adapter: `session_id: Option<String>` and `reported_cost_microusd: Option<u64>`. Codex never populates them. Execution history and usage accounting do not consume them in this PRD; pricing-config estimation remains the sole source of `estimated_cost_microusd`.
2. `AgentExecutionError` display text becomes adapter-neutral (or names the failing executable) instead of hardcoding "Codex". Variants and structure are otherwise unchanged; one additive variant is permitted only if the budget rule below requires it.
3. No other trait, struct, or enum changes are permitted.

## Process Invocation

The adapter launches the configured executable directly via `std::process::Command` — no shell, no string interpolation. Adapter-owned argv, in deterministic order:

```text
<executable> --print --output-format stream-json --verbose
             [--model <model>] [--permission-mode <mode>] [<effort option>]
             [<validated extra args>...]
```

- `--print` selects non-interactive mode; the prompt arrives on stdin, so no positional prompt argument is passed.
- `--output-format stream-json` selects the line-delimited structured event stream. The Claude CLI requires `--verbose` alongside `stream-json` in print mode; the adapter always supplies it.
- `--model` is passed when `ExecutionRequest.model` is `Some`, otherwise when the agent's configured model is set, otherwise omitted.
- `--permission-mode` is passed per the Permissions section.
- The effort option is passed only when `effort` is configured, using the CLI's documented reasoning-effort control; the adapter never silently drops a configured value — if the installed CLI rejects it, the execution fails visibly.
- Configured `extra_args` are appended last, after validation (Configuration section).

The adapter never emits `--resume`, `--continue`, `--session-id`, `--fork-session`, or `--dangerously-skip-permissions`. Every execution is a fresh session; Familiar-owned durable state, not vendor session state, carries continuity between executions.

Child process wiring matches Codex: `current_dir(working_directory)`, `stdin(piped)`, `stdout(piped)`, `stderr(inherit)`; on Unix with a timeout, the child is placed in its own process group before spawn.

When `denied_read_path` is `Some`, the launch is wrapped by the shared isolation helper (macOS `/usr/bin/sandbox-exec` deny-read profile; unsupported platforms fail launch with the existing unsupported-isolation error). Version probing (`<executable> --version`) runs only when `denied_read_path` is `None`, mirroring the existing rule that adapter binaries are never executed outside the isolation boundary during review.

## Stdin and Streaming Behavior

The Familiar-compiled prompt is written to child stdin as raw bytes, then stdin is closed. Prompt bytes are exactly those produced by the existing context compiler and budgeter — this PRD changes no prompt rendering.

Stdout is consumed line by line as the child runs. For each line:

- a parseable stream-json event is handled per the next section; events that yield human-readable text are written to `output` followed by a newline and flushed immediately, so progress streams through Familiar as it arrives;
- a line that is not valid JSON is forwarded verbatim to `output` and flushed, mirroring Codex's malformed-line behavior — the adapter never suppresses child output it cannot classify, and never fabricates metrics from it.

Stderr is inherited so diagnostics reach the operator unmodified. Streamed output is untrusted agent output: it is displayed and captured, never parsed for policy, authority, or completion decisions.

Stdin write failures follow the existing Codex rule: an input error is surfaced as `AgentExecutionError::Input` unless the child already exited unsuccessfully, in which case the child's failure takes precedence.

## Stream-JSON Event Parsing

Parsing is deterministic, per line, with a closed set of recognized `type` values. Unrecognized event types are ignored without output and without state changes. Recognized events:

- `system` with `subtype == "init"` — capture `model` and `session_id` when present as strings. No output is emitted.
- `assistant` — for each element of `message.content` with `"type": "text"`, the `text` value is written to `output` as human-readable progress. Tool-use blocks and other content types produce no output in this PRD.
- `user` — tool results; ignored (no output).
- `result` — terminal event. Capture, when present and well-formed: `usage` (token fields per the next section), `total_cost_usd`, `session_id`, `is_error`, `subtype`, and `result` text. When `is_error` is true or `subtype` is any non-`success` value, one line `error: <subtype or result text>` is written to `output`. A `success` result's `result` text is not re-emitted if its content already streamed via assistant events; the adapter must not duplicate final text.

Rules:

- A field that is absent, `null`, of the wrong JSON type, negative, or exceeding `i64::MAX` leaves the corresponding captured value unknown. Nothing is coerced to zero or an empty string.
- Multiple `result` events (malformed stream) keep the first terminal capture and forward subsequent anomalies as unclassified lines.
- Event parsing never mutates policy, never interprets imperative text in agent output, and never decides workflow success — exit status and orchestration own that, unchanged.

## Result and Usage Mapping

`ExecutionResult` is populated exclusively from the sources below; every unavailable value remains `None` — never zero, never inferred:

- `agent_version` — from the `--version` probe (first line, non-empty, must contain a Claude identifier case-insensitively), only outside the isolation boundary; otherwise `None`.
- `model` — from the `system`/`init` event; if absent there, from the `result` event when it names exactly one model; otherwise `None`. The requested model is never copied into the reported model.
- `input_tokens` — the checked sum of `usage.input_tokens`, `usage.cache_creation_input_tokens`, and `usage.cache_read_input_tokens`, representing total submitted input so the existing `calculate_cost` cached-subset arithmetic remains valid. If any addend is absent or malformed, or the sum overflows, the value is `None` (absent cache fields are unknown, not zero).
- `cached_tokens` — `usage.cache_read_input_tokens`, or `None`.
- `output_tokens` — `usage.output_tokens`, or `None`.
- `session_id` (additive field) — from `init`, else `result`, else `None`.
- `reported_cost_microusd` (additive field) — `total_cost_usd` converted to micro-USD with documented half-up rounding and checked arithmetic; non-finite, negative, or overflowing values yield `None`.
- `exit_code` / `signal` — from the child's exit status exactly as Codex maps them.

Existing accounting is preserved: execution history's `estimated_cost_microusd` continues to come only from configured `[execution_history.pricing]` and the existing `calculate_cost`; unknown pricing or incomplete usage continues to record the existing `unavailable_fields` reasons. Claude's self-reported cost is retained on the result for observability and future PRDs but does not alter history semantics here.

Maximum budget: when the agent's `max_budget_microusd` is configured and the parsed `reported_cost_microusd` is known and exceeds it, the adapter reports a typed budget-exceedance failure carrying the complete `ExecutionResult` (an additive `AgentExecutionError` variant, handled in orchestration's existing per-variant outcome mapping with a distinct retained-reason string). Unknown reported cost is not a violation and is never treated as zero; ceilings that require enforcement guarantees stronger than post-execution detection remain the province of review's existing aggregate limits.

## Configuration

A new typed `[agents]` section in `familiar-core` configuration, loaded through the existing figment TOML + `FAMILIAR_`-prefixed environment pipeline:

```toml
[agents.implementation]
adapter = "claude-code"          # "codex" | "claude-code"; default "codex"
executable = "claude"            # default: "codex" for codex, "claude" for claude-code
model = "sonnet"                 # optional; omitted -> CLI default
effort = "high"                  # optional; claude-code only: "low" | "medium" | "high"
permission_mode = "acceptEdits"  # optional; claude-code only:
                                 # "default" | "plan" | "acceptEdits" | "bypassPermissions"
max_budget_microusd = 0          # optional; 0/absent -> no adapter budget ceiling
extra_args = []                  # optional; validated passthrough

[agents.reviewer]
adapter = "claude-code"
executable = "claude"
model = "sonnet"
effort = "high"
permission_mode = "default"
```

Validation is fail-closed and runs at configuration load:

- `adapter` is a closed enum; unknown values fail configuration.
- `executable` must be non-empty after trimming; it may be a bare name (PATH-resolved) or a path. It is always passed as argv[0] to `Command`, never through a shell.
- `effort` and `permission_mode` are closed enums valid only for `adapter = "claude-code"`; supplying them for `codex` fails configuration rather than being silently ignored.
- `permission_mode` defaults to `"default"`. `"bypassPermissions"` is rejected for the reviewer entry unconditionally, and the adapter never emits `--dangerously-skip-permissions` regardless of configuration.
- `extra_args` entries are rejected if they equal or prefix (`<flag>=`) any adapter-owned or forbidden flag: `--print`, `--output-format`, `--input-format`, `--verbose`, `--model`, `--permission-mode`, `--resume`, `--continue`, `--session-id`, `--fork-session`, `--dangerously-skip-permissions`. Validation is exact string matching on the flag token, not substring heuristics.
- When review is enabled, the existing `review.implementation_agent`/`review.reviewer_agent` identity blocks remain authoritative for review audit identity, and consistency is enforced: `review.*_agent.adapter_id` must equal the corresponding `agents.*.adapter`, and when both declare a model they must be equal. Contradictions fail configuration before any claim or launch.
- `ExecutionRequest.model` (supplied by orchestration from review configuration) takes precedence over the configured agent model at invocation time; the consistency rule above prevents that precedence from ever being a silent conflict.

Defaults preserve today's behavior exactly: with no `[agents]` section, both entries resolve to `adapter = "codex"`, `executable = "codex"`, no model, no effort, no permission mode, no budget, no extra args.

## Agent Construction

Construction is deterministic and lives only in the CLI composition root:

- `familiar run` builds the implementation agent from `[agents.implementation]` and the reviewer agent from `[agents.reviewer]` via one pure `build_agent(&AgentConfig) -> Box<dyn CodingAgent>` function (exact location per repository convention; `familiar-daemon` composing over `familiar-agent` types, mirroring today's `CodexAgent::new("codex")` call site).
- Construction performs no probing, no network access, no filesystem checks, and no model calls; a missing or broken executable surfaces later as the existing `AgentExecutionError::Launch`.
- `run::execute` and `execute_with_config` accept the two agents and pass the implementation agent to implementation/remediation and the reviewer agent to `StructuredReviewAdapter`. No orchestration code inspects which adapter it holds.
- `familiar next`, `history`, `usage`, and `backlog` commands construct no agents and are unchanged.

## Implementation and Reviewer Independence

Implementation and reviewer agents are configured, constructed, and held independently. Supported deterministic combinations include Codex/Codex (today's behavior), Codex implementation with Claude reviewer, Claude implementation with Codex reviewer, and Claude/Claude.

Independence semantics are enforced by the existing review coordinator and are not weakened:

- Reviewer execution always uses a fresh Claude process (fresh session, no `--resume`), satisfying `FreshProcessPerExecution`.
- Reviewer execution occurs in the isolated review workspace with `denied_read_path` set to the repository tree, exactly as today; a Claude reviewer on a platform without the isolation mechanism fails closed at launch.
- Same-model detection, `allow_isolated_same_model_fallback`, attempt ceilings, token/cost/duration ceilings, and finding-resolution rules operate unchanged on the observed metadata (`model`, `agent_version`) the adapter reports; unknown metadata remains unknown and continues to trigger the existing conservative paths.
- A Claude/Claude configuration with the same model is legitimate only through the existing isolated same-model fallback policy; this PRD adds no new waiver.

## Permissions and Trust Boundaries

Claude Code's own permission system is the enforcement mechanism inside the child process; Familiar configures it explicitly and never weakens it implicitly:

- `FilesystemPolicy::Normal` — the configured `permission_mode` (default `"default"`) is passed.
- `FilesystemPolicy::WorkspaceWrite` — the configured `permission_mode` is passed; a typical implementation profile is `"acceptEdits"`. The adapter never escalates a configured mode.
- `FilesystemPolicy::ReadOnly` — the adapter must produce an invocation that cannot mutate files or execute repository-modifying commands regardless of the configured permission mode: it passes the CLI's tool-restriction options disallowing file-editing and shell-execution tools in addition to a non-bypassing permission mode. The exact flag set is an adapter-owned constant pinned by tests. If the read-only guarantee cannot be expressed for the installed CLI, execution fails closed rather than running writable.

Trust boundaries:

- `--dangerously-skip-permissions` is never emitted, is rejected in `extra_args`, and has no configuration spelling. `bypassPermissions` mode is configurable only for the implementation agent, is never a default, and is rejected for the reviewer.
- The prompt travels via stdin; argv never contains prompt content, PRD content, or any repository-derived text, eliminating shell-interpolation and argument-injection surface.
- All child output — assistant text, result text, error text — is untrusted data. It is streamed and recorded but never parsed for instructions, never used to modify policy, warrants, backlog state, or review conclusions. Workflow success continues to be decided by exit status, deterministic verification, and review — unchanged.
- Session identity is recorded as provenance only; no Familiar decision may key on vendor session state.
- Credentials remain wholly owned by the Claude CLI's own authentication; Familiar passes no keys, reads no vendor credential stores, and adds no environment-variable credential plumbing.

## Failures and Timeouts

The existing error taxonomy applies unchanged, with adapter-neutral messages:

- Launch failure (missing executable, spawn error, unavailable isolation mechanism) → `AgentExecutionError::Launch` with the attempted executable.
- Stdin delivery failure → `Input`, with the existing child-already-failed precedence rule.
- Wait failure → `Wait`.
- Stdout read/write failure → `Output`, retaining all metadata captured before the failure.
- Timeout → the existing Unix watchdog: process group created at spawn, `SIGKILL` to the group at `timeout_ms`, `AgentExecutionError::Timeout` carrying the partial `ExecutionResult` (exit/signal recorded; usage fields remain whatever was parsed — typically `None`).
- Budget exceedance (when configured) → the additive typed failure defined in Result and Usage Mapping.

In every failure path the partial `ExecutionResult` is preserved and propagated so execution history finalization records exactly what was observed and marks the rest with the existing `unavailable_fields` reasons. A nonzero exit, `is_error` result, or signal is never converted into success, and a missing `result` event is recorded as unknown usage — never zeroed. Orchestration's existing outcome mapping (`succeeded`/`failed`/`signaled`/`timed_out`, retained `in_progress` backlog entries, review stop reasons) is unchanged.

## Compatibility

- **Codex preserved:** `CodexAgent` behavior, argv, event parsing, and tests remain byte-identical; helper extraction must not alter its observable behavior. Default configuration reproduces today's `familiar run` exactly, including prompt bytes, streaming, history rows, and exit codes.
- **Trait stability:** `CodingAgent`, `ExecutionRequest`, and `FilesystemPolicy` are unchanged. `ExecutionResult` gains only the two additive `Option` fields (default `None`); `AgentExecutionError` gains at most the budget variant and neutral wording. Existing struct-literal constructions in tests are updated mechanically.
- **Orchestration neutrality:** `run.rs` changes are limited to accepting and threading the second agent; it gains no adapter names, no vendor branches, and no Claude-specific behavior.
- **History and accounting:** no schema change is required; `ExecutionStart`, `ExecutionFinalization`, pricing estimation, and `unavailable_fields` semantics are untouched. Backlog admission, claim, completion, and PRD-012 recovery are untouched. Context compilation and budgeting are untouched.
- **CLI surface:** no new commands or flags; `familiar run` signature and output conventions are unchanged apart from agent construction reading configuration.
- The change is confined to the expected files and is independently mergeable; a Claude CLI need not be installed for any existing behavior or test to pass.

## Acceptance Criteria

1. `ClaudeCodeAgent` implements the existing `CodingAgent` trait in `familiar-agent`, reports `FreshProcessPerExecution`, and requires no orchestration knowledge of its concrete type.
2. Execution launches the configured executable directly (no shell) with `--print`, `--output-format stream-json`, and `--verbose`, in the requested working directory, with the Familiar-compiled prompt delivered byte-exact through stdin and never through argv.
3. Assistant text events are written to the supplied output stream and flushed as they arrive; non-JSON stdout lines are forwarded verbatim; unrecognized event types are ignored without output or fabricated state.
4. The adapter captures model and session identity from the init event and usage, cost, error, and session information from the result event, tolerating absent or malformed fields by leaving values unknown.
5. `ExecutionResult` maps total input tokens (including cache creation and cache reads) via checked arithmetic, cached tokens from cache reads, and output tokens directly; any missing or invalid component yields `None`, and no usage, cost, or token value is ever coerced to zero.
6. Claude-reported cost is preserved as an additive optional micro-USD field without altering existing pricing-based history estimation, and session identity is preserved as an additive optional field defaulting to `None` for all other adapters.
7. The adapter never emits `--resume`, `--continue`, `--session-id`, `--fork-session`, or `--dangerously-skip-permissions`, and every execution uses a fresh session and fresh process.
8. `FilesystemPolicy::ReadOnly` produces an invocation that cannot edit files or run repository-modifying commands regardless of configured permission mode, and reviewer execution honors `denied_read_path` through the shared isolation helper, failing closed on unsupported platforms.
9. Typed `[agents.implementation]` and `[agents.reviewer]` configuration supports adapter, executable, model, effort, permission mode, maximum budget, and validated extra arguments, with closed enums, fail-closed validation, rejection of forbidden extra arguments, and rejection of `bypassPermissions` for the reviewer.
10. With no `[agents]` configuration, both agents deterministically resolve to the existing Codex adapter with executable `codex`, and `familiar run` behavior is byte-identical to today, including prompt bytes and history semantics.
11. Implementation and reviewer agents are constructed independently in the CLI composition root and threaded separately through run orchestration, supporting all four Codex/Claude combinations without orchestration branching on adapter identity.
12. When review is enabled, configured review agent identity and `[agents]` selection are validated for consistency before claim, and contradictions fail configuration rather than executing.
13. Timeout enforcement kills the whole child process group and returns the existing timeout error with partial results; launch, input, wait, and output failures preserve captured metadata and map to the existing error variants with adapter-neutral messages.
14. When a maximum budget is configured and the parsed reported cost exceeds it, the execution surfaces a typed budget failure retaining the full result; unknown reported cost is never treated as a violation or as zero.
15. Codex adapter behavior, review isolation, reviewer-independence policy, verification, execution history, usage accounting, backlog lifecycle, context budgeting, and all existing CLI commands remain observably unchanged.
16. No automatic provider routing, Cursor, Ollama, MCP integration, or session reuse is introduced, and `CodingAgent` is extended only by the minimal additive changes named in this PRD.
17. All new behavior is covered by tests using fake executables, fixture streams, and temporary repositories; no test invokes a real Claude or Codex binary, network, or developer credentials.
18. The implementation is confined to the expected files and is independently mergeable.

## Test Strategy

### Adapter unit tests (`familiar-agent`)

- Fake `claude` shell scripts emit fixture stream-json: init + assistant + result success; assistant-only with missing result; result with `is_error` and error subtypes; malformed interleaved non-JSON lines; duplicate result events; absent/negative/overflowing usage fields.
- Assert streamed output ordering and flushing, verbatim forwarding of unclassifiable lines, and exact `ExecutionResult` mapping including `None` preservation for every absent field.
- A fake executable that records its argv and stdin proves: prompt arrives byte-exact on stdin; argv contains the adapter-owned flags in order; argv never contains prompt bytes, `--resume`, `--continue`, `--session-id`, `--fork-session`, or `--dangerously-skip-permissions`; model precedence (request over configuration) holds; effort and permission-mode flags appear exactly when configured.
- Read-only policy test proves the pinned restriction flags are present for `FilesystemPolicy::ReadOnly` independent of configured permission mode.
- Timeout test mirrors the Codex watchdog test: a sleeping fake is killed within bounds and returns `Timeout`.
- macOS isolation test mirrors the Codex denied-read test through the shared helper; non-macOS asserts the fail-closed launch error.
- Version probe: parsed outside isolation, skipped inside; non-Claude or failing probe yields `None`.
- Budget: reported cost under, equal, over, and unknown against a configured ceiling; only strict exceedance fails, carrying the full result.
- Codex regression: existing Codex tests pass unmodified (module paths aside) after helper extraction.

### Configuration tests (`familiar-core`)

- Parse the canonical `[agents]` TOML above; verify defaults with the section absent resolve to Codex/`codex`.
- Reject unknown adapters, empty executables, effort/permission-mode on Codex entries, reviewer `bypassPermissions`, forbidden `extra_args` (exact-token matching, including `=`-joined forms), and review-identity contradictions when review is enabled.
- Environment-variable overrides via the existing `FAMILIAR_AGENTS__...` mapping round-trip correctly.

### Construction and orchestration tests (`familiar-daemon`)

- `build_agent` maps each adapter enum to the correct concrete type deterministically.
- Fake implementation and reviewer agents with distinct recording state prove implementation/remediation calls reach only the implementation agent and review calls reach only the reviewer agent, with existing review fixtures (clean review and one remediation) passing under split agents.
- Default-configuration run reproduces existing behavior: prompt-bytes tests, history mapping tests, and backlog tests pass unchanged.
- Additive `ExecutionResult` fields default to `None` through history finalization without new `unavailable_fields` regressions.

### Verification commands

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Focused suites for the new adapter, configuration, and construction must be independently runnable. Tests use only temporary directories, fixture executables, and in-memory or temporary databases; none touch a developer's real Familiar state, real agent CLIs, or the network. Demonstrably pre-existing failures are reported separately with exact evidence.
