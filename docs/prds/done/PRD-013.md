# PRD-013: Deterministic Review Scope Authorization

**Status:** Completed
**Date:** 2026-08-03  
**Depends on:** PRD-008, PRD-011  
**Architectural direction:** Repository Is Truth; Determinism Before Intelligence; Small, Bounded Work Wins  
**Delivery boundary:** Independently mergeable replacement of review scope evaluation and reporting

## Objective

Replace review's coarse path-only scope check with a deterministic change-authorization policy that evaluates the active PRD's `Expected Files` contract, configured allowed paths, configured prohibited changes, and the actual Git change kind for every changed file.

Legitimate implementation and remediation changes that are explicitly expected and authorized must be able to reach verification, independent review, and PRD-011 completion without repeatedly stopping as `ScopeBroadened`. Prohibited or undeclared changes must still fail closed. Ambiguous policy or evidence must stop for human review rather than being guessed by an LLM or hidden behind a generic scope result.

## Motivation and Current Behavior

The current review implementation constructs `ReviewTask.allowed_paths` and `ReviewTask.prohibited_changes` directly from static configuration. `check_scope` accepts only exact configured files or prefixes ending in `/`. `enforce_scope` additionally rejects symlinks, treats path-shaped prohibited strings as prohibited prefixes, recognizes a hard-coded dependency filename list, and interprets any prohibited-change string containing `dependenc` as a dependency prohibition. The result has only `Contained` or `Broadened`, and the coordinator records only `ScopeBroadened`.

This loses the authorization already expressed by an active PRD's `Expected Files` section, conflates policy categories, depends on substring matching, and cannot report which file and rule stopped the run. A valid implementation can therefore be stranded `in_progress` even when its changed files match the PRD that Familiar admitted and supplied to the coding agent.

This PRD makes scope a compiled, persisted policy decision. It does not make the PRD unlimited authority: configuration remains the project-owned ceiling, prohibited rules always win, and any permitted PRD-declared expansion must be explicitly enabled.

## Scope

This PRD includes:

1. Parsing the active PRD's `Expected Files` section into a typed, validated expected-file contract before backlog claim or agent launch when review is enabled.
2. Compiling that contract with a validated snapshot of configured allowed paths, PRD-expansion behavior, prohibited-change rules, special-file policies, and supported Git change kinds.
3. Classifying every observed changed path, including both sides of a rename or copy, before initial review and after every remediation.
4. Producing an ordered structured finding for every scope-relevant file/rule decision.
5. Distinguishing allowed changes, justified expected-file changes, prohibited changes, undeclared scope expansion, and ambiguous changes requiring human review.
6. Giving dependency manifests, lockfiles, migrations, configuration, tests, and generated artifacts explicit typed policy.
7. Reporting the exact file, change kind, matched declaration, and policy rule responsible for `ScopeBroadened`.
8. Persisting the compiled policy snapshot and findings needed to reproduce and audit the decision.
9. Preserving PRD-008 review isolation, evidence budgets, retries, remediation, accounting, and stopping behavior and PRD-011 completion semantics.
10. Focused parser, policy, coordinator, configuration, storage, and run integration tests with no real model or non-temporary repository.

## Non-goals

This PRD does not:

- authorize a PRD to override a prohibited-change rule;
- make all paths named in a PRD automatically writable;
- infer intent from prose outside the exact `Expected Files` contract;
- inspect file contents semantically, invoke an LLM, or use reviewer prose to decide scope;
- add Ollama, routing, provider selection, embeddings, semantic search, or a new agent adapter;
- change reviewer independence, review-package evidence budgets, deterministic verification, retry ceilings, remediation assignment, usage/cost accounting, persistence recovery, or finding-resolution rules;
- change PRD-011 admission, claim ownership, clean-review completion predicate, retained `in_progress` behavior, or PRD-012 recovery authority;
- add automatic commit, reset, merge, rebase, push, publication, deployment, or worktree cleanup;
- authorize dependency updates, migrations, generated outputs, configuration changes, tests, or symlinks merely because their filenames look conventional;
- edit prior PRDs, philosophy, architecture documents, ADRs, or contracts; or
- create a general execution-warrant, repository permission, or host sandbox system.

## Scope-Policy Inputs

The scope engine receives one immutable `ScopePolicyInput` assembled before review:

- canonical repository identity and worktree identity;
- active PRD canonical repository-relative path and content hash;
- parsed `ExpectedFilesContract`, including source ranges and normalized entries;
- configured `allowed_paths`;
- configured `allow_prd_expected_file_expansion`;
- configured typed `prohibited_changes` rules;
- configured typed policy for dependencies, lockfiles, migrations, configuration, tests, and generated artifacts;
- policy schema/version identifier;
- baseline revision and resulting tree identity;
- complete, deterministically ordered `ChangedFile` values from Git, including `path`, `old_path`, and `GitChangeKind`; and
- deterministic filesystem/Git metadata required to classify file type, symlink state, and generated-file declarations.

The compiled `ScopePolicySnapshot` stores normalized rules, the PRD hash and parsed expected entries, configuration provenance, defaults, and a stable hash. The same snapshot governs initial implementation scope and every remediation attempt in that run. Configuration or PRD changes after compilation do not silently alter authority; they cause a stale-input conflict and human review.

Missing, unreadable, malformed, stale, non-UTF-8, non-relative, or non-canonical inputs fail closed. Map iteration, filesystem enumeration, and configuration declaration order must not affect the result.

## Expected Files Parsing Contract

Only one level-two Markdown heading whose trimmed, case-sensitive text is exactly `Expected Files` is authoritative. The section begins after that heading and ends at the next level-one or level-two heading or end of document. A missing or duplicate authoritative heading is invalid when review is enabled.

The section must contain a bullet list. Each top-level bullet authorizes exactly one path expression and may contain explanatory prose after the expression. The path expression must be represented by the bullet's first inline-code span. A bullet with no first inline-code span, multiple path expressions joined in one first span, an unclosed span, or an empty expression is ambiguous and invalid. Nested bullets and prose do not create additional authority.

Supported expressions are deliberately closed:

- `path/to/file` means that exact repository-relative file;
- `path/to/directory/` means every descendant of that directory, but not the directory entry itself; and
- `path/to/directory/**` is equivalent to the directory form and is normalized to it.

No other glob syntax is supported. Absolute paths, backslashes, `.` or `..` components, empty components, URI forms, home expansion, environment variables, brace expansion, character classes, `*` outside the terminal `/**`, and repository-external paths are rejected. Duplicate normalized expressions are rejected so that the source contract has one unambiguous provenance entry per rule.

Phrases such as “focused modules beneath” or “only if required” remain human-readable explanation; they do not widen or narrow the first path expression. If conditional or multi-path authorization is needed, the PRD author must use separate explicit bullets or a directory rule. Existing PRDs are not rewritten by this increment; an active PRD that does not satisfy this grammar stops before claim with a diagnostic identifying its line and parsing rule.

The parser returns source line, original bullet text, normalized expression, and match kind. Parsing is deterministic and uses no LLM, embedding, filename heuristic, or semantic interpretation.

## Authorization Precedence

Each changed path is evaluated using the following precedence. The first terminal rule wins; lower rules cannot waive it:

1. **Invalid or incomplete evidence:** malformed Git status, unsupported change kind, unsafe path, symlink, missing required old path, repository containment failure, stale PRD/configuration, or policy-evaluation error produces an ambiguous finding and human review.
2. **Explicit prohibition:** a matching prohibited path, prohibited change kind, prohibited file class, or prohibited operation produces a prohibited-change finding. Expected-file and allowed-path matches cannot override it.
3. **Special-file policy:** a dependency manifest, lockfile, migration, configuration file, test, or generated artifact must be explicitly permitted for its class and observed change kind. `deny` produces a prohibited finding and `human_review` produces an ambiguous finding. No generic path match bypasses this step.
4. **Static ceiling:** a path within configured `allowed_paths` may continue to declaration evaluation. A path outside that ceiling may continue only when `allow_prd_expected_file_expansion = true` and it matches the Expected Files contract. Otherwise it is undeclared scope expansion under the exact `static_allowed_path_ceiling` rule.
5. **PRD declaration:** a changed path matching Expected Files is authorized. Inside the static ceiling it is an allowed change; outside the ceiling under enabled expansion it is a justified expected-file change.
6. **Configured-only path:** a path inside the static ceiling but absent from Expected Files is allowed only when the configured declaration mode explicitly permits configured-only changes. Otherwise it is undeclared scope expansion under `expected_file_declaration_required`.
7. **No match:** the change is undeclared scope expansion.

The default declaration mode is `expected_or_configured`, preserving existing allowed-path behavior while recognizing PRD declarations. Projects may select `expected_required` to require both the static ceiling (or permitted PRD expansion) and an Expected Files match. There is no mode in which an Expected Files entry overrides a prohibition.

A file listed by the active PRD must therefore never be labeled undeclared merely because it is outside `allowed_paths`: with expansion enabled it is `justified_expected_file_change`; with expansion disabled it is rejected specifically by `static_allowed_path_ceiling`, retaining its Expected Files match in the finding.

## File and Change Classification

Canonical file classes are closed typed values:

- `ordinary_source`;
- `dependency_manifest`;
- `dependency_lockfile`;
- `migration`;
- `configuration`;
- `test`;
- `generated_artifact`; and
- `ambiguous`.

Classification uses only configured exact paths and directory rules plus built-in, versioned exact basename/path rules. It never uses arbitrary substring containment. Configuration rules take precedence over built-in rules and must identify their rule ID and provenance. If zero special-class rules match, the file is `ordinary_source`. If incompatible special classes match and no configured precedence resolves them, the file is `ambiguous`.

Supported Git change kinds remain closed: `added`, `modified`, `deleted`, `renamed`, `copied`, `type_changed`, and `unmerged`. Policy is evaluated against the observed kind, not merely the current filename. Rename and copy evaluate both source and destination as separate path subjects with one shared change ID. A rename is authorized only when the old-path removal and new-path addition are both authorized. A copy requires authorization for the destination and applies any source-side read classification required by policy. `type_changed` and `unmerged` default to human review. Symlinks remain ambiguous and are never made automatically safe by a path declaration.

Findings are sorted by canonical current path, old path, change-kind order, precedence, and rule ID. The aggregate decision is independent of Git output order.

## Migration and Dependency-File Handling

Special classes use explicit per-class policies with allowed change kinds:

```text
deny | human_review | allow_when_expected | allow_when_configured | allow
```

Defaults fail closed:

- dependency manifests: `human_review`;
- dependency lockfiles: `human_review`;
- migrations: `human_review`;
- configuration: `human_review`;
- generated artifacts: `human_review`;
- tests: `allow_when_expected`.

Dependency manifests and lockfiles are separate classes and decisions. Permitting a manifest does not permit its lockfile, and permitting a lockfile does not prove the manifest change is authorized. The policy must explicitly enumerate recognized ecosystem files and may add project-specific exact paths through configuration. The implementation must remove the current `contains("dependenc")` interpretation and must not replace it with another free-text heuristic.

Migration classification is based on configured migration directories or exact files, not a filename containing “migration.” Adding, modifying, deleting, or renaming a migration may have distinct configured outcomes. Existing applied migration files should normally be denied modification/deletion by project policy; this PRD supplies the typed mechanism and fail-closed defaults, not database-specific semantic inference.

Generated status must come from an explicit configured path rule or an existing deterministic repository declaration supported by a versioned adapter. A generated-looking name is insufficient. When both a generator source and its output change, each file requires independent authorization.

## Scope Decisions and Structured Findings

Every evaluated path produces a `ScopeFinding` equivalent in serialized semantics to:

```rust
pub struct ScopeFinding {
    pub finding_id: String,
    pub change_id: String,
    pub path: String,
    pub old_path: Option<String>,
    pub change_kind: GitChangeKind,
    pub file_class: ScopeFileClass,
    pub decision: ScopeDecision,
    pub rule_id: String,
    pub rule_source: ScopeRuleSource,
    pub rule_detail: String,
    pub expected_file_match: Option<ExpectedFileMatch>,
    pub allowed_path_match: Option<String>,
    pub prohibited_rule_match: Option<String>,
    pub policy_snapshot_hash: String,
}

pub enum ScopeDecision {
    AllowedChange,
    JustifiedExpectedFileChange,
    ProhibitedChange,
    UndeclaredScopeExpansion,
    AmbiguousHumanReview,
}
```

Exact Rust names may follow repository conventions, but these fields and closed semantics are canonical. `rule_id` is a stable machine identifier, not rendered prose. `rule_source` distinguishes built-in policy, project configuration, Expected Files, and evidence validation. Matches retain the normalized rule and its configuration key or PRD source line.

The aggregate result is:

- `contained` only when every finding is `allowed_change` or `justified_expected_file_change`;
- `broadened` when at least one finding is `prohibited_change` or `undeclared_scope_expansion`; or
- `human_review_required` when there is ambiguity and no broadened finding. If both occur, broadened is terminal and all ambiguous findings are still retained.

For every `ScopeBroadened` stop, CLI/human output and durable state must report at least one exact tuple of `path`, `change_kind`, `decision`, and `rule_id`; it must also report all scope findings in stable order within evidence/output budgets. A generic “scope broadened” message without an exact causing file and rule is invalid. Bounded rendering may summarize additional findings only after persisting all canonical findings and must report the omitted count and artifact reference.

Ambiguity uses a distinct stop reason equivalent to `ScopeAmbiguous`; it must not masquerade as clean review or as a model finding.

## Interaction with Review and Remediation

Scope authorization occurs after each diff capture and before verification or reviewer invocation. A broadened or ambiguous result is persisted and stops the cycle without invoking a reviewer or starting another remediation. Familiar never reverts the worktree.

The initial implementation and every remediation use the same compiled policy snapshot. Remediation requests include the normalized authorized path rules, special-file constraints, and unresolved blocking findings; they must not reduce policy to the old `allowed_paths` list. A reviewer finding cannot grant scope, and implementer or reviewer prose cannot resolve a scope finding.

An already authorized changed file remains authorized after remediation only if its new observed change kind is also permitted. Newly changed files are evaluated normally. A remediation request whose demanded fix cannot fit the policy stops for human review without broadening authority.

Existing evidence budgeting, verification selection, reviewer independence, attempt counting, token/cost/duration ceilings, persistence ordering, interruption recovery, and finding-resolution behavior remain unchanged. Scope-policy evaluation itself consumes no model budget and does not create a retry. Failed or malformed agent attempts still have their resulting diff captured and evaluated as required by PRD-008.

PRD-011 may complete a backlog entry only after the unchanged clean terminal review predicate succeeds. `ScopeBroadened` and `ScopeAmbiguous` leave the entry `in_progress` for explicit PRD-012 recovery or later human-directed action.

## Configuration Behavior

Review configuration gains validated typed scope-policy settings. Canonical behavior is equivalent to:

```toml
[review.scope]
allow_prd_expected_file_expansion = false
declaration_mode = "expected_or_configured"

[review.scope.file_classes]
dependency_manifest = "human_review"
dependency_lockfile = "human_review"
migration = "human_review"
configuration = "human_review"
test = "allow_when_expected"
generated_artifact = "human_review"
```

Existing `review.allowed_paths` remains the static outer ceiling. `allow_prd_expected_file_expansion = false` is the compatibility and fail-closed default. Enabling it permits only paths exactly matched by the active parsed Expected Files contract; it does not permit unrelated paths, prohibited rules, unsafe file types, or disallowed special classes.

`prohibited_changes` must become a typed list/table with stable rule IDs, rule kind, exact path/directory or file class, applicable change kinds, and optional bounded description. Free-form legacy strings are accepted only if they parse losslessly into a documented closed legacy grammar; otherwise enabled-review configuration validation fails before claim. No substring, fuzzy, case-folded prose, or semantic interpretation is allowed.

Allowed and prohibited path normalization uses the same canonical grammar as Expected Files. Duplicate, shadowed, contradictory, unknown, or unsupported rules fail configuration validation unless a documented precedence makes the result unique. An empty static allowed list remains invalid unless PRD expansion is enabled and a valid non-empty Expected Files contract exists. Empty prohibited rules do not disable built-in unsafe/ambiguity checks.

Configuration is loaded and the policy compiled during PRD-011 preflight so invalid policy leaves a pending PRD unclaimed. With review disabled, existing run behavior remains unchanged and no Expected Files parsing is newly required by this PRD.

## Failure Semantics

- Parser, configuration, normalization, overflow, containment, Git evidence, snapshot-hash, storage, or policy-version failures stop before further external invocation.
- Preflight failures occur before PRD-011 claim whenever possible and leave backlog and execution history unchanged.
- A post-claim scope failure durably finalizes the review cycle as `HumanReviewRequired` and leaves the backlog entry `in_progress`.
- Prohibited and undeclared findings record `ScopeBroadened`; ambiguous findings record `ScopeAmbiguous` unless a broadened finding already supplies the terminal scope reason.
- Unknown file class, unsupported change kind, conflicting rules, missing rename source, symlink, type change, unmerged path, or insufficient evidence is never coerced to allowed or prohibited; it requires human review.
- Persistence failure prevents reviewer/remediation invocation and follows existing interrupted-cycle recovery. Recovery never silently reevaluates under newer policy.
- Output-budget truncation cannot discard canonical findings; it retains an artifact/hash and exact omitted count.
- No failure path commits, resets, deletes, merges, pushes, deploys, or rewrites the worktree or PRD.

## Acceptance Criteria

1. Review scope is computed from a versioned policy snapshot containing the active PRD Expected Files contract, configured allowed paths, configured prohibited rules, special-file policies, and actual changed files/change kinds.
2. Expected Files parsing follows the exact heading, section, bullet, inline-code, path-expression, normalization, provenance, duplicate, and failure rules in this PRD.
3. A valid Expected Files match outside static allowed paths is classified as `justified_expected_file_change` when configured PRD expansion is enabled and is not prohibited or restricted by special-file policy.
4. With expansion disabled, that same change fails specifically under `static_allowed_path_ceiling`, while retaining and reporting its Expected Files match; it is not mislabeled as undeclared.
5. Prohibited rules always take precedence over allowed paths and Expected Files, and this implementation provides no waiver mechanism.
6. Every changed file, and both sides of rename/copy changes where applicable, receives a deterministic structured finding with exact path, change kind, class, decision, rule ID, provenance, and policy hash.
7. Decisions distinguish allowed, justified expected-file, prohibited, undeclared expansion, and ambiguous human-review outcomes as closed typed values.
8. Dependency manifests, lockfiles, migrations, configuration, tests, and generated artifacts are classified and authorized through explicit typed rules rather than substring matching.
9. Manifest and lockfile decisions are independent; project-specific special files can be declared by exact path/directory configuration; unknown or conflicting classifications fail closed.
10. Deleted, renamed, copied, type-changed, unmerged, and symlinked paths follow the explicit semantics in this PRD and cannot become authorized from destination path matching alone.
11. Any `ScopeBroadened` stop durably and visibly identifies the exact causing file, change kind, decision, and rule ID; all findings use stable ordering.
12. Ambiguity produces human review through a distinct typed result/stop reason and never invokes an LLM to decide scope.
13. Scope evaluation runs before verification/review for initial implementation and after every remediation diff, using the unchanged policy snapshot.
14. Scope findings cannot be waived by implementer claims, reviewer output, retry, remediation, passing tests, or clean review prose.
15. Invalid configuration or Expected Files fails before PRD-011 claim when review is enabled; post-claim violations leave the PRD `in_progress` under unchanged PRD-011 semantics.
16. Review isolation, package/evidence budgets, retries, verification, remediation assignment, accounting, persistence/recovery, finding resolution, and clean-review completion semantics remain compatible.
17. Existing disabled-review behavior remains unchanged. Existing configurations either map losslessly to the closed legacy grammar or fail with an exact migration diagnostic; they are never interpreted heuristically.
18. No automatic commit, merge, push, deployment, worktree rewrite, Ollama integration, routing, embeddings, semantic search, or new provider behavior is introduced.
19. The change remains confined to the expected files and is independently mergeable.

## Test Strategy

### Expected Files parser tests

- Parse one exact-file bullet, directory bullet, terminal `/**` bullet, explanatory prose, and multiple explicit bullets with source-line provenance.
- Reject missing/duplicate headings, nested-only lists, missing or unclosed inline code, empty/multiple expressions, unsupported globs, absolute/traversing/backslash paths, variables, duplicates, and non-UTF-8 input.
- Prove prose outside the first inline-code span and outside the section grants no authority.
- Parse all repository PRD fixtures intended for enabled review and pin either the normalized contract or exact validation error without changing prior PRDs.

### Policy and precedence tests

- Cover all five decisions for exact files and directory rules, with expansion enabled and disabled and both declaration modes.
- Exhaustively assert the precedence matrix: evidence ambiguity, prohibition, special-file policy, static ceiling, Expected Files, configured-only path, and no match.
- Prove a prohibited match wins over Expected Files and allowed paths for every supported change kind.
- Randomize rule and changed-file input order and assert byte-identical findings, aggregate disposition, rendering, and policy hash.
- Reject duplicate, contradictory, shadowed, unknown, malformed, stale, and overflowing policy inputs.

### Classification and change-kind tests

- Cover ordinary source, manifest, lockfile, migration, configuration, test, generated artifact, conflicting class, and project-specific exact classification.
- Prove classification uses exact/versioned path rules and never `contains`, fuzzy, semantic, or case-insensitive prose matching.
- Cover add, modify, delete, rename, copy, type change, unmerged, symlink, missing old path, and unsafe path; require both rename sides.
- Independently permit/deny a manifest and lockfile, new versus modified migration, expected test, configured-only test, and generated source/output pair.

### Coordinator, persistence, and remediation tests

- Persist and reload the policy snapshot and every structured finding without loss, including Expected Files source provenance and exact rule ID.
- Assert scope evaluation precedes verifier and reviewer invocation and that broadened/ambiguous fixtures invoke neither.
- Run one successful remediation that changes only authorized files and one that adds a prohibited, undeclared, special, renamed, and ambiguous file.
- Assert remediation reuses the original policy hash and cannot acquire authority from changed PRD/configuration bytes or reviewer prose.
- Inject storage failure before and after finding persistence and assert existing interruption behavior and no unrecorded retry.
- Pin bounded CLI/human rendering, omitted-count/artifact behavior, and exact file/rule reporting for `ScopeBroadened`.

### Run and compatibility tests

- With review enabled, prove a PRD-expected file outside static paths reaches review only when expansion is explicitly enabled and can satisfy unchanged PRD-011 completion after clean review and verification.
- Prove expansion-disabled, prohibited, undeclared, and ambiguous runs remain `in_progress` after claim with exact terminal evidence.
- Prove invalid preflight policy or Expected Files leaves the PRD pending and launches no agent.
- Preserve disabled-review prompt bytes, streaming, execution history, usage/pricing, exit behavior, backlog behavior, review isolation, budgets, retries, and accounting.
- Use only fake agents/commands and temporary repositories; no test invokes a remote model, developer credentials, commit, merge, push, or deployment.
- Run `cargo fmt --all -- --check`, focused Clippy with warnings denied, focused affected-crate tests, and `cargo test --workspace`, reporting demonstrably pre-existing failures separately.

## Definition of Done

PRD-013 is done when:

1. Familiar compiles one deterministic, versioned, persisted scope-policy snapshot from the active PRD and validated configuration before review execution.
2. The exact Expected Files grammar is enforced with path and source provenance, and an explicitly enabled expected-file expansion can authorize a legitimate file outside the static ceiling without authorizing unrelated changes.
3. Every observed path/change kind receives one reproducible typed decision, and prohibited, undeclared, and ambiguous outcomes fail closed under the defined precedence.
4. Dependencies, lockfiles, migrations, configuration, tests, and generated artifacts use explicit class policy with no substring, LLM, routing, embedding, or semantic inference.
5. Every `ScopeBroadened` result names the exact file and rule, every ambiguity reaches human review, and complete findings remain durable under output budgets.
6. Initial implementation and all remediation attempts use the same authority snapshot; neither agents, reviewers, retries, verification, nor PRD/configuration mutation can widen it.
7. PRD-008 isolation, evidence budgeting, verification, retry/remediation, accounting, persistence, and recovery semantics and PRD-011/012 backlog semantics remain intact.
8. No prohibited enforcement is weakened and no automatic commit, merge, push, deployment, reset, or worktree rewrite is added.
9. Focused parser/policy/classification/coordinator/storage/run tests, formatting, focused Clippy, and workspace tests pass, or unrelated pre-existing failures are reported with exact evidence.
10. Only the bounded Expected Files surface changes, prior documents remain untouched, and the implementation is independently mergeable.
