# PRD-036: Repository Onboarding and Policy Generation

**Status:** Completed
**Date:** 2026-08-26
**Depends on:** PRD-019, PRD-026, PRD-030, PRD-031, PRD-033, PRD-039

## Objective

Onboard a new repository without changing Familiar code by producing a
reviewable operator-owned policy and a harmless validation fixture.

## Scope

- Discover languages, build tools, PRD layout, protected paths, and likely
  verification commands as untrusted proposals.
- Ask the operator to approve repository identity, structured metadata mode,
  verification, worker policy, budgets, and delivery authority.
- Store secrets only by external reference.
- Validate the final policy without claiming a PRD or invoking a model.
- Run a harmless fixture proving context, review isolation, reporting, and any
  selected supervisor/delivery boundary.

## Acceptance Criteria

1. Generated policy grants no authority before explicit approval.
2. Malicious repository content cannot inject commands or configuration.
3. Two materially different repositories onboard without Familiar code changes.
4. Re-running onboarding produces an explainable policy diff.
5. A successful onboarding ends with a signed/attributed policy snapshot.

## Owner Guidance (recorded 2026-08-30, human:trollboy)

Answers to the implementation questions raised during the first drive
attempt, binding for any implementer. Do not stop to ask these again.

1. **CLI surface:** four subcommands — `familiar-ai onboard
   {propose|approve|validate|fixture}` — mirroring the `plan` precedent.
   Each authority boundary stays independently testable.
2. **Approval input:** a deterministic answers file (`--answers <path>`,
   TOML), parsed and validated. No interactive prompting; nothing else in
   this CLI prompts.
3. **Approved policy location:** one generated TOML file per repository
   under a configurable `repositories_dir` (default `config/repositories/`),
   merged additively by `Config::load`, with a hard refusal when a
   repository key exists in both the main file and a generated file.
   Never edit `config/default.toml` in place.
4. **Worker policy and budgets:** map onto existing repository-scoped
   fields only — `review.implementation_agent`/`reviewer_agent` and the
   existing `review`/`execution_context` ceilings. Do not add new
   repository-scoped config sections (PRD-026's closed set stands).
5. **"Signed" snapshot:** content hash plus durable human-actor
   attribution, matching `plan approve`. No cryptographic signing and no
   new dependencies.
