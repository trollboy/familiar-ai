# PRD-066: Integration-Aware Parallel Orchestration

## Objective

Make concurrent multi-process PRD execution actually compose. Wave 2 proved
the three layers of the problem are in different states: concurrent
*execution* works (worktrees, threads, per-PRD leases), concurrent
*composition* does not exist (completed candidates sat in dirty worktrees
while successors built on stale bases and minted duplicate migration
numbers), and concurrent *authorization* is starved by coarse scope
declarations that force honest width one. This PRD builds composition and
restores width — the two missing layers — and nothing else. It never falls
back to serial execution as a safety mechanism: after this PRD, serial is
not safer, so it is never the answer.

Covers wave-2 after-action defects 1–4 and 13–15.

## Design

### 1. Merge queue: parallel execution, ordered landing (defects 2–3)

Workers execute concurrently; landings are sequenced. Each drive session
maintains a persisted **session integration revision**, starting at the
session base. When a candidate passes review, the driver commits it in its
worktree and merges it onto the integration revision — in review-completion
order — before anything else may consume it. Three consequences, enforced
rather than hoped:

- **Scope release happens at integration, not at review.** A reviewed but
  unintegrated candidate still holds its expected-file scopes and declared
  resources, so a scope-overlapping successor is admitted only against a
  base that already contains the predecessor's work.
- **Completion happens at integration.** The backlog transition to
  completed occurs when the candidate is merged into the integration
  revision — never while the work exists only as a dirty worktree.
  Checkpoint phases distinguish `review_complete` from `integrated`;
  dependency satisfaction and scope release consume `integrated`.
- **New worktrees branch from the integration revision**, never from the
  stale session base. A merge that cannot complete cleanly re-enters
  bounded remediation against the integrated base instead of landing by
  hand.

The wave-2 failure is the regression fixture: two scope-overlapping PRDs
that each add a storage migration must land as consecutive numbers with no
manual rebase.

### 2. Continuous admission (defect 15's sibling; batch lockstep)

The current loop selects a batch, joins every thread, then selects again —
one slow PRD idles every finished worker. Admission becomes event-driven:
when a worker integrates (or terminally retains), the scheduler immediately
runs selection against the updated ready set and admits the next PRD into
the freed slot. Wave boundaries stop costing wall-clock; overlapping PRDs
pipeline through the integration revision instead of waiting for the
slowest sibling.

### 3. Scope math: authoring-time width validation and resource allocation (defect 1)

Width is a property of declared scopes, so it is computed where scopes are
authored, not discovered at runtime:

- **Plan validation** computes achievable width for a wave from its PRDs'
  authoritative expected-file scopes and declared resources, using the same
  overlap rules the scheduler enforces. A plan claiming a width the scopes
  cannot deliver fails validation naming the conflicting pairs. The
  execution plan records graph width and achievable width as distinct
  columns.
- **Migration-number allocation** converts the hottest shared directory
  into an allocatable resource. A PRD authorized for the storage migrations
  directory receives a reserved, persisted migration version number at
  admission; reservations are distinct across concurrent holders, survive
  crash recovery, and are consumed or released exactly once. Shared
  migration authorship then pipelines through the merge queue instead of
  serializing on a blanket directory conflict.

### 4. Hash-bound scope decisions (defect 4)

Human-gated scope findings (dependency manifests, lockfiles) currently
strand a worktree and force a manual review/rebase/cherry-pick/complete
sequence that also invalidates the approve-and-complete candidate binding.
One command lists pending scope findings with their finding and candidate
hashes and accepts or rejects each by hash — interactively at a terminal,
non-interactively by flags for controlled environments — transitioning the
checkpoint durably and letting the workflow continue. When the merge queue
rebases a candidate, the binding is recomputed against the rebased
candidate so approve-and-complete keeps working instead of going stale.

### 5. Reconciled recovery and live heartbeats (defects 13–15)

Recovery discovery reconciles against durable backlog completion and
integration evidence in one transactionally consistent snapshot: integrated
work is never offered as resumable, superseded leases are suppressed,
multiple candidates for one PRD are grouped as one decision, and every
suggested command is valid for the state it is printed against. During
execution, each active worker emits a flushed phase heartbeat at a bounded
interval — PRD, stage, elapsed, last durable transition — so a silent
session is a stalled session by definition, observable while it is
happening.

## Scope

- Merge queue and session integration revision in `drive.rs`/`run.rs`,
  with integration-gated completion, scope release, and worktree basing.
- Event-driven admission replacing the batch join.
- Achievable-width computation shared between plan validation and the
  scheduler; execution-plan width honesty.
- Migration-number reservation (storage table plus admission wiring).
- The hash-bound scope-decision command and rebase-aware candidate
  rebinding.
- Reconciled `resume` inventory and periodic flushed worker heartbeats.
- Regressions for the wave-2 failure shapes: duplicate-migration
  composition, batch-lockstep idling, stale recovery inventory, and the
  no-serial-fallback width pin.

Out of scope: the daemon control plane (PRD-056), review terminal
semantics and open-finding waivers (defect 7, PRD-041's family), durable
verification truth and environment identity (defects 8 and 17), context
failure classification beyond what landed in `19c90d4` (defect 9),
model-cache lifecycle noise (defect 16), and metadata adoption UX
(defect 18).

## Assumptions (recorded at specification time, 2026-08-30)

- Checkpoint phase machinery (PRD-039) already distinguishes phases and
  admits new ones; `integrated` extends the existing closed set.
- The merge queue uses ordinary Git merges onto the integration revision;
  a conflicting merge is a remediation input, not an operator task.
- The scheduler's scope-overlap and resource rules from PRD-065 are the
  single authority plan validation reuses; no second implementation.
