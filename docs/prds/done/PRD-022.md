# PRD-022: Recorded Completion for Untracked Work

**Status:** Completed
**Date:** 2026-08-05
**Depends on:** PRD-011, PRD-012
**Architectural direction:** Trust Is Earned Through Verification; Repository Is Truth; Memory Must Be Durable
**Delivery boundary:** Independently mergeable third recovery action closing the pending-to-completed gap

## Objective

Add `familiar-ai backlog record-complete <prd_path> --actor human:<identity> --reason <text>`: an audited human declaration that a `pending` PRD was in fact completed outside Familiar's tracking.

Familiar has verbs for a PRD stranded `in_progress` (PRD-012 release and manual override) and for first-time historical seeding (PRD-010 bootstrap manifest, one-shot by design). It has none for the situation where the database is simply behind reality — a fresh database, a restored machine, or work merged before Familiar tracked it. Today that state is unreachable through any command, and the only remedy is direct SQL, which is exactly the kind of unaudited edit the backlog exists to prevent.

## Motivation

This gap was found by using the system: a fresh database listed ten merged PRDs as `pending`, `next` selected an already-implemented PRD, and every downstream command faithfully honored the wrong state. Fail-closed design protects against *unknown* state, not *wrong* state — the database asserted `pending` with full confidence and nothing could contradict it.

The bootstrap manifest cannot serve here: its lineage guard deliberately refuses re-application with a changed manifest, so that no one can retroactively rewrite what counted as already-done. That guard is correct and must stay. What is missing is an incremental, per-PRD, audited declaration carrying the same human authority PRD-012 already demands.

## Scope

This PRD includes:

1. A third `BacklogRecoveryAction` — recorded completion — whose target status is `completed` and whose only legal source status is `pending`.
2. CLI `backlog record-complete` with the mandatory `--actor human:<identity>` and non-empty `--reason` that PRD-012 recovery already validates.
3. Refusal, fail-closed and by exact diagnostic, when the entry is `in_progress` (PRD-012's verbs own that transition), already `completed`, `blocked`, absent from the backlog, or when any declared dependency is not itself `completed`.
4. Durable audit identical in shape to PRD-012 recovery: a status event plus a recovery event carrying action, actor, and reason.
5. One additive migration extending the recovery-event action set; because SQLite cannot alter a `CHECK` constraint in place, the migration rebuilds `backlog_recovery_events` by creating the widened table, copying every existing row, dropping the old table, and renaming — preserving all prior rows and their `status_event_id` foreign keys.
6. Focused tests over temporary repositories only.

## Non-goals

This PRD does not:

- verify that the work was actually done — this is a human declaration, exactly as PRD-012's manual override is, and it is recorded as such;
- alter PRD-011 admission, claim, completion-evidence, or PRD-012 recovery semantics;
- alter the bootstrap manifest, its lineage guard, or its one-shot behavior;
- accept a non-`human:` actor, or infer one;
- add bulk or glob forms — one PRD per invocation, so every declaration is individually attributed;
- change discovery, the dependency graph, or where PRD files live (that is PRD-023); or
- modify prior PRDs, architecture documents, ADRs, contracts, or philosophy.

## Behavior

```
familiar-ai backlog record-complete docs/prds/PRD-014.md \
  --actor human:trollboy \
  --reason "implemented, reviewed, and merged before this database existed"
```

Preconditions, all fail-closed with the exact reason named:

- the path resolves to an active backlog entry (same resolution `run` uses);
- its status is `pending`;
- every declared dependency is `completed` — a completed PRD whose prerequisites are not completed would leave the graph internally inconsistent, so reconciliation of a batch proceeds in dependency order;
- actor matches `human:<identity>` and reason is non-empty after trimming.

On success it prints one line in the existing recovery style, naming the transition, action, actor, and reason, and writes both audit rows in a single transaction.

## Acceptance Criteria

1. A `pending` entry with completed dependencies transitions to `completed` under an explicit `human:` actor and non-empty reason, in one transaction.
2. Status and recovery events are both written, carrying action, actor, and reason, and are readable afterward.
3. `in_progress`, `completed`, `blocked`, and unknown-path targets are refused with exact diagnostics, and PRD-012's verbs remain the only path for `in_progress`.
4. An entry with any incomplete dependency is refused, naming the offending dependencies.
5. A non-`human:` actor or empty reason is refused by the same validation PRD-012 recovery uses.
6. The migration widens the recovery-action set while preserving every pre-existing recovery row and its foreign key; existing migrations are untouched.
7. `next`, `run`, `drive`, admission, claim, completion, bootstrap, and PRD-012 recovery behavior are otherwise unchanged.
8. All tests use temporary repositories and databases; formatting, focused Clippy, focused tests, and the workspace suite pass, or demonstrably pre-existing failures are reported with exact evidence.
9. The change is confined to the expected files and is independently mergeable.

## Test Strategy

- Transition: pending → completed succeeds and both audit rows appear with the exact actor and reason.
- Refusals: in_progress, completed, blocked, unknown path, incomplete dependency, non-human actor, blank reason — each asserted by exact diagnostic, with no row mutated.
- Ordering: a two-PRD chain reconciled in dependency order succeeds; reversed order is refused at the dependent.
- Migration: a database seeded with pre-existing release and manual-override recovery rows upgrades with every row and foreign key preserved, and the widened action becomes insertable.
- Regression: `next` selection, admission, and PRD-012 recovery suites unchanged.

## Definition of Done

PRD-022 is done when a human can declare, one PRD at a time and under recorded authority, that work merged outside Familiar's tracking is complete — with dependency consistency enforced, every refusal named exactly, the audit trail indistinguishable in rigor from PRD-012 recovery, and no other backlog semantics touched.
