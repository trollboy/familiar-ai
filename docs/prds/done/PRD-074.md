# PRD-074: Platform Credential-Store Authentication

## Objective

Close FAM-BUG-003: BYO-auth accepts `env: NAME` but not a platform
credential-store reference, so a credential stored securely in macOS
Keychain had to be bridged into the environment by hand — and background
workers cannot use the endpoint at all unless that environment is
separately provisioned, because a launchd-supervised process has no login
shell to inherit it from. The credential store is where the credential
already lives; Familiar should read it there, at use time, without ever
exporting it.

## Design

- **Descriptor, not credential.** Configuration carries a typed
  credential-store descriptor (service/account for macOS Keychain first;
  the descriptor form is platform-neutral so other stores can implement
  later). The configuration file, decision rows, logs, and diagnostics
  only ever contain the descriptor.
- **Resolve at use, hold in memory.** Probe, verification, and
  execution-time authentication resolve the descriptor when the request
  is built. Nothing writes the resolved value anywhere; the existing
  hash-only comparison and redaction rules from PRD-047 apply.
- **Supervisor-real.** The acceptance surface explicitly covers the
  daemon/launchd context — resolution must work where there is no login
  shell, because that is the entire reason the environment bridge fails.
- **Fail closed, named.** Missing entry, denied access, or an
  unsupported platform produce a diagnostic naming the descriptor and
  condition. No empty-credential requests, no silent fallback to other
  auth forms.

## Scope

The descriptor type and validation in core configuration, resolution in
the provider probe/auth path, preflight coverage for supervisor
contexts, comment-preserving CLI editing, contract documentation, and
regressions in a dedicated test file (resolution via a fake store
backend, fail-closed conditions, no-export/no-persist guarantees,
unchanged `env:` behavior).

Out of scope: credential writing or rotation (Familiar reads, never
manages credentials), Linux secret-service implementation (the
descriptor admits it; implementing it is follow-up work when a Linux
worker needs it), and any provider-specific auth semantics beyond
PRD-047's existing contract.

## Assumptions (recorded at specification time, 2026-08-31)

- Keychain access from a launchd agent in the user session is
  grantable; where the OS prompts for access, first use is interactive
  and subsequent supervised use is not.
- Tests exercise a store-backend trait with a fake; live Keychain
  behavior is verified on the target machine rather than in CI.
