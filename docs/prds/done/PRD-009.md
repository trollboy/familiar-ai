# PRD-009: Deterministic Backlog Manager

## Objective

Implement a deterministic backlog subsystem that discovers repository PRDs, records their workflow status, validates explicit dependencies, and selects the next eligible PRD without requiring the user to name a file.

Expose selection through `familiar next`. The command reports one selected PRD and its status but never invokes an agent, calls an LLM, changes status, generates a PRD, or starts `familiar run`.

The subsystem must be independently mergeable: it adds discovery, selection, persistence, and a read-only CLI command without changing the behavior of `familiar run` or requiring any later task, scheduler, daemon, IPC, or execution-policy work.

## Motivation

The current CLI executes only `familiar run <prd-path>`. A user must already know which PRD should be worked next, and Familiar has no durable backlog status or dependency-aware selection rule. As the repository accumulates PRDs, choosing by directory listing, filename intuition, or conversational memory becomes non-reproducible.

Familiar's philosophy says the repository is truth and deterministic software should be preferred to model inference. Backlog selection can be solved entirely from repository files, explicit metadata, and durable status. A model must not decide what a PRD depends on, whether it is complete, or which item is next.

This PRD establishes only that deterministic boundary. It makes a next item discoverable and inspectable while keeping execution and human authorization separate.

## Scope

This PRD includes:

1. Discovering canonical PRD files under the repository's `docs/prds/` directory.
2. Parsing a small, explicit dependency field from PRD Markdown.
3. Treating absent dependency metadata as an empty dependency set.
4. Defining the closed statuses `pending`, `in_progress`, `completed`, and `blocked`.
5. Persisting explicit status by repository identity and canonical repository-relative PRD path in SQLite.
6. Reconciling discovered files with persisted status without deleting history or fabricating transitions.
7. Validating identifiers, dependency references, duplicate identities, self-dependencies, and cycles.
8. Selecting exactly one next eligible PRD by a documented deterministic algorithm.
9. Adding a read-only `familiar next` CLI command with stable human-readable output and categorized failures.
10. Unit, storage, migration, parser, algorithm, CLI, and integration tests that require no LLM or coding-agent executable.

### Separation of responsibilities

The backlog domain service owns discovery validation, dependency-graph construction, eligibility, and ordering. It accepts repository and status-store boundaries and returns typed results; it does not print, invoke agents, or know SQLite statements.

The filesystem discovery adapter owns bounded enumeration and exact Markdown metadata parsing. It does not infer dependencies from prose, filenames mentioned outside the dependency field, Git history, headings, or directory placement.

The storage repository owns durable status reads and writes plus additive reconciliation of newly discovered PRDs. It does not discover files or choose the next PRD.

The CLI adapter resolves the current repository, opens and migrates the configured database through the existing path, calls the backlog service, and renders the result. It contains no independent eligibility or ordering rules.

## Non-goals

This PRD does not:

- invoke an LLM, an inference backend, Codex, or any other coding agent;
- infer dependencies from PRD content, numbering, hyperlinks, prose, Git history, architecture documents, or code;
- generate, edit, rename, move, archive, or delete PRDs;
- automatically execute the selected PRD or compose `next` with `run`;
- change `familiar run <prd-path>` or permit `familiar run` without a filename;
- automatically mutate a status before, during, or after selection;
- infer status from Git state, execution history, review results, file location, or whether a PRD has acceptance criteria;
- add CLI commands or flags for changing status;
- add priorities, labels, due dates, estimates, ownership, scheduling, retries, leases, work queues, or concurrency admission;
- add dependency version constraints, optional dependencies, dependency groups, or cross-repository dependencies;
- treat completed PRDs in `docs/prds/done/` as active backlog entries;
- add daemon, MCP, dashboard, tray, socket, HTTP, watcher, or background-worker behavior;
- create a general canonical task subsystem or claim to implement target-state task lifecycle semantics;
- modify prior PRDs, architecture documents, ADRs, contracts, philosophy, or existing migrations; or
- migrate or reinterpret standalone execution-history rows as backlog status.

## Repository and Identity Boundary

`familiar next` operates on the Git worktree containing the process current directory. Repository resolution must use Git without changing the working tree. Failure to resolve a containing worktree is a categorized error.

The canonical discovery root is `<worktree>/docs/prds`. Discovery considers only direct children whose filenames match exactly:

```text
PRD-<digits>.md
```

Matching is case-sensitive. `<digits>` contains one or more ASCII decimal digits and its numeric value must fit `u64`. Files in subdirectories, including `docs/prds/done/`, are not active backlog entries. Symlinks are rejected rather than followed. Non-matching files such as `vision.md` and `PRD-001-sequencing-review.md` are ignored.

Each discovered file has:

- `id`: `PRD-` followed by the parsed number rendered without leading zeroes for comparison, for example `PRD-009` and `PRD-9` both have the logical ID `PRD-9`;
- `number`: the checked numeric filename component;
- `path`: the canonical `/`-separated repository-relative path preserving the actual filename;
- `title`: the complete first level-one Markdown heading after optional UTF-8 BOM and blank lines;
- `dependencies`: the explicitly parsed dependency IDs; and
- `content_hash`: SHA-256 of the exact file bytes, retained for diagnostics and reconciliation provenance.

Two files that normalize to the same logical ID are a duplicate identity error. A file must be valid UTF-8 and its first nonblank Markdown content must be a level-one heading in the form `# PRD-<digits>: <non-empty title>`. The heading ID must normalize to the same logical ID as the filename. Familiar does not derive identity from the title or other prose.

Paths persisted by this subsystem are repository-relative identities. Absolute host paths are runtime locations and must not be stored as PRD identity.

## Dependency Model

Dependencies are declared by one optional metadata line in the initial metadata block immediately following the level-one heading:

```markdown
# PRD-012: Example

**Depends on:** PRD-003, PRD-008
```

The initial metadata block consists of blank lines and consecutive lines shaped as `**<label>:** <value>` before the first other nonblank line. The dependency label is exactly `Depends on`, case-sensitive. At most one such line is permitted.

The dependency value is either:

- `none`, meaning an empty set; or
- a comma-separated list of one or more `PRD-<digits>` identifiers.

Surrounding ASCII whitespace around list elements is ignored. Empty elements, duplicate normalized IDs, numeric overflow, noncanonical tokens, a self-reference, a second `Depends on` field, or mixing `none` with an identifier is malformed metadata. Dependency order in the document carries no priority semantics; the parsed set is stored and compared in ascending numeric order.

An absent `Depends on` field means no dependencies. This compatibility rule allows existing PRDs to participate without edits and does not infer that their prose is dependency-free; it means only that no machine-readable dependency was declared.

Every dependency must resolve to a PRD discovered in the active discovery root. A dependency is not satisfied by a similarly numbered file under `docs/prds/done/`, an execution-history record, or an absent persisted status row. The graph must be acyclic. Missing targets and cycles invalidate selection for the whole backlog; Familiar must not silently skip the invalid component and select from another component.

## Status Model

The closed status enum is:

```rust
pub enum BacklogStatus {
    Pending,
    InProgress,
    Completed,
    Blocked,
}
```

Semantics are:

- `pending`: available for consideration once every dependency is completed;
- `in_progress`: explicitly claimed as active work and never selectable;
- `completed`: explicitly finished and able to satisfy dependents;
- `blocked`: explicitly unable to proceed and never selectable until another authorized interface changes the persisted status.

Only `completed` satisfies a dependency. `in_progress` and `blocked` do not satisfy dependencies, and a dependent remains ineligible regardless of why its prerequisite is not completed.

Status is explicit canonical backlog state. This PRD provides the storage mutation API needed by tests and future application services, but no new public status-changing CLI. The API accepts the expected current status and new status in one transaction so stale callers receive a conflict rather than overwriting a newer value. Same-status writes are idempotent and do not add a transition event.

Newly discovered PRDs receive `pending` exactly once during reconciliation. Rediscovery must never reset an existing status. Status does not change when content or dependencies change. Selection is read-only and produces no transition.

All four statuses may transition explicitly to any other status. This PRD deliberately does not invent lifecycle authorization or completion gates; those belong to later task and policy work. Each real transition records old status, new status, UTC timestamp, and an explicit actor string supplied by the caller. The storage boundary rejects an empty actor.

## Persistence

Add one forward-only SQLite migration after the current latest migration. It creates tables equivalent to:

```text
backlog_prds
  repository_key       TEXT NOT NULL
  prd_path              TEXT NOT NULL
  prd_number            INTEGER NOT NULL
  content_hash          TEXT NOT NULL
  status                TEXT NOT NULL CHECK status in closed values
  discovered_at         TEXT NOT NULL
  last_seen_at          TEXT NOT NULL
  missing_since         TEXT NULL
  created_at            TEXT NOT NULL
  updated_at            TEXT NOT NULL
  PRIMARY KEY (repository_key, prd_path)

backlog_status_events
  event_id              INTEGER PRIMARY KEY
  repository_key        TEXT NOT NULL
  prd_path              TEXT NOT NULL
  old_status            TEXT NOT NULL
  new_status            TEXT NOT NULL
  actor                 TEXT NOT NULL
  changed_at            TEXT NOT NULL
  FOREIGN KEY (repository_key, prd_path) REFERENCES backlog_prds
```

Exact SQL names may follow existing conventions, but these semantics and constraints are required. `repository_key` is a deterministic identity for the containing Git repository: the canonical Git common-directory path encoded as a normalized absolute path. It distinguishes separate repositories while allowing worktrees sharing one Git repository to share backlog state. The actual worktree path is not part of the key.

Reconciliation and selection run in a single database transaction:

1. Upsert every valid discovered PRD, inserting new rows as `pending` and updating only number, content hash, `last_seen_at`, and clearing `missing_since` for existing rows.
2. Mark previously known rows for the same repository that were not discovered with `missing_since` if it is not already set.
3. Read the status snapshot for exactly the discovered set.
4. Validate the graph and select from that snapshot.
5. Commit the discovery reconciliation and return the result.

A missing file's row and event history are retained. Missing rows never participate in selection or satisfy a dependency. If the same path reappears, its prior status is preserved and `missing_since` is cleared. A different path, even with the same number after the old file disappeared, is a new identity and begins `pending`; ambiguous simultaneous identities remain an error.

Migration must be additive, transactional, idempotent through the existing migration runner, and must not rewrite any existing table or fabricate backlog state before the first discovery. Rollback is code-only; persisted backlog rows remain readable by the migration-aware implementation and are not destructively removed.

## Eligibility Algorithm

The backlog service must apply these steps in order:

1. Resolve the containing Git worktree and repository key.
2. Enumerate and parse all candidate PRDs under the discovery boundary.
3. Sort parsed records by numeric PRD number and then by raw repository-relative path bytes.
4. Reject malformed candidate files, duplicate normalized identities, self-dependencies, missing dependency targets, and cycles.
5. Reconcile discovery and load one transactional status snapshot.
6. For every PRD in the snapshot, classify eligibility.
7. Keep only PRDs whose own status is `pending` and whose every explicit dependency has status `completed`.
8. Select the first eligible PRD in the deterministic order below.
9. Return `NoEligiblePrd` with a deterministic reason summary if no candidate remains.

The eligibility reason for each discovered PRD is exactly one of:

```rust
pub enum IneligibilityReason {
    StatusInProgress,
    StatusCompleted,
    StatusBlocked,
    DependenciesIncomplete { dependencies: Vec<PrdId> },
}
```

`DependenciesIncomplete` contains every explicit dependency whose status is not `completed`, ordered by numeric ID. It does not claim why that dependency is incomplete and does not recursively infer a root blocker.

An empty backlog is distinct from a non-empty backlog with no eligible PRD. Graph errors are distinct from both.

## Deterministic Ordering

Eligible PRDs are ordered by:

1. ascending numeric PRD number; then
2. ascending raw UTF-8 bytes of canonical repository-relative path.

The second key is a defensive total-order tie-breaker. Valid discovery rejects duplicate normalized IDs, so it should not normally decide a result.

Filesystem enumeration order, modification time, creation time, database row order, status update time, Markdown dependency order, locale, case folding, Git status, and process timing must not affect selection.

There is no implicit priority boost for dependency depth, number of dependents, an in-progress sibling, or a previously selected PRD. Repeated calls against unchanged files and status must return the same path and must not modify status.

## Public Types and Service Boundary

Exact Rust module paths may follow repository conventions, but the neutral domain semantics must be equivalent to:

```rust
pub struct DiscoveredPrd {
    pub id: PrdId,
    pub number: u64,
    pub path: RepositoryPath,
    pub title: String,
    pub dependencies: Vec<PrdId>,
    pub content_hash: String,
}

pub struct BacklogEntry {
    pub prd: DiscoveredPrd,
    pub status: BacklogStatus,
}

pub struct NextPrd {
    pub id: PrdId,
    pub path: RepositoryPath,
    pub title: String,
    pub status: BacklogStatus,
    pub dependencies: Vec<PrdId>,
}

pub trait BacklogStatusStore {
    fn reconcile_and_snapshot(
        &mut self,
        repository: &RepositoryIdentity,
        discovered: &[DiscoveredPrd],
    ) -> Result<Vec<BacklogEntry>, BacklogStoreError>;

    fn transition(
        &mut self,
        repository: &RepositoryIdentity,
        path: &RepositoryPath,
        expected: BacklogStatus,
        next: BacklogStatus,
        actor: &str,
    ) -> Result<BacklogEntry, BacklogStoreError>;
}

pub struct BacklogManager<D, S> { /* discovery and store adapters */ }

impl<D, S> BacklogManager<D, S> {
    pub fn next(&mut self, repository: &Path) -> Result<NextPrd, BacklogError>;
}
```

The domain crate must not depend on `rusqlite`, Clap, the daemon binary, an LLM crate, or an agent crate. SQLite and CLI types remain adapters around this boundary. If the existing `RepositoryPath` type cannot represent the required identity without broadening its contract, a backlog-specific validated path type may be used rather than weakening existing invariants.

## CLI Behavior

Add this command to the existing `familiar` binary:

```text
familiar next
```

It accepts no positional path and no options in this PRD. It uses the process current directory to locate the containing Git worktree and the existing configured database path and migration runner.

On success, stdout contains exactly one tab-separated line terminated by a newline:

```text
PRD-9\tdocs/prds/PRD-009.md\tpending\tDeterministic Backlog Manager
```

Fields are normalized logical ID, canonical repository-relative path, lowercase status, and title. Tabs and line breaks are forbidden in a valid title. No progress, migration, or diagnostic text is written to stdout. The command exits zero.

`familiar next` is a query with discovery reconciliation. It may create the database, run additive migrations, insert newly discovered `pending` rows, update discovery metadata, and mark missing rows. It must not create a status transition event, change an existing status, invoke `run`, construct an agent, render a prompt, or open execution/review history.

On failure, stdout is empty, stderr uses the existing `error: <message>` convention, and the command exits non-zero. Error messages identify the category and relevant repository-relative PRD IDs or paths without exposing SQL statements or a panic backtrace.

The command is intentionally human-readable only. JSON output, list output, explanation output, status mutation, `--execute`, and shell command emission are deferred.

## Failure Cases

The implementation must return typed, actionable failures for at least:

- current-directory lookup failure;
- no containing Git worktree or failure to resolve the Git common directory;
- missing or unreadable `docs/prds` directory;
- directory enumeration failure;
- a symlink matching the PRD filename pattern;
- unreadable or non-UTF-8 candidate content;
- filename number overflow;
- missing, malformed, mismatched, or duplicate level-one PRD identity;
- invalid, duplicate, empty, overflowing, or repeated dependency metadata;
- self-dependency;
- duplicate normalized PRD identity;
- dependency target absent from active discovery;
- dependency cycle, reported in a stable numeric/path order;
- database open or migration failure;
- invalid persisted status or referential-integrity failure;
- optimistic status-transition conflict;
- empty backlog; and
- non-empty backlog with no eligible PRD.

Discovery must collect candidate parse errors and report them in deterministic path order. It must not let filesystem order choose which error appears first. Graph validation must be deterministic; if multiple cycles exist, report the cycle containing the numerically lowest PRD reachable under sorted adjacency, with the cycle rotated to its lowest numeric/path member.

No failure may fall back to LLM interpretation, inferred dependency repair, status reset, partial selection, PRD generation, or automatic execution. A database transaction must roll back on reconciliation, validation, or selection failure after it begins. Filesystem reads occur before the write transaction so the database is not held while reading arbitrary files.

## Acceptance Criteria

1. Direct child files matching `docs/prds/PRD-<digits>.md` are discovered; nested, symlinked, and non-matching entries are not silently treated as active PRDs.
2. Filename and level-one heading identities are validated and normalized by checked numeric value; ambiguous duplicate identities fail deterministically.
3. The optional `**Depends on:**` field is parsed only from the initial metadata block. Its absence means an empty set, and no other text is interpreted as a dependency.
4. Missing dependency targets, self-dependencies, duplicate dependencies, and cycles fail selection with stable diagnostics.
5. The only statuses are `pending`, `in_progress`, `completed`, and `blocked`; newly discovered PRDs begin `pending` and rediscovery never resets status.
6. Only `pending` PRDs with every explicit dependency `completed` are eligible.
7. Selection uses ascending numeric PRD number with canonical path bytes as the total-order tie-breaker and is independent of enumeration and database row order.
8. Repeated unchanged calls select the same PRD and do not change a status or create a status event.
9. Status transitions use an expected-current-status check, preserve an append-only transition record, reject empty actors, and treat same-status writes as event-free idempotent operations.
10. Status and event history are isolated by deterministic repository identity and canonical repository-relative PRD path.
11. Missing files are retained as missing history, excluded from selection, and cannot satisfy dependencies; reappearance at the same path preserves status.
12. The additive migration upgrades an existing latest-version database, is idempotent, preserves every existing row, and fabricates no backlog rows before discovery.
13. `familiar next` prints exactly one stable tab-separated success line and exits zero when an eligible PRD exists.
14. Empty backlog, no eligible PRD, malformed backlog, Git-resolution failure, and storage failure produce empty stdout, categorized stderr, and non-zero exit.
15. `familiar next` never invokes an agent or LLM, renders a prompt, creates execution/review history, changes status, generates a PRD, or automatically executes work.
16. Existing `familiar run`, `history`, and `usage` behavior and tests remain unchanged.
17. The backlog domain is independently testable with in-memory discovery and status-store fakes and has no dependency on Clap, SQLite, LLM, or agent implementation types.
18. No daemon, MCP, dashboard, tray, watcher, architecture, ADR, contract, philosophy, configuration, or prior-PRD behavior changes.

## Test Strategy

### Discovery and parser unit tests

- Discover matching direct children from randomized enumeration orders and assert identical sorted results.
- Ignore `vision.md`, `PRD-001-sequencing-review.md`, nested `done/` files, directories, and unrelated extensions.
- Reject matching symlinks, invalid UTF-8, unreadable candidates, number overflow, missing headings, mismatched heading IDs, empty titles, tabs/newlines in titles, and normalized duplicate IDs.
- Parse absent dependencies, `none`, one dependency, multiple dependencies with surrounding whitespace, and normalize their order.
- Reject repeated fields, empty list elements, duplicates after numeric normalization, mixed `none`, self-reference, invalid tokens, and dependency prose outside the initial metadata block.
- Verify content hashes use exact bytes and do not affect selection priority.

### Dependency and selection unit tests

- Cover an empty graph, independent PRDs, chains, diamonds, disconnected graphs, and multiple simultaneously eligible PRDs.
- Assert only `completed` dependencies satisfy eligibility for every combination of the four statuses.
- Assert own `in_progress`, `completed`, and `blocked` status always makes an entry ineligible.
- Assert numeric ordering chooses PRD-9 before PRD-10 regardless of zero padding, lexical filename order, insertion order, timestamps, or dependency declaration order.
- Assert missing targets, self-edges, two-node cycles, longer cycles, and multiple cycles return stable typed errors.
- Assert unchanged snapshots always return byte-for-byte equivalent `NextPrd` values.

### Storage and migration tests

- Upgrade an exact pre-backlog migration fixture and assert all prior schema and data remain unchanged.
- Run migrations twice and assert the second run applies nothing.
- Assert no backlog rows exist immediately after migration.
- Reconcile new files and assert `pending`; reconcile again after explicit transitions and assert status preservation.
- Assert checked transitions, conflicts, actor validation, idempotent same-status writes, event ordering, and transaction rollback.
- Assert two repositories and two paths cannot read or overwrite each other's state.
- Mark a file missing, assert history retention and selection exclusion, then restore the same path and assert status preservation.
- Inject invalid status and referential-integrity fixtures where SQLite permits and assert categorized failures rather than defaulting to `pending`.

### CLI and integration tests

- Build fixture Git repositories with isolated temporary configuration/data paths and invoke the compiled `familiar` binary.
- Assert exact stdout, empty stderr, and zero exit for a successful selection.
- Assert exact repeated output and no new status event on a second call.
- Assert dependency completion changes the selected PRD only through a storage API fixture, never through `next` itself.
- Assert stable non-zero failures and empty stdout for no repository, missing discovery root, empty backlog, no eligible item, malformed metadata, missing dependency, cycle, and database failure.
- Put fake `codex` and LLM executables on `PATH` that fail if launched; assert every `next` scenario leaves them untouched.
- Assert execution-history and review tables have no new rows after `next`.
- Preserve existing CLI parse and behavior tests for `run`, `history`, and `usage`.

### Verification commands

At minimum, implementation verification must run:

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Focused backlog, storage, and CLI tests must also be runnable independently while iterating. Tests must use temporary repositories and databases and must not read or mutate a developer's real Familiar data directory.
