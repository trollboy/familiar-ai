# PRD-011: Backlog-Aware PRD Execution

**Status:** Completed

**Depends on:** PRD-009, PRD-010

## Objective

Integrate deterministic backlog admission and lifecycle transitions into `familiar run <path>`.

Before launching the coding agent, Familiar must resolve the supplied PRD as one active backlog entry, admit only eligible `pending` work, and atomically claim it as `in_progress` with actor-attributed audit evidence. Familiar may transition that same entry to `completed` only after implementation, required verification, and review readiness have all succeeded. Every failure, interruption, or human-review-required outcome leaves the entry `in_progress` for explicit recovery.

The change must preserve the existing path-taking command, streaming agent output, and standalone execution-history behavior. It must remain independently mergeable and must not introduce model-based status decisions or adjacent scheduling features.

## Motivation

PRD-009 provides deterministic discovery, dependency-aware eligibility, durable status, optimistic transitions, and append-only status events. PRD-010 bootstraps explicitly declared historical completion. The current `familiar run <path>` remains separate: it compiles context, records standalone execution history, invokes Codex, and optionally runs verification and review, but it neither admits work through the backlog nor updates backlog state.

That separation permits completed, blocked, or concurrently claimed PRDs to be executed and leaves successful reviewed work pending. It also creates a dangerous shortcut: the coding-agent process exit code can appear to represent task completion even though Familiar's philosophy requires deterministic verification and review evidence.

This PRD joins the existing subsystems at a narrow orchestration boundary. Backlog state remains canonical workflow state, execution history remains an observation of each standalone agent process, and review remains the source of verification and review disposition. Familiar coordinates those facts deterministically; it does not ask an LLM to classify status.

## Scope

This PRD includes:

1. Resolving the `run` path against PRD-009's containing repository and active discovery set.
2. Reconciling discovery and admitting only an exact active `pending` entry whose explicit dependencies are all `completed`.
3. Atomically transitioning `pending` to `in_progress` immediately before execution begins.
4. Recording each real transition through the existing append-only backlog status-event mechanism with a run-attributed system actor.
5. Preserving execution-history start and finalization records for every coding-agent process that is launched.
6. Returning a structured terminal workflow result from the run coordinator so the CLI can distinguish agent exit from backlog completion eligibility.
7. Transitioning `in_progress` to `completed` only after a successful implementation and a terminal clean review cycle containing successful required verification evidence.
8. Leaving `in_progress` unchanged on all implementation, verification, review, persistence-after-claim, interruption, or human-review-required outcomes.
9. Stable CLI diagnostics for admission, claim, retained state, and completion without buffering or replacing streamed agent output.
10. Unit, storage, run-coordinator, CLI, failure-injection, and interruption tests requiring no real coding agent or remote LLM.

### Separation of responsibilities

The backlog domain owns identity, active-entry validation, dependency eligibility, expected-status transitions, and transition errors. It does not interpret agent output or review prose.

The run coordinator owns ordering the existing context, execution-history, agent, verification, review, and backlog operations. It maps typed, already-recorded outcomes to the closed completion rule in this PRD; it does not make semantic status judgments.

The review subsystem continues to own verification evidence, review state, disposition, stop reasons, scope checks, and remediation. This PRD consumes its structured terminal result and does not infer readiness from printed reviewer text.

The storage layer owns SQLite transaction boundaries and append-only status events. The CLI owns argument parsing, rendering, and process exit status; it contains no independent admission or completion policy.

- add a manual status-changing CLI or manual SQLite instructions;
- add retries, leases, heartbeats, timeouts for abandoned claims, automatic resumption, automatic rollback to `pending`, or concurrent work scheduling;
- change PRD-009 discovery, identity, dependency, status, eligibility, or ordering semantics;
- broaden PRD-010 bootstrap eligibility, apply, rollback, or trigger semantics;
- infer status or completion from agent messages, model output, Git diff size, commits, branch state, elapsed time, execution-history outcome, or exit code alone;
- use an LLM, reviewer prose, embedding, heuristic classifier, Ollama, inference routing, or provider selection to decide admission or status;
- require review approval from a human or add an approval UI; `ReadyForHumanApproval` is the existing machine review-readiness disposition, not a new human approval event;
- change the review policy, verification commands, remediation limits, or independent-review requirements;
- merge execution history and backlog events into one canonical record or rewrite historical execution rows;
- add a daemon worker, MCP surface, dashboard, tray behavior, watcher behavior, network service, or background recovery job; or
- modify philosophy, architecture documents, ADRs, contracts, or prior PRDs.

## Status Transition Authority

For this workflow, `familiar run` has authority over exactly two transitions for the one admitted entry:

```text
pending -> in_progress
in_progress -> completed
```

No other transition is authorized. In particular, `run` may not set `blocked`, return work to `pending`, reopen `completed`, steal `in_progress`, or override a concurrent status change.

Each invocation generates its execution ID before claiming the PRD. Both status events use the stable actor format:

```text
system:familiar-run:<execution-id>
```

The execution ID component must satisfy the existing execution-history identifier rules and makes the status events attributable to the standalone execution without requiring status decisions from execution history. An empty or malformed actor is rejected by the storage boundary.

The claim transition is authoritative proof that this invocation acquired the work. A zero agent exit is only an execution observation. The completion transition is authoritative proof that the deterministic completion predicate was satisfied and committed.

## Run Admission Rules

`familiar run <path>` retains exactly one required path argument. Before context is supplied to an agent, Familiar must:

1. Resolve the process current directory to the containing Git worktree and PRD-009 repository key.
2. Discover and validate the complete active backlog using PRD-009 rules before opening a write transaction.
3. Resolve the user-supplied path to an existing regular file and canonical repository-relative path without following a symlink.
4. Require that the canonical path exactly matches one discovered active PRD. A file under `docs/prds/done/`, a non-matching Markdown file, an outside-repository path, and a path alias that cannot be safely canonicalized are not active entries.
5. Require that the resolved file identity and bytes are the same discovery record used for admission. A changed, missing, renamed, or replaced file causes a conflict rather than execution against stale metadata.
6. Reconcile discovery and load one repository-scoped status snapshot.
7. Require the selected entry's status to be `pending`.
8. Require every explicit dependency of the selected entry to be `completed` in that same snapshot.
9. Atomically claim the entry with expected status `pending` and actor `system:familiar-run:<execution-id>`.

`completed`, `blocked`, and `in_progress` are refused with distinct typed admission errors. A `pending` entry with incomplete dependencies is also refused and reports the incomplete dependency IDs in PRD-009 deterministic order. Familiar never chooses a different PRD when the requested one is inadmissible.

Discovery and reconciliation do not implicitly apply, reapply, roll back, or extend PRD-010 historical bootstrap. `run` consumes the canonical backlog state already established by PRD-009/010. Bootstrap remains governed by PRD-010's existing trigger and commands.

Configuration loading, context compilation and budgeting, review-configuration validation, database migration, incomplete-review recovery, and review-baseline capture are preflight operations. They must complete before the claim when they can be performed without launching or mutating the implementation workflow. A preflight failure leaves a still-`pending` PRD unchanged and creates neither status event nor execution-history row.

## Transaction Boundaries

Filesystem discovery, PRD parsing, graph validation, context compilation, and Git baseline capture occur outside SQLite write transactions. Agent, verification, and review processes must never run while a SQLite transaction is open.

### Admission and claim transaction

One immediate SQLite transaction must:

1. Revalidate the exact repository key, canonical PRD path, content hash, active/not-missing state, and dependency status snapshot used by admission.
2. Reconcile permitted discovery metadata without resetting any existing status.
3. Confirm the target is still `pending` and all dependencies are still `completed`.
4. Update exactly one target row from `pending` to `in_progress` using an expected-current-status predicate.
5. Append exactly one linked ordinary backlog status event with the run actor and the same UTC timestamp.
6. Commit before execution-history insertion or agent launch.

Any error or affected-row count other than one rolls back the whole transaction. No claim event may exist without the corresponding status change, and no status change may exist without its event. Familiar does not wait, retry, or steal after a conflict.

### Execution-history transactions

After the claim commits and before the agent is launched, Familiar inserts the existing `running` execution-history row using the already generated execution ID. After the agent terminates or returns a captured execution error, Familiar finalizes that row using existing outcome, usage, exit-code, signal, and unavailable-field semantics.

Execution-history writes remain separate from backlog transitions. A history insertion or finalization failure after claim leaves the PRD `in_progress`. Existing `history` and `usage` queries continue to include the execution irrespective of later backlog completion, verification, or review disposition. This preserves standalone execution history rather than redefining it as task history.

### Completion transaction

Only after the completion predicate is satisfied, one immediate SQLite transaction must:

1. Re-read the target by repository key and canonical path.
2. Require current status `in_progress`.
3. Require that the latest claim event for the entry has this invocation's actor; a later event or different claimant is a conflict.
4. Revalidate the persisted terminal review cycle and its required verification evidence for this execution ID.
5. Update exactly one row from `in_progress` to `completed`.
6. Append exactly one ordinary status event with the same run actor.
7. Commit atomically.

Completion-evidence validation and status update must share the transaction so deleted, incomplete, corrupt, or concurrently changed review evidence cannot be accepted. A completion conflict or storage error changes nothing, leaves the entry `in_progress`, and makes the command fail.

## Success Criteria for Completion

The completion predicate is a closed deterministic conjunction. Every condition must be true:

1. This invocation successfully committed the target's `pending -> in_progress` claim.
2. The implementation agent returned normally with exit code `0` and no signal, timeout, launch, input, wait, or output-processing failure.
3. Review was enabled and its configuration was valid before claim.
4. A review task and terminal review cycle were durably recorded for this execution ID.
5. The terminal cycle state is `completed`.
6. The terminal disposition is exactly `ready_for_human_approval`.
7. The terminal stop-reason set is exactly the coordinator's clean-review outcome and contains `clean_review` with no failure or interruption reason.
8. Every required verification check in the configured plan has current evidence with status `passed` for the candidate identity accepted by the terminal review cycle.
9. No blocking review finding remains open in the terminal accepted review result.
10. The completion transaction's ownership and audit checks succeed.

The predicate uses enums, persisted relationships, hashes, check requirements, and process observations. It never parses free-form agent or reviewer text and never invokes an LLM to decide status.

An implementation-agent exit code of zero is necessary but never sufficient. If review is disabled, no review cycle is produced, or the verification plan cannot establish the required evidence, the run is not completion-eligible and remains `in_progress`.

`ready_for_human_approval` means the implementation is verified and review-ready under the existing coordinator. This PRD treats that clean terminal disposition as sufficient for backlog `completed`; it does not claim that a human approved, merged, or deployed the change.

## Failure and Interruption Behavior

Once the claim transaction commits, every non-completing path leaves the PRD `in_progress`. Familiar must not compensate back to `pending` or change it to `blocked`.

This rule covers at least:

- execution-history insertion or finalization failure;
- agent launch, stdin, wait, output, timeout, signal, non-zero exit, or missing-exit-status failure;
- context or configuration failure that can arise only after claim despite preflight;
- worktree evidence or scope failure;
- required verification failure, timeout, signal, unavailability, inconclusive result, or skip;
- reviewer or remediation agent failure;
- malformed or conflicting findings;
- remediation, review, token, cost, duration, or retry limit exhaustion;
- broadened scope, invariant violation, architectural approval requirement, or lack of an independent reviewer;
- review persistence failure or corrupt/incomplete review evidence;
- terminal `human_review_required`, `rejected`, `remediation_required`, or nonterminal `pending` review disposition;
- completion-transition conflict or database failure;
- SIGINT, SIGTERM, process crash, host shutdown, or any other interruption after claim; and
- any outcome not explicitly included in the closed completion predicate.

When the process can observe the failure, it finalizes execution and review records according to their existing contracts, prints the retained status diagnostic, and exits non-zero. Abrupt termination may leave the execution-history row `running`; existing recovery semantics remain responsible for representing that incomplete observation. Backlog recovery never uses the history row to guess completion.

## Interaction with Review Disposition

The mapping from structured terminal review state to backlog behavior is:

| Review result | Backlog result |
| --- | --- |
| `Completed` + `ReadyForHumanApproval` + `CleanReview`, with all required verification passed and no open blocking finding | Attempt `in_progress -> completed` |
| `HumanReviewRequired` for any stop reason | Leave `in_progress` |
| `Rejected` | Leave `in_progress` |
| `RemediationRequired` | Leave `in_progress` |
| `Pending`, missing, incomplete, interrupted, or corrupt cycle | Leave `in_progress` |
| Review disabled | Leave `in_progress` |

The coordinator's structured state, disposition, findings, stop reasons, and verification evidence are authoritative. Printed review summaries and model-authored explanations have no status semantics.

A human-review-required disposition is a terminal stop for this invocation, not backlog `blocked` and not completion. Subsequent work requires an explicit authorized recovery transition outside this PRD; rerunning the path while it remains `in_progress` is refused.

## Recovery Behavior

Recovery is conservative and read-only with respect to backlog status. At startup, the existing review recovery may convert incomplete review cycles to their interrupted/human-review-required representation. It must not complete, reopen, or release a backlog entry.

An `in_progress` PRD remains owned work after a crash, interruption, ambiguous storage result, human-review-required disposition, or failed completion transaction. A later `familiar run` reports that status and refuses to launch another agent. Familiar must not infer that work is complete from a clean worktree, commits, a zero execution exit, a ready-looking agent message, a terminal history row, or partial review evidence.

The run actor embedded in the claim event and execution history ID provides deterministic forensic linkage. Operators may inspect ordinary backlog events, execution history, and review records using existing interfaces. Any future command that releases, blocks, or completes abandoned work requires separate authorization and is outside this PRD; this PRD provides no manual SQLite procedure.

If a crash occurs before the claim commit, the PRD remains `pending`. If it occurs after claim commit, the PRD is `in_progress` even if the execution-history row was not inserted. If it occurs after the completion transaction commits, the PRD is `completed`; failure to print the final line does not undo the committed audit state.

## CLI Output and Exit Behavior

The command syntax remains:

```text
familiar run <path>
```

Existing coding-agent and review output continues to stream to stdout as it becomes available. Familiar must not buffer the stream until status resolution and must not rewrite agent output as evidence.

After a successful claim, Familiar writes one concise lifecycle line to stderr:

```text
backlog: PRD-11 docs/prds/PRD-011.md pending -> in_progress actor=system:familiar-run:<execution-id>
```

After a committed completion, it writes:

```text
backlog: PRD-11 docs/prds/PRD-011.md in_progress -> completed actor=system:familiar-run:<execution-id>
```

On any observed post-claim non-completing outcome, it writes:

```text
backlog: PRD-11 docs/prds/PRD-011.md remains in_progress reason=<stable_reason>
```

`<stable_reason>` is a closed machine-stable snake-case category such as `implementation_failed`, `verification_failed`, `human_review_required`, `interrupted`, `review_disabled`, `review_failed`, `history_failed`, or `completion_conflict`. Free-form model text and raw SQL are excluded.

Admission refusal occurs before agent output, leaves stdout empty, uses the existing `error: <message>` stderr convention, names the PRD path/status or incomplete dependencies, and exits non-zero. A completed workflow exits zero. Every retained-`in_progress` outcome exits non-zero, including an implementation agent that exited zero without satisfying the completion predicate. When the implementation process supplies a non-zero code representable by the CLI, Familiar may preserve that code; otherwise it uses the existing generic failure code. Lifecycle diagnostics do not replace existing agent stderr.

Exact wording and ordering must be pinned by CLI tests. Execution IDs and timestamps are variable values but their format is stable. `history` and `usage` output formats remain unchanged.

## Audit Events

Every real status mutation creates exactly one existing `backlog_status_events` row in the same transaction as its status update:

- claim event: `old_status=pending`, `new_status=in_progress`, actor `system:familiar-run:<execution-id>`;
- completion event: `old_status=in_progress`, `new_status=completed`, the identical actor.

Events retain repository key, canonical repository-relative PRD path, UTC timestamp, and monotonic event ID under the existing schema. Same-status writes are not used and produce no event. Admission refusal, dependency refusal, preflight failure, retained `in_progress`, and recovery inspection create no status event.

For a completed run, the two events must be ordered and the completion event must be attributable to the claim owned by the same execution. The execution-history row and review task/cycle use that execution ID. Audit validation must detect missing claim events, different actors, later intervening events, missing review evidence, and inconsistent terminal cycles and must fail closed.

No migration is required merely to duplicate execution or review data into the backlog event table. If implementation needs an index or explicit linkage constraint for transactional evidence validation, it may add one forward-only additive migration, but it must not rewrite migration 005, 006, 007, or 008 or fabricate historical run events.

## Failure Cases

Typed failures must cover at least:

- current-directory or Git repository resolution failure;
- missing, unreadable, malformed, symlinked, duplicate, or cyclic active backlog;
- supplied path outside the worktree, outside active discovery, missing, non-regular, symlinked, or not identical to the discovered record;
- requested status `completed`, `blocked`, or `in_progress`;
- requested `pending` PRD with incomplete dependencies;
- repository, path, content-hash, dependency, or expected-status conflict inside the claim transaction;
- empty or invalid run actor;
- database open, migration, transaction, constraint, or audit corruption failure;
- context, budget, configuration, baseline, or history failure;
- every agent execution failure class and non-zero or absent exit status;
- verification, evidence, scope, review, remediation, accounting, or persistence failure;
- human-review-required, rejected, incomplete, or unavailable review disposition;
- missing, failed, stale, or mismatched required verification evidence;
- open blocking findings in an otherwise terminal cycle;
- completion attempted by an invocation that does not own the latest claim; and
- process interruption at every boundary before claim, after claim, during execution/review, and during completion.

All failures are deterministic and fail closed. No failure falls back to another PRD, agent exit inference, LLM classification, automatic status reset, automatic block, partial status/event writes, or audit rewriting.

## Acceptance Criteria

1. `familiar run <path>` retains one required path argument and preserves existing path invocation, streamed output, and standalone execution-history behavior.
2. The supplied path must resolve exactly to one PRD-009 active backlog entry in the containing repository; inactive, symlinked, stale, outside-repository, or ambiguous paths are refused before agent launch.
3. Admission permits only `pending` PRDs whose explicit dependencies are all `completed` in the transactional snapshot.
4. `completed`, `blocked`, and already-`in_progress` PRDs are refused distinctly, without agent, execution-history, review, or status writes.
5. Admission and claim atomically change exactly one entry from `pending` to `in_progress` and append exactly one actor-attributed status event.
6. Concurrent runs for the same PRD yield at most one committed claim and at most one launched coding agent; losers fail without retry or status overwrite.
7. Preflight failures before claim leave `pending` unchanged and create no execution or status audit record.
8. Every launched coding-agent process retains the existing standalone execution-history start/finalization semantics, regardless of later verification, review, or backlog result.
9. Agent exit code zero alone never marks a PRD completed.
10. Completion requires successful implementation, persisted passing evidence for every required verification check, a terminal clean review cycle, `ready_for_human_approval`, no open blocking finding, and ownership by the same run actor.
11. The completion transition atomically changes `in_progress` to `completed` and appends exactly one second status event after revalidating persisted evidence.
12. Implementation failure, verification failure, review failure, interruption, human-review-required disposition, disabled review, incomplete evidence, or completion conflict leaves the PRD `in_progress` and creates no compensating transition.
13. Every observed retained-`in_progress` outcome exits non-zero and emits a stable reason; only a committed completed workflow exits zero.
14. Recovery never guesses completion or returns an abandoned claim to `pending`; a later run refuses the existing `in_progress` entry.
15. Claim and completion events share the exact `system:familiar-run:<execution-id>` actor and can be correlated with execution and review records without parsing model text.
16. Dependency, admission, completion, and recovery decisions use only repository facts and structured persisted state; no LLM, Ollama backend, routing layer, or heuristic status classifier is called.
17. Existing `familiar next`, bootstrap status/rollback, `history`, and `usage` behavior remains unchanged.
18. Tests prove transaction rollback and fail-closed behavior at every claim and completion write boundary.
19. No batch execution, PRD generation, manual SQLite workflow, scheduling, daemon orchestration, or new status-management UI is added.
20. The implementation changes only the narrow backlog/run/storage integration surface and remains independently mergeable.

## Test Strategy

### Admission and domain tests

- Resolve relative and absolute spellings of the same in-repository PRD to one canonical active path while rejecting traversal, outside paths, symlinks, inactive files, stale bytes, and normalized identity ambiguity.
- Exercise all four target statuses and assert only eligible `pending` is admitted.
- Exercise no dependencies, completed dependencies, and each non-completed dependency status; assert deterministic incomplete-dependency ordering.
- Assert a requested inadmissible PRD never causes another eligible PRD to be selected.
- Use a deterministic fake completion predicate and assert only the closed all-true case authorizes completion.
- Assert agent and reviewer free-form output cannot affect admission or completion classification.

### Storage and transaction tests

- Claim a reconciled pending entry and assert one status update plus one event with the exact run actor.
- Race two database connections claiming the same entry and assert one success, one expected-status conflict, one event, and no retry.
- Inject failure before the claim update, between update and event, and before commit; assert no partial claim.
- Complete an owned entry with valid persisted review evidence and assert one atomic update and second event.
- Reject completion for a missing/different claim actor, later intervening event, wrong current status, missing cycle, nonterminal cycle, failed required check, open blocking finding, or non-clean disposition.
- Inject failure at every completion write boundary and assert the entry remains `in_progress` with no completion event.
- Upgrade fresh and populated post-PRD-010 databases, run migrations twice, and assert all backlog, bootstrap, execution, and review history is preserved.

### Run-coordinator tests

- Use fake discovery, storage, coding-agent, verifier, reviewer, and history adapters to assert exact operation ordering and that no transaction spans an external process.
- Assert all discoverable configuration, context, budget, review-policy, and baseline errors occur before claim.
- For agent success, non-zero exit, signal, timeout, launch/input/wait/output error, and history failure, assert exact execution finalization and backlog result.
- Cover every verification status for required and optional checks; optional failure follows existing review policy, while any required non-pass prevents completion.
- Cover clean review, open blocking findings, remediation success, remediation exhaustion, malformed review, conflicting findings, architectural approval, no independent reviewer, evidence failure, resource limits, and persistence failure.
- Assert review-disabled plus agent exit zero leaves `in_progress` and returns a non-completing result.
- Assert the run coordinator returns the structured terminal review cycle rather than relying on its printed summary.

### Interruption and recovery tests

- Terminate fixtures before claim commit, after claim/before history insert, while the agent runs, during verification, during review, and before completion commit.
- Assert pre-claim interruption leaves `pending`; every post-claim interruption leaves `in_progress`; post-completion interruption observes `completed` on restart.
- Recover an incomplete review cycle and assert it becomes interrupted/human-review-required without changing backlog status.
- Restart and rerun the same path after a post-claim interruption; assert refusal and no second agent launch.
- Assert a dangling claim actor without an execution-history row is retained and diagnosable, never auto-released.

### CLI and integration tests

- Build temporary Git repositories and isolated databases, configure fake agents and deterministic verification commands, and invoke the compiled binary.
- Pin admission errors, lifecycle stderr lines, retained-state reason categories, stdout streaming, and process exit codes.
- Assert completed, blocked, in-progress, dependency-incomplete, and concurrent invocations never launch the fake agent.
- Assert fake output is visible before the agent exits even though completion is decided later.
- Assert zero implementation exit with review disabled, failed verification, failed review, and human-review-required disposition never completes.
- Assert a clean implementation/verification/review path produces two ordered status events, one execution-history row, one terminal review cycle, and final `completed` state.
- Assert `history` and `usage` display the execution with their existing formats for both completed and retained-in-progress runs.
- Put failing fake LLM, Ollama, and routing executables on `PATH` outside the configured coding/review adapter and assert status decisions never invoke them.
- Preserve all existing `next`, bootstrap, run, history, usage, review, and storage regression tests, updating only run fixtures that must now establish backlog admission and explicit review evidence.

### Verification commands

At minimum, implementation verification must run:

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Focused backlog, storage, run-coordinator, review, CLI, concurrency, and interruption suites must also be independently runnable. Tests must use temporary Git repositories, configuration, databases, and artifact directories and must never access or mutate a developer's real Familiar state.

## Definition of Done

PRD-011 is done when:

1. `familiar run <path>` deterministically resolves and admits exactly one active eligible backlog PRD before launching an agent.
2. The pending claim and actor-attributed event are one atomic transaction, and concurrent invocation cannot double-launch the same work.
3. Standalone execution history remains complete and query-compatible for every launched implementation process.
4. Backlog completion occurs only from the closed persisted implementation, required-verification, clean-review, and ownership predicate.
5. A coding-agent zero exit without qualifying verification and review evidence demonstrably leaves the PRD `in_progress`.
6. Every implementation, verification, review, persistence, human-review-required, and interruption path after claim retains `in_progress` without automatic compensation.
7. Completion is one atomic `in_progress -> completed` transition with a second event attributed to the same run actor.
8. Recovery is fail-closed, refuses already claimed work, and never infers or rewrites status.
9. CLI streaming, lifecycle diagnostics, refusal behavior, and exit codes satisfy the acceptance criteria while `next`, bootstrap, history, and usage remain compatible.
10. No status decision invokes an LLM or uses model-authored prose, and no batch execution, PRD generation, Ollama/routing, or manual SQLite workflow is introduced.
11. Focused tests, concurrency and interruption tests, formatting, Clippy with warnings denied, and the full workspace test suite pass, or any demonstrably pre-existing failure is recorded with exact evidence.
12. The implementation remains narrowly scoped, additive where persistence changes are necessary, and independently mergeable.
