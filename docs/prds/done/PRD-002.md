# PRD-002: Legacy Summary Identity Reconciliation

**Status:** Completed
**Date:** 2026-08-03  
**Roadmap milestone:** M1 — Repository Identity and Reconciliation  
**Epic:** EPIC-M1-01 — Canonical File Identity and Compatibility  
**Backlog source:** PRD-TBD-M1-02

## Objective

Reconcile pre-PRD-001 absolute-path file-summary records into the canonical project-scoped, repository-relative identity established by PRD-001, without silently losing, merging, or misattributing stored summary data.

After this PRD, every legacy row that can be mapped exactly and safely from its registered project root has a deterministic outcome: it is converted in place when no canonical row exists, or removed from the active summary set only after its complete original value is preserved when a canonical row already owns the identity. Rows that cannot be mapped with certainty remain unchanged and are reported as unresolved. Reconciliation is transactional, repeatable, observable, and reversible.

This is the highest-leverage next implementation PRD because PRD-001 intentionally stopped new identity drift but left two active representations of the same repository entry. The current storage lookup contains an exact legacy fallback and explicitly detects canonical-versus-legacy conflicts; project listing, search, module behavior, and future lifecycle work can therefore still encounter duplicate or host-specific records. Resolving that bounded compatibility debt now completes EPIC-M1-01 and gives delete, rename, complete-scan, content-hash, branch/worktree, and context work one reliable active identity set. Implementing repository lifecycle reconciliation first would force it to preserve duplicate identity semantics that this backlog item is already responsible for removing.

## Scope

This PRD includes:

1. Deterministic project-scoped discovery and classification of legacy absolute-path file-summary rows.
2. Exact mapping only from a project's currently registered repository root to the PRD-001 canonical relative identity.
3. A reversible record of every row changed or removed from the active summary set, including its complete pre-reconciliation value and outcome.
4. In-place identity conversion when the canonical identity is unoccupied.
5. Deterministic canonical precedence when both canonical and exact legacy rows exist, without field-level merging.
6. Explicit unresolved outcomes for rows that cannot be mapped safely and exactly.
7. Transactional, idempotent reconciliation that can be retried after interruption.
8. Project-scoped reconciliation status and diagnostics sufficient to prove completeness or identify remaining work.
9. Removal of the ordinary exact legacy read fallback only when its mapped legacy population has been reconciled successfully.
10. Migration, storage, and current-client integration tests covering conversion, conflict preservation, retry, interruption, rollback, and isolation.

### Reconciliation classifications

Each examined file-summary row must receive exactly one deterministic classification:

- **Canonical:** The stored path already satisfies the PRD-001 canonical identity contract; no data change is made.
- **Convertible:** The stored path is the exact lossless host path obtained from the row's registered project root plus one valid canonical relative identity, and no active canonical row occupies that identity.
- **Conflict:** The row maps exactly to a canonical identity already occupied by another active row.
- **Unresolved:** The row is noncanonical but cannot be mapped exactly and safely under the registered project root.
- **Previously reconciled:** Durable reconciliation evidence proves that the same original row and value already received its terminal outcome.

Classification must use project identity, registered root, and the shared PRD-001 path contract. String-prefix similarity, filename similarity, summary content, timestamps, filesystem search, and model inference are not identity evidence.

## Non-goals

This PRD does not:

- implement file deletion, rename lifecycle, tombstones, scan cursors, or resumable repository scans;
- infer mappings from an old machine root, a moved repository, Git history, matching content, or similarly named files;
- merge summary text, tags, symbols, timestamps, or other fields between conflicting rows;
- choose a conflict winner by freshness, perceived quality, or model judgment;
- regenerate summaries or read source files to repair legacy data;
- reconcile decision or session-rollup path references;
- change the canonical identity rules established by PRD-001;
- change project identity or project-root registration semantics;
- introduce content hashes, Git object identity, branch identity, or worktree identity;
- introduce the future daemon command/query runtime, local IPC, or adapter cutover assigned to M2;
- implement the future audit/evidence subsystem assigned to M4;
- make derived summaries canonical source truth;
- add a general migration framework or storage backend;
- perform cross-project matching or reconciliation; or
- delete an unresolved row merely because it is noncanonical.

## Functional Requirements

### FR-1: Bounded candidate discovery

Reconciliation must enumerate file-summary rows within one declared project at a time and classify each path with the PRD-001 canonical identity contract.

Candidate discovery must be bounded, deterministically ordered, and independent of ordinary file-summary lookup. It must not accept a caller-supplied absolute path as a canonical identity or search other projects for a match.

### FR-2: Exact safe mapping

A legacy row is mappable only when all of the following hold:

1. its `project_id` resolves to one existing project;
2. its stored path is absolute and losslessly representable;
3. the stored path is lexically contained beneath that project's registered repository root on the supported host;
4. removing the exact registered-root prefix yields a non-empty path accepted by the shared canonical file-identity rules; and
5. reconstructing the legacy host path from that root and canonical relative identity yields the same stored legacy identity under the contract's supported host semantics.

Reconciliation must not require the source file to still exist. Physical absence is not proof that an identity is invalid, because the summary may describe a removed file and lifecycle reconciliation has not yet run. A path whose mapping requires traversal, lossy conversion, cross-project access, or symbolic-link inference is unresolved.

### FR-3: Convertible-row outcome

When a legacy row maps exactly and no canonical row exists for `(project_id, canonical_path)`, reconciliation must:

- preserve the row's stable `id` and every non-identity field;
- preserve its complete original value in the reversible reconciliation record before changing active identity;
- replace only the active `path` with the canonical repository-relative path; and
- record the terminal converted outcome and resulting identity in the same transaction.

Conversion must not refresh timestamps that describe summary generation or source observation. Any migration bookkeeping timestamp must remain separate from the summary's existing timestamps.

### FR-4: Conflict outcome

When a canonical row already occupies the mapped identity, that canonical row remains the sole active winner. Reconciliation must not overwrite it or combine either row's fields.

Before removing the legacy conflict row from the active `file_summaries` set, Familiar must preserve its complete original value, original row identity, mapped canonical identity, and conflict outcome in the reversible reconciliation record. The canonical row must remain byte-for-byte unchanged by the conflict operation.

The preserved legacy value must remain available for deterministic inspection and rollback, but it must not continue to appear as a current file summary in ordinary lookup, listing, module, search, packing, or dashboard counts.

### FR-5: Unresolved outcome

Noncanonical rows that cannot be mapped exactly must remain unchanged in active storage and receive an explicit unresolved result with a stable reason category.

Required reason distinctions include:

- missing project;
- non-absolute but noncanonical path;
- registered-root mismatch;
- lexical or traversal failure;
- empty relative identity;
- lossless-representation failure;
- unsupported host-path form; and
- internal persistence or validation failure.

Unresolved rows must not be hidden, rewritten, deleted, associated with another project, or reported as successfully reconciled.

### FR-6: Complete preservation

The reversible reconciliation record must preserve enough information to restore every changed or removed row exactly as it existed before reconciliation, including its original primary key, project, path, summary, tags, extracted symbols, source metadata, and timestamps present in the schema at execution time.

It must also identify the reconciliation run, classification, mapped canonical identity when one exists, resulting active row when applicable, and completion time. Preservation must occur transactionally with the active-row change.

### FR-7: Idempotency and replay

Re-running reconciliation over the same database state must not create another conversion, another preserved copy, another deletion, or a different outcome.

A run interrupted before transaction commit must leave neither a partial active-row change nor a terminal reconciliation record. A retry after commit must recognize the prior outcome. Reconciliation of additional rows inserted later must not alter completed outcomes.

### FR-8: Transaction and constraint safety

Each row outcome must preserve the existing `(project_id, path)` uniqueness constraint and all foreign keys. Conversion or conflict preservation must be atomic for that row. If a project-level transaction is used, failure must roll back the entire declared project batch; if bounded batches are used, batch boundaries and progress must be explicit and replay-safe.

Reconciliation must fail closed when preservation cannot be committed. It must never delete or rewrite an active row first and attempt to record rollback information afterward.

### FR-9: Reconciliation status

Familiar must expose a deterministic project-scoped result containing at least:

- total rows examined;
- canonical rows unchanged;
- legacy rows converted;
- conflicts preserved and removed from the active set;
- unresolved rows grouped by reason;
- previously reconciled rows;
- failed rows or batches;
- whether the run completed; and
- stable references to preserved records without exposing unrelated host paths.

An empty legacy set, a completed run with unresolved rows, and a failed or interrupted run are distinct results.

### FR-10: Ordinary read behavior after reconciliation

Canonical lookup remains authoritative throughout the transition. After all exactly mappable legacy rows for a project have terminal converted or conflict outcomes, ordinary reads must no longer depend on the exact absolute-path compatibility fallback for those rows.

The fallback may be removed globally only when tests prove that supported databases are reconciled during upgrade before ordinary reads require it. If unresolved rows remain, their visibility must be explicit and must not permit absolute caller input or arbitrary legacy matching. Archived conflict records are historical migration data, not current summaries.

### FR-11: Upgrade behavior

Opening an existing supported database and running the normal migration path must install all additive storage needed for reversible reconciliation without destroying or rewriting file-summary data as a schema side effect.

The data-reconciliation step must run through one controlled storage-owned operation after schema compatibility is established. Its completion or failure must be observable. A fresh database and an already reconciled database must pass through the same code safely with no synthetic legacy history.

### FR-12: Rollback operation

Rollback must be an explicit, deterministic operation over one identified completed reconciliation run or bounded project result. It must verify that restoring an original active row will not overwrite state created or changed after reconciliation.

When exact restoration would conflict with later state, rollback must stop and report the conflict; it must not overwrite, merge, renumber, or silently choose a winner. Successful rollback restores preserved rows exactly and retains the reconciliation history needed to explain both operations.

### FR-13: No fabricated evidence

The implementation may retain migration and reconciliation records required by this PRD, but it must not fabricate historical command actors, audit events, source observations, or timestamps that the pre-existing system did not record. Legacy and migration provenance must be labeled explicitly.

## Non-functional Requirements

### Determinism

The same database contents, registered project roots, supported host semantics, and reconciliation version must produce the same classifications and row outcomes. Ordering, counters, and reason categories must be stable.

### Safety and isolation

Reconciliation must fail closed on ambiguous mapping and operate within one project. A legacy row must never be attached to a different project, even when another project root or file path appears to match.

### Reversibility

No changed or removed legacy value may become unrecoverable. Rollback information must be durable before the corresponding active-row mutation commits and must remain queryable until a future approved retention policy permits removal.

### Compatibility

Fresh databases and databases containing only canonical rows must remain unchanged in behavior. Current valid canonical file-summary lookup, module, search, packing, and summary production must continue to work while upgrade reconciliation is introduced.

### Bounded behavior

Reconciliation may scan the bounded file-summary population of one project, but it must not walk the repository tree, scan other projects, invoke an LLM, or perform unbounded fuzzy matching. Large projects must have an explicit transaction or batch bound and replay-safe progress.

### Observability

Every noncanonical row receives a visible outcome. Logs and status must distinguish converted, conflict, unresolved, failed, interrupted, rolled back, and already completed states. Diagnostics must avoid exposing host paths outside the affected project scope.

### Architectural compatibility

The work must remain inside the existing Repository Identity and Reconciliation and storage boundaries. It must use the PRD-001 identity contract and remain compatible with future daemon-owned command, query, and audit contracts without partially implementing those later milestones.

## Acceptance Criteria

1. An absolute legacy row at `<registered-root>/src/main.rs` with no canonical peer retains its `id` and all non-path fields while its active path becomes `src/main.rs`.
2. The convertible row's complete original value is durably preserved before the active path change commits.
3. When both absolute and canonical rows map to `src/main.rs`, the canonical row remains unchanged and is the only current summary for that identity.
4. The conflicting legacy row remains exactly recoverable from the reconciliation record and does not appear in ordinary current-summary reads or counts.
5. No conflict fields are merged and no winner is selected by timestamp, content, or model judgment.
6. A legacy row outside the registered root remains unchanged and is reported as unresolved with a root-mismatch reason.
7. Missing source files do not prevent otherwise exact lexical identity conversion.
8. Traversing, lossy, unsupported, or ambiguous paths are not converted or deleted.
9. Re-running a completed reconciliation produces no duplicate preservation records or additional active-row changes.
10. A forced failure between preservation and active mutation leaves both active data and reconciliation history uncommitted.
11. Two projects with equivalent relative paths reconcile independently without cross-project reads or writes.
12. All foreign keys and the project/path uniqueness constraint remain valid after conversion, conflict handling, retry, and rollback fixtures.
13. A fresh database and a canonical-only database undergo no file-summary data changes.
14. Project-scoped status reports exact examined, unchanged, converted, conflict, unresolved, prior, and failed counts.
15. Successful rollback restores a converted or archived legacy row exactly when no later-state conflict exists.
16. Rollback refuses to overwrite later state and reports the exact conflict.
17. Ordinary canonical lookup, module listing, search, packing, and dashboard counts do not return archived conflicts as current summaries.
18. No reconciliation path invokes summary generation, source inspection, filesystem search, or an LLM.
19. The full workspace test suite passes.
20. A deterministic fixture inspection accounts for every pre-reconciliation file-summary row as unchanged canonical, converted, conflict-preserved, or unresolved, with no silent loss.

## Test Strategy

### Migration fixtures

Create representative pre-PRD-001 databases containing:

- canonical-only rows;
- one exactly mappable absolute row;
- canonical and absolute rows for the same identity with differing complete payloads;
- several projects with identical relative paths;
- paths outside or similarly prefixed to the registered root;
- missing files;
- root-level and nested entries;
- traversal-like and unsupported host forms;
- non-lossless paths where the host test environment supports them; and
- mixed canonical, convertible, conflict, and unresolved populations.

For every fixture, retain deterministic before-and-after row counts, primary keys, field values, uniqueness checks, foreign-key checks, and reconciliation classifications.

### Storage integration tests

Verify:

- additive schema upgrade and repeated migration execution;
- exact conversion with stable row identity;
- complete conflict preservation and canonical precedence;
- unresolved-row non-mutation;
- transactional failure injection;
- repeated reconciliation and late-added candidates;
- bounded batch restart if batching is used;
- project isolation;
- current versus preserved-record query separation; and
- exact rollback plus rollback-conflict refusal.

### Current consumer integration tests

Verify after reconciliation that:

- file lookup returns the canonical active row;
- module listing and counts contain one active identity;
- search and packed context exclude preserved conflicts;
- dashboard or project counts count active summaries only;
- callers still cannot submit absolute paths; and
- unresolved legacy data is never mistaken for an empty or successful result.

### Deterministic verification

The implementation pull request must record:

- focused core identity and storage migration test results;
- current MCP consumer and daemon regression results;
- the full workspace test result;
- formatting and static-analysis results under existing repository commands;
- before-and-after fixture manifests accounting for every row and field;
- SQLite foreign-key and integrity-check results;
- an idempotent replay result showing zero additional mutations; and
- a rollback fixture proving exact restoration and conflict refusal.

No model judgment may substitute for these checks.

## Rollback Strategy

This PRD has a reversible data boundary and must not rely on source regeneration.

1. Stop reconciliation before rollback begins and identify the exact completed run or project result.
2. Verify preserved-record completeness and current active-row expectations.
3. Restore converted rows to their original paths and restore conflict rows with their original primary keys and complete values only when doing so cannot overwrite later state.
4. Roll back each declared transaction atomically and record its outcome separately from the original reconciliation result.
5. If any identity, primary-key, or later-write conflict exists, stop without partial restoration and report it for human resolution.
6. Retain reconciliation and rollback provenance; do not erase the fact that either operation occurred.
7. Re-enable the PRD-001 exact legacy compatibility read only if code rollback requires it and the restored database again contains active exact legacy rows.
8. Run row-accounting, uniqueness, foreign-key, integrity, canonical-lookup, and legacy-read fixtures before declaring rollback complete.

Rollback must not delete canonical rows, merge payloads, fabricate older state, renumber restored rows, or discard unresolved legacy data.

## Definition of Done

PRD-002 is done when:

1. Every existing file-summary row in each migration fixture has one deterministic reconciliation classification and accounted outcome.
2. Exactly mappable, nonconflicting rows use canonical active identity with stable row IDs and unchanged non-identity data.
3. Canonical rows win conflicts unchanged, while complete legacy conflicts are preserved outside the current-summary set.
4. Uncertain mappings remain unchanged and explicitly unresolved.
5. Reconciliation is transactional, idempotent, retry-safe, project-isolated, and reversible.
6. Ordinary current-summary consumers no longer observe reconciled duplicate identities.
7. Fresh and canonical-only databases remain behaviorally unchanged.
8. Upgrade and rollback behavior pass deterministic row-accounting, uniqueness, foreign-key, and integrity checks.
9. Focused tests, the full workspace suite, formatting, and static analysis pass.
10. The implementation is contained in one independently reviewable pull request.
11. No repository lifecycle, M2 authority, or later-roadmap capability is implemented incidentally.
