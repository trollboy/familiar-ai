# PRD-005: Agent-Neutral Execution Abstraction

**Status:** Ready for implementation  
**Date:** 2026-08-03  
**Architectural direction:** Agents Are Replaceable  
**Delivery boundary:** Predecessor extraction for EPIC-M6-02 — Neutral Agent Contracts

## Objective

Remove the hard-coded Codex dependency from Familiar's execution orchestration by introducing a permanent, agent-neutral execution boundary.

After this PRD, a `CodingAgent` trait is the only boundary through which the `familiar run` orchestration layer invokes a coding agent. An agent-neutral `ExecutionResult` reports the observed process result and supported execution metadata. All knowledge of the Codex executable, command-line arguments, version probe, JSONL event schema, output rendering, and Codex-specific error wording lives behind a `CodexAgent` implementation.

The existing `familiar run <prd-path>` command remains the sole execution entry point and continues to run the locally installed Codex CLI with exactly the same prompt, working directory, terminal streaming, history, metrics, pricing, failure, and exit-status behavior. This is a structural extraction with zero functional changes.

This PRD establishes the execution abstraction that every future coding-agent adapter must implement. It intentionally does not add any future adapter or the broader task, context, finding, handoff, capability, routing, or supervision contracts assigned to later milestones.

## Motivation

Familiar's philosophy requires coding agents to be replaceable and forbids dependence on a single vendor. The current repository violates that boundary locally: `crates/familiar-daemon/src/run.rs` combines agent-neutral orchestration with direct `codex exec --json -` process construction, `codex --version` probing, Codex JSONL parsing, Codex output rendering, and Codex-specific errors. The CLI also describes and constructs Codex directly.

That coupling makes the orchestrator itself a Codex adapter. Any future execution implementation would have to duplicate the orchestration path or add vendor branches to it, allowing provider details to leak into prompt construction, history finalization, and CLI semantics.

The smallest independently useful correction is to extract the existing behavior behind one narrow interface now. This honors the target-state rule that agent adapters translate neutral contracts while avoiding premature implementation of the much broader neutral task-and-result contracts described by `PRD-TBD-M6-03`. The repository, Git state, validated PRD, and existing execution history remain authoritative within their current scopes.

## Scope

This PRD includes:

1. A dedicated agent-execution module or crate with the public `CodingAgent` trait and `ExecutionResult` type.
2. The minimum agent-neutral request/input types needed to supply a prepared prompt, working directory, and live output sink to an agent.
3. An agent-neutral execution error boundary that preserves all currently distinguishable launch, input, output, and wait failures.
4. A `CodexAgent` implementation containing all Codex-specific executable invocation, arguments, version probing, structured-event parsing, supported metric extraction, and human-visible stdout rendering.
5. Refactoring the `familiar run` orchestration path to accept or construct a `CodingAgent` and depend only on the trait and neutral result/error types during execution.
6. Preservation of existing repository/worktree resolution, PRD validation, prompt construction, direct ADR/contract inclusion, fixed execution constraints, database initialization, execution-history insertion and finalization, pricing, and CLI exit propagation.
7. Focused unit, boundary, and fake-executable regression tests proving both abstraction conformance and exact current behavior.

### Separation of responsibilities

The orchestration layer continues to own:

- resolving and validating repository, worktree, Git commit, and PRD identity;
- constructing the complete execution prompt;
- opening and migrating the configured database;
- creating exactly one pre-launch execution-history record;
- timing the run and mapping neutral execution observations into the existing history finalization and pricing rules;
- finalizing history on every currently handled path; and
- returning the command result to the CLI.

The `CodexAgent` owns:

- the configured Codex executable name or path;
- `codex --version` probing and validation;
- the exact `exec --json -` argument contract;
- child-process creation in the supplied working directory;
- prompt delivery over stdin;
- inherited or streamed stderr behavior;
- incremental parsing of Codex JSONL stdout;
- rendering supported human-visible Codex events to the supplied output sink;
- ignoring unknown structured events and forwarding malformed lines exactly as today;
- extracting only the currently supported model and token observations; and
- translating Codex process failures into neutral boundary errors without losing their source or category.

## Non-goals

This PRD does not:

- add Claude, Ollama, Cursor, OpenCode, MCP, or any other coding-agent implementation or protocol;
- add agent discovery, selection, routing, scheduling, fallback, retries, queues, concurrency, or configuration for additional agents;
- add model selection, capability advertisement, capability negotiation, provider configuration, plugin loading, or dynamic dispatch by agent name;
- implement the full M6 vendor-neutral task, context package, finding, handoff, or canonical result schemas;
- move execution into the daemon, add IPC, or alter the CLI/daemon authority boundary;
- add tasks, approvals, warrants, policy, isolation, worktree management, verification, review, acceptance, or external effects;
- change the execution prompt or which directly referenced documents it contains;
- change Codex arguments, supported JSON event paths, output rendering, version parsing, missing-value reasons, metrics, pricing, or history schema;
- generalize execution history for additional agents or remove its current `agent = codex` constraint;
- change public `familiar run`, `familiar history`, or `familiar usage` syntax or output;
- introduce asynchronous execution solely for abstraction purposes;
- modify architecture documents, ADRs, contracts, or prior PRDs; or
- perform unrelated cleanup or reorganize other Familiar LLM/inference interfaces.

## Architecture

The implementation introduces one dependency direction:

```text
familiar CLI
    |
    v
run orchestration
  - validate repository and PRD
  - build prompt
  - create/finalize history
  - calculate price
    |
    | CodingAgent only
    v
agent execution boundary
    |
    v
CodexAgent
  - codex process contract
  - Codex JSONL parsing/rendering
  - Codex metadata extraction
```

The orchestration module must not import or inspect Codex event types, construct Codex commands, call a Codex version probe, or branch on a Codex identifier. It invokes a `CodingAgent`, receives an `ExecutionResult` or neutral execution error, and applies the existing generic timing, persistence, pricing, and exit behavior.

`CodexAgent` may be selected in the CLI composition root because Codex remains the one existing concrete implementation. Constructing that implementation at the outermost boundary is dependency injection, not routing or additional-agent configuration. The `run` command's help text remains unchanged in this PRD because changing user-visible text would violate the zero-functional-change constraint.

The abstraction must remain narrow. It represents execution of an already prepared prompt in an already selected working directory. It must not absorb repository discovery, PRD interpretation, prompt assembly, storage, pricing, workflow policy, or future task orchestration.

No schema migration is required. The existing execution-history record remains explicitly Codex because Codex is still the only implementation invoked by this command. Generalizing durable agent identity belongs to later canonical contract work and is not necessary to remove the orchestration dependency.

## Public Interfaces

The exact Rust module paths may follow the repository's established naming, but the public semantic contract must be equivalent to:

```rust
pub trait CodingAgent {
    fn execute(
        &self,
        request: ExecutionRequest<'_>,
        output: &mut dyn std::io::Write,
    ) -> Result<ExecutionResult, AgentExecutionError>;
}

pub struct ExecutionRequest<'a> {
    pub working_directory: &'a std::path::Path,
    pub prompt: &'a str,
}

#[derive(Debug, Clone, Default, PartialEq, Eq)]
pub struct ExecutionResult {
    pub agent_version: Option<String>,
    pub model: Option<String>,
    pub input_tokens: Option<u64>,
    pub output_tokens: Option<u64>,
    pub cached_tokens: Option<u64>,
    pub exit_code: Option<i32>,
    pub signal: Option<i32>,
}
```

`ExecutionResult` contains observations, not claims of correctness or acceptance. Normal exit code zero, non-zero exit, and signal termination are successful observations of a completed child process and are represented in the result rather than converted into interface errors. `exit_code` and `signal` retain the current mutually exclusive operating-system termination semantics.

`AgentExecutionError` must distinguish the current boundary failures at minimum:

- child launch failure;
- prompt input failure when it is not superseded by an observed non-success child result;
- child wait failure; and
- structured-output read or output-sink failure.

The concrete error representation may carry an `io::Error` and any partial neutral observations needed to preserve current history finalization. It must not expose Codex JSON shapes or require the orchestrator to interpret Codex-specific state.

`CodexAgent` is the one concrete implementation and is constructed with the executable string currently supplied to `execute`. Its public constructor must permit a fake executable in tests. The production composition continues to use `codex`.

The trait must be object-safe so orchestration can be tested with a deterministic fake implementation and future adapters can implement the same permanent boundary without changing orchestration. It must not contain methods for routing, capabilities, configuration discovery, task scheduling, or provider enumeration.

## Data Flow

1. The CLI parses the unchanged `familiar run <prd-path>` command and constructs the production `CodexAgent` with executable `codex`.
2. The orchestration layer resolves the current Git worktree, common repository identity, optional `HEAD`, and validated repository-relative PRD identity exactly as today.
3. The orchestration layer builds the same prompt from the PRD, fixed execution constraints, and directly referenced ADR/contract documents.
4. The orchestration layer opens the configured database, applies migrations, and inserts the existing `running` execution row before agent probing or launch.
5. The orchestration layer calls `CodingAgent::execute` with only the prepared prompt, validated worktree, and live stdout sink.
6. `CodexAgent` probes `codex --version`, launches `codex exec --json -` in the supplied worktree, writes the prompt, inherits or streams stderr, parses stdout line by line, flushes rendered output incrementally, and accumulates supported neutral metadata.
7. `CodexAgent` returns an `ExecutionResult` for an observed child termination or a neutral categorized error carrying the information required by the existing finalization behavior.
8. The orchestration layer maps the result or error to the existing outcome, exit code, signal, missing-value reasons, duration, totals, configured exact-model price, and final execution-history update.
9. The CLI returns the same child exit code when representable and otherwise the same failure code it returns today. `history` and `usage` continue reading identical records and producing identical output.

No prompt, transcript, stdout, stderr, environment, credential, or repository source is newly retained or passed to storage.

## Acceptance Criteria

1. A public object-safe `CodingAgent` trait exists and is the only execution dependency of the `run` orchestration layer.
2. A public agent-neutral `ExecutionResult` exists with optional agent version, model, input-token, output-token, cached-token, normal exit-code, and signal observations.
3. A `CodexAgent` implements `CodingAgent` and contains every reference required to invoke or interpret Codex: executable construction, `--version`, `exec --json -`, Codex JSONL event parsing, supported output rendering, and metric extraction.
4. The orchestration layer contains no Codex process arguments, Codex event parsing, Codex version parsing, or Codex-specific execution-error wording or branches.
5. The production CLI still invokes the locally installed executable named `codex`; no selection or configuration for another agent is added.
6. `familiar run <prd-path>` syntax, help text, prompt bytes, current working directory, stdout, stderr, live flush behavior, and exit-code behavior are unchanged.
7. Repository/worktree resolution, Git commit observation, PRD path validation, direct document inclusion, and fixed execution constraints are byte-for-byte or behaviorally identical to the existing implementation.
8. A successful fake Codex run receives exactly `exec`, `--json`, and `-`, receives the same prompt over stdin, streams the same supported messages, and creates the same successful history values as before.
9. A non-zero fake Codex run returns the exact same CLI status and persists the same `failed` outcome and exact exit code as before.
10. Signal termination, launch failure, prompt-input failure, stdout/output failure, wait failure, version-probe failure, unknown events, malformed JSONL, and partial/missing metrics retain their current externally visible and history-finalization semantics.
11. Model and token observations remain derived only from the same supported typed Codex event paths; no text scraping, inference, defaulting, or new event support is introduced.
12. Existing total-token, pricing, unavailable-field, timing, and history rules produce identical stored values for identical fake-agent observations.
13. `familiar history` and `familiar usage` require no behavior or presentation changes and all existing tests continue to pass.
14. Orchestration tests can supply a deterministic fake `CodingAgent` without placing a fake `codex` executable on `PATH`; Codex adapter tests continue to use a fake executable and never invoke real Codex.
15. No Claude, Ollama, Cursor, OpenCode, MCP, additional agent, router, scheduler, fallback, capability registry, or additional-agent configuration appears in production code.
16. No database schema, migration, prior document, architecture document, ADR, contract, daemon runtime, LLM backend, or unrelated subsystem is changed.
17. The implementation is one independently mergeable structural refactor and produces zero functional changes.

## Test Strategy

### Interface and orchestration unit tests

- Compile-time or focused tests prove `CodexAgent: CodingAgent` and that the trait is usable through `&dyn CodingAgent` or `Box<dyn CodingAgent>`.
- A deterministic fake agent captures `ExecutionRequest` and returns selected `ExecutionResult` values without spawning a process.
- Orchestration fixtures verify the exact worktree and prompt passed to the trait.
- Fake results cover exit zero, non-zero exit, signal termination, complete metrics, partial metrics, absent version/model/usage, and integer bounds.
- Fake errors cover launch, input, wait, and output categories and assert unchanged history outcomes, finalization attempts, and caller errors.
- Existing prompt construction, reference discovery, PRD containment, Git identity, total-token, pricing, and missing-value tests remain in the orchestration module or an equally focused neutral module.

### Codex adapter unit tests

- Keep exact fixtures for supported `turn.completed`, `item.completed`, and `error` events.
- Verify unknown events and fields remain ignored, malformed lines remain forwarded, invalid numeric values remain unavailable, and no unbounded transcript is retained.
- Verify version probing accepts and rejects exactly the same values as the current implementation.
- Verify human-visible messages are written and flushed incrementally through the supplied writer.
- Tests must use a fake executable or in-memory JSONL; they must never invoke a real Codex installation.

### CLI integration tests

- Preserve the current fake-`codex` end-to-end test as the compatibility proof for exact arguments, stdin prompt, stdout, stderr, non-zero status propagation, and history/usage records.
- Preserve the timing test proving output is visible before the fake child exits.
- Add or retain focused fixtures for success, signal, launch failure, malformed structured output, and missing metrics where current coverage supports them.
- Run against a temporary database and temporary executable path without reading or modifying user data.

### Verification commands

Implementation must run:

- formatting checks;
- focused unit tests for the agent boundary, Codex adapter, run orchestration, pricing, and prompt construction;
- the fake-executable CLI integration suite;
- focused static analysis with warnings denied; and
- an attempted full workspace test suite, with pre-existing or unrelated failures identified separately.

Because the requirement is zero functional change, test expectation changes are prohibited unless they are limited to module paths, type names, or dependency injection mechanics. Snapshot, output, prompt, argument, history, and exit-status expectations must not change.

## Expected Files

The implementation is expected to change only:

- `Cargo.toml` to add a focused workspace member if the boundary is implemented as a crate;
- `Cargo.lock` only if workspace metadata or dependencies require it;
- `crates/familiar-daemon/Cargo.toml` to depend on the focused agent boundary;
- `crates/familiar-daemon/src/bin/familiar.rs` for production `CodexAgent` construction at the composition root;
- `crates/familiar-daemon/src/run.rs` to retain only agent-neutral orchestration and existing prompt/history behavior;
- `crates/familiar-daemon/src/lib.rs` if exports must be adjusted;
- `crates/familiar-daemon/tests/cli_run.rs` for unchanged end-to-end compatibility coverage;
- a new focused `crates/familiar-agent/Cargo.toml` and `crates/familiar-agent/src/lib.rs`, plus small `agent.rs` and `codex.rs` modules if a dedicated crate is used; or
- equivalently focused `agent.rs` and `codex.rs` modules under `crates/familiar-daemon/src/` if implementation evidence shows a separate crate adds no useful dependency enforcement.

The preferred structure is a small `familiar-agent` crate because the workspace dependency graph then prevents daemon orchestration from owning Codex internals and gives future adapters one stable implementation contract. The crate must remain limited to the interface, neutral result/error types, and current `CodexAgent`; it must not become a provider registry or agent framework.

Changes outside this list require explicit justification. No migration, configuration file, storage implementation, architecture document, ADR, contract, prior PRD, or other subsystem is expected to change.

## Definition of Done

PRD-005 is done when:

1. `CodingAgent` is the permanent, object-safe execution boundary and `ExecutionResult` is the neutral observation returned by implementations.
2. All Codex-specific process, version, JSONL, rendering, and metric behavior resides in `CodexAgent`.
3. The orchestration layer prepares and records execution while knowing only the agent interface and neutral types.
4. The production composition still selects the one existing `CodexAgent` with executable `codex`, without adding selection logic or additional-agent configuration.
5. Every existing `familiar run` user-visible behavior and execution-history value is preserved for equivalent inputs, including prompt content, streaming, stderr, exit propagation, errors, missing values, metrics, and pricing.
6. Neutral fake-agent tests verify orchestration independently, and fake-Codex tests verify adapter conformance without invoking real Codex.
7. Existing `run`, `history`, and `usage` regression tests pass without functional expectation changes.
8. Formatting and focused static analysis pass, and the workspace suite is attempted with unrelated failures reported separately.
9. No additional agent, protocol, routing, scheduling, fallback, capability, configuration, task, warrant, verification, review, or later-roadmap feature is introduced.
10. No database or documentation other than this PRD is changed by the implementation unless an expected-file deviation is explicitly justified.
11. The change is independently mergeable and reviewable as a behavior-preserving dependency inversion.
