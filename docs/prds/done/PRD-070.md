# PRD-070: Daemon Context Service

## Objective

Turn context from a per-run expense into a maintained asset. Today every
worker rediscovers the repository from zero — the wave-one watcher sees
every file change, yet nothing downstream consumes that knowledge, and
measured spend is dominated by context (94% of usage from >150k-context
sessions; 97%+ cache reads in instrumented runs). The daemon that already
tracks projects becomes the owner of two amortized artifacts: an
incrementally maintained repository symbol map, and deterministic,
prefix-stable serializations of it that provider prompt caches can hold
across sessions and workers. The daemon also becomes the place where
per-project token spend is understood: a sink report over the PRD-051
ledger says where each project's tokens actually go.

## Design

- **Incremental repo map.** A `familiar-ai-repomap` crate builds and
  maintains per-repository symbol maps (definitions, signatures,
  reference edges) with language-aware parsing. The daemon's watcher
  feeds it: one changed file triggers one file's reindex. Ranking follows
  the reference graph so a bounded map serves the most-connected symbols
  first — signatures instead of bodies, with drill-down left to the
  worker.
- **Prefix-stable serving.** Serialization is deterministic and
  content-addressed by file: unchanged content yields identical bytes
  across restarts, and an edit perturbs only its own region. Served two
  ways — an MCP tool for any agent (the wave-one `pack_for_task` promise,
  rebuilt on this mechanism), and optional injection into Familiar's own
  run context, off by default with byte-identical prompts when off,
  enabled per repository through the audited configuration path.
- **Token-sink intelligence.** A report over PRD-051 observations ranks a
  project's spend by stage, worker, and token category, and an effect
  comparison partitions ledger rows by injection state to report what the
  context service actually changes. Only measured values are reported;
  promotion of injection to a default requires this evidence.
- **Explicit degradation.** Partial coverage (unwatched repository,
  unparseable file) is named, never silent — a worker trusting the map
  must know its edges.

## Scope

The repomap crate, watcher wiring in a dedicated daemon module, MCP tool
surface, optional run-context injection behind audited config, sink and
effect reports over the ledger, the context-service contract document,
and regressions in a dedicated test file (incremental reindex, byte
stability across restarts, symbol-location correctness, byte-identical
prompts when off, partial-coverage reporting).

Out of scope: semantic summarization (wave-one summaries/rollups remain a
separate lossy mechanism), compression of served content (PRD-069
composes with this; the map is small by construction), batch review
(PRD-071), and any change to worker edit formats (PRD-072).

## Assumptions (recorded at specification time, 2026-08-30)

- The wave-one watcher provides usable per-file change events; if its
  event surface is too coarse, extending it is in scope for the daemon
  module, not a new PRD.
- Repository identity keys the maps (Git common-directory identity);
  PRD-055's richer project identity attaches when it lands without
  rekeying.
- Ranked-signature maps materially reduce context for real repositories;
  the effect comparison exists to verify this on Familiar itself rather
  than assume it.
