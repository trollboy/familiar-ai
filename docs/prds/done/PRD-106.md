# PRD-106: Split the Hub Files That Serialize the Queue

## Objective

The 1.0 definition says Familiar runs a collection of PRDs in parallel at
the width the scope graph allows. The scope graph allows less than it
should, and the reason is five files. The execution plan measured it on
2026-09-17:

| Contended file | PRDs declaring it then |
|---|---|
| `config/default.toml` | 088, 089, 094, 097, 100, 101 |
| `README.md` | 090, 092, 098, 099, 101 |
| `crates/familiar-ai-core/src/config/registry_workers.rs` | 086, 094, 100, 101 |
| `crates/familiar-ai-daemon/src/run.rs` | 086, 088, 094, 100 |
| `crates/familiar-ai-storage/src/migrate.rs` | every migration-bearing PRD |

Thirty-seven conflict edges across fifteen PRDs; twenty-two of them were
one of the first four files, and the plan's own words for the fifth were
"every migration-bearing PRD must touch `migrate.rs`, so no two of them
can ever run in the same round." PRD-076 split the previous generation of
hot surfaces and width went up. Nobody split this generation. The plan
said a split "is worth its own PRD"; this is it.

## Scope, and what is deliberately left out

Three of the five surfaces are documentation or registration, where a
split is mechanical and the width return is certain: the migration
registry, the defaults file, and the README's reference sections. Those
are in scope.

`registry_workers.rs` and `run.rs` are code, and their contention is
mostly among PRD-086, 094, 100 and 101, which are dependency-ordered on
each other anyway. Splitting them buys little width until those four have
landed and may cost a merge conflict with PR #19. They are out of scope
here and the fourth criterion measures whether that judgment was right:
if the recorded width after this PRD is still bound by them, that is a
successor with the number in hand.

## Design

- **Migrations register themselves.** A build script or `include_dir!`
  over `migrations/` produces the array `migrate.rs` hand-maintains today.
  `migration_allocation.rs` already fails the build on collisions, gaps
  and filename/version disagreement; it keeps doing so against the
  derived list.
- **Defaults are per feature.** `config/default.d/<feature>.toml`,
  concatenated or merged in a fixed order into the same `Config`. Whether
  that happens at build time into a generated single file or at load time
  through figment is an implementation choice; the byte-identical
  regression is the contract either way.
- **The README stops being an API.** It keeps status, goals, quick start
  and pointers. The command table and the configuration reference live in
  guides, which is where PRD-101's `provider-setup.md` already put the
  provider half.
- **Width is measured, not asserted.** The last criterion is the plan's
  own rule: rounds are computed by `achievable_width()`, so the proof that
  this PRD did anything is that number, recorded with its command.

## Assumptions (recorded at specification time, 2026-09-22)

- The scheduler treats a directory entry as a prefix claim since the
  FAM-BUG-051 fix, so `config/default.d/` conflicts correctly with any PRD
  declaring a file beneath it.
- No queued PRD needs to run concurrently with this one; it conflicts with
  most of the queue by construction and is scheduled alone, first, exactly
  as PRD-076 was.
