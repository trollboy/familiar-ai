# PRD-102: The Tray Says When It Needs You

## Objective

Familiar has exactly one ambient surface, and it cannot ask for help.

On 2026-09-19 a four-PRD wave produced two PRDs awaiting a human decision —
PRD-090 blocked on a scope finding at 12:39, PRD-100 needing review at
22:47. The owner learned about both from a chat transcript, hours later.
For that entire span the tray icon sat in the system tray looking exactly
as it looks when everything is fine, while the daemon behind it held the
answer in a durable table it already queries.

The data is not missing. `pending_human_gates` exists in stewardship, is
already plumbed to the tray through `Query::Gates`, and is already rendered
by `build_gates_view` — which is thoughtfully built, grouping by PRD
because "a PRD that stopped four different ways is one thing to decide
about, not four".

Three things are missing, and they are the difference between unattended
and abandoned:

1. **Nothing signals.** There is no notification path anywhere in the tray
   or the daemon — zero references. A gate appears in silence.
2. **The icon has one state.** `assets/icon.png`, loaded once, set once.
   Identical at zero gates and at five.
3. **Nothing is answerable.** `GateGroup` carries `recovery_commands` — a
   list of shell commands to go and type. That is a reference card, not a
   response.

The north star asks for zero bother. Zero bother means never interrupting
unnecessarily; it does not mean never speaking. A blocked PRD is the one
moment the autopilot genuinely needs its operator, and it is precisely the
moment Familiar currently stays quiet.

## Design

- **The count rides on the icon.** A small badge composed onto the tray
  image, showing how many PRDs are waiting. `icon.rs` already decodes the
  base icon with the `image` crate, so the badge is composed with a
  dependency that is already present — no new one is introduced.
- **Zero is silence.** No badge, no notification, no tooltip change. A
  surface that lights up when nothing is wrong is a surface people stop
  reading, and the whole value here is that the icon means something.
- **Notify once per stop, never again.** The point is to be worth glancing
  at. A gate that has already been announced is visible in the badge and
  the list; announcing it repeatedly converts a signal into noise.
- **Answer where you are told.** A decision from a closed set is a set of
  choices. A decision needing justification gets a text field. What is
  recorded is the same durable decision PRD-080 already mints — actor, PRD,
  the stop being answered, and the reason — so a decision made from the
  tray is indistinguishable in the ledger from one made at a terminal.
- **The UI holds no truth.** Count and list are read from
  `pending_human_gates` on refresh. A decision made elsewhere, a restarted
  daemon, or a wave finishing while the window is open all converge on the
  next read rather than on a cached number.
- **A missing notifier is not a missing gate.** If the desktop notification
  service is absent or refuses, the badge and the list still tell the
  truth. Absence of a notification is never evidence of absence of work —
  the same discipline the verification gate applies to unknown outcomes.

## Scope

Badge composition and the icon refresh path; the notification on first
sight of a gate; the decision affordances and the durable decision they
record; reading count and list from durable state; the silent-at-zero
behaviour; notifier-failure containment; the escalation-surface contract
document; regressions in a dedicated test file.

Out of scope: what constitutes a gate in the first place, and the taxonomy
of stop reasons (PRD-085); the stall taxonomy those reasons come from;
notification on macOS or any platform other than the Linux tray this runs
on, which is a successor with its own acceptance; and any change to how
decisions are adjudicated once recorded (PRD-080 owns that shape, and this
PRD reuses it rather than extending it).

## Assumptions (recorded at specification time, 2026-09-20)

- `tray_icon` 0.22 permits replacing the icon on a live tray. The current
  code discards the handle (`let _tray = TrayIconBuilder::new()...`), so
  holding it is a precondition of this work rather than an incidental
  refactor. If the crate turns out not to support it, the badge is a
  named platform limitation to report, not a reason to drop the count.
- `gio::Notification` is reachable through the `gtk` 0.18 dependency the
  tray already carries, so notification costs no new dependency. The tray
  already owns a GTK main loop on the main thread, which is where a
  notification must be raised from.
- The existing background refresh thread in `tray.rs`, which already polls
  status to update menu and tooltip, is the right place to refresh the
  badge. This PRD adds to that cadence rather than introducing a second
  timer.
- A count large enough to overflow a small badge is a display problem, not
  a data problem. The cap form (for example `9+`) is a rendering decision
  and does not change what the list reports.

## Resolved: the menu signals, the window decides (2026-09-20)

**Where does the decision UI live?** The tray menu carries the count and a
single item that opens the window at the gates view. Every decision is made
in the window.

One place decisions are made, and the menu stays a signal rather than a
workspace. The alternative — closed-set decisions as submenu items, with
only reason-requiring ones opening the window — is fewer clicks for the
common case but splits decision-making across two surfaces, and a muda menu
item is a poor host for the free text several stop classes require. The cost
is one extra click on the common path, accepted deliberately.

## Acceptance evidence

The regressions drive a view over a fixture gate set, not a live daemon:
composing the icon at zero and non-zero counts and comparing bytes,
presenting the same gate set twice and counting notifications, submitting a
decision and asserting the durable record carries actor, PRD, stop and
reason, mutating the gate set beneath a built view and asserting the
refresh reflects it, and driving a notifier that fails and asserting the
badge and list are unaffected.

Everything the operator sees stays a tested pure function; GTK only lays it
out. That is the crate's existing idiom and this PRD does not depart from
it.
