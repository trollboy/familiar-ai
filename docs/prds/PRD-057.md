# PRD-057: Worker Identity, Runtime, and Capability Generalization

## Objective

Replace `provider/model` as Familiar's notion of a worker with the
complete executable configuration — provider, runtime, model or
artifact, auth profile, capability profile — so routing selects,
accounting attributes, empirical scoring ranks, and evidence records
the thing that actually ran, and so new providers and runtimes are
configuration, not surgery.

## Problem

The registry already stores the ingredients — a free-text `provider`,
an `adapter`, a `model` — but flattens identity to `provider/model`
for addressing, selection records, and scores. That conflates
categorically different things: Claude Code and Codex are agent
harnesses that own their conversation loops, select models, and bill
against subscriptions; Anthropic Messages and OpenAI Responses are raw
inference APIs; a nominally identical open-weight model behaves and
costs differently under Ollama, llama.cpp, MLX, or vLLM. The same
model through a different runtime is a different empirical worker with
different capabilities, economics, failure modes, and usage
granularity. `provider/model` cannot say which one ran.

## Domain model

Distinct, typed identities (names follow existing config conventions;
the aggregate shape adapts to the registry rather than forcing a
struct):

- **ProviderId** — the commercial or operational provider (anthropic,
  openai, xai, local). Never implies capability.
- **RuntimeId** — the execution mechanism: claude-code, codex,
  anthropic-api, openai-api, xai-api, ollama, llama-cpp, mlx, vllm, …
  Today's registry `adapter` field is its ancestor.
- **ModelId** — provider model identity or local model
  family/revision. May be an explicit `unknown` or
  `runtime-selected` state: a harness that picks its own model hides
  exact identity, and Familiar records what the runtime reports
  per-observation (PRD-051 per-model rows) without pretending the
  spec pinned it.
- **ModelArtifactId** — immutable content-derived identity of a local
  artifact (weights file/dir hash, quantization included). A changed
  artifact is a different identity.
- **AuthProfileId** — an externally managed credential or entitlement
  reference (a PRD-047 provider auth descriptor, a subscription
  entitlement, an env reference). Optional for local runtimes. Never
  a value.
- **CapabilityProfileId** — the declared-and-probed capability set a
  worker routes on.
- **WorkerSpec** — the routable aggregate of the above, carried by
  each `[worker_registry.workers.<id>]` entry; the operator-chosen
  worker id remains the human alias, and a canonical spec identity is
  derived from the normalized identity fields for persistence.

Representative configurations (model identifiers illustrative, not
verified or pinned by this document):

    [worker_registry.workers.sonnet-cc]        # harness, subscription
    provider = "anthropic"
    runtime = "claude-code"
    model = "claude-sonnet-5"                  # or "runtime-selected"
    auth_profile = "claude-cli-login"
    capability_profile = "agentic-implementer"

    [worker_registry.workers.gpt-codex]        # harness, ChatGPT plan
    provider = "openai"
    runtime = "codex"
    model = "runtime-selected"
    auth_profile = "codex-chatgpt"

    [worker_registry.workers.claude-api]       # raw hosted API
    provider = "anthropic"
    runtime = "anthropic-api"
    model = "claude-sonnet-5"
    auth_profile = "env-anthropic-key"

    [worker_registry.workers.qwen-local]       # local runtime
    provider = "local"
    runtime = "ollama"
    model = "qwen3"
    model_artifact = "sha256:…"                # immutable
    # no auth_profile: local execution

    [worker_registry.workers.qwen-local.runtime_config]
    host = "127.0.0.1:11434"                   # typed, adapter-owned

`sonnet-cc` and `claude-api` share a provider and model and are still
different workers everywhere: routing, accounting, scores, evidence.

## Identity and versioning

Identity fields always partition: any change to provider, runtime,
model, artifact, or capability profile is a new worker for empirical
purposes. Beyond identity, each runtime adapter declares its
**material parameters** — the settings that change behavior enough to
partition history (quantization, prompt template identity, tool
policy, reasoning/effort configuration, context ceiling, temperature
class, seed where determinism is claimed). A material-parameter
change creates a new empirical version of the spec; non-material
provenance (patch-level CLI version, host details) is recorded on
observations and may be grouped or split by deterministic PRD-032
operator policy — never silently merged across a declared partition.
Historical rows keep the identity in force when recorded; migration
adds identity, it never rewrites history.

## Capability model

One closed, typed vocabulary, extending PRD-031's capability notion:
edits-files, executes-commands, reads-repository, native-tool-calling,
mcp-client, structured-output, streaming, resumable-sessions,
context-compaction, prompt-caching, image-input, max-context,
reasoning-controls, sandbox-behavior, remote-or-local,
usage-reporting-categories, cost-reporting-mode, parallel-tool-calls,
deterministic-seed. Each capability persists with provenance:
**declared** (operator/adapter configuration), **probed** (verified by
a safe, non-billable probe under PRD-047 discipline), **observed**
(evidenced by execution history), or **unknown**. Unknown is a valid
routing input that policy may reject; it is never coerced to a
default, and nothing is inferred from the provider name. Probes that
would spend money or tokens are not probes; those facts arrive as
observations.

## Routing and review integration

`RouteRequest` selection (PRD-044) and registry eligibility evaluate
complete specs: capability-profile fit, availability, auth-profile
presence, budget properties, and risk rules. PRD-032 empirical scores
rank spec identities and versions — accepted-PRD rate, stage success,
review findings, remediation cycles, human touches, latency and
throughput, token categories (including reasoning), estimated or
reconciled cost per PRD-051/053, declared subscription headroom,
local-resource consumption, failure/timeout rates, tool-use
reliability — each score bound to the exact spec version that earned
it. Reviewer independence is judged on provider and model lineage,
not runtime: Claude via the API is not an independent reviewer of
Claude via Claude Code.

## Accounting integration

Every PRD-051 observation carries the complete spec identity where
known (today's `provider/model` worker identity column widens to the
spec identity; degraded/unknown states stay explicit). Billing mode
binds per spec through its auth profile: the same nominal model under
a subscription-backed harness and under an API key are different
specs with different billing modes, so Claude Code subscription usage
never mixes with Anthropic API spend, Codex plan credits never mix
with OpenAI API dollars, hosted spend never mixes with local
inference, and two local artifacts never share one vague label. Price
and credit schedules (PRD-051/054) key on provider, runtime, model or
artifact, and billing mode.

## Configuration and migration

This extends PRD-047's single configuration system — providers stay
kind-tagged endpoint entries with auth descriptors; worker entries
gain the typed identity fields above plus an adapter-owned
`runtime_config` extension table validated closed. Migration is
deterministic: existing registry workers map `adapter` → runtime,
free-text `provider` → ProviderId, `model` → ModelId, enablement
capabilities → a capability profile; existing `provider/model`
addresses resolve as aliases only while each maps uniquely to one
migrated spec — the moment a second runtime shares the pair, the
alias is ambiguous and fails with a remediation message naming the
candidate specs, never silently preferring a harness or a raw-API
runtime; anything else ambiguous
fails validation naming the entry and the fix. Legacy `[agents]`
configurations keep their current fixed behavior (PRD-044's rule).
Compatibility shims cover only the existing Claude Code and Codex
workers; no raw-API conversation loop, xAI adapter, or local-runtime
adapter is implemented here — they become addable configuration plus
adapters later, with routing, accounting, project identity, and
execution state machines untouched.

PRDs whose `provider/model` language this eventually updates:
PRD-031/043 (registry addressing, done — historical record stands),
PRD-032 (scores by spec), PRD-044 (selection records), PRD-047
(enablement addressing), PRD-051 (observation worker identity —
cross-referenced now), PRD-053/054/055 (worker dimension naming), and
PRD-056 (MCP session worker scoping). Each is a wording alignment,
not a scope change.

## Security

Auth profiles are references under the PRD-047 BYO-Auth contract;
specs, selection rows, scores, and logs never carry credential
values. A spec with a missing or failed auth profile fails closed
with the operator remedy. Artifact identities are content hashes, so
a swapped local model cannot impersonate a scored one. Repository
content cannot declare or elevate workers outside the PRD-049
approval gate. Capability probes run with no credentials beyond what
the probe target requires and never execute repository content.

## Phasing

1. Identity types, capability vocabulary, and the configuration
   schema with deterministic migration and aliases.
2. Selection, persistence, and evidence carry spec identity;
   independence policy moves to lineage.
3. Capability provenance (declared/probed/observed/unknown) with safe
   probes wired into PRD-047 verification.
4. PRD-032 scoring and PRD-051 accounting bind to spec versions and
   partitions.

## Assumptions (recorded 2026-08-30)

- The registry's existing operator-chosen worker ids remain the
  primary human handle; the canonical spec identity is additive.
- `runtime-selected` model identity plus PRD-051's per-model
  observation rows is sufficient to account honestly for harnesses
  that choose their own models; no scraping of harness internals.
- The material-parameter lists are owned by runtime adapters and
  versioned with them; the initial lists cover the parameters named
  here and may grow without schema change.
