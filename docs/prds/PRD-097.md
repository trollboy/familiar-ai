# PRD-097: Delivery Is Forge-Agnostic

## Objective

Familiar's delivery path is written in GitHub's command grammar. The
executable is configurable; the language it speaks is not.

`DeliveryConfig::provider_argv` already lets an operator name any binary
(default `["gh"]`), which looks like an abstraction and is not one. Every
verb and flag after the executable is spelled inline in `delivery.rs`:

```rust
provider_argv(policy, &["pr", "create", "--fill", "--base", &policy.base,
                        "--head", &branch]);
provider_argv(policy, &["pr", "view", &branch, "--json", "number",
                        "--jq", ".number"]);
provider_argv(policy, &["pr", "checks", &pr.to_string(), "--watch",
                        "--fail-fast"]);
provider_argv(policy, &["pr", "check", &pr.to_string(), check]);
provider_argv(policy, &["pr", "merge", &pr.to_string(), "--merge",
                        "--delete-branch"]);
```

Pointing `provider_argv` at `glab` mostly works by coincidence — GitLab's CLI
deliberately mirrors `gh` — and then breaks on `--json number --jq .number`,
which is `gh`'s own output grammar. Pointing it at Gitea's `tea`, at a
Bitbucket or Gerrit client, or at nothing at all does not work in any degree.

Two further assumptions sit underneath the argv:

- **A change request is an integer.** `DeliveryJournal::pr_number` is
  `Option<u64>`, parsed out of `gh`'s JSON. Gerrit change ids, Phabricator
  revisions and GitLab's `!123` spelling do not survive
  `str::parse::<u64>()`.
- **A forge exists.** When no number is parsed, delivery fails outright:

  ```rust
  .ok_or_else(|| "provider adapter did not return a pull request number")?
  ```

  A repository that publishes by pushing a branch, by mailing a patch series,
  or by pushing straight to a trunk has no path through delivery at all. It
  cannot decline the pull request; it can only fail.

## Why this matters now

Familiar's pitch is an app-building autopilot for *a user's* projects, not for
this repository. The owner runs GitHub; a large share of target projects will
not. Every one of them currently hits a wall at the last step of the loop —
after implementation, review, verification and merge-queue work have all
succeeded. Failing at delivery is the most expensive place to fail, because
everything before it has already been paid for.

This is also cheap to fix relative to its blast radius: the seam already
exists (`provider_argv`), the call sites are five, and the repository already
has a closed-vocabulary provider-extension pattern to copy from
(`docs/contracts/providers-index.md` and its domain documents).

## Scope: forge, not version control

This PRD makes the **forge** pluggable — the thing that hosts change
requests, runs checks, and merges. It does **not** make the **version control
system** pluggable. Git stays assumed.

That boundary is deliberate, not an oversight. Familiar's concurrency model
is built on `git worktree`: parallel workers, worktree ownership records, the
merge queue, and scope authorization all address work by worktree path.
Supporting Mercurial, Jujutsu or Subversion means replacing that substrate,
which is a different and much larger piece of work. Naming it here so the
next reader does not mistake this PRD's title for that promise.

What does follow from this PRD, and should be a separate one if wanted:
`git push`, `git worktree`, and the `.git`/`.github` entries in
`onboarding.rs`'s protected-path list remain git-shaped.

## Relationship to PRD-095

PRD-095 (merged 2026-09-13, `833aa02`) declares *which identity* a
repository authors and publishes under. This PRD declares *which forge
grammar* delivery speaks. The concerns are orthogonal — who, versus what
language — but they land in the same two files
(`config/delivery.rs`, `delivery.rs`), and they meet at one point.

PRD-095's fourth criterion requires that publication "selects the declared
forge account explicitly for that invocation rather than relying on which
account is globally active". Selecting an account explicitly is itself
forge-specific grammar: `gh` spells it one way, `glab` another, and a
forge-less flow has no account to select.

PRD-095 landed first. So this PRD **must route account selection through
the adapter verb set defined here, not add a second GitHub-specific flag
beside it**: the `forge_account` preflight and the `gh`-shaped argv that
`delivery_identity.rs` records become adapter verbs, and PRD-095's tests
must still pass unmodified, exactly as the GitHub delivery tests must.

No dependency is declared in the frontmatter because PRD-095 is already
integrated; the constraint above is a compatibility requirement, not a
scheduling edge.

## Approach

1. **Define the verb set as a closed vocabulary**, in a new
   `docs/contracts/forge-adapters.md` linked from the providers index. The
   verbs the code actually needs today are: publish a change request, locate
   an existing one for a branch, wait on its checks, query one named check,
   merge it, and comment on it. That is the whole surface — it is small
   because delivery's needs are small.
2. **Declare the forge by identity, not by executable.** Delivery
   configuration names `forge = "github" | "gitlab" | "none" | …`, validated
   closed against the known set. An unknown identity fails validation rather
   than silently behaving like GitHub. `provider_argv` stays as the
   executable/prefix override so an operator can point at a wrapper or a
   pinned binary without redefining the grammar.
3. **Make the change-request identifier opaque.** Replace
   `pr_number: Option<u64>` with an adapter-supplied string identity plus the
   URL where available. Nothing in delivery does arithmetic on it; it is only
   ever passed back to the adapter and shown to a human.
4. **Make "no forge" a first-class adapter, not a failure.** `forge = "none"`
   pushes the branch and stops at a terminal phase naming the branch and the
   base, which is a *successful* outcome awaiting a human, in the same family
   as today's `ReviewedPrManual` stop at `awaiting_merge_authority`.
5. **Let an adapter decline a verb.** Not every forge can watch checks or
   merge programmatically. A declined verb must be a typed, journaled outcome
   that delivery handles — not an error, and not a silent skip that lets a
   mode claim an authority it never exercised.

## Compatibility

The GitHub path must not change behaviour. The `github` adapter reproduces
today's argv exactly, and the existing delivery tests are the proof: they run
unmodified against it. Any diff in the argv those tests observe is a
regression, not a migration.

`provider_argv` keeps working as an executable override. An existing
configuration that sets it and nothing else needs to keep delivering, so
`forge` defaults to `github` **for an existing configuration that already
names a provider** — but see the open question.

## Resolved (2026-09-22)

1. **Default for a fresh repository: `none`.** An existing configuration
   that already names a provider keeps `github`, so nobody's delivery
   breaks. A repository section written fresh defaults to `none`, which
   pushes the branch and stops at a terminal phase naming branch and base
   for a human to open the request. Honest, and it stops re-centring
   GitHub for every new project, which is what this PRD exists to do.
2. **Second adapter: `gitlab` plus `gitea`.** `gitlab` is the cheap proof
   because `glab` mirrors `gh`; `gitea` (`tea`) has a genuinely different
   grammar, so the abstraction is validated against something that is not
   a near-clone. Both ship with exact-argv tests per verb.

## Acceptance evidence

The decisive mechanical check is that `delivery.rs` no longer spells any
forge verb: `grep -n '"pr"' crates/familiar-ai-daemon/src/delivery.rs`
returns nothing. Adapter tests assert exact argv per verb, so a grammar
change is a visible diff rather than a runtime surprise. The `none` adapter
has a test that drives delivery end to end and asserts it reaches a terminal
success phase naming branch and base, with no pull request identifier and no
error.
