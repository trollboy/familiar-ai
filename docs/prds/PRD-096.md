# PRD-096: A Failing Required Check Is Work, Not a Wall

## Objective

When a required verification check fails, the coordinator stops before the
reviewer runs:

```rust
// coordinator.rs:303-313
if required_failed(&cycle.verification_before_review) {
    let reason = if /* … EnvironmentDenied … */ {
        ReviewStopReason::EnvironmentDenied
    } else {
        ReviewStopReason::VerificationUnsuccessful
    };
    return self.stop(cycle, reason);
}
```

Remediation is only ever invoked on findings a *review* produced. A review
never happens on this path, so the implementer is never asked to fix the
failing test.

The attended pause then offers `[r] retry remediation`, which calls
`resume_implemented_checkpoint`, which re-runs the same verification against
a byte-identical worktree, which fails identically, and returns to the same
prompt. That is the loop the owner sat in on PRD-63 with the implementation
provably unchanged between attempts. The only forward options were to accept
a known-bad landing or to stop.

This is logged as FAM-BUG-054.

## Why this one matters more than its size suggests

A red required test is the most common way work is unfinished, and it is
precisely the case the loop cannot act on. The system can remediate a
reviewer's *opinion* but not a compiler's or a test runner's *fact* — which
inverts the "Determinism Before Intelligence" principle the verification gate
exists to serve. The deterministic signal is the one it discards.

It also distorts every PRD that passes through the gate. PRD-081 shipped only
because its oracle tests were `#[ignore]`d, letting verification pass so that
review and remediation could run at all. That attribute was recorded as
housekeeping; it was load-bearing. A failing-by-design test — the entire
premise of the oracle pattern this repository uses deliberately — is not a
work item to this architecture. It is a wall, and the workaround is to hide
the failure from the gate. That is exactly backwards.

## What the code already gives us

This is mostly wiring, not new architecture, which is why it is worth doing
properly rather than papering over the pause:

- `RemediationRequest` already carries
  `verification_failures: Vec<VerificationEvidence>`. Every call site passes
  `vec![]`. The channel to the implementer exists and is unused.
- `VerificationEvidence` already carries everything a fix needs: `check_id`,
  `argv`, `exit_code`, `signal`, `status`, `summary`, and `stdout`/`stderr`
  as `EvidenceRef`s.
- The remediation loop already enforces `max_remediation_attempts`, reserves
  budget per attempt via `self.reserve(.., Action::Remediation)`, and
  re-verifies after the implementer returns.

So the work is to build a blocking finding out of a failing check, enter the
existing remediation loop with it, and keep every bound that loop already
applies.

## Approach

1. On `required_failed`, branch on the failure kind before stopping.
   `EnvironmentDenied` keeps stopping — a denied environment is not a code
   defect and the implementer cannot fix it. Every other required failure
   becomes work.
2. Synthesise one blocking `ReviewFinding` per failed required check. It
   needs a category; `CorrectnessDefect` is the honest existing fit for "a
   check the repository declared required came back red", and adding a
   `VerificationFailure` variant is the alternative if the distinction is
   worth carrying in the taxonomy. **This is the one open design question
   below.**
3. Populate `verification_failures` with the failing evidence so the
   implementer gets the captured output, not just a claim about it.
4. Enter the existing remediation loop. Do not add a separate one, and do not
   exempt this path from `max_remediation_attempts` or budget reservation: a
   red check must not buy unlimited attempts, or a deterministically-failing
   test becomes a spend loop instead of a wall.
5. When attempts are exhausted or the check stays red, stop with a reason
   that names the check, and make the attended pause stop offering `[r]` in
   states where it provably cannot help. `cli/run.rs` already warns when
   retries are exhausted and when a failure is deterministic; this turns the
   warning into a withheld option.

## Resolved: no new `FindingCategory` (2026-09-19)

**Does a failed required check deserve its own `FindingCategory`?** No — not
in this PRD. The synthesised finding uses `CorrectnessDefect`.

The reasoning is the one the question itself points at: a dedicated
`VerificationFailure` variant is a closed-vocabulary change touching
serialization, and vocabulary is a contract. Widening it is the irreversible
direction; reusing an existing variant is not. Nothing in the acceptance
criteria needs the distinction — the check id, exit status and captured
evidence all travel on the finding and in
`RemediationRequest::verification_failures`, so the origin is legible to any
consumer that looks, without minting a term every consumer must now handle.

Add `VerificationFailure` when a consumer demonstrably needs to branch on it,
as its own change, with the serialization migration that implies. Doing it
speculatively here would bake a contract change into a PRD whose subject is
routing, not taxonomy.

## Acceptance evidence

The regression drives a cycle whose required check fails with a reviewer that
panics if invoked, and asserts the implementer was handed the check id and
its captured failure. It fails against the current coordinator, which never
calls the implementer on this path at all.

Note the self-referential trap: this PRD's own test is a failing-by-design
scenario driven through the coordinator under test, not a failing check in
this repository's verification plan. It must not be `#[ignore]`d to get past
the gate — doing so would reproduce the exact pathology the PRD exists to
remove.
