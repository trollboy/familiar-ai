# PRD-029: Stable Prompt Prefixes and Cache Accounting

**Status:** Ready for implementation
**Date:** 2026-08-09
**Depends on:** PRD-006, PRD-007, PRD-014
**Architectural direction:** Context Is Precious; Determinism Before Intelligence; Memory Must Be Durable
**Delivery boundary:** Independently mergeable prompt-layout guarantee plus cache-hit measurement, changing no context selection and no authority

## Objective

Never send the same bytes twice at full price. The compiled prompt gains a **stability contract**: a byte-stable shared prefix holding everything invariant across attempts in a repository, with everything attempt-specific ordered strictly after it — so provider-side prompt caching prices repeated context as cached input. Cache effectiveness becomes a measured, reported number instead of an assumption.

The context compiler is already deterministic; this PRD makes that determinism *cacheable* and then proves what it earns.

## Motivation

Familiar's economy thesis is that caching beats compression, and it is untested. Meanwhile the workloads are cache-shaped in the extreme: a drive session over sibling PRDs recompiles near-identical reference context per attempt; remediation loops resend the same repository block within one attempt; the deterministic compiler guarantees the bytes are *reproducible*. What it does not guarantee is *layout*: nothing promises the invariant material forms an unbroken prefix, and one attempt-specific byte early in the prompt invalidates the provider cache for everything after it.

The adapters already report `cached_tokens`, storage already persists it, and pricing already carries a cached-input rate. The measurement plumbing exists end to end; nothing arranges the prompt to earn cache hits, and nothing reports the rate. This PRD is the caveman feature: arrange the bytes, then count them.

## Semantics

- **The prompt is two ordered blocks.** The *stable block* contains material invariant across attempts within one repository under one configuration: the invariant instruction preamble, repository identity, and the referenced documents, in the compiler's existing deterministic order. The *volatile block* contains everything attempt-specific: the PRD document, attempt identifiers, and per-run values. Every volatile byte orders strictly after every stable byte.
- **Prefix stability is a tested guarantee, not an emergent property.** Two compilations differing only in volatile inputs produce byte-identical stable blocks. A change to any referenced document, the configuration, or the repository legitimately changes the stable block — staleness is never tolerated to preserve a cache hit. Correctness owns the bytes; caching only owns their order.
- **Prompt content is unchanged.** The same documents are selected, budgeted (PRD-007 ceilings apply to the whole prompt exactly as today), and rendered — reordered, not rewritten. Where the current rendering already satisfies the layout, bytes are identical; where it does not, the change is ordering only.
- **Adapters pass caching through; they never fabricate it.** Adapter-level cache configuration (for providers requiring explicit cache markers) is operator configuration on the agent entry. An adapter that cannot cache reports what the provider reports, including nothing.
- **Cache economics are first-class and honest.** Each execution already records cached tokens; `usage` and the morning report additionally render the cached share of input and the cost delta implied by the configured cached-input price. Unknown remains unknown — a provider reporting no cache data renders as unmeasured, never as zero savings.

## Scope

This PRD includes:

1. The two-block prompt layout in execution-context rendering, with the stable block's composition documented and deterministic.
2. A prefix-stability test contract: byte-identity of the stable block across volatile-only changes, and legitimate invalidation on stable-input changes.
3. Adapter pass-through of provider cache configuration where the adapter supports it, defaulting to today's behavior.
4. Cached-share and implied-savings rendering in `usage` and the morning report, from already-persisted per-execution data.
5. Focused tests over temporary repositories and fake agents, including a drive session over sibling PRDs asserting an identical stable block across attempts.

## Non-goals

This PRD does not:

- change which documents are selected, budgeted, or excluded from context;
- introduce cross-attempt persistence of prompts, a local cache store, or the context-service daemon (that thesis is measured by this PRD, built by a later one);
- trade staleness for hit rate under any circumstance;
- add difficulty routing or model selection (PRD-019/PRD-028 territory);
- guarantee any provider-side hit rate — it guarantees the layout that makes hits possible and the measurement that reports them; or
- modify prior PRDs, architecture documents, ADRs, contracts, or philosophy.

## Behavior

A drive session executes `0177a` through `0177c` in one repository. Each attempt's prompt begins with the identical stable block — same bytes, same order — followed by that attempt's PRD and identifiers. The provider prices the repeated block as cached input from the second attempt on. The morning report ends:

```
CACHE
  input:      412k tokens, 61% cached
  implied saving: 118k input tokens at the cached rate
  unmeasured: 1 attempt(s) reported no cache data
```

Editing a referenced ADR between attempts changes the stable block, the next attempt misses cache, and the report simply shows a lower share. Nothing was served stale.

## Acceptance Criteria

1. Two compilations differing only in the PRD and attempt identifiers produce byte-identical stable blocks, proven at the bytes level over a temporary repository.
2. A change to a referenced document or to configuration changes the stable block — staleness is never preserved for cache advantage.
3. Every volatile byte orders after every stable byte, proven structurally rather than by sampling.
4. Where the existing rendering already satisfies the layout, prompt bytes are unchanged; the prompt-byte regression suites pass unchanged or their pinned bytes are updated with the reorder as the only delta.
5. PRD-007 budgeting applies to the complete prompt exactly as today, including when truncation falls inside either block.
6. A fake-agent drive over three sibling PRDs records one identical stable block across all attempts.
7. `usage` and the morning report render cached share and implied savings from persisted data, pinned byte-exact, with no-cache-data attempts rendered as unmeasured.
8. All tests use temporary repositories, databases, and fake agents; formatting, focused Clippy, focused tests, and the workspace suite pass, or demonstrably pre-existing failures are reported with exact evidence.
9. The change is confined to the expected files and is independently mergeable.

## Test Strategy

- Stability: byte-diff of stable blocks across volatile-only permutations; invalidation on each stable-input change.
- Structure: an assertion over the rendered layout that the stable/volatile boundary is a single position, not an interleaving.
- Budget interaction: ceilings binding across the block boundary, pinned against PRD-007's existing fixtures.
- Accounting: seeded executions with known cached-token values rendered in `usage` and the report, including the unmeasured case.
- Regression: existing prompt-byte and budgeting suites as the canary for unintended content change.

## Definition of Done

PRD-029 is done when the token miser stops being an aspiration and becomes a ledger line: every attempt's invariant context is a byte-stable prefix a provider can cache, every cached token is counted against the price it avoided, and the caching-beats-compression thesis has real numbers attached — earned without serving one stale byte.
