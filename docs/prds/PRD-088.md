# PRD-088: Load-Faithful Verification

## Status: draft, 1.x (2026-09-22)

Moved from `ready` to `draft` in the queue audit against the 1.0
definition, for four reasons that are each checkable:

- Its two motivating bugs are closed. FAM-BUG-047 was fixed 2026-09-03 and
  FAM-BUG-050, including the load-dependent SIGTERM layer, on 2026-09-21
  under the gate's own contended load. The reproduction mode is still a
  real capability; it no longer has a live case.
- Its third criterion, refusing a bug closure that cites the wrong
  evidence, duplicated PRD-098's third criterion. Struck here; PRD-098
  owns it.
- Its tiering criterion contradicted PRD-099's second criterion as
  written. Restated so tiers select a subset of the single definition's
  steps and never substitute one.
- It was written against the Docker `[[review.verification]]` gate.
  PRD-099's 2026-09-19 amendment made `scripts/gate.sh` and the `pre-push`
  hook the gate. `docker-compose.yml` in the expected files is now a
  secondary target, and `verification-gate.md` documents two paths that
  this PRD would have to reconcile before adding a third.

None of the 1.0 stops on the ledger are gate-load stops. This returns to
`ready` when a load-dependent failure is next observed in the gate, which
`scripts/gate.sh` now records by test name.

## Objective

Verification is heavy and load-sensitive, and the product has no way to
say so. A startup budget had to move from 5s to 30s because the test only
failed under the gate's own load. FAM-BUG-047 was closed wrongly first,
on sixteen standalone runs that could not reproduce a load-dependent
flake — sixteen runs of the wrong experiment. Two things are missing: a
way to reproduce a failure under the conditions that produced it, and any
differentiation in what a landing must pay for. Every landing runs the
full Docker gate regardless of what it touched, which makes the gate both
expensive and uniform, and uniform gates get skipped rather than tiered.

## Design

- **Reproduce under load, not beside it.** A reproduction mode runs a
  named test under the gate's concurrency and resource shape. This is the
  experiment that FAM-BUG-047 needed and did not have.
- **Load context travels with the result.** A failure record names the
  conditions. A standalone pass is then visibly not an answer to a gated
  failure, and a closure that cites one is refused rather than argued
  about.
- **Budgets are contextual by declaration.** A timeout that must differ
  under load says so, with both values and the reason. Silently raising a
  constant until the flake stops is how a load bug becomes folklore.
- **Tier above a floor.** Risk classes and touched surfaces select the
  checks above a required floor that nothing may drop below. Cheaper
  landings get cheaper gates without anything becoming optional.
- **Measure the gate.** Verification cost per landing becomes a number in
  the ledger, so arguments about gate weight cite data.

## Scope

The load-faithful reproduction mode; load context in verification records
and the closure rule that consumes it; per-context budget declarations
and the bare-constant check; risk-tiered gate selection above a required
floor with the tier recorded; per-landing gate cost recording;
regressions in a dedicated test file.

Out of scope: declared skips inside a required gate (PRD-089), the
preflight execution contract itself (PRD-078), review disposition
computation (PRD-067), and any change to which checks constitute the
required floor.

## Assumptions (recorded at specification time, 2026-09-04)

- The gate's load shape is reproducible locally in Docker with the
  compose definition the gate already uses; where a failure depends on
  host resources the gate cannot reproduce, the record says so rather
  than claiming reproduction.
- Tiering is a cost reduction, not a coverage reduction; if the required
  floor turns out to be nearly the whole suite, that is a finding to
  report, not a reason to lower the floor.
