# PRD-104: Cross-platform Tauri desktop UI

## Problem

Familiar does not currently have one graphical product across its supported
desktop platforms. Linux has substantial GTK windows inside the daemon
process. macOS has a native menu-bar icon, but Dashboard and configuration
actions leave the application and open browser pages. Earlier macOS builds
sent configuration actions to a text editor. These paths expose similar
concepts through different implementations, have already drifted, and make a
successful tray build look like successful UI parity when it is not.

AppKit cannot host GTK widgets. Continuing with GTK on Linux and a second
AppKit implementation on macOS would require every screen, state transition,
confirmation rule, accessibility fix, and regression to be implemented and
maintained twice. Opening the loopback dashboard in a browser avoids that
duplication, but it is not a desktop application and does not satisfy the
operator experience Familiar is intended to ship.

The replacement is a Tauri desktop shell used on both macOS and Linux. Tauri
uses each platform's system WebView, but the application owns the windows,
tray, lifecycle, capabilities, and native packaging. Familiar's daemon remains
the authority for state and mutations.

This PRD closes FAM-BUG-067. It does not reopen FAM-BUG-066's fixed build and
AppKit event-pump defects.

## Outcome

An installed Familiar system consists of two independently supervised
processes:

1. `familiar-ai-daemon` is headless and owns scheduling, persistence,
   inference, configuration mutation, credentials, and control-plane state.
2. `familiar-ai-desktop` owns the cat tray icon and all human-facing windows.
   It is a replaceable same-user client of the daemon, not a second authority.

The same desktop code and interaction model runs on macOS and Linux. Dashboard,
Settings, and Configure Local LLM are real application windows. No ordinary UI
path needs a browser, editor, terminal, or Docker.

## Non-goals

- Rewriting the daemon, scheduler, storage schema, inference router, CLI, MCP,
  or existing business rules in JavaScript.
- Giving the frontend direct database, filesystem, process, credential-store,
  or provider-network access.
- Making the existing loopback dashboard a public remote-management service.
- Windows support in this PRD. The architecture must not gratuitously prevent
  it, but only macOS and Linux are release gates.
- Restyling Familiar at the expense of behavioral parity. Visual refinement is
  welcome after every existing operator capability has an explicit home.
- Keeping GTK as a permanent second frontend. It is a migration scaffold, not
  an alternate product that must continue to evolve.

## Architecture

### Process boundary

The current tray-enabled daemon couples a long-running Tokio runtime to a GUI
event loop on the main thread. That coupling is removed. The production daemon
build is headless on every platform. The desktop app can be restarted or
upgraded without interrupting active drives, reviews, inference, or durable
history.

The desktop is single-instance per user. A second launch sends an
`activate(window, optional repository)` request to the first instance and
exits successfully. Opening an already-open Dashboard, Settings, or Local LLM
window focuses it and refreshes its snapshot; it never creates an unbounded
set of duplicate WebViews.

### Shared operator contract

The semantic contract now represented by `familiar-ai-tray::data::{Query,
Action}` moves to a UI-neutral shared module. Every query and action has:

- a stable serialized name and version;
- typed request and response data rather than unvalidated JSON blobs at the
  frontend boundary;
- explicit capability and authorization requirements;
- a bounded response shape and pagination rule where applicable;
- a documented idempotency rule for mutations;
- a user-safe error code plus diagnostic detail retained only in Rust logs.

The daemon serves this contract over the existing local-transport trust
boundary or a dedicated sibling socket with the same guarantees: owner-only
permissions, same-user peer verification, mandatory version negotiation,
bounded frames, timeouts, and explicit stale-owner recovery. The UI protocol
must not weaken or overload model-facing control-plane permissions.

Tauri commands are a narrow Rust adapter over that client. JavaScript may ask
for declared snapshots and actions only. It cannot submit arbitrary SQL,
paths, TOML keys, shell commands, URLs, or control-plane payloads.

### State synchronization

Each window loads a revisioned snapshot and then subscribes to ordered,
bounded events. Events are hints to reconcile, not an independent source of
truth. A missed sequence, lagged receiver, daemon restart, protocol mismatch,
or reconnect causes a fresh snapshot. The interface shows `Disconnected`,
`Reconnecting`, and `Incompatible daemon` as distinct states and never
silently presents stale controls as live.

Polling is permitted only as a bounded fallback when the daemon cannot emit an
event yet. Network/provider probes run asynchronously and are cancellable;
they never block the Tauri or WebView event loop.

### Security boundary

Bundled frontend assets are application presentation, not trusted authority.
The release configuration uses a restrictive CSP, no remote scripts, no
arbitrary navigation, no generic shell/open plugin, and the smallest Tauri
capability allowlist that supports the declared commands. The OS may open a
small allowlist of documentation links only after an explicit user action and
Rust-side URL validation.

Credentials remain opaque descriptors resolved by daemon-side credential
stores at use time. Provider discovery and connection tests return identity,
capability, health, latency, and sanitized errors—never tokens, authorization
headers, environment values, or credential-store contents.

## Required screens and behavior

### Dashboard

The Dashboard shows daemon connection/generation, Familiar version, repository
state, active work, recent sessions and executions, unresolved gates, budget
state, and inference health. Every status includes text and an accessible
label. Links into a repository, PRD, session, attempt, execution, or gate open
the relevant in-app detail view.

### Backlog and recovery

The backlog displays status, dependencies, unmet prerequisites, current
checkpoint, blocked reason, and retained-work location without implying that
`in_progress` means a worker is still running. Start and Resume are offered
only when daemon capabilities say the operation is legal. Cancel, Release,
and Force Complete retain their present warnings, actor/reason requirements,
and durable attribution. A transport retry cannot repeat a mutation: the
desktop supplies a stable idempotency key for the user's one confirmed action.

### Settings

Settings is a schema- and capability-driven form over the real configuration,
not a raw TOML editor. It supports all editable fields currently exposed by
the GTK settings window, preserves unknown/unmodified configuration, validates
the complete proposed document before atomic replacement, creates a backup,
and reports errors beside the responsible field. Restart-required changes are
identified before save; runtime-safe changes are applied immediately.

### Configure Local LLM

The Local LLM screen works when Familiar has never been configured. It can
select inference mode, discover available providers and models (including any
OpenAI-compatible local provider such as Ollama or Unsloth when configured),
test the selected endpoint, save the choice, and show the router's applied
state. Provider identity comes from the daemon registry and discovery result;
the frontend must not contain a vendor-only switch statement.

## Tray and lifecycle semantics

The cat icon and menu are owned by `familiar-ai-desktop`. Menu items reflect
the latest daemon snapshot and remain useful while disconnected: window items
still open, while daemon mutations are disabled with an explanation.

`Quit Desktop` closes the UI only. `Stop Familiar` is separate, confirmed,
and asks the daemon to perform its bounded graceful shutdown. Closing the last
window follows the platform convention and does not implicitly stop active
work. Autostart definitions launch the daemon and desktop independently and
do not create restart storms when either is intentionally stopped.

## Migration sequence

1. Extract and version the operator query/action contract without changing
   current GTK behavior. Pin the inventory and response bounds in tests.
2. Add the daemon-side transport endpoint and prove same-user access,
   negotiation, idempotency, event ordering, reconnection, and denial cases.
3. Add the Tauri shell, singleton tray/windows, locked-down capabilities, and
   disconnected state.
4. Implement every row of the parity inventory and run behavior-level tests
   against the same daemon fixtures used by the existing GTK surface.
5. Build and smoke the packaged application on both macOS and Linux. The smoke
   test must click tray routes into application windows and exercise at least
   one safe query and a reversible configuration mutation.
6. Switch installed/autostart defaults to the desktop process, make the daemon
   uniformly headless, remove GTK windows and dependencies, and rerun the full
   gates from a fresh install.

Steps 1–5 may land incrementally behind a development-only opt-in. Step 6 may
not land until all parity and platform gates are green. A partially implemented
Tauri frontend must never become the operator default.

## Parity inventory

Implementation maintains a checked-in, test-consumed inventory mapping every
shared query and action to its desktop route/control and regression. The
minimum inventory is:

| Area | Reads | Mutations |
|---|---|---|
| Inference | status, choices, discovery, effective settings | test, save, live reload |
| Repositories | repositories, project state | pause, resume |
| Backlog | PRDs, text, dependencies, checkpoints, blocked reasons | start, resume, release, force-complete |
| Execution | executions, sessions, attempts, rounds | cancel |
| Governance | gates, review, budget | existing adjudication/navigation actions |
| Configuration | complete editable document and validation metadata | atomic save |

Adding a future shared query or action without adding a desktop mapping must
fail a test. This prevents Linux/macOS parity from silently decaying after the
migration.

## Packaging and platform gates

The workspace pins Rust and frontend dependencies in normal lockfiles. The
desktop has one documented build command and one install command per supported
platform. macOS output is an `.app` bundle with icon, bundle identifier,
version, minimum OS, hardened-runtime/signing hooks, and no GTK linkage. Linux
output declares its WebKitGTK/system-tray runtime packages and produces the
repository's selected desktop formats; it must not pull AppKit dependencies.

Docker may be used by CI maintainers as an optional Linux test host, but no
developer build, production install, launch, or feature requires Docker. A
real Linux graphical smoke gate—not merely cross-compilation—remains required
before GTK removal.

## Verification plan

- Shared-contract unit tests enumerate every query/action, serialization name,
  permission, bound, warning, and attribution requirement.
- Daemon transport tests cover peer identity, protocol mismatch, oversized and
  malformed frames, unauthorized commands, idempotent replay, pagination,
  event gaps, reconnect, and daemon generation changes.
- Tauri Rust tests cover command validation, window singleton/focus behavior,
  URL denial, redaction, menu routing, and disconnected operation.
- Frontend tests cover every parity row, keyboard operation, dialog cancel and
  confirm, validation display, loading/error/empty states, stale-event refresh,
  scaling, and non-color status cues.
- Lifecycle integration tests prove the daemon survives desktop exit/crash and
  active work survives desktop upgrade; the desktop survives a daemon restart
  and reconnects to the new generation.
- Packaged macOS and Linux smoke tests start from an empty user-data directory,
  present the cat tray icon, open all three primary windows without a browser,
  configure a harmless fake local provider, restart both processes in each
  order, and cleanly uninstall without deleting durable Familiar history.
- Repository gates run from a clean checkout and include format, strict lint,
  workspace tests, dependency-boundary assertions, CSP/capability audit, fresh
  packaging, and `git diff --check`.

## Rollout and rollback

Before the default flip, Tauri is an explicit development preview and GTK is
unchanged. At the flip, installers and supervisors start the headless daemon
plus Tauri desktop. The release notes identify the last GTK-capable release as
the binary rollback; durable storage and config formats are unchanged, so
rolling back does not require data migration.

If either platform smoke gate fails, the default does not flip and GTK is not
removed. Browser or editor fallback is not accepted as evidence that a failed
desktop gate passed.

## Completion evidence

The implementation report records the commit and exact results for:

- clean workspace build and test gates;
- macOS packaged-app launch, tray, window, configuration, reconnect, and
  independent-lifecycle smoke;
- Linux packaged-app launch, tray, window, configuration, reconnect, and
  independent-lifecycle smoke;
- dependency inspection proving macOS has no GTK and the final Linux desktop
  no longer links the retired GTK window stack;
- capability/CSP audit proving the WebView has only the declared command
  surface;
- a fresh install with no browser/editor fallback and no Docker dependency.

PRD-104 is complete only when the cross-platform desktop is the shipped
default and the old split UI is gone—not when a Tauri skeleton happens to
compile.
