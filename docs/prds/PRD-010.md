# PRD-010: Historical Backlog Bootstrap

## Objective

Bootstrap historical backlog state so a repository adopting the deterministic backlog manager can explicitly classify already implemented and merged PRDs as `completed` without manually transitioning each one and without using an LLM.

The bootstrap is driven by a version-controlled manifest containing exact repository-relative PRD paths and content hashes. On the first eligible `familiar next`, Familiar validates the complete manifest and applies one all-or-nothing, durable bootstrap run before selecting the next PRD. Every classification is attributable to the manifest and retained as an auditable status transition.

The process must be deterministic, idempotent, explicitly auditable, safely reversible, and independently mergeable. It does not infer completion, execute work, generate PRDs, or weaken the PRD-009 eligibility and ordering rules.

## Motivation

PRD-009 correctly initializes every newly discovered active PRD as `pending`. That is safe for a new repository, but it creates an adoption gap for a mature repository: historical implementation PRDs remain in `docs/prds/` even though their changes were already reviewed and merged. The first `familiar next` therefore selects the oldest historical PRD rather than the first unimplemented one.

Automatically treating all lower-numbered PRDs, all old files, all files mentioned in Git history, or all PRDs whose described files exist as complete would be inference. Those signals cannot prove that acceptance criteria were met, and their meaning varies by repository. Moving files into `done/` would also modify the repository's established documentation layout and would conflict with PRD-009's active discovery boundary.

A checked-in bootstrap manifest makes the repository maintainer's historical classification explicit. Exact content hashes bind that classification to the reviewed PRD bytes. Familiar can then validate and persist the declaration mechanically, provide a durable audit trail, and refuse ambiguous or stale input.

## Scope

This PRD includes:

1. A repository-owned historical bootstrap manifest at `.familiar/backlog-bootstrap.toml`.
2. A strict, deterministic manifest parser and canonical manifest hash.
3. Eligibility rules that permit exactly one successful bootstrap lineage per repository and prevent overwriting active backlog work.
4. Automatic bootstrap evaluation during `familiar next`, after PRD discovery and graph validation but before normal selection.
5. One transactional operation that changes only manifest-listed, eligible `pending` PRDs to `completed`.
6. Durable bootstrap-run and per-item evidence records linked to PRD-009 status events.
7. Deterministic behavior when the manifest is absent, already applied, stale, invalid, or ineligible.
8. An explicit, guarded rollback operation exposed through `familiar backlog bootstrap rollback <run-id>`.
9. A read-only inspection command, `familiar backlog bootstrap status`, for auditability and operational diagnosis.
10. Additive SQLite migration, focused domain and storage boundaries, stable CLI behavior, and comprehensive tests requiring no model or agent.
11. A repository manifest that classifies the historical implementation PRDs completed before PRD-010 while leaving PRD-010 and later PRDs pending.

### Separation of responsibilities

The bootstrap domain service owns manifest validation, eligibility, deterministic item ordering, apply and rollback preconditions, result classification, and audit values. It depends on neutral discovery and storage interfaces and contains no TOML library, SQL, Clap, LLM, agent, or execution code.

The manifest adapter owns exact bytes, strict TOML decoding, path validation, content hashing, and conversion into neutral bootstrap types. It does not decide whether a PRD is complete.

The backlog storage adapter owns transactions, optimistic status checks, bootstrap-run records, item evidence, status events, and rollback linkage. It does not infer manifest contents or select the next PRD.

The CLI adapter composes existing PRD-009 discovery with bootstrap and selection. It renders stable results and errors but contains no eligibility, apply, rollback, or ordering policy.

## Non-goals

This PRD does not:

- change PRD-009 or reinterpret any of its discovery, status, dependency, or ordering contracts;
- use an LLM, coding agent, embedding, heuristic classifier, or model-generated evidence;
- infer completion from PRD number, filename age, file location, Git commit messages, branches, tags, merge topology, source files, tests, execution history, review history, prose, or acceptance-criteria wording;
- claim that a manifest-listed PRD was verified by Familiar at bootstrap time;
- mark every discovered PRD completed or use a numeric cutoff such as “all PRDs before 10”;
- classify `docs/prds/done/` or other files outside PRD-009 active discovery;
- modify, move, rename, generate, or delete a PRD;
- bootstrap `pending`, `in_progress`, or `blocked` as target states; bootstrap has the single target status `completed`;
- overwrite explicit user status, resolve a blocked PRD, complete in-progress work, or repair missing history;
- automatically execute the selected PRD or change `familiar run`;
- add general status-management, task lifecycle, scheduling, daemon, MCP, dashboard, tray, HTTP, or background-worker behavior;
- accept a remote manifest, command-line path, environment-provided manifest, wildcard, range, or generated manifest;
- silently update stale content hashes; or
- remove audit records or reverse later legitimate status changes.

## Bootstrap Manifest

The only authoritative bootstrap declaration is the regular, non-symlink file at:

```text
.familiar/backlog-bootstrap.toml
```

The file must be valid UTF-8 and use this closed schema:

```toml
version = 1

[[completed]]
path = "docs/prds/PRD-001.md"
sha256 = "<64 lowercase hexadecimal characters>"

[[completed]]
path = "docs/prds/PRD-002.md"
sha256 = "<64 lowercase hexadecimal characters>"
```

Unknown top-level keys, unknown item keys, duplicate keys, unsupported versions, an empty `completed` array, and non-string field values are errors. Each item contains exactly `path` and `sha256`.

`path` must be the exact canonical repository-relative path of a PRD currently discovered by PRD-009. Absolute paths, `.` or `..` components, backslashes, noncanonical separators, normalization aliases, symlinks, directories, and paths outside `docs/prds/PRD-<digits>.md` are invalid. Two entries may not refer to the same path or normalized PRD identity.

`sha256` is the lowercase SHA-256 digest of the exact current PRD bytes. Familiar computes the discovered content hash independently and requires equality. Hash mismatch is a stale manifest error; it is never accepted based on semantic similarity.

Array order has no policy meaning. Familiar sorts validated entries using PRD-009's numeric PRD number and canonical path byte ordering before hashing, storing, applying, reporting, or rolling back them.

The canonical manifest hash is SHA-256 over a versioned, length-delimited binary encoding of:

1. the schema version as an unsigned big-endian integer; and
2. each sorted item as the UTF-8 path length and bytes followed by the 32 decoded digest bytes.

Raw TOML formatting, comments, newline style, and item order therefore do not alter bootstrap identity. The raw file SHA-256 is also stored for provenance, but canonical manifest identity controls idempotency.

The repository manifest delivered with this PRD must enumerate only PRDs that maintainers explicitly assert were implemented and merged before PRD-010. It must list each exact path and implementation-time content hash individually. PRD-010 must not list itself.

## Eligibility

A repository is eligible to apply a manifest only when all of the following are true in one consistent discovery and storage snapshot:

1. The bootstrap manifest exists and passes strict schema, path, identity, and hash validation.
2. PRD-009 discovery and dependency-graph validation succeed for the entire active backlog.
3. No successful, rolled-back, applying, failed, or interrupted bootstrap run exists for the repository, except as permitted by the explicit reapply rule below.
4. Every manifest item resolves to exactly one currently discovered PRD at the exact listed path.
5. Every manifest item's discovered content hash equals the listed hash.
6. Every manifest item currently has status `pending`.
7. No manifest item has any prior PRD-009 status event.
8. No manifest item is marked missing.
9. Every explicit dependency of a manifest item is also listed earlier in the sorted manifest set or is already `completed` with non-bootstrap audit evidence.
10. Applying the set would not alter any non-listed PRD status.

Rule 9 ensures the completed historical set is dependency-closed relative to currently incomplete backlog state. “Earlier” means PRD-009 deterministic order, not source array order. A listed PRD depending on another listed PRD is valid even though both begin `pending`; the transaction applies them in sorted order.

An existing explicit status or event makes an item ineligible even when its current value is `pending`. Bootstrap is for untouched adoption state, not a bulk override mechanism. An existing `completed` item is not silently absorbed into the new run; maintainers must remove it from the manifest or address the state explicitly outside bootstrap.

The only permitted reapplication follows a successful rollback of the same canonical manifest hash. Reapply is allowed only when every rollback item remains at the exact restored status, no later item event exists, PRD bytes and manifest identity still match, and no different bootstrap lineage exists. Reapplication creates a new run linked to the rolled-back run; it never reopens or edits the old run.

## Bootstrap Trigger

Bootstrap evaluation is part of `familiar next` and occurs in this order:

1. Resolve the repository and database using PRD-009 behavior.
2. Discover and fully validate the active PRD backlog.
3. Reconcile newly discovered PRDs as `pending` using PRD-009 persistence.
4. Check for `.familiar/backlog-bootstrap.toml` without following a symlink.
5. If the manifest is absent, record nothing and continue normal PRD-009 selection unchanged.
6. If the manifest is present and the canonical manifest hash already has a successful, non-rolled-back run, verify that the run is internally complete and continue selection without writing anything.
7. If the manifest is present and no run exists, validate every eligibility rule and apply the complete bootstrap transaction.
8. Load the post-bootstrap status snapshot and run the unchanged PRD-009 eligibility and ordering algorithm.

The first eligible `familiar next` therefore bootstraps historical items and selects the first remaining eligible pending PRD in one invocation. Its success stdout remains exactly the PRD-009 selected-PRD line. Bootstrap diagnostics must not pollute stdout. A successful new bootstrap may emit one concise stderr informational line containing the run ID, item count, and canonical manifest hash; tests must pin its exact format. Subsequent calls emit no bootstrap line.

A present but invalid, stale, or ineligible manifest is a hard failure. `familiar next` must not ignore it and select from unbootstrapped state. Absence is the only silent no-bootstrap case.

`familiar backlog bootstrap status` never applies or rolls back state. It reports `absent`, `eligible`, `applied`, `rolled_back`, `ineligible`, `failed`, or `interrupted`, plus the repository key, run ID when present, canonical manifest hash when available, and deterministic item counts. It exits non-zero for malformed storage or manifest data, but `ineligible` is a valid inspected state and exits zero.

## Invariants

1. Repository files and the explicit manifest are authoritative inputs; database state is durable workflow state and never substitutes for missing source evidence.
2. Bootstrap has exactly one automatic effect: eligible listed PRDs transition from `pending` to `completed`.
3. Every changed status has exactly one ordinary backlog status event and exactly one bootstrap item record in the same transaction.
4. Every bootstrap item records the exact path, normalized PRD identity, listed content hash, observed content hash, old status, new status, status-event ID, and deterministic ordinal.
5. A successful run accounts for every manifest item exactly once; partial success is impossible.
6. Non-listed PRDs, missing historical rows, execution history, and review history are never changed.
7. No existing status event is deleted, rewritten, renumbered, or relabeled as bootstrap evidence.
8. No timestamp, row ID, filesystem order, TOML order, locale, Git state, or process timing affects classification or item order.
9. Repeating `familiar next` after success creates no run, item, or status-event duplicates and performs no status writes.
10. Manifest changes after a successful non-rolled-back run never extend, replace, or partially reapply the run. They fail with `BootstrapManifestChanged` until the discrepancy is explicitly resolved.
11. A crash before transaction commit leaves no applied status, terminal run, item, or event. Recovery never guesses that an uncommitted operation succeeded.
12. Neither apply nor rollback invokes an LLM, agent, prompt renderer, execution coordinator, or review coordinator.
13. A bootstrap completion classification means “declared historical completion by this exact manifest,” not “verified now,” “accepted by an agent,” or “proven by Git.”

## Data Model and Auditability

Add durable records equivalent to:

```text
backlog_bootstrap_runs
  run_id                    TEXT PRIMARY KEY
  repository_key            TEXT NOT NULL
  canonical_manifest_hash   TEXT NOT NULL
  raw_manifest_hash         TEXT NOT NULL
  manifest_path             TEXT NOT NULL
  manifest_version          INTEGER NOT NULL
  status                    TEXT NOT NULL
  item_count                INTEGER NOT NULL
  applied_at                TEXT NULL
  rolled_back_at            TEXT NULL
  rollback_run_id           TEXT NULL
  reapplies_run_id          TEXT NULL
  created_at                TEXT NOT NULL
  updated_at                TEXT NOT NULL

backlog_bootstrap_items
  run_id                    TEXT NOT NULL
  ordinal                   INTEGER NOT NULL
  repository_key            TEXT NOT NULL
  prd_path                  TEXT NOT NULL
  prd_number                INTEGER NOT NULL
  declared_content_hash     TEXT NOT NULL
  observed_content_hash     TEXT NOT NULL
  old_status                TEXT NOT NULL
  new_status                TEXT NOT NULL
  status_event_id           INTEGER NOT NULL
  PRIMARY KEY (run_id, ordinal)
  UNIQUE (run_id, prd_path)

backlog_bootstrap_rollbacks
  rollback_run_id           TEXT PRIMARY KEY
  bootstrap_run_id          TEXT NOT NULL
  repository_key            TEXT NOT NULL
  actor                     TEXT NOT NULL
  reason                    TEXT NOT NULL
  item_count                INTEGER NOT NULL
  created_at                TEXT NOT NULL
  completed_at              TEXT NOT NULL

backlog_bootstrap_rollback_items
  rollback_run_id           TEXT NOT NULL
  ordinal                   INTEGER NOT NULL
  prd_path                  TEXT NOT NULL
  old_status                TEXT NOT NULL
  restored_status           TEXT NOT NULL
  status_event_id           INTEGER NOT NULL
  PRIMARY KEY (rollback_run_id, ordinal)
```

Exact SQL names may follow repository conventions, but the semantics, foreign keys, closed status constraints, and uniqueness guarantees are required. Successful automatic application may insert a terminal `applied` run directly in the same transaction; it must not persist a misleading `applying` record before the atomic status transaction. `failed` and `interrupted` are reserved for recovery of implementations that introduce an explicit preflight journal; such a journal must never imply that item statuses committed.

Bootstrap status events use the stable actor `system:historical-backlog-bootstrap` and carry their link through the item table. Rollback events use the human-supplied actor from the rollback command. Run IDs are opaque unique identifiers and do not determine ordering or idempotency.

The status command must reconstruct and validate a run from stored items and linked status events. Missing items, count mismatch, duplicate ordinal/path, wrong old/new status, missing or mismatched event, manifest-hash conflict, or rollback-link inconsistency is audit corruption and blocks `next`.

Timestamps are UTC RFC 3339 audit observations. They are not classification inputs. Diagnostics and status output order runs by created timestamp and run ID only for presentation; classification remains keyed by repository and manifest lineage.

## Migration Strategy

Add one forward-only migration after the PRD-009 backlog migration. The migration creates bootstrap run, item, rollback, and rollback-item tables plus required indexes and foreign keys. It does not add bootstrap rows, change any backlog status, inspect the filesystem, or assume this repository's PRD numbers.

Repository-specific historical classification is data in `.familiar/backlog-bootstrap.toml`, never SQL seed data. This keeps the database migration reusable across projects and keeps the declaration reviewable in version control.

The migration must:

- run transactionally through the existing migration runner;
- be idempotent through schema version recording;
- upgrade fresh and exact post-PRD-009 databases;
- preserve all backlog PRD rows, status events, execution history, review history, and earlier data byte-for-byte;
- enforce repository-scoped references and item/event linkage;
- create no audit history until an eligible manifest is actually applied; and
- require no LLM, Git network access, or agent executable.

Code rollback may leave the additive tables unread by an older binary but must not require dropping them. Reinstalling the bootstrap-aware binary must recover the exact audit state. Destructive down migrations are outside scope.

## Apply Algorithm

After filesystem parsing and graph validation complete outside the write transaction:

1. Canonicalize and sort manifest items.
2. Compute the raw and canonical manifest hashes.
3. Begin one immediate SQLite transaction using the repository key.
4. Re-read the discovered backlog snapshot and existing bootstrap lineage inside the transaction.
5. Revalidate every eligibility rule and exact expected `pending` status.
6. Create one run ID independent of selection order.
7. For each sorted item, update `pending` to `completed` with an affected-row count of exactly one, append the PRD-009 status event, and append its linked bootstrap item.
8. Insert the terminal applied run with exact item count and hashes, or insert it before items with deferred constraints; either approach must remain invisible unless the whole transaction commits.
9. Validate item count, status-event linkage, and resulting statuses.
10. Commit.
11. Reload the post-bootstrap snapshot and invoke normal PRD-009 selection.

Any error rolls back every write. The implementation must not retry automatically after a storage conflict. A later invocation may retry from the unchanged pre-bootstrap state.

## Rollback Behavior

Rollback is explicit and never triggered by `next`, manifest removal, manifest edits, code rollback, or a failed selection:

```text
familiar backlog bootstrap rollback <run-id> --reason <non-empty-text>
```

The command resolves the current repository, requires an exact applied run belonging to that repository, records the invoking human identity using the existing local CLI actor convention or an explicit required `--actor` if no convention exists, and requires a non-empty reason. It prints a stable rollback run ID and restored item count only after commit.

Rollback is eligible only when:

- the target run is applied and has not been rolled back;
- its stored run, item, and event audit graph is internally valid;
- every target PRD still exists at the same path with the same content hash;
- every target currently has status `completed`;
- for each target, the bootstrap status event is its latest status event; and
- no dependent PRD outside the bootstrap set is currently `in_progress` or `completed` while depending directly or transitively on a target.

Rollback restores each item to its recorded old status, which is necessarily `pending` in this PRD. It processes reverse deterministic item order, appends ordinary status events, and writes one rollback record and one rollback item per restored PRD in the same transaction. It never deletes or edits the original run, items, or events. The applied run gains an immutable linkage to the rollback record and is presented as `rolled_back`.

If any guard fails, rollback changes nothing and reports every conflicting PRD or event in deterministic order. There is no force flag. Resolving later state requires normal authorized status operations, not destructive audit rewriting.

Rollback of the database schema or manifest file is not status rollback. Removing the manifest after application does not restore statuses and causes audit status to report the applied run with manifest absent.

## Failure Cases

Typed failures must cover at least:

- unreadable, non-UTF-8, non-regular, or symlinked manifest;
- invalid TOML, unknown or duplicate keys, unsupported version, or empty item set;
- invalid, duplicate, noncanonical, missing, or non-active PRD path;
- invalid SHA-256 syntax or content-hash mismatch;
- duplicate normalized PRD identity;
- PRD-009 discovery, metadata, dependency, or cycle failure;
- a manifest set that is not dependency-closed;
- target status other than `pending`;
- any prior status event on a target;
- missing or stale target row inside the transaction;
- prior bootstrap lineage, changed manifest after apply, or disallowed reapply;
- database open, migration, constraint, transaction, or optimistic-write failure;
- run/item/event count or linkage corruption;
- rollback run not found, wrong repository, already rolled back, or not applied;
- empty rollback actor or reason;
- changed or missing PRD during rollback;
- later status events or current status incompatible with rollback;
- active or completed dependent that makes rollback unsafe; and
- post-bootstrap absence of any eligible PRD under unchanged PRD-009 rules.

Manifest parse and validation errors are collected and reported in sorted PRD path order. Storage conflicts and rollback blockers are also reported deterministically. Error messages distinguish `manifest_invalid`, `manifest_stale`, `bootstrap_ineligible`, `bootstrap_conflict`, `audit_corrupt`, `rollback_ineligible`, and ordinary PRD-009 selection failures.

A bootstrap may commit successfully even if subsequent normal selection returns `NoEligiblePrd`; the command must report that bootstrap applied and then return the selection failure. This is not a partial bootstrap failure because historical classification and next-item availability are separate facts. Repeating the command must observe the applied run idempotently.

No failure falls back to inferred completion, partial application, manifest rewriting, event deletion, automatic rollback, LLM judgment, or execution.

## Acceptance Criteria

1. Historical completion is sourced only from the checked-in `.familiar/backlog-bootstrap.toml` manifest with exact active PRD paths and SHA-256 hashes.
2. Manifest parsing is strict, deterministic, rejects unknown or ambiguous input, and canonical identity is independent of TOML formatting and item order.
3. A missing manifest preserves PRD-009 behavior exactly and creates no bootstrap audit rows.
4. On the first eligible `familiar next`, every listed untouched `pending` PRD becomes `completed` atomically before normal selection.
5. PRDs not listed in the manifest retain their exact statuses, and PRD-010 is not classified completed by its own bootstrap.
6. Every changed PRD has one linked status event and bootstrap item containing exact declared and observed hashes, old/new statuses, path, ID, and deterministic ordinal.
7. A successful run stores canonical and raw manifest hashes, version, item count, repository identity, timestamps, and complete item/event linkage.
8. Repeated `familiar next` calls with unchanged state create no additional run, item, event, or status write and return the same PRD selected by PRD-009 ordering.
9. Hash mismatch, invalid manifest, ineligible status, prior target event, non-closed dependencies, or audit corruption blocks bootstrap without changing any status.
10. A changed manifest after successful application cannot silently add, remove, or reclassify PRDs.
11. The only supported reapply follows a valid explicit rollback of the identical canonical manifest and creates a separately linked run.
12. `familiar backlog bootstrap status` is read-only and exposes absent, eligible, applied, rolled-back, ineligible, failed, interrupted, and corrupt conditions deterministically.
13. Explicit rollback restores all target PRDs to their recorded prior statuses in one transaction, appends rollback evidence, and preserves the original audit trail.
14. Rollback refuses changed files, later status events, mismatched current statuses, wrong repositories, repeated rollback, or active/completed dependents without partial change.
15. Schema migration is additive and idempotent, seeds no repository-specific state, and preserves all preexisting data.
16. Bootstrap application, inspection, rollback, and reapply never invoke an LLM, coding agent, prompt renderer, execution path, or review path.
17. Existing `familiar next` selection, dependency eligibility, deterministic ordering, and success-line format remain unchanged after bootstrap evaluation.
18. Existing `run`, `history`, and `usage` behavior remains unchanged.
19. The repository manifest explicitly enumerates the historical PRDs completed before PRD-010 and passes exact hash validation in a clean checkout.
20. No PRD, architecture document, ADR, contract, philosophy document, daemon service, MCP surface, dashboard, tray, watcher, or model subsystem is modified.

## Test Strategy

### Manifest and domain unit tests

- Parse the exact schema and reject unknown keys, duplicate keys, missing fields, unsupported versions, empty arrays, invalid UTF-8, invalid paths, symlinks, invalid hashes, duplicate paths, and normalized duplicate identities.
- Shuffle TOML item order, comments, whitespace, and newline style and assert identical canonical manifest hash and sorted items while raw hashes may differ.
- Change one path or one digest byte and assert a different canonical hash.
- Verify exact-byte PRD hashing, including BOM and newline differences.
- Exercise every eligibility rule with in-memory discovery and store fakes.
- Assert dependency-closed sets, pre-completed dependencies with explicit evidence, and invalid incomplete dependency sets.
- Assert apply order is PRD-009 numeric/path order regardless of manifest, filesystem, or store order.

### Apply and idempotency tests

- Start from an exact PRD-009 database with newly reconciled pending rows, apply a valid manifest, and assert all-and-only listed statuses and exact linked audit records.
- Invoke bootstrap repeatedly and concurrently; assert one successful lineage, no duplicate events, and deterministic conflict handling.
- Inject failure before each write and commit boundary and assert either no bootstrap effects or one complete committed run, never a partial set.
- Apply successfully and then make normal selection fail; assert the run remains valid and retry is read-only.
- Assert manifest absence writes nothing and preserves byte-for-byte PRD-009 command output.
- Assert manifest edits after apply fail rather than extending the run.
- Roll back and reapply the identical manifest; assert distinct linked run IDs and preserved prior history.

### Storage and migration tests

- Upgrade fresh and populated exact post-PRD-009 databases and assert prior rows and events are unchanged.
- Run the migration twice and assert the second run applies nothing.
- Assert migration alone creates no run, item, rollback, or status event.
- Exercise foreign keys, closed statuses, unique item ordinals and paths, run counts, repository isolation, and event linkage.
- Corrupt each reconstructible linkage in controlled fixtures and assert `audit_corrupt` blocks `next`, apply, and rollback.
- Assert timestamps and generated IDs do not influence classification or deterministic item order.

### Rollback tests

- Roll back a valid run and assert reverse-order status restoration, append-only rollback events, immutable original evidence, and one complete linkage.
- Reject wrong repository, unknown run, repeated rollback, empty actor/reason, changed or missing PRD, wrong current status, and later status event.
- Cover direct and transitive dependents in all four statuses; only the explicitly prohibited `in_progress` and `completed` dependent states block rollback.
- Inject transaction failures at every item and assert no partial restoration or partial audit record.
- Assert manifest deletion or modification never triggers rollback.

### CLI and integration tests

- Use temporary Git repositories, isolated configuration/data directories, and the compiled `familiar` binary.
- In a mature fixture, assert the first `familiar next` bootstraps historical items and prints the first unlisted eligible PRD using the exact PRD-009 stdout format.
- Assert the first-run informational stderr and subsequent silence exactly.
- Assert `bootstrap status` is read-only and stable for every state.
- Assert rollback output, audit records, post-rollback `next`, and identical-manifest reapply.
- Cover absent, malformed, stale, ineligible, changed, and dependency-incomplete manifests with empty success stdout and categorized errors.
- Put failing fake Codex and LLM executables on `PATH`; assert apply, status, rollback, and reapply never launch them.
- Assert execution-history and review tables receive no rows.
- Preserve all existing PRD-009 and CLI regression tests.

### Repository manifest test

- In a clean checkout, discover the repository's active PRDs and validate every manifest path and exact hash.
- Assert the expected historical PRD identity set explicitly; do not derive it from a numeric range in the test.
- Assert PRD-010 and every later PRD are absent from the completed set.
- Assert the resulting first `next` choice is determined solely by PRD-009 eligibility after bootstrap.

### Verification commands

At minimum, implementation verification must run:

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Focused bootstrap domain, storage, migration, rollback, manifest, and CLI suites must also be independently runnable. Tests must never read or modify a developer's real Familiar database or configuration.

## Definition of Done

PRD-010 is done when:

1. A strict checked-in manifest explicitly identifies every historical PRD to classify, with exact path and content hash, and does not list PRD-010.
2. The first eligible `familiar next` applies the manifest atomically and then selects through the unchanged PRD-009 algorithm.
3. Application is deterministic across manifest formatting, item order, filesystem order, database row order, locale, and timing.
4. Application is idempotent under repetition and concurrency and never duplicates a run, item, status event, or status write.
5. Every classification is reconstructible from the immutable manifest hashes, item evidence, ordinary status event, repository identity, and run record.
6. Invalid, stale, ambiguous, incomplete, previously touched, or corrupt state fails closed without partial classification or inferred repair.
7. Explicit guarded rollback restores recorded prior statuses transactionally, preserves all original evidence, and refuses to erase later work.
8. Identical-manifest reapply after valid rollback creates a new linked, auditable run; no other automatic reapply is possible.
9. The additive migration preserves existing data, seeds no project-specific state, and is safe on fresh and post-PRD-009 databases.
10. Tests prove that no bootstrap path invokes an LLM, coding agent, execution flow, or review flow.
11. Focused tests, formatting, Clippy with warnings denied, and the full workspace test suite pass, or any demonstrably pre-existing failure is recorded with exact evidence.
12. Existing PRD-009 behavior remains intact when the manifest is absent or already applied, and no existing document is changed.
13. The work remains independently mergeable and useful without general status-management UI, task scheduling, automatic execution, daemon orchestration, or later canonical task-state work.
