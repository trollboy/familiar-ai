# PRD-098: The Gate Runs Without Being Asked

## Objective

There is no gate. `.github` has never existed on any branch in this
repository's history. What the roadmap, PRD-082, PRD-088, PRD-089,
PRD-092, and PRD-093 all call "the gate" is four commands in a README
section, run by one person, on one machine, when that person remembers:

```
docker compose build test
docker compose run --rm test cargo test --workspace --no-default-features
docker compose run --rm test cargo fmt --all -- --check
docker compose run --rm test cargo clippy --workspace --all-targets -- -D warnings
```

Ninety-one PRDs are archived as done. Fourteen hundred tests exist. Not
one of them has ever been run by anything except a human typing a
command, and nothing anywhere records whether that human typed it.

This is the mechanism behind failures the project has already paid for
and already documented. The tray shipped in PRD-004 and was dark for
months while three defects stacked up behind each other — a stale
`daemon_run` call, a SIGTERM path that left the process alive, an icon
assertion pinned to 32x32 after the asset became 512x512 — and PRD-092
correctly names a green gate as the reason they were invisible. But a
gate that is not excluding the tray is still not a gate if nobody runs
it. `familiar-ai-tray` carries 4,876 lines and 72 tests today; those
tests are not failing, and they are not passing either. Nothing has asked
them.

The same hole makes nine queued PRDs unfalsifiable. Their criteria are
written in the language of automatic verification — *"proven by a gate
job"*, *"a check scans and fails"*, *"pinned by a regression"* — and
every one of them is satisfiable today by committing a test file that is
never executed. PRD-089 is titled *no holes in required gates*; there are
no required gates. PRD-092 fixes what the gate compiles and assumes
throughout that a gate job exists to compile it.

A project whose first principle is Determinism Before Intelligence, and
whose second is Trust Is Earned Through Verification, verifies itself by
hand, on one box, and keeps no record that it did.

## The split with PRD-092

These two are adjacent and must not be conflated. PRD-092 owns **what**
the gate compiles and tests: default features, the `--no-default-features`
workaround, system dependencies, feature-set parity between gate and
install, and the workspace-membership check that catches an excluded
crate. All of that stays there.

This PRD owns **that it runs at all**: automatic triggering, a single
definition, honest reporting of unknown outcomes, required rather than
advisory status, a queryable verdict, and in-repository control of what
verification means. It changes no step's contents.

Either can land first. PRD-092 landing first means the gate that later
gets automated already compiles the right things; this one landing first
means PRD-092's criteria become checkable for the first time. The second
ordering is worth more, which is why this is filed with no dependencies
rather than behind the queue that assumes it.

## Design

- **Automatic, on both triggers.** Push to the default branch and pull
  request. A verification that runs when someone chooses to run it
  measures diligence, not correctness.
- **One definition, every caller.** `scripts/gate.sh` becomes the sole
  statement of what verification is. The automation invokes it. The
  README tells a contributor to invoke it. The compose service invokes
  it. Two lists that are supposed to match will eventually not match, so
  there is one list and a check that no second list exists.
- **Unknown is failure.** A cancelled run, a dead runner, a step that
  never started, a verdict that cannot be read — each reports failure.
  This is the same discipline the usage ledger already applies to token
  counts, where unknown stays unknown and never becomes zero. A gate that
  reports green because it could not tell is worse than no gate, because
  it is trusted.
- **Required, and overrides are on the record.** Red or absent refuses
  the merge. An override is a durable record naming who, which commit,
  and why — the same shape as PRD-012's audited recovery. The point is
  not to make override impossible; it is to make it impossible to do
  quietly.
- **The verdict is a shipped command.** Per PRD-084, an operator
  capability that only exists in a web interface is not a capability this
  project has. `familiar-ai gate status` answers green, red, absent, or
  unreadable, for a person and for the daemon that will eventually want
  to know before it drives.
- **Verification is defined in the repository.** A step that can be
  disabled by a setting stored somewhere else is a step whose removal
  leaves no diff and no reviewer. Everything that decides the verdict is
  a reviewed file in this tree.

## Scope

The gate definition file and its triggers; `scripts/gate.sh` as the
single definition; the check forbidding verification steps declared
anywhere else; unknown-outcome handling; required status, merge refusal,
and the recorded override; the `gate status` command and its four
answers; in-repository control of the step list; the verification-gate
contract document; README updates replacing the four-command block with
the one command; regressions in a dedicated test file.

Out of scope: what the gate compiles or which features it enables
(PRD-092); which tests it selects and under what load (PRD-088);
declared, expiring gate exclusions (PRD-089); build-time ceilings, which
still need a platform this project does not have; release artifacts,
packaging, and installers; and self-hosted or multi-platform runners —
one Linux runner matching the documented environment is the whole of this
PRD, and a macOS job is a successor with its own acceptance.

## Assumptions (recorded at specification time, 2026-09-16)

- The repository is hosted on GitHub under `trollboy/familiar-ai`, and
  enabling Actions plus the branch protection that makes a check required
  is a one-time human step outside this repository. That step is named in
  the contract document as a precondition rather than designed around; an
  unprotected branch makes the fourth criterion unenforceable, and the
  gate is honest about that rather than reporting green.
- The hosted Linux runner can build this workspace within the free tier's
  per-run limits. If it cannot, the failure is a named build-time problem
  to report, not a reason to narrow what the gate covers.
- The existing Docker image is the right environment for the gate to run
  in, since it is already what the README's local commands use; sharing
  it is what makes "green here, red there" reduce to a single cause.
- No CI has ever run in this repository, so there is no history to
  migrate and no existing green record to reconcile. The first run's
  verdict is the first verdict, whatever it is — including a red one, on
  the tray or anywhere else, which is the PRD working rather than failing.
