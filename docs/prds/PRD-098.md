# PRD-098: Delivery Claims Are Computed, Not Asserted

## Objective

Familiar's own database on the Linux host,
`~/.local/share/familiar-ai/familiar.db`, at 2026-09-17:

| On this host | |
|---|---|
| Driver sessions | 26 |
| PRD attempts | 39 |
| Attempts with outcome `completed` | **2** |
| Attempts with a non-null `integrated_at` | **2** (PRD-53, PRD-81) |
| Last PRD attempt of any kind | **2026-09-05** |
| Adapters that have ever run here | `claude-code` only; `codex` never |

Two deliveries out of thirty-nine attempts. There is no merge-queue or
integration table anywhere in the schema; `driver_attempts.integrated_at`
is the only record of integration that exists, and it has two rows.

**And that table is one machine.** Every `repository_key` in this store is
a `/home/trollboy` path. The M1 Mac did the early heavy lifting and ran
every Codex execution against its own SQLite, which this host cannot
read. `driver_sessions` has no host-identity column, so the two histories
could not be told apart even if they were merged; PRD-091 adds host
identity to the *lease*, for mutual exclusion, and deliberately does not
merge history.

This makes the problem worse than a low delivery rate, and it is the
reason this PRD exists rather than a rate-improvement PRD. The first
version of this document — and the README and bug-ledger corrections
written alongside it on 2026-09-16 — presented the table above as the
project's lifetime record. It is not. That error was made by the person
with the query in hand, on purpose-built tooling, one day after finding
the same class of error in a bug closure. A number whose scope is not
carried with it will be over-claimed by whoever picks it up next,
including by someone actively looking for over-claims.

The README says *"the autonomy half works"* and *"it has done this on its
own codebase twice."* FAM-BUG-019 — the release-blocking dogfood bug,
whose exit criterion was one multi-PRD wave delivered using only Familiar
commands — was closed on 2026-09-02 with the evidence *"Wave 5
(038/053/058) and wave 6 (059/060/061) ran claim → implement → verify →
independent review → merge-queue integration without manual git
operations."* The ledger rows for those six PRDs are:

| PRD | Outcome | Reason | Integrated |
|---|---|---|---|
| PRD-38 | retained | `scope_ambiguous` | no |
| PRD-53 | completed | — | **yes** |
| PRD-58 | retained | `scope_ambiguous` | no |
| PRD-59 | retained | `scope_broadened` | no |
| PRD-60 | retained | `scope_ambiguous` | no |
| PRD-61 | retained | `scope_ambiguous` | no |

One of the six. The bug's exit criterion required a *multi-PRD* wave; the
best session in this project's history integrated exactly one PRD. The
criterion says, in its own words, *"until then, this bug remains open
regardless of whether the individual underlying defects are dispositioned
elsewhere."* It was closed anyway, by an audit that read narratives
instead of querying the table sitting underneath them.

This is not a complaint about a bug disposition. It is the mechanism that
lets a five-percent delivery rate coexist with a status table reading
green, and it is load-bearing for every decision made since. Sixteen
PRDs — 082 through 097, this one's predecessors — were specified against
a picture of the system that its own ledger does not support. Some of
them plainly do move delivery: PRD-096 routes a failed required check
into remediation instead of a wall, which is the `verification_failed`
class directly. Others plainly do not. **Nobody can currently tell which
is which**, because neither north-star metric has ever been computed.
There is no command that computes them. Producing the table above
required opening sqlite by hand.

That is the whole problem in one sentence: the roadmap's scope filter
says a change moving neither metric is off-mission, and the filter has
never once been applied, because applying it is not possible.

Meanwhile the ledger says plainly what is actually stopping delivery:

| Retained reason | Count |
|---|---|
| `review_failed: enabled review requires an explicit PRD Acceptance Criteria section` | 6 |
| *(no reason recorded)* | 6 |
| `scope_broadened` | 5 |
| `scope_ambiguous` | 4 |
| `unclassified_result` | 3 |
| `interrupted` | 3 |
| `human_review_required` | 3 |

Scope authorization refuses nine attempts. Six die on a review
precondition. Six record no reason at all. PRD-76 was attempted six times
in one day and retained six times with six different reasons — the
retry-loop fire the north star names as enemy number two, running
unmeasured. The roadmap's own scope filter says a change that moves
neither metric is off-mission. It cannot be applied to anything, because
the metrics do not exist as numbers.

The elephant is not that autonomy is unfinished. It is that the project
does not know it is unfinished, because its claims are written by hand
and its evidence is never consulted.

## What this PRD does not do, because two queued PRDs already do it

This document was first filed claiming the north-star metrics as its own
work. That was wrong, and the queue already said so:

- **PRD-085 — Unattended Stall Taxonomy and Autonomy Measurement** already
  requires a closed stall vocabulary with a recovery command per class
  (which closes the six attempts retained with no reason recorded), every
  human intervention recorded with the command that produced it, session
  reporting of unattended versus assisted completions *"computed from
  durable rows and never from narration"*, a stewardship autonomy query
  grouped by stall class and intervention, and an autonomy floor below
  which a session is reported as a failure. That is the human-touches
  metric and the retained-reason histogram, specified before this PRD
  existed.
- **PRD-086 — Cost Measurement: Make CostUnmeasured the Exception**
  already requires a declared cost basis with stored provenance, ledger
  observations with no cost *"counted and reported rather than silently
  dropped"*, and a session below a cost-coverage floor reported as a
  measurement failure. That is the cost-per-accepted-PRD metric and the
  unknown-stays-unknown discipline.

So the metrics are owned. What remained unowned, and is all this PRD now
claims, is three things nothing else covers: **host scope**, **documented
claims being recomputed against the ledger**, and **execution-outcome bug
closures requiring a query**. The first came from the owner correcting
this document's own numbers; the second and third came from FAM-BUG-019
being closed on a narrative. Both are failures of a claim, not of a
measurement, which is why they survive the narrowing.

## Design

- **The metrics belong to PRD-085 and PRD-086.** This PRD consumes their
  queries rather than reimplementing them, and fails if a document
  disagrees with what they return.
- **One definition of delivered autonomously.** Claim, implement,
  verify, independent review, integrate — recorded against one attempt,
  with no operator recovery, manual completion, or backlog override in
  between. Definitions are contracts: a term that means one thing in the
  README, another in a bug closure, and a third in the schema is how the
  last three months happened. The phrase gets one meaning and everything
  else must use it.
- **Unknown stays unknown.** The usage ledger already refuses to record
  an unknown token count as zero. The same discipline applies here: a
  window with no runs reports no runs. A flattering default is worse than
  a blank, because a blank prompts the question.
- **Host scope travels with every number.** A figure computed on one box
  is labelled as such, and a project-wide claim that cannot be computed
  is refused by name rather than approximated from whatever store is
  local.
- **A claim carries its window, and the check recomputes it.** Status
  assertions in the README, roadmap, and after-action reports name what
  they were computed over. The check re-runs the computation and fails on
  disagreement. This is the criterion that would have caught FAM-BUG-019's
  closure on the day it was written.
- **An execution-outcome bug closes on a query.** If the exit criterion
  is an observed outcome, the closure carries the query and its result.
  Narrative audit evidence is refused.

## Scope

Host scope carried on every metric and delivery answer, and the refusal
of an uncomputable project-wide claim; the documented-claim check over
the README, roadmap, and after-action reports, recomputing against
PRD-085's autonomy query and PRD-086's cost coverage; the
closure-evidence requirement for execution-outcome bugs; the
delivery-claims contract document; correcting the README status section
to whatever the ledger says at implementation time; regressions in a
dedicated test file.

Out of scope because PRD-085 and PRD-086 own them: the stall taxonomy,
the intervention record, the autonomy and cost-coverage queries, the
per-session floors, and unknown-cost handling.

Also in scope: carrying host scope on every answer, and either
aggregating the contributing hosts' ledgers or refusing a project-wide
claim by name. Merging the M1's history into this store is **not** in
scope — that is a data-movement question with its own PRD; what is in
scope is that no answer pretends the merge already happened.

Out of scope: **fixing the delivery rate.** Nothing here makes a single
additional PRD land. Scope authorization, the review acceptance-criteria
precondition, the unrecorded retained reasons, and the retry loop are
each real work with their own PRDs or ledger entries, and this PRD
deliberately does not attempt them — it makes them rankable so the next
one is chosen by evidence rather than by whoever argues best. Also out of
scope: changing the definition of an accepted PRD, backfilling
attribution onto historical attempts, and the FAM-BUG-019 disposition
itself, which is the owner's call and is raised rather than taken here.

## Assumptions (recorded at specification time, 2026-09-16)

- The existing `driver_attempts` and `driver_sessions` tables carry
  enough to compute both metrics for attempts recorded after PRD-051.
  Where an older attempt lacks cost attribution, the window reports it as
  unattributed rather than excluding it silently — an excluded row is how
  a rate flatters itself.
- `integrated_at` is the authoritative integration record. No other table
  records integration, which was confirmed against the live schema rather
  than assumed; if a merge-queue table is introduced later, the predicate
  moves and this assumption is what names the place to change.
- Human touches are countable from recorded events — recovery commands,
  overrides, waivers, scope decisions, manual completions. Touches that
  leave no record, including the operator running `git cherry-pick`
  outside Familiar, are not countable, and the metric states that limit
  in its own output rather than implying completeness it does not have.
- The six attempts retained with no reason recorded are a defect in
  retention classification, not an empty category. They are reported as
  unclassified, and the count is expected to be the first thing the
  histogram makes someone fix.
