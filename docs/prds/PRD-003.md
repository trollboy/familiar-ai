# PRD-003: Repository Lifecycle and Scan Reconciliation

**Status:** Ready for implementation  
**Date:** 2026-08-03  
**Roadmap milestone:** M1 — Repository Identity and Reconciliation  
**Epic:** EPIC-M1-02 — Repository Lifecycle Reconciliation  
**Backlog source:** PRD-TBD-M1-03

## Objective

Make Familiar's active file-summary state converge deterministically with the current repository entries observed from repository source and Git-aware filesystem rules.

After this PRD, file creation, modification, deletion, and rename observations use the canonical project-relative identities established by PRD-001; watcher observations and initial or recovery scans feed one lifecycle reconciliation boundary; stale or removed summaries no longer appear as current; scan completeness is durable and truthful; interrupted or saturated work resumes without silently losing repository entries; and a completed reconciliation accounts for every in-scope active summary and observed repository entry.

This PRD assumes PRD-002 legacy identity reconciliation is complete for the project. Lifecycle reconciliation must not operate over unresolved competing absolute identities. Repository source and Git remain authoritative for whether an entry currently exists. File summaries, scan records, watcher observations, lifecycle tombstones, and pending work are subordinate operational or derived records.

### Selected boundary

This remains one bounded PRD. The delivery backlog explicitly merges delete and rename reconciliation with scan completeness because they share one operating and recovery boundary. The repository confirms that coupling:

- the watcher declares removed and renamed event types but currently converts every native notification into `FileChanged`;
- daemon removal and rename handlers currently log without changing storage;
- initial scan sends directly to the bounded summary queue and stops at the first full or closed result without recording incompleteness;
- the summary worker drops new pending identities when its in-memory limit is reached; and
- storage has canonical identity and reversible legacy migration support but no repository lifecycle, scan, or durable pending-work state.

Typed watcher handling alone cannot recover missed, coalesced, or platform-divergent events. Scan state alone cannot safely reconcile repository changes racing the scan. Both require the same project-scoped observation ordering, stale-summary treatment, durable pending work, rollback preservation, and convergence fixtures. Splitting them would create an intermediate state that cannot truthfully satisfy either completion boundary.

## Scope

This PRD includes:

1. Typed, project-scoped handling of file creation, modification, removal, and exact paired rename observations from the existing watcher boundary.
2. Conservative handling of coalesced, ambiguous, unpaired, and platform-divergent watcher notifications.
3. One shared lifecycle operation that validates every path through the PRD-001 canonical identity contract before observation, persistence, queueing, or removal.
4. Durable, bounded pending summary work for created and modified eligible files so queue saturation or restart cannot silently lose required work.
5. A durable project-scoped scan run with explicit progress, completeness, interruption, failure, and reconciliation outcome.
6. Deterministic enumeration of in-scope repository entries under the current supported Git-aware ignore and file-eligibility rules.
7. Convergence between scan observations, watcher observations, active file summaries, lifecycle tombstones, and pending summary work.
8. Removal of stale or deleted summaries from all ordinary current-summary reads and counts.
9. Reversible preservation of every active summary retired by deletion, rename, changed eligibility, or deterministic scan absence.
10. Restart reconciliation for scans and pending summary work left in progress.
11. Explicit project-scoped status and counts for scan and lifecycle completeness.
12. Deterministic unit and integration coverage for create, modify, delete, rename, atomic save, scan saturation, watcher races, restart, and rollback.

### Lifecycle identity and rename semantics

The lifecycle identity remains:

```text
(project_id, canonical_repository_relative_path)
```

Identity follows the logical repository entry path. A rename from `old/path.rs` to `new/path.rs` therefore retires the old identity and observes the new identity. This PRD must not claim that the two paths have the same content identity, preserve a summary as fresh under the new path, or infer continuity from size, modification time, inode, filename, or summary text.

When the watcher supplies one exact paired rename observation within one project, retirement of the old active summary and creation of durable pending work for the new identity share one storage transaction. The new summary is generated from the authoritative new source path. When a rename is unpaired or ambiguous, Familiar records conservative remove/create candidates and relies on authoritative path checks and a complete scan to converge. It does not guess a rename relationship.

### Stale-summary treatment

This PRD selects removal from the active `file_summaries` set with complete tombstone preservation rather than leaving stale rows visible or adding a status that older readers could ignore.

Before an active summary is retired, its complete row value and lifecycle reason are copied transactionally to additive lifecycle preservation storage. The active row is then removed in the same transaction. Ordinary lookup, module, search, packing, recent-summary, and dashboard count paths continue to treat `file_summaries` as the current active set and therefore cannot return the preserved stale row accidentally.

Creation or modification produces durable pending work. Successful current-source summarization creates or updates the active canonical row and completes that pending item. A stale summary may not remain active merely because regeneration is delayed or fails. Preserved tombstones are compatibility and rollback records, not canonical events and not current source truth.

### Scan completion boundary

A scan is **enumeration-complete** only when its declared project root and fixed scan policy have been walked to a terminal boundary without skipped work, unrecorded queue loss, traversal ambiguity, watcher failure that invalidates completeness, or unresolved storage error.

A scan is **reconciliation-complete** only when every staged in-scope identity has been compared with active summary and pending-work state, every absence candidate has been revalidated against authoritative repository state and later watcher observations, every required lifecycle transition has committed, and every difference has one explicit outcome.

Summary generation may remain durably pending after reconciliation completes. Scan status must therefore report enumeration completeness, reconciliation completeness, and pending-summary count separately. A completed scan does not claim that every summary has already regenerated.

## Non-goals

This PRD does not:

- introduce file-content hashes or content-addressed identity;
- add Git revision, branch, commit, object, or worktree identity;
- infer rename continuity from content, hashes, inode, size, timestamps, names, or model output;
- manage Git branches, worktrees, checkout, staging, commits, or repository mutations;
- implement context compilation, selection, ranking, or token-packing changes;
- introduce command, query, event, audit, IPC, adapter, or daemon-authority runtime infrastructure assigned to M2 or M4;
- create tasks, findings, approvals, warrants, policy, verification, review, or acceptance state;
- introduce a general scheduler or the M3 blocking-work execution boundary;
- use an LLM for lifecycle classification, rename detection, completeness, eligibility, or reconciliation;
- change deterministic summary quality or language extraction;
- reconcile decisions or session-rollup file references;
- migrate or repair PRD-002 unresolved legacy identities;
- expose cross-project scans or lifecycle operations;
- treat watcher delivery as authoritative proof of repository state;
- treat a complete scan as a Git revision snapshot;
- follow symbolic links outside the canonical project root; or
- delete preserved lifecycle history under a retention policy not yet approved.

## Functional Requirements

### FR-1: Shared lifecycle identity boundary

Every watcher observation, scan entry, pending work item, active summary lookup, tombstone, and reconciliation comparison must use `CanonicalFileIdentity` from PRD-001.

Observed host paths must be associated with one registered project root and converted losslessly to canonical repository-relative paths before storage or queueing. Absolute stored lifecycle identities, traversal, root mismatch, symbolic-link escape, lossy conversion, and cross-project scope must fail explicitly. A path rejection must not be translated into absence or deletion.

### FR-2: Project eligibility precondition

Lifecycle reconciliation may begin only for an existing active project whose registered root still resolves to the intended repository and whose PRD-002 identity reconciliation has no unresolved active legacy conflict that could describe the same current entry.

If these preconditions cannot be proved, Familiar must mark lifecycle work blocked or incomplete. It must not reconcile by scanning arbitrary absolute paths, matching another project, deleting legacy rows, or assuming that an empty enumeration is authoritative.

### FR-3: Typed watcher translation

The watcher boundary must stop coercing every native notification into `FileChanged`. It must preserve enough deterministic native information to emit or derive:

- `FileCreated` for an observed new path;
- `FileModified` for an observed existing path whose source may have changed;
- `FileRemoved` for an observed path that no longer exists;
- `FileRenamed` only when the native observation binds exact old and new paths; and
- an explicit ambiguous/change-candidate observation when native semantics are coalesced, incomplete, or unsupported.

The current mini debouncer exposes no precise event kind, so implementation may replace that watcher mechanism with the already supported `notify` event stream or another bounded precise mechanism. This is a watcher implementation change, not a new subsystem or later milestone.

Watcher types are observations, not source authority. Before a destructive transition, the daemon must check current repository state. Unknown or ambiguous events request bounded re-observation or scan work; they do not authorize deletion.

### FR-4: File creation

For an eligible created file, Familiar must:

1. resolve one project and canonical identity;
2. verify that the current source entry exists, remains contained, and is an eligible regular file;
3. record or update durable pending summary work before relying on an in-memory channel;
4. deduplicate repeated create/modify observations for the same project and identity;
5. enqueue or resume bounded summarization; and
6. mark the pending item complete only after the active canonical summary commits.

Creation of an ineligible directory, escaping link, oversized file, unsupported non-text file, ignored entry, or unrepresentable path receives an explicit ignored, rejected, or ineligible outcome. It must not create a current summary.

### FR-5: File modification

For an eligible modified file, Familiar must validate current existence and identity, transactionally preserve and retire any active summary for that identity as stale, and create or refresh one durable pending summary item.

Repeated modification observations coalesce by project and canonical path without losing the fact that work remains pending. Modification time and size may remain bounded staleness hints under the current implementation, but they must not become durable content identity or proof that content is unchanged.

If the file disappears before processing, the operation converges through removal handling. If it changes again during summarization, the worker must not publish a result as current without rechecking the source metadata boundary it actually read; it must leave or recreate pending work for the later observation.

### FR-6: File deletion

A deletion observation may retire an active summary only after the canonical path is rechecked and the repository entry is authoritatively absent or no longer eligible under the fixed project policy.

Deletion handling must atomically:

- preserve the complete active summary and its identity in lifecycle tombstone storage;
- record the reason and source of the lifecycle transition without fabricating a future canonical event;
- remove the row from the active `file_summaries` set;
- cancel or supersede pending summary work for the absent identity; and
- retain enough causal linkage to the watcher observation or scan run for future audit adoption and rollback analysis.

A filesystem error, inaccessible root, incomplete scan, containment failure, watcher error, or uncertain Git/source observation is not proof of deletion and must leave the active summary untouched while reporting uncertainty.

### FR-7: File rename

An exact paired rename within one project must be handled as one bounded lifecycle transaction:

- canonicalize and validate old and new identities independently;
- verify the old path is absent and the new path currently exists and is eligible;
- preserve and retire the old active summary with reason `renamed` and a reference to the new identity;
- cancel old pending work;
- create or refresh pending work for the new identity; and
- retain the exact observed old/new relationship as compatibility evidence.

The old summary must not be copied or re-keyed as the current summary for the new path. Cross-project moves, one-sided events, rename-over-existing-target cases, case-only platform ambiguities, and atomic-save patterns are not silently treated as exact renames. They are decomposed conservatively into independently validated removal and creation/modification observations and settled by scan reconciliation.

### FR-8: Atomic-save and event-order convergence

Common editor sequences—temporary create, writes, rename-over-target, old-path removal, and repeated modifications—must converge to exactly the current eligible path set without duplicate active summaries or lost pending work.

Watcher arrival order and timestamps are not truth. Familiar must assign a durable project-scoped observation order at ingestion and make lifecycle application idempotent. A repeated or older observation cannot overwrite a later authoritative observation for the same identity. When order or source state remains ambiguous, Familiar schedules re-observation or scan reconciliation rather than guessing.

### FR-9: Durable pending summary work

Pending summary work must be project-scoped, canonical-path keyed, durable across daemon restart, and bounded by explicit status and attempt fields. At minimum it distinguishes pending, leased/in-progress, completed, superseded, failed, and interrupted work.

Queue delivery is an optimization, not durability. A full or closed in-memory channel must leave work durably pending and mark dispatch deferred. The daemon must resume pending or interrupted work after startup without creating duplicate active summaries. Retry of deterministic local summarization remains bounded and must revalidate current source state before publication.

This is a narrow summary-work recovery boundary, not the future Background Scheduler, task workflow, warrant lease, or execution-attempt system.

### FR-10: Scan-run creation

Initial project discovery, explicit recovery, and reconciliation requests must create or resume one project-scoped scan run with:

- stable run identity;
- registered project and root identity;
- fixed scan-policy version and eligibility inputs;
- started, updated, and terminal times;
- durable status;
- bounded progress or work cursor;
- counts for visited, eligible, excluded, rejected, failed, staged, and pending entries;
- the project observation-order boundary at scan start; and
- an explicit stopping condition.

Starting a scan must not imply completeness. Empty, running, incomplete, interrupted, failed, enumeration-complete, and reconciliation-complete states remain distinct.

### FR-11: Deterministic scan enumeration

Scan enumeration must use the registered project root, PRD-001 containment, the existing hardcoded skip rules, supported Git-aware ignore behavior, configured ignore rules where applicable, maximum-file-size policy, and deterministic file eligibility.

Enumeration must be bounded by persisted progress and bounded batches. It must not accumulate the entire project inventory only in memory. Every accepted staged path is canonical and unique within the scan run. Repeating a batch or restarting enumeration must not duplicate entries or skip an unprocessed entry.

Filesystem or Git-access errors, walker errors, unreadable directories, containment failures, and storage failures must be counted and make enumeration incomplete unless the fixed policy explicitly classifies the entry as excluded. Silently flattening or dropping walker errors is prohibited.

### FR-12: Initial scan and watcher convergence

Watcher observations must continue during a scan. Each accepted watcher observation receives a project-scoped order after the scan's start boundary. Scan finalization must not apply an older staged observation over a later watcher observation for the same identity.

Initial scan and watcher creation/modification for one file must converge on one pending item and one active canonical summary. A watcher removal after the scan observed a file prevents the scan from recreating it. A watcher creation after the scan passed a directory prevents absence reconciliation from deleting or ignoring it.

The implementation must define a deterministic precedence rule using durable observation order and current source revalidation, not wall-clock comparison.

### FR-13: Complete-scan reconciliation

Only an enumeration-complete scan may reconcile absence across the project. Reconciliation must compare, in deterministic canonical-path order:

- staged eligible repository identities;
- staged excluded or rejected identities where they affect an existing summary;
- active canonical file summaries;
- durable pending summary work;
- later watcher observations; and
- existing lifecycle preservation records relevant to idempotency.

For each identity it must produce exactly one bounded outcome:

- unchanged current summary;
- created or modified summary work pending;
- active summary retired because the entry is authoritatively absent;
- active summary retired because the entry became ineligible;
- later watcher observation takes precedence;
- explicitly excluded by policy;
- rejected identity or containment violation;
- failed or unavailable observation; or
- previously reconciled/idempotent.

Every destructive absence candidate must be revalidated against current source state immediately before its transaction. A scan that is incomplete or whose root became unavailable must not retire anything by absence.

### FR-14: Bounded reconciliation and partial progress

Large reconciliations may commit deterministic bounded batches. Batch identity, ordered boundaries, counts, and progress must be durable and replay-safe. A failed or interrupted batch must leave prior committed batches visible and must not claim whole-run completion.

Continuation resumes at the last committed boundary, rechecks watcher precedence and current source state, and does not repeat tombstoning or pending-work creation. If the declared scan policy, project root, or required source boundary changes incompatibly, the run becomes incomplete or superseded and a new scan begins; it is not silently reinterpreted.

### FR-15: Interruption and restart recovery

On daemon restart, Familiar must identify scan runs and pending summary items left running or leased. It must mark the interrupted boundary truthfully, preserve staged entries and committed lifecycle transitions, release only stale local ownership, and resume or supersede work deterministically.

Recovery must distinguish:

- enumeration interrupted before completion;
- enumeration complete but reconciliation not started;
- reconciliation interrupted after bounded committed batches;
- summary work interrupted before active write;
- active summary committed but pending completion recording interrupted; and
- watcher failure requiring a new complete scan.

Recovery checks current active summary and source state before repeating work. It must not infer success from a missing response or process restart.

### FR-16: Current read behavior

Ordinary current-summary lookup, listing, module, search, packing, recent-summary, and dashboard count behavior must expose only active `file_summaries`. Tombstones, staged scan entries, failed observations, and superseded pending work are not current summaries.

Lifecycle and scan status must remain explicitly available through storage-owned project-scoped results until M2 wraps them in the canonical query runtime. A read must not trigger a scan, lifecycle mutation, summary generation, or repair implicitly.

### FR-17: Lifecycle status and accounting

For each project, Familiar must expose deterministic status containing at least:

- latest and active scan identities;
- scan policy and root binding;
- enumeration and reconciliation statuses;
- durable progress boundary;
- visited, eligible, excluded, rejected, failed, and staged counts;
- unchanged, pending-create, pending-modify, retired-delete, retired-rename, retired-ineligible, later-watcher-wins, and previously-applied counts;
- pending, in-progress, failed, interrupted, and superseded summary-work counts;
- unresolved watcher or source errors;
- whether absence reconciliation was permitted;
- whether inventory reconciliation is complete; and
- stable references to tombstones and compatibility evidence.

Zero entries, an incomplete scan, a complete scan with pending summaries, an interrupted scan, a failed scan, and a blocked project are distinct results.

### FR-18: Tombstone preservation and idempotency

Every retired active summary must be preserved completely before removal, including its original primary key, project, canonical path, summary, tags, symbols, source metadata, and timestamps. The tombstone also records the bounded lifecycle reason, scan or watcher cause, related rename identity when applicable, observation order, and retirement time.

Repeated deletion, rename, scan reconciliation, retry, or restart must not create another tombstone for the same active row transition or remove a newer active row. Re-creation at the same canonical path creates new current derived state without deleting or rewriting the prior tombstone.

Tombstones and scan compatibility records must be explicitly labeled as pre-event-subsystem lifecycle evidence. They must not fabricate a principal, command, approval, event ID, Git revision, occurrence time, or historical fact that was not observed.

### FR-19: Deterministic rollback and repair

Rollback of this PRD must preserve authoritative repository reality. It must not restore a tombstoned summary as current merely because an older row is available.

The supported repair path is:

1. stop or disable lifecycle application;
2. retain all additive scan, pending-work, observation, and tombstone records;
3. run a deterministic complete inventory reconciliation under the last supported code or a focused compatibility repair;
4. regenerate active summaries from current authoritative source where required; and
5. verify current active paths against a fresh repository inventory before declaring rollback complete.

An optional explicit tombstone restoration operation may restore the exact row only as non-current recovery data unless current source existence, identity, and summary validity can be proved under the implementation's existing deterministic semantics. Modification time and size alone are insufficient proof of unchanged content.

### FR-20: Audit and future-contract compatibility

Lifecycle transitions, scan outcomes, failures, interruptions, and repair records must retain stable project, operation, cause, prior active row, resulting active state, progress, and timestamps that the current implementation actually observes.

These records are migration and compatibility evidence only. They must not partially implement the future event store, assign synthetic actors, claim event atomicity, or become an event-sourcing stream. Future daemon-owned command and event handlers must be able to wrap the same lifecycle operations and reference retained compatibility records without changing canonical path or convergence semantics.

## Non-functional Requirements

### Determinism

Given the same project identity, registered root, fixed scan policy, ordered observations, staged entries, and authoritative path state at each guarded transition, Familiar must produce the same lifecycle outcomes, ordering, counts, and terminal status. No model inference or heuristic rename matching is permitted.

### Safety and isolation

Every operation is scoped to one project and one canonical path or bounded scan run. Destructive retirement fails closed on missing root, access error, incomplete enumeration, later observation conflict, containment uncertainty, or cross-project ambiguity. Symlinks may not escape the project.

### Bounded resources

Watcher ingestion, scan enumeration, staged storage, reconciliation batches, pending summary dispatch, retries, and status results must have explicit size or work bounds. Backpressure persists pending work or marks the scan incomplete; it never silently drops required work. This PRD does not promise the M3 control-plane latency guarantees.

### Crash consistency

Tombstone preservation and active-row removal share one SQLite transaction. Exact rename lifecycle changes share one transaction. Scan and pending-work progress advances only after the corresponding records commit. Restart never depends on in-memory queue contents to establish completeness.

### Compatibility

Existing canonical summary producers and consumers remain usable. Additive lifecycle storage must not reinterpret PRD-002 reconciliation history or require destructive migration. Current-summary readers must not need to understand tombstones to avoid stale data.

### Portability

Observable lifecycle outcomes must be equivalent on supported macOS and Linux hosts. Native watcher event shapes may differ, but ambiguous shapes degrade to re-observation and scan convergence rather than platform-specific truth.

### Observability

Creation, modification, removal, rename, ambiguity, exclusion, saturation, deferred work, scan progress, interruption, failure, completion, tombstoning, and repair remain distinguishable. Empty or missing results must not conceal incomplete state.

### Performance

Ordinary single-file watcher handling must not trigger a project-wide scan synchronously. Scans and reconciliation operate in bounded persisted batches. No operation computes file-content hashes, builds branch intelligence, or invokes an LLM.

## Acceptance Criteria

1. Creating one eligible file produces one canonical durable pending item and eventually one active summary; repeated watcher and scan observations do not duplicate either.
2. Modifying an active summarized file preserves and retires the old summary as stale before one current summary is regenerated from source.
3. Deleting a summarized file preserves its complete row, removes it from current lookup/list/module/search/packing/recent/count results, and cancels pending work.
4. A deletion observation for a path that still exists does not retire its summary and requests re-observation or scan reconciliation.
5. An exact paired rename retires the old identity and creates pending work for the new identity in one lifecycle transaction without copying the old summary as current.
6. An unpaired or ambiguous rename is not guessed; conservative path observations plus a complete scan converge to the current path set.
7. Rename-over-existing-target and case-only fixtures fail closed or converge without duplicate active identities or overwritten tombstones.
8. Atomic-save event sequences converge to one active target summary, no active temporary summary after completion, and no lost pending work.
9. Initial scan plus watcher modification for the same file converges on one pending item and one active canonical summary.
10. A watcher removal later than a staged scan observation prevents scan finalization from recreating or retaining the removed path.
11. A watcher creation later than the scan start is not retired as absent by that scan.
12. Queue saturation leaves durable pending work and explicit deferred status; it does not stop enumeration while claiming success or drop a lifecycle requirement.
13. A scan containing walker, containment, root-access, or storage errors is incomplete and performs no project-wide absence retirement.
14. Only an enumeration-complete scan may tombstone active summaries absent from the staged authoritative inventory.
15. Every destructive scan absence is rechecked against current repository state immediately before retirement.
16. Interrupted enumeration resumes or is explicitly superseded without duplicating staged entries or skipping remaining work.
17. Interrupted reconciliation resumes after its last committed bounded batch and reports prior versus remaining outcomes accurately.
18. Interrupted summary work is recovered without publishing stale source output or creating duplicate active rows.
19. A complete empty repository scan retires prior active summaries only when the root is available, enumeration is proven complete, and every absence is revalidated.
20. An unavailable or accidentally empty root is reported unavailable/incomplete and retires nothing.
21. Files that become directories, escaping symlinks, oversized, ignored, binary/unsupported, or otherwise ineligible retire prior active summaries with explicit reasons only after authoritative validation.
22. Two projects with identical relative paths remain isolated across watcher events, scans, pending work, tombstones, and current reads.
23. Every active and staged identity is canonical, repository-relative, lossless, contained, and project-scoped.
24. Repeated lifecycle application and scan replay are idempotent: no duplicate tombstone, pending work, active mutation, or completion count occurs.
25. Tombstones preserve every field needed to reconstruct the retired row exactly and retain explicit pre-event compatibility provenance.
26. Fresh databases and canonical PRD-002 databases upgrade additively without changing active summary rows as a schema side effect.
27. Current MCP summary, module, search, packing, recent, and dashboard behavior excludes tombstones and remains compatible for active summaries.
28. Lifecycle status distinguishes empty, running, incomplete, interrupted, failed, enumeration-complete, reconciliation-complete, and complete-with-pending-summary states with exact counts.
29. A deterministic before/after fixture accounts for every staged repository identity, active pre-scan summary, pending work item, tombstone, and final active summary with no silent loss.
30. No lifecycle path invokes an LLM, computes file-content hashes, infers a branch/worktree identity, or introduces command/query/event runtime infrastructure.
31. Focused core, watcher, storage, daemon, and current-consumer tests pass.
32. Formatting, static analysis, and the full workspace test suite pass, or pre-existing failures are identified separately with evidence.

## Test Strategy

### Canonical lifecycle unit tests

Add table-driven fixtures for:

- create, modify, remove, and exact paired rename classification;
- absolute, traversing, wrong-root, lossy, missing, and escaping-link paths;
- same relative path under two projects;
- repeated and out-of-order observations;
- exact versus ambiguous rename shapes;
- rename-over-target and case-only platform behavior;
- entry becomes directory or symlink;
- ignored, oversized, binary/unsupported, and unreadable entries; and
- deletion revalidation when a path reappears.

Tests must prove that watcher type or timestamp alone cannot cause destructive retirement.

### Watcher tests

Using temporary repositories and precise native event fixtures, verify:

- create and modify translation;
- remove translation;
- exact paired rename where the platform supplies it;
- explicit ambiguity where it does not;
- atomic-save sequences;
- ignored-path behavior;
- watcher error propagation; and
- bounded delivery and clean shutdown.

Platform-specific native observations may use deterministic adapter fixtures so macOS and Linux semantics are tested without assuming identical raw event sequences.

### Storage and migration tests

Verify:

- additive migration from the PRD-002 schema;
- no schema-time active-row mutation;
- durable scan-run, staged-entry, observation-order, pending-work, and tombstone constraints;
- tombstone plus active removal atomicity through failure injection;
- exact rename transaction atomicity;
- canonical and project uniqueness;
- pending-work deduplication and supersession;
- bounded scan/reconciliation progress and replay;
- complete field preservation;
- re-creation at the same path without tombstone loss;
- foreign-key and SQLite integrity checks; and
- repair or rollback conflict behavior.

### Daemon integration tests

Using temporary Git repositories, bounded channels, restartable daemon components, and controlled source mutations, verify:

- initial scan and watcher convergence;
- create → modify → delete;
- exact and ambiguous rename;
- atomic save;
- summary queue saturation;
- worker pending-limit saturation;
- scan interruption during enumeration;
- interruption between enumeration and reconciliation;
- interruption after a committed reconciliation batch;
- interruption during summary processing;
- watcher failure followed by a recovery scan;
- unavailable and empty roots;
- later watcher precedence over staged scan state; and
- two-project isolation.

Every fixture must compare authoritative final repository paths with final active summary paths and explicit pending or ineligible outcomes.

### Current consumer regression tests

Verify:

- current file lookup does not return a removed or stale tombstoned summary;
- module listing and counts exclude tombstones;
- search, packing, recent-summary, project status, and dashboard counts exclude tombstones;
- a currently active regenerated summary remains visible through all current surfaces;
- absolute caller paths remain rejected; and
- incomplete scan status is never rendered as an empty, complete inventory where a current compatible surface exposes it.

### Deterministic verification

The implementation pull request must retain:

- focused canonical identity and lifecycle test results;
- watcher, storage, daemon, and current MCP consumer results;
- create/modify/delete/rename/atomic-save fixture manifests;

- formatting and static-analysis results; and
- the full workspace test result with pre-existing failures distinguished from PRD-caused failures.

No LLM assessment may substitute for these checks.

## Rollback Strategy

This PRD uses additive lifecycle storage and preserves retired summaries outside the active table.

If lifecycle reconciliation must be rolled back:

1. Stop watcher lifecycle application, scan continuation, and pending-work dispatch at a recorded bounded boundary.
2. Preserve all scan runs, staged entries, lifecycle observations, pending work, tombstones, and compatibility records; do not drop the additive migration.
3. Mark in-progress operations interrupted and record the last committed progress without claiming completion.
4. Do not bulk-restore tombstones into active summaries. Repository state may have changed, and modification time or size cannot prove an old summary current.
5. Run a deterministic complete inventory scan using the last supported implementation or a focused compatibility repair.
6. Regenerate missing active summaries from current contained source and leave absent or ineligible paths inactive.
7. Verify authoritative current repository identities against active summary identities, explicit pending work, and explicit exclusions.
8. Only after verification, revert lifecycle code paths while leaving additive records recoverable for later re-enable or human inspection.
9. Confirm legacy PRD-002 reconciliation and canonical PRD-001 writes remain intact.

Rollback must not copy a renamed summary to a new identity, restore a deleted summary as current without source validation, delete tombstones, fabricate audit events, discard interrupted progress, broaden path containment, or infer repository history.

## Definition of Done

PRD-003 is done when:

1. Create, modify, delete, and exact rename observations use canonical project-relative identity and have deterministic, idempotent lifecycle outcomes.
2. Ambiguous watcher behavior degrades to guarded re-observation and complete-scan convergence without guessed deletion or rename.
3. Stale, deleted, renamed, and newly ineligible summaries are completely preserved and absent from all current-summary consumers.
4. Durable pending summary work prevents queue saturation, in-memory limits, shutdown, or restart from silently losing required work.
5. Initial scan and watcher observations converge through one durable project-scoped order and later-observation precedence rule.
6. Scan enumeration and reconciliation completeness are distinct, durable, bounded, and truthful.
7. Incomplete, unavailable, failed, or interrupted scans cannot perform project-wide absence retirement.
8. Complete scans deterministically account for every staged path, active summary, pending item, tombstone transition, and final active result.
9. Restart resumes or supersedes interrupted enumeration, reconciliation, and summary work without duplicate mutation.
10. Tombstone preservation and active-row removal are atomic and replay-safe.
11. Repository source and Git-aware filesystem state remain authoritative; watcher, mtime, size, summary content, and model output do not become identity truth.
12. Additive migration and rollback preserve PRD-001 identity, PRD-002 evidence, active user data, and future audit compatibility.
13. No content hashing, branch/worktree intelligence, context compilation, command/query/event runtime, or later-milestone capability is implemented.
14. All acceptance criteria have retained deterministic evidence.
15. Focused tests, formatting, static analysis, and the full workspace test attempt are recorded, with unrelated pre-existing failures identified separately.
16. The implementation is contained in one independently mergeable pull request with any file-list deviation justified.
