# PRD-082: Tool-Output Retention Hardening

## Objective

When token discipline bounds a large tool result, the full output is retained
so review evidence is not silently narrowed, and the model is handed a paging
handle to reach the elided region:

```rust
let handle = format!(".familiar/tool-output/{}.txt", call.call_id);
if let Ok(handle_path) = self.resolve_within_worktree(&handle) {
    if let Some(parent) = handle_path.parent() {
        let _ = std::fs::create_dir_all(parent);
    }
    let _ = std::fs::write(&handle_path, &combined);
}
let bounded = bound_tool_result(&combined, &window, Some(handle));
```

Three defects, in descending severity:

**1. The retained file is world-readable.** `create_dir_all` and `write` take
the ambient umask, which on this machine yields mode `775` on the directory.
The retained content is verbatim command output from a worker that has been
reading the repository — build logs, test output, whatever the command
printed. On a single-user box this is nil risk; on a shared host it is
disclosure. `driver.worktree_root` is operator-configurable, so the retention
directory need not live under `$HOME` at all.

**2. A failed retention write still advertises the handle.** Both filesystem
calls discard their errors with `let _ =`, and the handle is passed to
`bound_tool_result` unconditionally afterward. If the write fails, the model
is told the full output is "retrievable via read-file at
.familiar/tool-output/<id>.txt" and that file does not exist. The model then
spends a turn discovering the pointer is dead.

**3. The comment asserts an invariant the code does not hold.** Directly above
the discarded errors:

> *"the full output lands in the worktree ... before the bounded view is
> computed, so a failure to persist it never silently narrows what review
> evidence can recover."*

A silently-discarded write error is exactly that silent narrowing. Either the
code should uphold the comment or the comment should describe the code.

There is also no cleanup: nothing removes `.familiar/tool-output/` for the
life of the worktree. That may well be correct — retained output is review
evidence, and worktrees are leased and reaped — but it is currently unstated,
so it reads as an oversight rather than a decision.

## Scope note

The code being hardened landed on `main` in `ea9a85a` (PRD-072). No dependency
on PRD-072 is declared because the work is already integrated in the tree.

Latent, not live: `agent_runtime.token_discipline.enabled` defaults to
`false` and no shipped configuration enables it.

## Approach

Create the retention directory and file with explicit restrictive modes
rather than inheriting the umask, and decide the handle from whether
retention actually succeeded. Failing closed is acceptable; succeeding
without a handle is acceptable; succeeding with a handle to a file that was
never written is not.

## Acceptance evidence

`crates/familiar-ai-daemon/tests/runtime_path_containment.rs` contains
`a_failed_retention_write_never_advertises_an_unresolvable_handle` and
`retained_tool_output_is_not_readable_by_other_users`. Both currently fail.
The change is complete when they pass with no assertion relaxed.
