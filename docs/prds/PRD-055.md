# PRD-055: Project Attribution and Historical Usage Series

## Objective

Make the Familiar project the central reporting identity of the
PRD-051 ledger and give the accounting family its historical
time-series surface: durable project identity that survives paths and
machines, explicit project↔provider attribution bindings, a
provider-neutral `usage_series` query contract, and rebuildable
rollups — so "how much did Project1 spend on Claude versus Codex, and
how has that changed?" is answerable locally, offline, from evidence.

## Problem

Every identity Familiar records today is path-bound: wave-one
`projects` is unique on `repo_root`, `RepositoryIdentity.key` is the
canonicalized Git common directory (worktrees correctly share it, but
a moved checkout or second machine becomes a new key), and
`execution_history.repository` stores a path string. PRD-051 defines
the minimal remedy ledger rows need — the globally unique `ProjectId`,
degraded-identity classification, and machine-local issuance behind a
stable resolver boundary — but machine-local issuance alone cannot
survive a second machine, and no query surface can return a bucketed
series. The ledger records honest observations and PRD-053 reconciles
them; nothing yet answers the product question: per-project,
per-provider spend over time, drillable to evidence.

## Terminology

**Project** — the durable Familiar reporting identity. **Repository**
— a Git history (common-dir identity). **Checkout/worktree** — one
working copy. **Installation** — one Familiar machine/database.
**Billing source / provider org / provider project** — provider-side
scopes per PRD-051/052/054; attribution evidence, never substitutes
for project identity. **Observation** — one append-only ledger fact.
**Rollup** — a derived, rebuildable aggregate. **Attribution** — the
evidence-backed mapping from an observation to a project.

## Design

**Durable project identity.** The `ProjectId` type, its degraded
states, and the resolver boundary are PRD-051's contract; this PRD
implements full resolution behind that boundary without schema change
and without being required for PRD-051's acceptance. The id is minted
once per project and carried by two cooperating registrations: a
shareable declaration in the repository's `familiar.toml` (PRD-049 — travels with every clone
and machine; identity declarations label reporting only and grant no
authority, but bind locally only under the 049 approval gate) and a
machine-local registry mapping resolution evidence —
`RepositoryIdentity.key`, wave-one `projects.id`, configured paths —
to the project id. Resolution order: bound familiar.toml declaration,
then machine-local registry, then an explicit **degraded identity**
(keyed by the observed evidence, labeled unresolved) that an operator
can later merge into a real project through reattribution correction
records — never a silent path-derived project. Worktrees resolve
through the Git common directory to their repository's project unless
configuration splits them deliberately. A repository without Git
metadata uses an operator-declared id or stays degraded. A clone on a
second machine is the same project by declaration; an intentional fork
declares a new id, and the fork boundary date is recorded.

**Dimensions.** Every observation supports, nullably and honestly:
project, repository, checkout/worktree, PRD, execution, attempt,
stage, session, worker, provider, provider organization/account,
provider project/workspace, model, billing source, and the configured
provider profile by reference (never a credential value). Local
telemetry fills the execution-side dimensions; collector rows
(PRD-052/054) fill the provider-side dimensions; neither pretends to
the other's grain. A missing dimension is null or classified, never
inferred deceptively.

**Time.** Observations use the PRD-051 envelope: half-open UTC
`[period_start, period_end)` for the covered interval, `observed_at`
for when the fact was produced, `ingested_at` for when Familiar
imported it, with reconciliation/correction timestamps on their own
rows (PRD-053's, once reconciliation lands — the series schema carries
those dimensions generically from the start). Series bucket by covered period, so late-arriving
provider data lands in the interval where usage occurred. Canonical
storage and bucket boundaries are UTC; any future calendar-timezone
grouping must be explicit, never a silent boundary shift. Records are
discrete interval facts — cumulative counters are never canonical.
Bucket assignment is deterministic and never fabricates precision:
local observations are emitted at narrow durable stage boundaries, and
an indivisible observation whose covered interval crosses a requested
bucket boundary is assigned wholly to the bucket containing its
`period_start` (the documented assignment timestamp) while retaining
its native interval and granularity for callers that care — tokens and
money are never prorated across buckets. Provider-native bucket
observations stay in their provider-defined interval; one coarser than
the requested bucket is not split — it is assigned by its
`period_start` and labeled with its native granularity. Week buckets
are ISO-8601 weeks (Monday 00:00 UTC); month buckets are UTC calendar
months, both half-open.

**Attribution.** Explicit configuration may bind a project to
provider-side scopes (Anthropic workspace, OpenAI organization or
project, a provider credential profile). A binding is evidence for
attributing collector rows, with recorded confidence — it never
asserts that everything in a broad organization belongs to one
project. Attribution status is a closed set: attributed (with
confidence and the evidence used), unattributed, degraded-identity,
and pending. For any billing source and period, total provider cost
equals attributed plus unattributed exactly; unexplained amounts stay
unattributed — never distributed to force totals to agree (the rule
PRD-053's reconciliation later enforces source-side). Reattribution is an
append-only correction record; history is never rewritten in place.

**Query semantics.** One provider-neutral interface serves CLI now
and any later UI:

    usage_series(
        range=[start, end),          # arbitrary half-open UTC
        bucket=hour|day|week|month,
        group_by=[project, provider, model, prd, execution, attempt,
                  stage, billing_source, attribution_status],
        filter=<same dimensions>,
        metrics=[estimated_cost, authoritative_cost, input_tokens,
                 cached_input_tokens, output_tokens, reasoning_tokens,
                 request_count, credit_estimate],
    )

Estimated and authoritative cost are separate metrics and are never
summed into one number; credit estimates are their own unit and never
mix with USD metrics. Results are deterministically ordered, available
sparse (machine processing) or dense with zero-valued buckets (direct
chart rendering) — a zero-filled bucket means observed-nothing only
where coverage exists; unknown stays unknown. Derived views (running
cumulative totals, burn rate, prior-period comparison) are computed
from the same series, and every aggregate is drillable to its
underlying observation ids. Callers never reconstruct reconciliation
rules or choose which monetary source is authoritative — the labels
travel with the data. The PRD-053 source-centric billing views
(month-to-date per source, variance) remain; this PRD adds the
project-centric axis over the same rows, counted once.

**Storage.** The existing SQLite persistence layer carries the model:
raw observation tables (PRD-051) already carry the ProjectId and gain
attribution columns and covered-period indexes; uniqueness constraints
implement each source's dedup identity (terminal result per attempt;
collector rows, when configured, by logical identity with
payload-hash revisions per the PRD-052/054 model, aggregates reading
the current-effective projection); rollup
tables are derived,
versioned by the rollup definition, and rebuildable from raw rows.
Raw usage and monetary observations are retained indefinitely by
default — historical project accounting is part of the engineering
record; any retention policy is explicit configuration. The logical
model stays portable (plain tables, no SQLite-isms in the contract)
so ordinary PostgreSQL or a time-series store can carry it later
without semantic change. No distributed infrastructure now.

**Budgets.** Budget views distinguish observed spend, estimated
pending spend, reserved spend, reconciled authoritative spend, and
remaining budget, by project and provider where evidence permits.
Reservation mechanics — atomic acquisition, commit, release, expiry,
crash recovery — are PRD-064's; this PRD consumes its states and adds
the project axis. A subscription is never an invented USD pool.

## Privacy and failure modes

Accounting rows carry identifiers and usage metadata only — never
prompts, responses, source code, diffs, credential values, or
authentication/bearer tokens (usage-token *counts* are the point of
the system); execution evidence is the PRD-051 sanitized envelope, and
retained billing payloads pass the existing secret-scanning/redaction
policy or are reduced to the fields accounting needs. Failure behavior:
ingestion crash mid-batch resumes idempotently; a failed rollup
rebuild leaves the prior rollup and raw truth intact; identity
resolution failure produces degraded observations, not dropped ones;
collector outages follow PRD-052/054 (prior complete snapshot kept);
finalization failure preserves stage-boundary observations (PRD-051,
ledger B13's blast-radius bound).

## Migration and backfill

Existing `execution_history`, driver-attempt, and checkpoint usage
rows are backfilled into the ledger best-effort as observations with
degraded or machine-local identity and explicit backfill provenance —
never retro-fabricated precision. The wave-one `projects` table keeps
serving memory features; its rowid becomes resolution evidence, not
the accounting identity. Rollups build after backfill; both are
re-runnable.

## CLI implications

Follows the existing grammar: `usage` gains range/bucket/group/filter
selection over `usage_series` with unit- and authority-labeled output;
`stewardship` and MCP gain the matching read queries (PRD-035
surfaces); `config` verbs (PRD-047 conventions: probe, comments,
actor/UTC provenance, decision rows) manage project declaration,
binding, worktree split, fork, and merge-degraded-identity
operations. Read commands serve cached local data and label staleness;
nothing refreshes over the network implicitly.

## Future Familiar Server compatibility

A later optional server may aggregate accounting across machines and
teams. This design keeps that possible — globally unique ids, schema
versions, append-oriented serializable observations, provenance/
attribution/reconciliation state on the rows, no canonical dependence
on filesystem paths, storage and queries behind interfaces, lossless
export — while local accounting stays complete, authoritative for
Familiar-controlled activity, and fully functional offline. The
server, if it ever exists, is a consumer and aggregator; it does not
own the accounting domain and is never required for execution or
local reporting. Server discovery/design is a separate future PRD;
REST/sync/dashboard/tenancy/RBAC/SSO/deployment are explicitly out of
scope here, as are Svelte/D3 components.

## Phasing

1. Full registry resolution, declarations, forks, and merges atop
   PRD-051's ProjectId contract and resolver boundary.
2. Attribution bindings, statuses, and the attributed/unattributed
   invariant over collector rows.
3. `usage_series`, sparse/dense rendering, derived views, drill-down,
   CLI/MCP exposure.
4. Rollups, retention configuration, backfill of historical rows.

## Assumptions (recorded 2026-08-30)

- `familiar.toml` (PRD-049) is the right cross-machine carrier for the
  project declaration; until PRD-049 lands, the machine-local registry
  alone serves, and declarations bind only under its approval gate.
  The owner may choose a different carrier without changing the
  ledger schema.
- Provider capability rows reflect documentation verified 2026-08-30
  in PRD-052/054; the Anthropic Admin usage surface is deliberately
  marked provider-dependent rather than assumed.
- Subscription-price allocation across projects is explicitly
  deferred; if ever wanted, it arrives as a visible operator-selected
  policy in a future PRD, never a default.
