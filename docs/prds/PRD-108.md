# PRD-108: Keep the backlog synchronized with the PRD filesystem

## Problem

Familiar already watches configured repositories, but watcher events currently
update only file summaries, context/search state, and generic lifecycle rows.
They do not run the backlog discovery and reconciliation path. Backlog state is
instead refreshed as a side effect of commands such as `next`, `run`, and
`drive`.

That split produces contradictory operator snapshots. The dependency query
discovers current PRD files directly, while the backlog query reads older
ledger rows. A newly pulled PRD therefore appears in the dependency graph with
no status, and a PRD moved into `docs/prds/done/` can coexist with a stale
missing row at its former path. The first dependency-Gantt implementation
rendered the failed exact-path join as `not found`, even though the PRD existed
and its Read action worked.

The backlog is durable workflow state, not a cache that may remain stale until
execution begins. Filesystem observation must keep it synchronized, and reads
must self-heal after downtime or a dropped watcher event.

## Outcome

The daemon owns one repository-scoped backlog reconciler. It performs the same
canonical discovery and transactional reconciliation used by execution paths,
and it is invoked from three places:

1. daemon startup, before the first operator snapshot;
2. a bounded debounce fed by relevant watcher events; and
3. a bounded reconcile-on-read fallback for operator backlog/dependency
   snapshots.

The watcher remains a hint, not the source of truth. Every reconciliation scans
the authoritative configured PRD locations and commits one complete view. A
rename may arrive as two events, one event, or an ambiguous event without
changing the result.

## Required behavior

### Reconciliation boundary

Reconciliation is serialized per repository and coalesces concurrent requests.
At most one run and one pending rerun exist for a repository. Different
repositories may reconcile independently. Discovery and parsing occur outside
the database write lock where possible; the resulting snapshot is committed
atomically through the existing backlog repository API.

Only events whose resolved paths fall under the repository's configured active
or archived PRD locations request reconciliation. The test must cover an
ordinary source-code edit proving it does not churn backlog state.

### Moves and durable history

The existing ledger deliberately leaves an old path row behind because other
tables reference the `(repository_key, prd_path)` identity. This PRD must not
delete or silently rewrite that history. It must distinguish historical rows
from the current discovered snapshot so an old missing path is available for
audit without being counted as present work. A newly discovered archive path
is completed by the existing archived-location authority.

If consolidating path identities requires schema work, it must use an explicit
migration with referential integrity and rollback coverage. It must not be
smuggled into event handling.

### Operator truth and refresh

Backlog and dependency queries must not independently observe different epochs.
After a successful commit the daemon emits one ordered operator event; clients
use their existing gap/restart logic to fetch a fresh snapshot. Reconciliation
failure never fabricates an empty backlog and never calls an existing document
`not found`.

The read fallback is bounded by repository freshness and single-flight state;
opening or polling the Dashboard must not cause a continuous full-tree scan.

## Non-goals

- Treating the filesystem watcher event stream as authoritative history.
- Deleting old backlog rows or execution evidence.
- Automatically editing PRD metadata or moving PRD files.
- Starting newly eligible PRDs merely because reconciliation discovered them.
- Broadening the generic file-summary scanner into backlog authority.

## Completion evidence

Completion includes focused reconciler, watcher, storage, operator transport,
and desktop contract tests; restart and burst tests using a real temporary Git
repository; strict linting of changed Rust targets; and workspace tests. The
evidence must demonstrate the UI moving from an old snapshot to the reconciled
snapshot without invoking an execution command.
