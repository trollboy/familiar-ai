# PRD-012: Explicit Backlog Recovery

**Depends on:** PRD-011

## Objective

Add deterministic, auditable commands for recovering one active backlog PRD that remains `in_progress` after a failed, interrupted, or intentionally stopped PRD-011 run:

```text
familiar backlog release <prd-path> --actor <actor> --reason <non-empty-text>
familiar backlog complete <prd-path> --actor <human-actor> --reason <non-empty-text>
```

`release` changes exactly one entry from `in_progress` to `pending`. `complete` changes exactly one entry from `in_progress` to `completed` and is an explicit human-authorized manual override. Both operations preserve the claim, execution, verification, review, bootstrap, and prior status histories and append one new status event in the same transaction as the status update.

The implementation must remain independently mergeable and must not change automatic execution or selection behavior.

## Motivation

PRD-011 correctly fails closed: after a claim commits, any outcome that does not satisfy its closed completion predicate leaves the backlog entry `in_progress`. That prevents a crash, model statement, process exit, or incomplete review from silently releasing or completing work. It also means an operator needs an explicit supported way to resolve retained claims without editing storage directly.

Recovery is a human decision, not an inference problem. Familiar can deterministically identify the exact active entry, verify its current state and audit lineage, require attributable intent, and commit an ordinary status transition. It cannot determine from Git, commits, tests, execution records, review records, elapsed time, or model output whether the work should be retried or accepted. The operator supplies that decision through one narrowly scoped command.

## Scope

This PRD includes:

1. `familiar backlog release <prd-path>` for `in_progress -> pending`.
2. `familiar backlog complete <prd-path>` for `in_progress -> completed`.
3. Required explicit `--actor` and non-empty `--reason` options on both commands.
4. A stricter human-authority rule and conspicuous manual-override labeling for `complete`.
5. Exact active-entry resolution through the PRD-009 repository, discovery, identity, and path rules.
6. Transactional expected-status and audit-lineage validation.
7. One atomic status-row update and one append-only status event containing recovery attribution and reason.
8. Typed conflicts, deterministic CLI output, and focused domain, storage, concurrency, and CLI tests.
9. Narrow reuse of the shared backlog status domain and existing CLI/storage composition boundaries.

### Separation of responsibilities

The backlog domain defines the two authorized recovery actions, their fixed transitions, actor and reason validation, human-authority rule, and typed results. It does not access files, storage, agents, reviews, or execution history.

The discovery boundary resolves the containing repository and the supplied path to exactly one current active PRD using PRD-009 and PRD-011 rules. It does not infer recovery intent.

The storage boundary owns the immediate transaction, current-state and latest-event checks, optimistic update, append-only event, and rollback on error. It does not decide which action the user meant or inspect execution, review, bootstrap, Git, or model evidence.

The CLI owns parsing, direct invocation authorization, rendering, and exit status. It must dispatch only the action explicitly named by the user and contains no fallback or status inference.

## Non-goals

This PRD does not:

- add automatic timeout, lease expiry, heartbeat, abandoned-work detection, or stale-claim inference;
- infer completion or releasability from model output, Git status, diffs, commits, tests, verification evidence, review disposition, execution history, elapsed time, process state, or filesystem timestamps;
- invoke a coding agent, reviewer, remediation agent, verification command, LLM, inference backend, or routing layer;
- resume, rerun, or cancel an execution or review cycle;
- delete, edit, replace, relabel, or reorder the prior PRD-011 claim event or any other audit record;
- add a `--force` flag, implicit confirmation, batch recovery, wildcard, PRD range, all-in-progress operation, or interactive bulk selector;
- recover `pending`, `completed`, or `blocked` entries;
- add a general status-set command or authorize any transition other than the two named here;
- reopen a manually completed entry or automatically reclaim a released entry;
- provide direct database-editing instructions or a manual storage workflow;
- change `familiar run`, `familiar next`, bootstrap application/status/rollback, `history`, or `usage` behavior, output, or authorization, except for reuse of shared status-domain types and validation;
- add daemon, MCP, dashboard, tray, watcher, scheduler, background-worker, or network behavior; or
- modify prior PRDs, architecture documents, ADRs, contracts, or philosophy.

## Command Syntax

The exact public forms are:

```text
familiar backlog release <prd-path> --actor <actor> --reason <reason>
familiar backlog complete <prd-path> --actor <human-actor> --reason <reason>
```

`<prd-path>` is one required path argument. Relative and absolute spellings are accepted only when they resolve to the same regular, non-symlinked active PRD beneath the containing worktree's direct `docs/prds/` discovery root. The canonical identity written and printed is the repository-relative path discovered by PRD-009.

`--actor` and `--reason` are required options with exactly one value each. After trimming surrounding whitespace, neither may be empty. The stored actor and reason are the validated trimmed values. Control characters, line breaks, and values exceeding implementation-defined documented bounds are rejected rather than normalized or truncated. Tests must pin reasonable bounds; no valid value may be silently shortened.

For `complete`, `<human-actor>` must use the explicit form:

```text
human:<non-empty-identity>
```

The identity after `human:` must remain non-empty after trimming. Reserved `system:` actors, including `system:familiar-run:<execution-id>`, are rejected for manual completion. `release` accepts any non-empty explicit actor because an authorized operational automation may release a claim, but it must never synthesize or default that actor.

The subcommand name is the complete action selection. Familiar must never choose `release` or `complete` from the reason text or surrounding repository state. Options may follow normal Clap ordering, but missing or duplicate required values are usage errors.

## Authorization Boundary

These are direct local administrative commands. Possession of permission to invoke the CLI and write Familiar's configured state is the outer authorization boundary; Familiar does not add accounts, login, role storage, signatures, or remote authorization in this PRD.

`--actor` is mandatory attribution, not proof of real-world identity. Callers and repository policy remain responsible for supplying an honest identity. Familiar validates its syntax and persists it exactly so the decision is auditable.

`release` is an explicit operational recovery decision. It may be initiated by a human or by separately authorized deterministic automation, but never internally by `run`, startup recovery, a timer, or an agent.

`complete` is a manual override and requires explicit human authority. It is available only through the directly invoked `backlog complete` CLI path, requires a `human:` actor, and must be labeled `MANUAL OVERRIDE` in help and successful output. No internal run coordinator, agent-facing interface, daemon path, or generic transition API may invoke the manual-completion application service. The command asserts that the named human accepts responsibility for completion despite PRD-011's normal evidence predicate; Familiar does not independently authenticate that assertion.

No confirmation prompt is required because the complete subcommand, human actor, and reason jointly express explicit intent and allow non-interactive auditability. There is no bypass for any authorization or eligibility check.

## Eligibility Rules

Both actions apply only when all of the following are true:

1. The process current directory resolves to a Git worktree and PRD-009 repository identity.
2. The complete active backlog discovers and validates successfully under PRD-009 rules.
3. The supplied path resolves byte-for-byte to exactly one discovered active entry using PRD-011 path protections, including regular-file, non-symlink, in-worktree, active-root, canonical-path, and content-hash checks.
4. The persisted row belongs to the resolved repository key and canonical PRD path, is not marked missing, and still matches the discovered PRD number and content hash.
5. The current persisted status is exactly `in_progress`.
6. The latest status event for that entry exists and is a structurally valid `pending -> in_progress` claim event.
7. The actor and reason satisfy the command's validation rules; `complete` additionally satisfies the human-authority rule.

No dependency-state check is required. Releasing the entry to `pending` does not make it selectable unless its dependencies satisfy the unchanged PRD-009 rules. Completing the entry may make dependents eligible; that is the explicit consequence accepted by the human manual override, not inferred proof that implementation or review succeeded.

The recovery actor need not equal the PRD-011 claim actor. Recovery exists specifically so a separately authorized operator can resolve retained ownership. The prior claimant and recovery actor remain separately visible in ordered events.

An absent, malformed, or non-claim latest event is audit corruption and fails closed. Familiar does not fabricate a claim event or repair lineage. Earlier execution, review, bootstrap, and status records may be absent, incomplete, failed, or contradictory without deciding recovery eligibility; they are preserved but are not read as evidence for either action.

## Transaction Boundaries

Repository resolution, discovery, graph validation, exact-path resolution, and actor/reason syntax validation occur before the write transaction. Opening and migrating configured storage follows existing CLI behavior. No transaction spans Git, filesystem discovery, user interaction, external process execution, or output rendering.

After preflight, one immediate write transaction must:

1. Re-read the row by exact repository key and canonical repository-relative PRD path.
2. Require the row to remain active, match the discovered number and content hash, and have status `in_progress`.
3. Read and validate the latest status event as the current `pending -> in_progress` claim for the same entry.
4. Select the fixed target from the explicit subcommand: `pending` for `release`, `completed` for `complete`.
5. Update exactly one status row with an optimistic `in_progress` predicate and one transaction timestamp.
6. Append exactly one ordinary backlog status event with old status `in_progress`, the fixed new status, validated actor, validated reason, action kind, and the same timestamp.
7. Verify the affected-row count and event linkage, then commit.

The status update and event append are one atomic unit. Any error, constraint failure, affected-row count other than one, stale snapshot, or commit failure rolls back both. The implementation must not retry, switch actions, rediscover and overwrite, or wait for a competing writer.

The existing event schema must be extended additively only as needed to retain a recovery reason and distinguish `release` from manual `complete`. Existing events remain valid and unchanged; new recovery metadata is required only for recovery-created events. A linked append-only recovery detail record is acceptable if repository conventions make that safer than extending ordinary events, provided exactly one ordinary status event is created and the detail cannot commit independently. No migration may seed, reinterpret, or backfill recovery decisions.

## Audit Events

Successful `release` appends exactly one event equivalent to:

```text
old_status=in_progress
new_status=pending
action=release
actor=<validated explicit actor>
reason=<validated explicit reason>
changed_at=<transaction UTC timestamp>
```

Successful `complete` appends exactly one event equivalent to:

```text
old_status=in_progress
new_status=completed
action=manual_complete_override
actor=human:<validated identity>
reason=<validated explicit reason>
changed_at=<transaction UTC timestamp>
```

The event retains the existing repository key, canonical PRD path, and monotonic event ID. The latest preceding event remains the PRD-011 claim with its original run actor. No claim or prior transition is deleted, modified, copied, or rewritten. Execution-history rows, review tasks and cycles, verification evidence, findings, bootstrap runs and items, and their rollback records are untouched.

Validation failure, usage failure, conflict, and read-only inspection during preflight append no event. A successful recovery produces no execution-history, review, verification, bootstrap, or agent record.

The event itself must carry or transactionally link the reason and recovery action; logging the reason only to stdout, stderr, or process logs is insufficient. Free-form reason text is audit context only and has no status, eligibility, or evidence semantics.

## Conflict Handling

Typed failures must distinguish at least:

- repository-resolution, discovery, metadata, identity, dependency, or cycle failure;
- missing, unreadable, changed, non-regular, symlinked, outside-worktree, inactive, or ambiguous PRD path;
- missing or inactive persisted entry;
- current status `pending`, `completed`, or `blocked` when `in_progress` is required;
- repository, path, PRD number, content hash, missing marker, or expected-status change between preflight and commit;
- absent, malformed, mismatched, or non-claim latest status event;
- missing, empty, malformed, too-long, or control-character actor or reason;
- non-human or reserved actor supplied to `complete`;
- database open, migration, transaction, constraint, event-linkage, or commit failure; and
- concurrent release, completion, or other status mutation.

Conflicts fail closed and report the expected `in_progress` state plus the observed stable category. They do not print raw storage statements, mutate another entry, fall back to a different PRD, or retry. If two processes recover the same claim concurrently, at most one commits one transition and one event; every loser observes a conflict and writes nothing.

Wrong-current-status invocations are not idempotent successes. Repeating a successfully committed command fails because the entry is no longer `in_progress`; this prevents a second reason or misleading duplicate recovery event.

## CLI Output and Exit Behavior

On a committed release, stdout contains exactly one stable line:

```text
backlog recovery: PRD-12 docs/prds/PRD-012.md in_progress -> pending action=release actor=<actor> reason=<reason>
```

On a committed manual completion, stdout contains exactly one stable line:

```text
backlog recovery: MANUAL OVERRIDE PRD-12 docs/prds/PRD-012.md in_progress -> completed action=manual_complete_override actor=human:<identity> reason=<reason>
```

Values must be rendered with a documented escaping rule so whitespace or terminal characters cannot create ambiguous extra fields or lines. Exact escaping and wording are pinned by CLI tests. Output is emitted only after commit. Success writes no stderr and exits zero.

Clap syntax failures use its existing usage behavior and exit code. All application, eligibility, authorization, audit, and conflict failures leave stdout empty, use the existing `error: <message>` stderr convention, and exit with the existing generic non-zero failure code. No agent or verification output can precede or follow these lines because neither command launches external work.

Help text for `complete` must include `MANUAL OVERRIDE`, state that it bypasses PRD-011's normal completion-evidence predicate, and state that `--actor human:<identity>` and `--reason` are mandatory. Help for `release` must state that it preserves the prior claim event and does not undo worktree changes.

## Interaction with PRD-011 Claims

PRD-011 remains the sole automatic owner of `pending -> in_progress` claims and evidence-qualified `in_progress -> completed` transitions during `familiar run`. This PRD does not weaken its admission, ownership, verification, review, or retained-state rules.

Recovery begins only after an `in_progress` claim already exists:

- `release` appends `in_progress -> pending`. The original claim remains the immediately preceding event and its execution ID remains available for forensic correlation. A later `familiar run` must perform a new ordinary PRD-011 claim with a new execution ID before launching another agent.
- `complete` appends `in_progress -> completed` with a distinct manual-override action and human actor. It does not impersonate the claim actor, manufacture a clean review, alter the prior execution outcome, or claim that PRD-011's completion predicate passed.

Neither command checks whether a run process is still alive and neither attempts to stop one. Operational callers are responsible for coordinating with any live process before recovery. A still-running PRD-011 invocation that later attempts completion must lose its expected-status transaction after either recovery action and must not overwrite the recovered state.

Execution and review history remain observations of what happened. Recovery events remain explicit decisions about backlog state. Neither is derived from the other.

## Recovery and Rollback Semantics

Recovery is the explicit transition itself; there is no automatic compensating transition.

Before commit, any failure leaves `in_progress` and creates no recovery event. After commit, failure to print output does not undo the status or event. On an ambiguous client-visible result, the operator must inspect ordinary backlog state and event history through supported interfaces when available; rerunning the same mutation cannot be treated as success solely because the target state is observed.

`release` does not roll back code, commits, files, execution records, review records, verification evidence, or the original claim. It only returns backlog status to `pending`. Its semantic inverse is not provided: subsequent ownership must occur through the normal PRD-011 claim path.

`complete` does not roll back or rewrite any execution or review outcome. It is deliberately irreversible within this PRD. Reopening `completed` work would require a separately specified authorized transition with its own safety and dependency rules.

Rolling back an implementation commit, database schema version, or deployment does not roll back either recovery event. Bootstrap rollback remains governed exclusively by PRD-010 and cannot target a recovery event. No startup path, timer, manifest operation, or later `next` call automatically reverses recovery.

## Acceptance Criteria

1. The CLI accepts exactly the two new single-target forms `familiar backlog release <prd-path>` and `familiar backlog complete <prd-path>` with required explicit `--actor` and non-empty `--reason`.
2. Both commands resolve the supplied path to exactly one current active PRD-009 entry and reject inactive, missing, changed, outside-repository, symlinked, stale, or ambiguous targets.
3. Both commands require current persisted status exactly `in_progress` and a valid latest PRD-011-style claim event.
4. `release` atomically changes only that entry from `in_progress` to `pending` and appends exactly one reason-bearing `release` status event.
5. `complete` atomically changes only that entry from `in_progress` to `completed` and appends exactly one reason-bearing `manual_complete_override` status event.
6. Manual completion is available only from the direct CLI path, requires a `human:<identity>` actor, rejects reserved system actors, and is labeled `MANUAL OVERRIDE` in help and success output.
7. Neither command derives its action or eligibility from model output, Git state, diffs, commits, tests, verification evidence, review state, execution history, elapsed time, or process state.
8. Neither command launches an agent, LLM, verification command, review cycle, remediation cycle, execution record, or background task.
9. The original claim event and all execution, review, verification, bootstrap, and earlier status history remain byte-for-byte unchanged and query-compatible.
10. Missing options, empty values, invalid authority, wrong status, corrupt lineage, stale discovery, and storage conflicts create no status update and no event.
11. Concurrent recovery attempts produce at most one committed transition and one recovery event, with no retry or last-writer-wins behavior.
12. A released PRD becomes subject to unchanged `next` dependency eligibility and requires a fresh PRD-011 claim before any later run.
13. A manually completed PRD may satisfy unchanged dependency selection, while its audit event unambiguously distinguishes override completion from PRD-011 evidence-qualified completion.
14. Repeating either successful command fails with a current-status conflict and never creates a duplicate event.
15. Success output is printed only after commit, failures leave stdout empty, exact escaping is deterministic, and exit behavior follows this PRD.
16. No force, batch, wildcard, timeout, lease, abandoned-work inference, generic status setter, or direct storage-editing workflow is added.
17. Existing `run`, `next`, bootstrap, `history`, and `usage` behavior and output remain unchanged except for narrow shared status-domain reuse.
18. Persistence changes are additive, do not rewrite or backfill existing events, and preserve databases created by PRD-009 through PRD-011.
19. The implementation is limited to the recovery CLI/domain/storage surface and remains independently mergeable.

## Test Strategy

### Domain and authorization tests

- Map `release` only to `in_progress -> pending` and `complete` only to `in_progress -> completed`; prove no caller-supplied target status exists.
- Accept valid bounded actor and reason values and reject missing, blank, control-character, and over-limit values without truncation.
- Require `human:<identity>` for completion and reject empty human identities and all `system:` actors; prove release never defaults an actor.
- Assert reason contents cannot change the selected action, target, eligibility, or output category.
- Assert model text, Git facts, execution outcomes, review dispositions, verification results, and timestamps are absent from the decision inputs.

### Resolution and eligibility tests

- Resolve relative and absolute spellings of one active PRD to the same canonical path.
- Reject traversal, outside-worktree paths, symlinks, directories, inactive files, stale bytes, duplicate identities, malformed metadata, missing dependencies, and cycles.
- Exercise current `pending`, `in_progress`, `completed`, and `blocked` statuses and assert only `in_progress` is eligible for either command.
- Accept claims whose execution or review history is missing, running, failed, interrupted, clean, or corrupt without reading those records, while requiring a structurally valid latest claim event.
- Reject a missing, non-claim, mismatched, or malformed latest event as audit corruption.

### Storage and transaction tests

- For release, assert one row changes to `pending`, one event records action/actor/reason, and the prior claim remains unchanged.
- For manual completion, assert one row changes to `completed`, one event records the manual-override action/human actor/reason, and no PRD-011 evidence rows are required or modified.
- Inject failures before the update, between update and event, after event, and at commit; assert either the complete pair commits or neither write is visible.
- Change repository key, path, number, hash, missing marker, status, and latest event between preflight and transaction; assert deterministic conflict with no writes.
- Race release against release, complete against complete, and release against complete using independent connections; assert exactly one winner, one event, and unchanged winner state.
- Repeat each committed command and assert a wrong-current-status failure with no second event.
- Upgrade fresh and populated databases from the prior migration, run migrations repeatedly, and assert every existing backlog, claim, bootstrap, execution, verification, review, and status record is preserved.

### CLI and integration tests

- Parse both exact command forms and reject omitted path, actor, or reason; reject extra positional targets and any force or batch spelling.
- Build temporary Git repositories and isolated databases, discover one claimed active PRD, and pin exact stdout, stderr, escaping, and exit codes for success and every failure category.
- Assert complete help and output visibly contain `MANUAL OVERRIDE` and describe the bypass of normal completion evidence.
- Assert release help states that claim and worktree history are preserved.
- Configure failing fake coding-agent, reviewer, verifier, LLM, and router executables and assert neither command invokes any of them or creates execution/review rows.
- After release, assert unchanged `next` eligibility and that a later `run` creates a new claim rather than reusing the released claim.
- After manual completion, assert an eligible dependent is selected through unchanged PRD-009 behavior and the completion remains distinguishable from an automatic run completion.
- Preserve existing `next`, run, bootstrap, history, usage, storage, and migration regression tests without changing their expected output.

### Verification commands

At minimum, implementation verification must run:

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Focused recovery domain, storage, migration, concurrency, parsing, and CLI suites must also be independently runnable. Tests must use temporary repositories, configuration, databases, and executable fixtures and must never read or mutate a developer's real Familiar state.

## Definition of Done

PRD-012 is done when:

1. Both explicit single-PRD commands implement only their fixed transitions from `in_progress`.
2. Exact active-entry identity, current status, and claim lineage are validated before one atomic update/event transaction.
3. Every committed event durably records the explicit actor, non-empty reason, action, timestamp, repository, path, old status, and new status.
4. Manual completion is human-authorized at the defined local CLI boundary and unmistakably labeled as an override rather than PRD-011 evidence-qualified completion.
5. Release preserves the original claim and all work/history, and later execution requires a new normal claim.
6. All preflight, conflict, concurrency, storage, and commit failures leave status and audit history unchanged.
7. No decision consults or invokes an agent, LLM, Git work-state signal, execution history, verification, review, timeout, lease, or inferred abandonment.
8. No force, batch, generic status setter, automatic recovery, direct storage-editing workflow, or unrelated behavior is introduced.
9. Existing `run`, `next`, bootstrap, history, and usage behavior remains compatible, and all prior audit data is preserved.
10. Focused tests, concurrency tests, formatting, Clippy with warnings denied, and the full workspace test suite pass, or any demonstrably pre-existing failure is recorded with exact evidence.
11. The implementation changes only the narrow expected surface and is independently mergeable.
