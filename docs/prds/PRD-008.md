# PRD-008: Independent Review and Bounded Remediation

**Status:** Ready for implementation  
**Date:** 2026-08-03  
**Architectural direction:** Trust Is Earned Through Verification; No Self-Approval; Small, Bounded Work Wins  
**Delivery boundary:** Independently mergeable post-implementation review, deterministic re-verification, and bounded remediation loop

## Objective

Add an agent-neutral post-implementation workflow to `familiar run` that captures the implementation diff and deterministic verification evidence, submits a bounded package to an independently selected reviewer, records structured findings, and returns blocking findings to the original implementation agent for bounded remediation.

After each remediation attempt, Familiar reruns the relevant deterministic verification and performs a new independent review. The loop is constrained by explicit attempt, token, cost, and duration limits. It always stops at a human approval boundary: either the implementation is clean enough to present for approval, or Familiar cannot safely continue automatically.

This PRD makes review, remediation, verification, accounting, and stopping decisions durable and inspectable. It does not grant acceptance authority to an agent, merge or push code, add a provider, or create an unrestricted repair loop.

## Motivation

PRD-005 established an agent-neutral execution boundary. PRD-006 and PRD-007 established deterministic, bounded implementation context. The current run path can execute one coding agent and retain coarse execution history, but successful process termination is not evidence that the change is correct. It does not collect a reviewable diff and verification bundle, assign an independent reviewer, persist findings, or bound attempts to repair blocking defects.

Familiar's philosophy requires both deterministic evidence and independent engineering reasoning. It also requires the implementing agent not to be the sole authority declaring its own work correct. A reliable post-implementation boundary therefore needs four distinct roles:

- the implementation agent proposes source changes;
- deterministic tools produce reproducible evidence;
- an independently selected reviewer challenges the result;
- a human accepts the implementation, approves architecture, or decides how to handle unresolved risk.

Without a structured loop, remediation is an ad hoc conversation whose scope, cost, and stopping point are unclear. This PRD turns that work into a finite workflow with exact inputs, durable evidence, explicit dispositions, and safe escalation.

## Scope

This PRD includes:

1. Capturing an implementation baseline and the repository-relative Git diff and changed-file set produced by the implementation agent.
2. Running a configured deterministic verification plan after implementation and after every remediation attempt.
3. Constructing a bounded `ReviewRequest` from the task, applicable contracts and invariants, implementation diff, changed files, and deterministic verification evidence.
4. Selecting a reviewer under explicit independence rules and invoking it through an agent-neutral review boundary.
5. Parsing and validating a structured `ReviewResult` containing evidence-backed `ReviewFinding` values.
6. Classifying findings with closed category and severity taxonomies and a recorded blocking policy.
7. Constructing one bounded `RemediationRequest` for unresolved blocking findings and dispatching it to the original implementation-agent assignment by default.
8. Recomputing the diff, enforcing scope containment, rerunning relevant deterministic verification, and reviewing the revised implementation.
9. Applying configurable maximum attempts and aggregate token, cost, and duration ceilings before each invocation or host operation.
10. Persisting each `ReviewCycle`, including actors, models when reported, usage, cost estimates when available, durations, findings, remediation outcome, and verification evidence.
11. Stopping for human review on clean review, exhausted limits, conflicting findings, scope expansion, architectural approval, unsuccessful verification, or lack of a suitable independent reviewer.
12. Defining a durable, human-governed lesson-proposal contract derived from resolved findings without implementing autonomous prompt rewriting or long-term learning.
13. Focused unit, storage, adapter, workflow, failure, accounting, and integration tests using fake agents and fake deterministic commands.

### Workflow ownership

The review coordinator owns lifecycle transitions, package construction, policy snapshots, attempt accounting, reviewer eligibility, remediation dispatch, stop decisions, and persistence coordination.

The repository evidence collector owns baseline-relative diff and changed-path capture. The deterministic verification runner owns exact command execution and evidence capture. Neither interprets model output.

Review-agent adapters own provider-specific invocation and translation to the neutral review contract. Implementation-agent adapters continue to own implementation and remediation execution. Adapters do not select themselves, waive limits, classify their own independence, or accept work.

Storage owns durable records and transactional integrity. The human remains the only acceptance and architectural authority.

## Non-goals

This PRD does not:

- add Ollama integration;
- add an additional provider or execution adapter;
- add a model router, capability router, automatic model ranking, or provider discovery;
- add semantic search, embeddings, vector storage, or relevance inference;
- send the entire repository to a reviewer by default;
- expose implementation chain-of-thought, hidden reasoning, credentials, unrelated logs, or unrelated project data;
- add autonomous architecture changes, create or approve ADRs, or alter an invariant without human approval;
- allow an implementation agent to review and approve its own work;
- treat reviewer agreement, an empty finding list, or passing tests as human acceptance;
- add automatic merging, rebasing, committing, pushing, publication, deployment, or release;
- add unrestricted retries, recursive task generation, open-ended repair, or scope expansion;
- add silent prompt mutation, autonomous prompt rewriting, or a long-term learning system;
- promote one-off findings into later prompts;
- modify architecture documents, contracts, ADRs, source files, or project policy during lesson extraction;
- generalize all existing execution history or build a complete target-state task, warrant, approval, or model-routing subsystem; or
- change prior PRDs.

## Architecture

The implementation adds a post-implementation coordinator around the existing agent-neutral execution and bounded-context boundaries:

```text
bounded implementation execution
          |
          v
capture base-relative diff + changed files
          |
          v
deterministic verification runner
          |
          v
bounded ReviewRequest
          |
          v
independent ReviewAgent
          |
          v
validated ReviewResult + findings
          |
          +-- no blocking findings ----------------------+
          |                                               |
          +-- blocking findings                           v
                  |                              human approval required
                  v
          bounded RemediationRequest
                  |
                  v
          original implementation agent
                  |
                  v
          scope check + diff recapture + verification
                  |
                  +---------- next review cycle
```

The coordinator is an application service, not a provider router. It receives explicit implementation and reviewer assignments from the composition root or test harness. Current production composition may construct Codex-backed implementations for both roles, but the domain contracts contain no Codex event types, executable arguments, or provider-specific session identifiers.

Review and remediation use separate role-specific interfaces even if an adapter shares lower-level process code:

```rust
pub trait ReviewAgent {
    fn review(
        &self,
        request: &ReviewRequest,
        output: &mut dyn std::io::Write,
    ) -> Result<ReviewResult, ReviewExecutionError>;
}
```

The existing `CodingAgent` remains the execution boundary for implementation and remediation unless a small neutral task-purpose extension is required. The reviewer contract is separate because review returns findings rather than a repository process result. Neither trait grants acceptance authority.

Canonical records are stored independently of rendered prompts and provider transcripts. Large diff, verification-log, and package payloads may be retained as content-addressed artifacts with hashes and repository-relative provenance; canonical rows retain their immutable references. Provider-specific raw output may be retained only under configured privacy and retention policy and is never authoritative over validated structured records.

### State progression

A review cycle progresses through explicit states equivalent to:

```text
collecting_evidence
  -> verifying
  -> awaiting_review
  -> reviewed
  -> remediating (only when policy permits)
  -> reverifying
  -> completed
```

Any stage can transition to `human_review_required` with an exact reason. Crashes leave an incomplete durable cycle that recovery marks interrupted; recovery must not silently re-invoke an agent or command because that could exceed a limit or duplicate a side effect.

`ReviewDisposition::ReadyForHumanApproval` means only that no unresolved blocking finding remains and required deterministic verification succeeded. ### Supporting canonical types

The implementation must also define closed supporting types rather than encode workflow state in strings:

- `AgentAssignment`: stable adapter/agent identity, provider identity when known, requested model when known, role, and isolated session identity when created.
- `AgentObservation`: assignment plus reported agent version and model, with explicit unavailable reasons.
- `ExecutionUsage`: optional input, output, and cached tokens; checked optional total; optional estimated cost in integer micro-USD; pricing provenance; and unavailable reasons.
- `ReviewTask`: task/PRD identity, objective, acceptance criteria, base revision, allowed paths, prohibited changes, and verification-plan identity.
- `ChangedFile`: path, Git change kind, old path for renames, and bounded line/range summary.
- `EvidenceRef` and `ArtifactRef`: content hash, media/type, byte size, repository and revision provenance, storage reference, truncation state, and omitted-byte count.
- `BoundedDocument` and `BoundedInvariant`: exact source identity, applicable excerpt or complete content, hash, selection reason, and token estimate.
- `VerificationEvidence`: check ID, exact argv and working directory identity, environment/tool identity, tested diff hash or revision, start/end/duration, exit or signal, status, structured summary, retained stdout/stderr references, and truncation metadata.
- `FindingEvidence`: a closed union of exact file range, diff hunk, test/check result, invariant, contract, or artifact evidence.
- `FindingStatus`: `Open`, `Resolved`, `Superseded`, `AcceptedRisk`, or `Invalid`; only a human may set `AcceptedRisk` for a blocking finding.
- `FindingResolution`: finding ID, claimed outcome, exact resulting evidence, and later reviewer disposition. An implementer claim alone does not set a finding to `Resolved`.
- `ReviewerIndependence`: `IndependentProviderOrModel` or `IsolatedSameModelFallback`, including the evidence used to establish it.
- `ReviewCycleState`: the explicit workflow states described above plus `HumanReviewRequired` and `Interrupted`.
- `ReviewStopReason`: `RetryLimitExhausted`, `TokenLimitExhausted`, `CostLimitExhausted`, `DurationLimitExhausted`, `ConflictingFindings`, `ScopeBroadened`, `ArchitecturalApprovalRequired`, `VerificationUnsuccessful`, `NoIndependentReviewer`, `MalformedReview`, `AgentFailure`, `EvidenceFailure`, `Interrupted`, or `CleanReview`.
- `ScopeCheckResult`: exact added, modified, deleted, and renamed paths compared with the request allowlist, plus a typed contained/broadened result.

### Finding validation and blocking policy

Every finding must contain at least one resolvable `FindingEvidence`. File evidence includes an exact path and non-empty line or diff-hunk range. Test evidence identifies the exact verification check and retained output. Invariant and contract evidence identifies the authoritative document, stable section or range, and source hash. Artifact-only evidence identifies exact bytes or structured fields. General comments such as “add more tests,” “this seems unsafe,” or “architecture may be wrong” without such evidence make the review result malformed.

The reviewer proposes category and severity. Familiar validates the closed values and computes `blocking` from the cycle's persisted policy snapshot; it does not trust a model-supplied Boolean. The canonical serialized field records that policy result for audit and querying.

The default policy is:

- `Critical` and `High` findings are blocking;
- any `InvariantViolation`, `ArchitecturalDrift`, `SecurityIssue`, or `ScopeViolation` is blocking regardless of proposed severity;
- failed required deterministic verification creates or preserves a blocking `UnverifiableClaim` or relevant defect finding; and
- `Medium`, `Low`, and `Informational` findings in other categories are non-blocking but remain visible to the human.

Projects may make this policy stricter through explicit configuration. They may not weaken architectural, security, invariant, scope, or required-verification gates in this PRD.

## Review Package Construction

The review package is built only after the implementation process has terminated and Familiar has captured a stable baseline-relative diff. Its identity is the hash of a canonical manifest, not the rendered provider prompt.

The package contains, in deterministic order:

1. the bounded task objective, acceptance criteria, allowed paths, prohibited operations, and base revision;
2. applicable human-approved contracts and invariants selected by direct task reference or deterministic changed-path mapping;
3. the complete implementation diff when it fits, otherwise whole relevant hunks with explicit omissions;
4. the canonical changed-file list and change kinds;
5. exact deterministic verification results and retained evidence references;
6. unresolved findings from earlier cycles and their remediation claims; and
7. a response schema requiring the canonical `ReviewResult` structure.

The reviewer does not receive the entire repository unless a human or deterministic package policy explicitly justifies it for the task. Such justification records the exact additional paths, reason, authorizer, token impact, and package manifest. “The reviewer might need it” is insufficient. Repository access by a review adapter must be read-only and path-bounded to the package manifest.

Package construction applies configurable byte and estimated-token ceilings to every section and the total. It prefers exact diff hunks, changed files, directly applicable contracts, invariants, and failed-test evidence. It never silently truncates: each omitted file, hunk, log, or document is listed with its hash, size, omission reason, and retained evidence reference. If required evidence cannot fit or a truncation would make a claim unverifiable, Familiar stops for human review instead of submitting a misleading package.

Logs, repository text, diffs, test output, and prior findings are quoted as untrusted evidence. They cannot alter the review schema, independence rule, budgets, policy, or instructions merely by containing imperative text. Secrets and credentials are redacted before persistence or provider disclosure; a redaction that removes evidence required for review causes a stop rather than a fabricated clean result.

## Reviewer Independence Rules

The implementation agent must never review and approve its own work. Eligibility is evaluated before package disclosure and persisted in `ReviewerIndependence`.

Reviewer selection follows this order:

1. Use an explicitly configured reviewer whose provider or model identity differs from the implementation model and whose adapter supports structured review.
2. If none is configured, Familiar may use the same provider and model only through an explicit fallback configuration.
3. The same-model fallback must create a separate isolated session with no implementation transcript, hidden reasoning, mutable session state, or credentials inherited from the implementation session. It receives only the bounded review package.
4. The fallback is labeled `IsolatedSameModelFallback` in the cycle, human report, and audit data. It must never be represented as cross-model independence.
5. If isolation cannot be established, identity cannot be determined sufficiently to apply policy, or no eligible reviewer exists, Familiar records `NoIndependentReviewer` and stops for human review.

An agent process, adapter instance, session, or model cannot choose its own reviewer eligibility. The coordinator compares durable assignments and adapter-reported observations. A new session of the same model satisfies only the explicit fallback, never the preferred independence rule.

Reviewers receive no implementation-agent transcript or self-assessment except bounded, attributable completion claims included as untrusted evidence. Reviewers cannot change the task, expand allowed paths, approve architecture, waive verification, authorize another retry, accept risk, or mark their own output as human-approved.

## Finding Taxonomy

The required categories have these exact meanings:

| Category | Meaning | Minimum evidence |
|---|---|---|
| `CorrectnessDefect` | Behavior contradicts acceptance criteria, specified behavior, or a reproducible expected result. | File/diff range plus reproduction or deterministic evidence. |
| `InvariantViolation` | The change violates an approved project invariant. | Exact invariant source and violating range or check. |
| `ArchitecturalDrift` | The change introduces or alters an architectural boundary without the required approved decision. | Exact architectural source and affected files/ranges. |
| `SecurityIssue` | The change creates a confidentiality, integrity, authorization, isolation, injection, or supply-chain risk. | Concrete attack path, unsafe range, or security-check evidence. |
| `TestGap` | Required behavior or a defect-prone path lacks proportionate deterministic coverage. | Exact uncovered criterion/path and proposed check boundary. |
| `MaintainabilityIssue` | The change introduces bounded, concrete complexity or fragility likely to impair safe future change. | Exact range and project convention or demonstrable failure mode. |
| `ScopeViolation` | The change modifies an unauthorized path, behavior, dependency, or external effect. | Task scope plus exact diff/path/effect. |
| `UnverifiableClaim` | A completion or remediation claim lacks required reproducible evidence, or evidence is missing/inconclusive. | Exact claim and missing, skipped, malformed, or inconclusive check. |

Severity reflects impact if the finding is real:

- `Critical`: immediate severe security, data-loss, irreversible, or system-wide correctness risk;
- `High`: task failure, required invariant/architecture/scope breach, or material security risk;
- `Medium`: meaningful defect or test/maintenance risk that does not invalidate the bounded implementation;
- `Low`: localized quality issue with limited impact; and
- `Informational`: evidence-backed observation requiring no corrective action.

Severity is not confidence. A reviewer must not inflate severity to compensate for weak evidence. Conflicting findings include mutually incompatible demanded remediations, incompatible interpretations of an authoritative contract, or a later review reopening a resolved finding without new evidence. Familiar preserves both findings and stops; it does not ask an agent to choose architecture or silently discard disagreement.

## Remediation Workflow

Blocking findings produce at most one `RemediationRequest` per cycle. Before dispatch, Familiar deduplicates only findings with the same category, affected evidence identity, and materially identical claim; disagreement and distinct evidence remain separate.

The request contains only:

- the original task objective and unchanged acceptance criteria;
- the original allowed and prohibited scope;
- unresolved blocking findings with exact evidence;
- relevant diff hunks, contracts, invariants, and verification failures;
- explicit checks that must pass; and
- per-attempt token, cost, duration, command, and path limits.

Remediation returns to the original implementation-agent assignment by default. This means the same neutral adapter and configured agent/model assignment, not the reviewer. When the adapter safely supports resuming the original implementation session, it may do so; otherwise it starts a new implementation-role session with the bounded remediation package. Session reuse is an adapter capability and is recorded, not a domain assumption. Changing the implementation assignment requires human approval and ends automatic remediation under this PRD.

The remediation agent may edit only the original allowed paths and may run only already authorized verification commands. It cannot broaden scope, alter acceptance criteria, change architecture or invariants, add unrelated cleanup, merge, commit, push, or publish. A requested fix that cannot be completed within those constraints is reported as blocked.

After remediation terminates, Familiar:

1. captures a new diff against the unchanged implementation baseline;
2. validates all changed paths and declared external effects against the original scope;
3. records the remediation agent's claims without treating them as resolved findings;
4. reruns the relevant deterministic verification plan;
5. creates a new bounded review package containing prior findings and new evidence; and
6. invokes an eligible independent reviewer in a new isolated review session.

A finding becomes `Resolved` only when later deterministic evidence and/or an independent review supports the resolution according to its category. A disappearance from reviewer output does not erase the prior finding; the next `ReviewResult` must explicitly resolve, supersede, or preserve each earlier blocking finding.

## Retry and Stopping Policy

Configuration adds a focused review section equivalent to:

```toml
[review]
enabled = false
max_review_attempts = 3
max_remediation_attempts = 2
max_total_tokens = 0          # zero means unavailable unless explicitly configured
max_total_cost_microusd = 0   # zero means unavailable unless explicitly configured
max_total_duration_ms = 0     # zero means unavailable unless explicitly configured
allow_isolated_same_model_fallback = false
```

Exact defaults may follow repository conventions, but review must be disabled by default for compatibility, and enabling automatic remediation requires finite positive review and remediation attempt limits plus at least one enforceable aggregate resource ceiling. A missing usage or price observation never counts as zero. If a configured cost or token ceiling cannot be evaluated before another invocation, Familiar stops for human review.

`max_review_attempts` counts every submitted review request, including malformed or failed responses. `max_remediation_attempts` counts every dispatched remediation request, including launch failures and interrupted executions. The initial implementation is not a remediation attempt. Limits apply to the task-wide workflow, not independently to a restarted process.

Before each review, remediation, or verification action, Familiar checks the persisted attempt counters and aggregate budgets. It reserves the configured per-action maximum where exact future consumption is unknown. It does not begin an action that could exceed a hard limit. Checked-arithmetic failure is a stop, never permission to continue.

Familiar stops and requires human review when:

- no unresolved blocking finding remains and all required deterministic verification succeeded (`ReadyForHumanApproval`);
- review or remediation retry limits are exhausted;
- token, cost, or duration limits are exhausted or cannot be enforced;
- findings conflict;
- remediation changes or requests paths, dependencies, behavior, authority, or external effects outside original scope;
- a finding or remedy requires architectural approval or an invariant change;
- required verification fails, is interrupted, is unavailable, remains inconclusive, or cannot be reproduced after remediation;
- no suitable independent reviewer is available;
- the review result is malformed or its evidence cannot be validated;
- evidence capture, persistence, agent execution, or recovery fails; or
- a human cancels or intervenes.

Only unresolved blocking findings may trigger automatic remediation. Non-blocking findings are reported to the human and do not consume a remediation attempt. A clean review never causes automatic merge, push, or acceptance.

## Verification Integration

Verification is deterministic, configured, and revision-bound. A `VerificationPlan` identifies exact commands, working directory, environment allowlist, timeouts, expected exit semantics, required/optional status, and which changed paths or finding categories make each check relevant. This PRD does not permit a reviewer or remediation agent to invent an executable verification command.

The initial post-implementation run executes all required task checks. After remediation, Familiar reruns:

- every required check affected by any changed path;
- every check cited by an open blocking finding;
- every check that previously failed or was inconclusive; and
- deterministic diff, scope, repository-cleanliness, and invariant checks on every attempt.

Projects may configure a full required verification suite after each remediation; that stricter choice supersedes relevance selection. Skipping an applicable required check is `Unsuccessful`, not `Passed`.

Each `VerificationEvidence` binds its result to the exact diff hash or tested revision and captures argv without shell ambiguity, working directory, selected non-secret environment identity, tool version when available, start and end times, duration, exit code or signal, structured status, and retained redacted logs. Valid statuses are `Passed`, `Failed`, `TimedOut`, `Signaled`, `Unavailable`, `Inconclusive`, and `Skipped`; only `Passed` satisfies a required check.

Verification output is untrusted data. It cannot alter policy, prompts, commands, or scope. Flaky retry behavior, if later supported, must be a deterministic verification policy with its own bound; it cannot consume hidden retries in this workflow.

## Execution Accounting

Every cycle records, for implementation, review, remediation, and verification stages as applicable:

- stable agent/adapter and role identity;
- provider and model when configured or reported;
- isolated session identity and same-model fallback status;
- start, end, and checked duration;
- input, output, cached, and checked total tokens when reported;
- estimated cost in integer micro-USD when pricing and usage are complete;
- pricing-table version or exact rates used;
- exact unavailable reason for every absent model, usage, cost, version, duration, or termination field;
- review package manifest and hash;
- findings and their lifecycle transitions;
- remediation request, result, changed paths, and scope outcome; and
- verification plan, commands, tested diff/revision, results, and evidence references.

Task-wide accounting is the checked aggregation of immutable stage observations. Cached tokens are reported separately and are not double-counted in totals. Cost is an estimate, not provider billing truth. Unknown values remain unknown and are never coerced to zero. Limits use the persisted aggregate plus reserved maximum for the proposed next action.

Cycle creation, stage finalization, finding insertion, and disposition changes are transactional where they share canonical state. Artifacts are written and hashed before their references become committed. If finalization fails, the workflow stops; it does not continue with an unrecorded action.

Existing `execution_history` remains a compatibility record for the implementation invocation. Review-cycle accounting uses additive normalized storage because one task may contain multiple actors, attempts, findings, verification results, and artifacts. It must not overload a single execution-history row or preserve the current `agent = 'codex'` constraint in new review tables.

## Lesson Extraction and Approval Lifecycle

After a finding is independently marked resolved, Familiar may create a durable `LessonProposal`. Lesson extraction is a proposal boundary, not automatic learning.

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum LessonClassification {
    ProjectInvariant,
    ProjectSpecificHeuristic,
    GeneralEngineeringHeuristic,
    OneOffFinding,
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct LessonProposal {
    pub lesson_id: String,
    pub project_id: String,
    pub classification: LessonClassification,
    pub statement: String,
    pub rationale: String,
    pub applicability: LessonApplicability,
    pub provenance: LessonProvenance,
    pub status: LessonStatus,
    pub proposed_at: String,
    pub reviewed_by: Option<HumanApproval>,
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct LessonProvenance {
    pub finding_id: String,
    pub review_cycle_id: String,
    pub remediation_id: String,
    pub resolution_evidence: Vec<EvidenceRef>,
    pub source_revision: String,
}
```

`LessonStatus` is `Proposed`, `Approved`, `Rejected`, or `Superseded`. `LessonApplicability` records relevant project, paths/modules, task/finding categories, exclusions, and a maximum future token allocation.

Lifecycle rules are:

1. Only a resolved finding can produce a lesson proposal.
2. Every heuristic and invariant proposal carries provenance linking to the exact finding, remediation, resolution evidence, review cycle, and source revision.
3. `OneOffFinding` is retained for audit but is ineligible for future prompt injection and cannot become `Approved` prompt guidance.
4. `ProjectInvariant` requires explicit human approval before it is authoritative or eligible for any future context package. Approval identifies the human, exact statement and scope, source revision, and time.
5. Project-specific and general engineering heuristics remain non-authoritative advice. Any future use must preserve provenance and label them as heuristics, not contracts.
6. Lesson extraction never edits architecture documents, contracts, ADRs, source files, prompts, or policy. A proposed architecture or invariant change stops at human review and follows the project's separate authoritative-document process.
7. Rejection and supersession remain durable; proposals are never silently overwritten.
8. Any later feature that injects approved lessons into a prompt must select them by deterministic relevance scope, apply an explicit section and total token budget, report omissions, and preserve source/provenance references.

This PRD implements the lesson contract, persistence boundary, proposal lifecycle, and tests only. It does not implement automatic lesson generation, autonomous prompt injection, prompt rewriting, cross-project learning, model training, or semantic retrieval. A human or later explicitly scoped command may create a proposal from a resolved finding.

## Trust Boundaries

### Human authority

Humans alone accept changes, approve architecture and invariants, accept blocking risk, authorize scope expansion, select a replacement implementation agent, and permit publication. `ReadyForHumanApproval` is a queue state, not approval.

### Implementer and reviewer

Both are untrusted workers. The implementer cannot review or resolve its own work authoritatively. The reviewer cannot edit source, grant authority, waive checks, or approve architecture. Same-model fallback is isolated and disclosed.

### Repository and evidence

The repository and Git history are authoritative for source and diff state. Repository content, diffs, test logs, generated artifacts, and issue text may contain prompt injection and are treated as quoted data. Evidence hashes and revision identity prevent a result for one diff from being applied to another.

### Verification tools

Commands may be incomplete, compromised, flaky, or misconfigured. Familiar records exact invocation and environment, distinguishes unavailable from passed, and never converts absence into success.

### Provider and privacy

Review packages may cross a provider boundary only under existing project privacy authority. They contain least context, no credentials, and explicit redaction and omission records. Provider output is untrusted until schema and evidence validation succeed.

### Storage and recovery

Canonical rows and artifact references are durable workflow state. Partial writes, missing artifacts, hash mismatches, and interrupted stages halt automation. Recovery is observable and does not replay work without rechecking limits and human policy.

### Lesson boundary

Model-proposed lessons are non-authoritative. They cannot mutate source or future prompts, and only explicit human approval can make a project invariant authoritative.

## Failure Semantics

Failures are explicit terminal or human-review states; they are never reported as a clean review.

- Diff capture failure, unstable worktree state, baseline mismatch, or artifact hash failure stops before review.
- A required verification status other than `Passed` is unsuccessful. Before the first review it may be included as evidence only if policy permits review for diagnosis; it cannot lead to `ReadyForHumanApproval`.
- Review launch, timeout, signal, malformed structure, unknown enum value, missing required evidence, manifest mismatch, or output validation failure consumes a review attempt and stops unless an explicitly bounded retry remains safe.
- Agent text outside the structured result is diagnostic only. It cannot create, resolve, or suppress a finding.
- Remediation launch, timeout, signal, malformed result, or output failure consumes a remediation attempt. Any produced diff is still captured and scope-checked before stopping.
- A path or effect outside original scope immediately records `ScopeBroadened` and stops. Familiar does not automatically revert user or agent changes.
- Architectural drift or a requested invariant/contract change records `ArchitecturalApprovalRequired`; no automatic remediation is issued for the architectural choice.
- Conflicting findings are retained together and stop the loop.
- Unknown token or cost usage prevents another action when that value is required to enforce a configured ceiling.
- Exhausted attempts or budgets retain all prior findings and evidence and end in `HumanReviewRequired`.
- A clean result with successful required verification ends in `ReadyForHumanApproval`, never `succeeded`, `merged`, or `approved`.
- Persistence failure stops before any further invocation. Finalization failure leaves an explicit interrupted record for recovery.
- Cancellation terminates the supervised process where supported, captures available evidence, and requires human review.

No failure path automatically commits, resets, deletes, merges, pushes, or otherwise rewrites the worktree.

## Acceptance Criteria

1. A post-implementation coordinator captures a baseline-relative diff, changed-file set, and deterministic verification evidence before review.
2. Canonical public types exist for `ReviewRequest`, `ReviewFinding`, `FindingCategory`, `FindingSeverity`, `ReviewResult`, `RemediationRequest`, `RemediationResult`, `ReviewCycle`, and `ReviewDisposition` with the semantics in this PRD.
3. Finding categories include correctness defect, invariant violation, architectural drift, security issue, test gap, maintainability issue, scope violation, and unverifiable claim as closed typed values.
4. Every accepted finding cites at least one exact file range, diff hunk, test/check, invariant, contract, or retained evidence reference; vague unsupported findings make the result malformed.
5. Blocking status is computed from a persisted policy snapshot, with critical/high and invariant, architecture, security, scope, and required-verification findings blocking by default.
6. Review input is limited to the task, applicable contracts and invariants, implementation diff, changed files, verification evidence, and unresolved prior findings under explicit byte and token budgets.
7. The entire repository is unavailable to the reviewer by default; any expansion is exact, justified, attributable, budgeted, and reported.
8. The implementation agent cannot be selected as its own reviewer or acceptance authority.
9. A different configured provider/model is preferred for review. Same-model review works only through an explicitly enabled, isolated, separately reported fallback session with no implementation transcript or state.
10. Absence of a suitable independent reviewer produces `HumanReviewRequired` and no remediation or clean disposition.
11. Unresolved blocking findings produce one bounded `RemediationRequest` containing only relevant evidence and the original task authority.
12. Remediation returns to the original neutral implementation-agent assignment by default and never to the reviewer; replacement requires human approval.
13. Remediation cannot expand allowed paths, task behavior, dependencies, architecture, privileges, external effects, or acceptance criteria.
14. Familiar captures and scope-checks the resulting diff and reruns every relevant required deterministic check after remediation.
15. A new independent review explicitly disposes every prior blocking finding; implementer claims or omission from later output do not resolve findings.
16. Review and remediation attempts have configurable finite maxima, and aggregate tokens, cost, and duration use checked accounting and pre-action limit checks.
17. Every cycle durably records agent/adapter, provider and model when available, isolated-session/fallback status, usage, estimated cost when available, duration, package manifest, findings, remediation outcome, changed files, and verification evidence.
18. Unknown model, usage, cost, version, or termination values remain `None` with exact unavailable reasons and are never coerced to zero.
19. The workflow stops for human review on exhausted limits, conflicting findings, scope broadening, architectural approval, unsuccessful verification, missing independence, malformed evidence, persistence failure, or interruption.
20. A clean review plus successful required verification produces only `ReadyForHumanApproval`; no code is accepted, merged, committed, pushed, published, or deployed automatically.
21. The workflow and durable schemas are agent-neutral and contain no Codex JSON, executable argument, or permanent provider assumption.
22. Current production may compose Codex-backed implementation and review adapters, but same-model use follows the isolated fallback rule and is disclosed.
23. Resolved findings may produce durable lesson proposals classified as project invariant, project-specific heuristic, general engineering heuristic, or one-off finding.
24. One-off findings are never eligible for future prompt injection; project invariants require explicit human approval; heuristics retain finding/remediation provenance.
25. Lesson extraction does not modify architecture, contracts, ADRs, source, policy, or prompts, and this PRD adds no autonomous prompt rewriting or long-term learning.
26. Review is disabled by default so existing `familiar run`, history, usage, context, prompt, streaming, pricing, and exit behavior remain unchanged unless the feature is explicitly enabled.
27. No Ollama integration, provider adapter, model router, semantic search, embedding, automatic merge/push, or unrestricted repair loop is introduced.
28. The implementation is one independently mergeable increment and changes no prior PRD, philosophy, architecture document, ADR, or contract.

## Test Strategy

### Domain and serialization tests

- Round-trip every canonical enum and record through the chosen durable serialization format.
- Reject unknown categories, severities, dispositions, states, evidence variants, and stop reasons.
- Validate repository-relative paths, non-empty ranges, unique IDs, diff/manifest hashes, timestamps, checked durations, and checked token/cost totals.
- Prove the blocking policy for every category/severity combination and retain the exact policy snapshot per cycle.
- Reject missing evidence, dangling finding references, duplicate finding IDs, invalid status transitions, and implementer-authored acceptance.

### Review-package tests

- Construct the same package twice and assert identical ordering, manifest, and hash.
- Assert inclusion of only task scope, applicable contracts/invariants, diff/changed files, verification evidence, and unresolved prior findings.
- Assert unrelated repository files, transcripts, credentials, environment values, and hidden reasoning are absent.
- Exercise exact-fit, one-unit-over, required-evidence-over-budget, whole-hunk omission, log truncation, redaction, and checked-overflow behavior.
- Assert every omission and redaction is visible and required-evidence loss stops before reviewer invocation.
- Assert whole-repository access is denied unless exact additional paths and human/policy justification are recorded.

### Independence and adapter tests

- Reject the implementation session as reviewer.
- Prefer a configured different provider/model assignment.
- Reject same-model review when fallback is disabled or session isolation cannot be proven.
- With fallback enabled, create a distinct fake session, pass only the package, and assert `IsolatedSameModelFallback` appears in durable state and the human report.
- Return `NoIndependentReviewer` without invoking remediation when no eligible reviewer exists.
- Use fake review agents only; tests never invoke a real Codex installation or remote provider.

### Finding and conflict tests

- Accept exact file, diff, test, invariant, contract, and artifact evidence fixtures.
- Reject vague claims, nonexistent paths/ranges, unknown checks, manifest mismatches, and unsupported clean results.
- Cover every category and severity and verify computed blocking status.
- Deduplicate materially identical findings without erasing distinct evidence.
- Preserve conflicting remediation demands and stop without choosing between them.
- Require the next review to dispose every previous blocking finding explicitly.

### Remediation and verification tests

- Assert a blocking result creates exactly one bounded request and a non-blocking-only result creates none.
- Assert the request targets the original implementation assignment and contains no unrelated source or findings.
- Use a fake implementation agent to modify only temporary-repository fixtures.
- Detect added, modified, deleted, renamed, symlinked, dependency, and external-effect scope expansion and stop without reverting it.
- Rerun all required, affected, cited, failed, and inconclusive checks after remediation.
- Bind results to the exact diff hash and reject stale verification evidence.
- Cover pass, fail, timeout, signal, unavailable, inconclusive, skipped, malformed log, and output-truncation statuses.
- Prove that an implementation claim alone cannot resolve a finding.

### Retry, accounting, persistence, and recovery tests

- Exercise exact review/remediation attempt limits, zero remaining budget, exact-fit budget, and one-unit-over token, cost, and duration ceilings.
- Count launch, timeout, malformed-output, and interrupted attempts.
- Treat unknown usage or price as unknown and stop when a configured ceiling cannot be enforced.
- Verify checked aggregation, cached-token treatment, price provenance, and unavailable reasons.
- Persist and reload complete multi-cycle workflows with findings, artifacts, verification, remediation, and dispositions intact.
- Inject failure between artifact write and transaction commit, during finalization, and after process termination; assert no unrecorded retry occurs.
- Recover incomplete cycles as interrupted and require policy/human action before replay.

### Lesson lifecycle tests

- Permit proposals only from resolved findings and require complete finding/remediation/evidence provenance.
- Keep one-off findings permanently ineligible for prompt use.
- Require attributable human approval before a project invariant becomes authoritative.
- Preserve proposed, rejected, approved, and superseded heuristic history.
- Assert lesson operations never write architecture, contract, ADR, source, configuration, policy, or prompt files.
- Assert no production path injects a lesson into an agent prompt in this PRD.

### Compatibility and verification commands

- With review disabled, preserve existing prompt bytes, fake-Codex arguments and streaming, history rows, pricing, usage, and exit-status behavior.
- With review enabled, run end-to-end temporary-repository fixtures for clean review, one successful remediation, exhausted remediation, conflicting findings, scope expansion, failed verification, and absent reviewer.
- Run `cargo fmt --all -- --check`.
- Run focused tests for the review domain, package builder, verification runner, agent adapters, coordinator, configuration, storage repositories, and migration.
- Run focused Clippy with warnings denied for affected crates and targets.
- Attempt the complete workspace test suite and distinguish pre-existing or unrelated failures.

No test may merge, commit, push, invoke a real remote model, read developer credentials, or modify a non-temporary repository.
