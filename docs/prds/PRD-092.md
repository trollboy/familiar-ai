# PRD-092: The Gate Builds What Users Install

## Objective

The verification gate does not build the tray. `Dockerfile` and
`docker-compose.yml` both pass `--no-default-features`, and the image
installs only `ca-certificates`, so `crates/familiar-ai-tray` is compiled
by nobody — it is excluded from the workspace as well.

That is not a hypothetical. The tray shipped in PRD-004 and was dark for
months, and when it was revived on 2026-09-08 three defects had
accumulated behind each other, every one of them invisible to a green
gate: a `daemon_run` call left stale by FAM-BUG-050 so the feature did
not compile at all, a SIGTERM path that stopped the workers and left the
process alive, and an icon assertion still pinned to 32x32 after the
asset became 512x512 in `ddd3d7a`.

A gate that proves a subset green and calls it the build is not a gate.
Whatever a user installs is what has to compile and pass.

## What changed since this PRD was written (2026-09-11)

The original specification required the tray to become opt-in so that the
default build needed no unusual system package. That premise is gone: the
package in question was `libxdo`, pulled in by default features of
`tray-icon` and `muda` purely to drive muda's predefined Copy/Cut/Paste
items, which this menu never uses. Turning those defaults off removed the
dependency outright, so the default build already needs no unusual
package, and the tray stays in the default set where the standing
direction requires it.

Two criteria are therefore retired rather than carried:

- *"the tray is an opt-in feature rather than a default"* — the goal it
  served is met by other means, and the means it prescribed now
  contradicts a standing direction. The goal survives in the first
  criterion; the means does not.
- *"build wall-clock measured per supported platform ... with the macOS
  build-speed pathology as the pinned case"* — no macOS host is available
  to this project, so the criterion could only ever be recorded as
  satisfied without being tested. Build-time ceilings are worth having and
  belong in their own PRD, against a platform that can actually run them.

## Design

- **The gate compiles what ships.** The verification image installs the
  documented minimal dependencies — GTK for the tray — and the gate drops
  `--no-default-features`. A crate that nothing compiles is a crate
  nothing tests.
- **The workaround flag disappears from documentation.** A check enforces
  it, so the flag cannot creep back into a README line and become
  permanent again. It currently has two live targets: `Dockerfile` and
  `docker-compose.yml`.
- **Optional features fail early and by name.** Enabling the tray without
  GTK reports the missing dependency at configure time instead of failing
  at link.
- **Gate and install agree.** One resolved feature set, checked.
- **No workspace member is silently excluded.** `familiar-ai-tray` sits
  outside the workspace today, which is the mechanism that made the rot
  possible; a check names any member the gate does not compile.

## Scope

The verification image's system dependencies; removing the workaround
flag from the gate and from documentation; the documented-flag check; the
tray's early dependency diagnostic; gate and install feature-set parity;
the workspace-membership check; documentation updates.

Out of scope: packaging, installers, or distribution channels; the tray's
own functionality; Windows support beyond whatever the current feature
matrix already claims; the verification gate's test selection (PRD-088);
and build-time ceilings, which need a platform this project does not have.

## Assumptions (recorded at specification time, 2026-09-04; revised 2026-09-11)

- Supported platforms are current Linux and macOS; a platform without a
  gate job is not claimed as supported. macOS has no gate job here, which
  is why the build-time criterion was retired rather than restated.
- GTK is an acceptable dependency of the default build. It is already
  required to build the tray at all, and the tray is required to be live.
- The tray is genuinely optional for the daemon and CLI at the code level
  even though it ships by default; if any non-optional path depends on
  it, that dependency is a defect to report rather than to design around.
