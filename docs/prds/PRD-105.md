# PRD-105: Finish PRD-100's unremediated findings

## Why this exists

PRD-100 (the owned agent loop — vendor CLI independence) was resumed on
2026-09-21 after a surgical repair unblocked its gate. Its independent
review returned four findings, none of them blocking. The coordinator's
remediation stage fixed exactly one:
`raw-agent-ignores-request-working-directory`, the high-severity sandbox
defect, by threading `request.working_directory` through
`RawAgentHost::executor()`.

Of the remaining three, one turned out not to be a defect at all (see
**Withdrawn** below). The two here are real, and they were dropped between
the first review and the second without being addressed.

"Did not block" is not "was done". A finding that ships unfixed with a
landed candidate is a defect in the tree, not a note in a ledger.

One of the two is worse than a leftover. The reviewer's own words on
`raw-agent-model-override-not-attributed`:

> The accounting row and the `ExecutionResult` disagree with the provider
> request whenever `request.model` is set, which is precisely the
> attribution this PRD's acceptance criteria require to be a measurable
> fact rather than an assumption.

That is an acceptance criterion of PRD-100 reported as unmet by the
reviewer that approved it. PRD-100 stays completed — completion is
immutable (see `docs/contracts/completion-is-immutable.md`). This PRD is
where the unmet part gets built.

## The two findings

### 1. `raw-agent-model-override-not-attributed` (medium, correctness_defect)

`RawAgent::execute` builds `LoopConfig.model` from
`request.model.map(str::to_owned).unwrap_or_else(|| self.spec.model.clone())`,
so a caller-supplied override is what the inference attempt actually runs
against. But `RawAgent::execution_result` unconditionally reports
`model: Some(self.spec.model.clone())`, and the PRD-051 persistence path
receives `self.model_identity`, captured in `SqliteRawAgentHost::new` from
`worker.model` at construction time.

Both name the worker's configured model, not the model the attempt ran on.
Cost and usage attribution are the point of PRD-051; an attribution that is
wrong whenever an override is set is not a measurement.

### 2. `reservation-leaked-on-pre-loop-failure` (low, correctness_defect)

`RawAgent::execute` acquires the PRD-064 reservation, then builds a
current-thread tokio runtime. If `Builder::build()` fails, `execute`
returns `AgentExecutionError::Launch` without calling
`RawAgentHost::finish` — the only path that settles or releases the
reservation. The grant id is already stored, so the reservation stays held
in `resource_reservations` with no terminal outcome.

The severity is low because the trigger is rare. The shape is not: any
future fallible step added between the reservation and `run_loop` inherits
it.

## Withdrawn

`denied-read-path-search-list-uncovered` (review 1), re-raised as
`denied-read-path-misses-search-list-argument` (review 2), is **not a
defect**. Both rest on the claim that `search-list` "does not carry its
target under the key `path`". Its declaration in `raw_runtime.rs` says
otherwise:

```rust
args_schema: ArgSchema { required: &["query"], optional: &["path"] },
```

`RequestScopedAuthorizer::authorize` reads `call.arguments.get("path")`,
which is exactly the declared key. The genuine escape — an absent `path`
walking from the worktree root through the denied subtree — was closed
inside this candidate with a fail-closed `None` arm and the regression
`denied_read_path_refuses_a_pathless_search_list`. The only other argument
is `query`, a search string, and the walk is bounded by the worktree root
per `runtime_path_containment.rs`.

This PRD originally carried a criterion to "fix" it. That criterion was
written by taking the finding at face value instead of reading the schema,
and has been removed.

## Resolved

- **Why not reopen PRD-100.** Completion is immutable. A completed PRD that
  is edited after the fact destroys the only durable record of what was
  actually delivered against what was promised.
- **Why these two and not a general hardening pass.** Each is a specific
  claim with cited evidence from one review. Widening the scope here is how
  a scope_broadened retention gets earned.
