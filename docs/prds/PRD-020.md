# PRD-020: Parallel Worktree Execution

**Status:** Partially implemented — reconciliation required by PRD-030
**Date:** 2026-08-04
**Depends on:** PRD-017, PRD-030
**Architectural direction:** Autonomy Fails Closed; Repository Is Truth; Small, Bounded Work Wins
**Delivery boundary:** Independently mergeable parallel scheduling of independent dependency subgraphs across isolated git worktrees

## Reconciliation Note

Current `main` has bounded concurrent per-PRD worktrees, conflict-scope
serialization, ownership, heartbeats, recovery, and optional delivery. Remaining
work is to make scheduling consume PRD-030's profile-neutral dependency graph,
prove direct and transitive prerequisite blocking under every profile, and
reconcile this specification's older component-worktree/no-delivery assumptions
with the newer repository delivery-policy boundary in PRD-033.

## Objective

Let `familiar-ai drive` execute independent regions of the backlog concurrently, each in its own dedicated git worktree, so one stuck PRD stalls only its own dependents instead of the whole night — while keeping every single-run semantic, the fail-closed doctrine, and the no-automatic-merge rule exactly as they are.

## Motivation

The serial driver (PRD-017) stops making progress on an entire night when an early PRD is retained, even when unrelated work was eligible. Dependency information already exists and is already validated; the missing piece is purely scheduling and workspace isolation. The prize is the north star's Stage 2: independent branches continue past a failure, and the morning report shows several finished tracks instead of one stalled one.

## Execution Model

- **Unit of parallelism: the independent subgraph.** The validated dependency graph is partitioned into weakly-connected components. PRDs in the same component share state by construction and execute serially, in eligibility order, inside one worktree. Distinct components share nothing and may run concurrently, bounded by a configured parallelism ceiling.
- **One worktree per active component.** The driver creates `git worktree add` workspaces under a driver-owned directory, each on a fresh branch named deterministically from the session and component. Successive PRDs of a component run in its worktree exactly as today's serial runs accumulate in the main worktree. Familiar still never commits, merges, rebases, or pushes: each component branch's worktree simply holds its uncommitted results, and integrating them remains the human's morning decision, with the worktree paths listed in the report.
- **Backlog truth stays global.** Claims, completions, and retained states go to the same single database with the same actors and semantics; the scheduler consults eligibility globally, so a retained PRD makes exactly its own dependents ineligible while other components proceed.
- **Fail-closed workspace handling.** A worktree that cannot be created cleanly (dirty target path, git failure) fails that component with a recorded reason and touches nothing else. Worktrees of finished components are left in place for the human; the driver never deletes a worktree containing changes.

Configuration, canonical shape:

```toml
[driver]
max_parallel_components = 1   # 1 = serial (today's exact behavior); >1 enables parallelism
worktree_root = ""            # default: a driver-owned directory under the data dir
```

`max_parallel_components = 1` must reproduce PRD-017 behavior byte-identically, including running in the primary worktree rather than creating any new one.

## Scope

This PRD includes:

1. Component partitioning over the validated graph and a deterministic scheduler (stable ordering; bounded concurrency; component-serial execution).
2. Worktree provisioning and branch naming, driver-owned root directory, and fail-closed creation handling.
3. Threading the per-component worktree through the existing run workflow's repository/worktree inputs without changing any run semantics.
4. Session and attempt records extended additively (component id, worktree path, branch) via the next unused migration.
5. Concurrent-safe budget-warrant enforcement: ceilings apply to the session as a whole; checks and record writes are serialized through the existing single database.
6. Report input: PRD-018's renderer gains the component/worktree columns from the extended records (rendering change only).
7. Focused tests with fake agents: partitioning, scheduling order, retained-component isolation, worktree fail-closed paths, serial-mode byte-identity.

## Non-goals

This PRD does not:

- commit, merge, rebase, push, or delete worktrees containing changes — integration remains human;
- parallelize within a component, split a PRD, or run implementation and review of one PRD concurrently;
- change claim, completion, recovery, review, verification, scope, or accounting semantics;
- add cross-machine or distributed execution;
- introduce model-driven scheduling decisions; or
- modify prior PRDs, architecture documents, ADRs, contracts, or philosophy.

## Acceptance Criteria

1. With parallelism enabled, PRDs in distinct components execute concurrently up to the ceiling, each component serially in its own worktree on its own deterministic branch, with all claims and completions recorded globally with unchanged semantics.
2. A retained PRD leaves its component stopped and its dependents ineligible while other components continue; the session terminates only for PRD-017's closed reasons evaluated session-wide.
3. `max_parallel_components = 1` is byte-identical to PRD-017 behavior, creating no worktrees.
4. Worktree creation failures fail only their component, with a recorded reason; no worktree containing changes is ever deleted; Familiar performs no commit, merge, or push anywhere.
5. Budget ceilings are enforced for the whole session under concurrency, with cost-unknown semantics unchanged.
6. Extended session records capture component, worktree, and branch per attempt; the report renders them; the storage change is one additive migration.
7. All tests use fake agents and temporary repositories; concurrency tests are deterministic (bounded, ordered assertions, no sleeps-as-synchronization).
8. Formatting, focused Clippy, focused tests, and the full workspace suite pass, with demonstrably pre-existing failures reported separately with exact evidence.
9. The change is confined to the expected files and is independently mergeable.

## Test Strategy

- Partitioning unit tests: known graphs → pinned components and orderings, including single-component (serial) and disjoint-roots shapes.
- Scheduler tests with fake agents and per-component recording: concurrency ceiling honored; retained component isolates; independent components complete; deterministic attempt records.
- Worktree tests in temp git repositories: creation, branch naming, fail-closed on unclean targets, preservation of changed worktrees.
- Serial-mode regression: `max_parallel_components = 1` fixture equals PRD-017 fixtures byte-for-byte in records and narration.
- Migration and round-trip coverage for the extended records; report rendering pinned with component columns.

## Definition of Done

PRD-020 is done when a night's drive runs independent backlog regions concurrently in isolated worktrees under one global warrant, a failure strands only its own branch of work, the morning report names each component's worktree for human integration, serial mode remains byte-identical to PRD-017, and nothing anywhere gained the power to commit, merge, or push.
