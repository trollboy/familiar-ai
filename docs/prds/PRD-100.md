# PRD-100: Familiar's Own Loop Is a Selectable Worker

## Objective

Familiar is not dependent on Codex and Claude. It **chooses** to be, and
the choice is a three-entry registry.

`builtin_adapter_factories()`
([registry.rs:137-147](../../crates/familiar-ai-agent/src/registry.rs#L137-L147))
is the complete set of things that can implement a PRD:

```rust
factories.register(Box::new(CodexFactory { id: "codex" }))
factories.register(Box::new(CodexFactory { id: "ollama" }))
factories.register(Box::new(ClaudeCodeFactory))
```

Three entries, two of them the same factory. `build_agent`
([run.rs:576](../../crates/familiar-ai-daemon/src/run.rs#L576)) is the
only path that constructs a worker for a stage, and it can only ask that
registry. In the entire production codebase, exactly two types implement
`CodingAgent`: `ClaudeCodeAgent` and `CodexAgent`. Every other
implementation is a test fake.

Note the second line. **Ollama — a local model on the owner's own
hardware — is driven through the Codex CLI.** The cheapest worker
available is reached by shelling out to a vendor's agent product.

## What Familiar already owns and cannot use

This is the uncomfortable part. Familiar has already built its own agent:

| Component | Lines | State |
|---|---|---|
| `raw_runtime.rs` — the loop: turn management, tool validation, tool results, stop reasons, resume | 1,387 | built |
| `anthropic.rs` — raw Messages API adapter | 1,502 | built |
| `openai.rs`, `xai.rs` — raw adapters | 248 | built |
| `agent_runtime.rs` — WAL tool journal, sandboxed executor, scope authorizer, usage persistence | — | built |
| `familiar-ai-repomap` | 235 | built |
| `familiar-ai-context`, `familiar-ai-compress`, `familiar-ai-tokens` | — | built |

The loop is write-capable. `CapabilityId::ALL`
([raw_runtime.rs:53](../../crates/familiar-ai-agent/src/raw_runtime.rs#L53))
is seven canonical capabilities including `apply-edit` and `run-command`,
and `agent_runtime.rs` supplies the sandboxed executor, the write-ahead
journal, and a write-scope authorizer derived from a PRD's own PRD-013
Expected Files contract. This is not a read-only prototype.

And it is referenced, outside its own module, only by **tests** and by
`local_worker_runtime.rs`. It is not in the factory registry. It does not
implement `CodingAgent`. `AnthropicAdapter` implements `InferenceAdapter`
— a different trait, on the other side of a wall with no bridge across
it.

So PRD-058's stated objective — *"give Familiar its own agent loop so raw
inference endpoints become real workers"* — is unmet in the only path
that matters. Its own phasing explains how: phase 1 was the read-only
reviewer, phase 2 the journaled write capabilities "for bounded
implementation stages", phase 4 "additional adapters". The capabilities
from phase 2 exist. Nothing ever promoted the loop to an implementer.

**One missing bridge is the entire vendor dependency.**

## What this costs today

- **Goal 1 cannot be attempted.** "Cheap — intelligent multi-step,
  multi-model orchestration" is unreachable when the cheapest selectable
  worker is a frontier vendor CLI. Every PRD attempt recorded on this
  host ran `claude-code`, almost all on Sonnet.
- **Cross-vendor review depends on which CLIs are installed.** The
  doctrine says multi-vendor pays at review time, one vendor implementing
  and a different one reviewing. Wave 4 routed review to Ollama through
  the Codex factory, the reviewer was incompatible, and the candidate was
  retained `human_review_required`. That is what vendor diversity through
  a CLI middleman actually delivers.
- **The epigraph is contradicted.** *"Keep the daemons replaceable."*
  There are two daemons, both vendor CLIs, and replacing them is not a
  configuration change.
- **The interface is not ours.** Prompt shape, tool vocabulary, session
  semantics, cost surface, and model availability are set by two vendors
  and change without notice. PRD-068 exists because of cache noise from
  one of them.

## What Aider demonstrates

Aider talks to providers directly — `--model deepseek --api-key
deepseek=<key>` — and owns the pieces in between: a whole-codebase repo
map, its own edit formats, its own git commits, and a published
edit-success leaderboard it uses to choose between models. No vendor
agent in the middle. It reports 88% of its own new code written by
itself.

The comparison is not "Familiar should become Aider." It is that Familiar
has already built the same organs — repo map, context compiler, token
accounting, tool loop, sandbox, three provider adapters — and then routes
every unit of real work through someone else's agent anyway.

The one thing Aider has that Familiar does not is the part worth
respecting: **a measured edit-success rate.** Aider's whole benchmark
practice exists because getting a raw model to emit an edit that applies
cleanly is genuinely hard, and it is exactly the risk this PRD takes on.
Familiar's `apply-edit` has never implemented a PRD, so its reliability
is unknown. That is why the last acceptance criterion records edit
outcomes: this PRD's success or failure must be a number, and PRD-098 is
what will read it.

## Design

- **One bridge type.** `RawAgent` implements `CodingAgent` over the
  existing loop and an injected `InferenceAdapter`. The loop core does
  not change; neither does the review, verification, scope, or
  accounting machinery above it.
- **Register it, and fail closed on the unregistered.** The owned runtime
  becomes a factory entry. A configured runtime with no factory is
  refused when configuration resolves, naming the registered set — not
  discovered mid-session, which is how the Unsloth credential failure
  (FAM-BUG-020) burned eleven silent minutes.
- **Local stops going through Codex.** The `ollama` id backed by
  `CodexFactory` is the clearest single artefact of the dependency, and
  it is the first thing to move.
- **Identical authority, no exceptions.** Scope authorization on every
  `apply-edit`, sandbox, journal, reservation, usage attribution. A
  Familiar-owned implementer that is trusted more than a vendor one would
  be a security regression dressed as ownership.
- **The CLIs stay, and stay the default.** They work. This PRD adds a
  third option and changes no default, so it can land without a
  migration and be judged on measured results.

## Scope

The `RawAgent` bridge; its factory registration and fail-closed
unregistered-runtime diagnostic; moving the local path off the Codex
factory; authority parity with the CLI path; cross-provider stage
independence enforced on recorded identity; edit-outcome recording;
default-preserving configuration; the agent-loop contract document;
regressions in a dedicated test file, including a full cycle with no
vendor CLI on `PATH`.

Out of scope: retiring either vendor CLI or changing any default to
prefer the owned loop — that is a decision for after the edit-success
number exists, and taking it here would be the same unmeasured steering
this queue has already paid for twice. Also out of scope: edit-format
design work beyond what `apply-edit` already specifies, a benchmark
harness comparing models (that is PRD-032's probation surface once this
lands), repo-map improvements, prompt-caching economics for raw providers
(PRD-029/068), and PRD-094's local dispatch reachability, which this
overlaps and should be sequenced against rather than duplicated.

## Assumptions (recorded at specification time, 2026-09-17)

- The seven canonical capabilities are sufficient for a bounded PRD
  implementation. If a real PRD needs a capability the set lacks, that is
  a finding to report with the named capability, not a reason to widen
  the set mid-implementation.
- `InferenceAdapter` and `CodingAgent` are bridgeable without changing
  either trait. If the bridge requires a trait change, the change is
  reported before it is made, because both are contracts other PRDs
  depend on.
- Raw-provider credentials already resolve through PRD-074's
  credential-store descriptors; this PRD introduces no credential
  handling of its own.
- Edit success on real PRDs may be poor on first contact. A low measured
  rate is a successful outcome of this PRD — it is the number that has
  been missing — and the response is model selection and edit-format
  work, not reverting to the CLIs by default, which remains where the
  default already is.
