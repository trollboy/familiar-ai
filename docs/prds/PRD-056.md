# PRD-056: Daemon-Owned Multi-Project Control Plane

## Objective

Make Familiar a persistent local control plane: one daemon owns
projects, queues, executions, routing, warrants, accounting, and
recovery across every registered project, while CLI, MCP, and any
later human-facing client are adapters over one shared
application-service boundary. Closing a terminal stops observing;
it stops work only under an explicit foreground-only policy.

## Problem

Execution is process-owned today: `drive`/`run`/`resume` orchestrate
inside the invoking CLI process under a per-repository pid lockfile
(`worker_lock.rs`), the PRD-034 supervisor persists work by having
launchd/systemd invoke that same CLI drive per repository, the
wave-one daemon binary only watches files and serves the localhost
dashboard, and the MCP binary opens the database directly. Three
process families write one SQLite database (the B13 contention class),
a closed terminal kills an unsupervised session, and nothing schedules
across projects. Routing and policy live where the command handler
happens to be.

## Goals and non-goals

Goals: daemon-owned detached execution; multi-project registry,
queues, and scheduling; one application-service layer under every
interface; capability-scoped MCP; deterministic recovery across
client, worker, and daemon failure; a migration that never creates two
sources of truth. Non-goals: the tray application (its needs are
served, not built), any public network or server API, Windows named
pipes (Windows is not a supported build today; WSL2 remains the
documented path), new scheduling intelligence beyond deterministic
configured policy, and the future Familiar Server.

## Component boundaries

**Application services (the domain).** One deterministic service layer
owns worker selection and routing (PRD-031/044 registry), execution
policy, warrants and reservations (PRD-024/064), the workflow phase
machine (PRD-039), accounting (PRD-051 ledger, ProjectId), project
identity and registry, authorization decisions, and state queries
(query-model contract). This layer is transport-free and hosts no
terminal I/O.

**Daemon (the host).** The daemon process hosts the services, the
scheduler, the event streams, and the single writer of the
control-plane database (topology below) — absorbing the wave-one
daemon's watcher/summary/dashboard duties so one process owns
mutation (retiring the B13 multi-writer contention class). It exposes
the local socket and supervises worker subprocesses.

## Persistence topology

One **per-user control-plane database** — the existing `familiar.db`
lineage — is the system of record; there are no per-project databases
and therefore no cross-database transactions. It authoritatively owns:
installation identity, project registrations and archival state,
per-project queues and priorities, execution claims and phase state,
event rows and reconnect cursors, global and per-project ceilings,
idempotency keys, capability sessions, PRD-064 reservations, and the
PRD-051 ledger. **Project-local state** is filesystem material the
database references by identity and hash: repository content,
worktrees, checkpoint working trees, and evidence artifacts — portable
with the project, never authoritative over control-plane rows.

Durable submission acknowledgement is one transaction in the
control-plane database; global concurrency and reservations are
enforced atomically there by the single writer. "Single writer" means
exactly one process — the daemon, or the claim-holding in-process
fallback — writes the control-plane database at a time; read-only
clients use snapshot reads labeled per the query model. Project
relocation re-binds resolution evidence to the same ProjectId
(PRD-051/055); removal and archival keep every row; backup is a
whole-database snapshot plus the referenced artifacts, and restore
reconciles against the filesystem, recording divergence (a missing
artifact is a recorded gap, not a deleted row); corruption fails
closed to restore-from-backup with filesystem evidence retained.
Existing rows already live in this one database and are adopted in
place — migration renames ownership, not location. Where
control-plane and project-local state disagree after recovery, the
control plane's record governs and the divergence is recorded as an
explicit fact.

**Adapters (the clients).** The CLI submits commands, streams events,
and renders; MCP exposes least-authority model-facing tools; the
localhost dashboard becomes a read adapter; a future tray client
attaches the same way. Adapters differ in authority, presentation,
and transport — never in domain behavior. MCP is one model-facing
interface into the control plane, not the control plane.

## Multi-project model

The daemon registers projects by durable `ProjectId` (PRD-051's
contract; PRD-055's fuller resolution composes later), each with its
repositories, worktrees, queue, policy, and budgets. Scheduling is
deterministic configured policy: per-project priority and concurrency
ceilings under global ceilings, fair selection among eligible
projects, PRD-039 conflict-scope and dependency rules within each.
Projects pause and resume (pause stops new claims, running work
finishes or checkpoints); archival freezes a project read-only with
full history retained. Budgets bind per project and across projects
through PRD-024 warrants and PRD-064 reservations. Isolation is
project-scoped authorization on every service call: no session,
agent, or repository-declared configuration of one project can read
or steer another (extending PRD-035's cross-repository rule).

## Execution lifecycle

Modes: **detached** (default for unattended work — daemon-owned, no
client required), **attached** (submitted and observed live; ownership
still the daemon's), and **foreground-only** (explicit policy or an
inherently interactive command such as the PRD-033 review decision
surface; bound to its session and cleanly retained if that session
ends).

A submission is validated, persisted to the project queue, and only
then acknowledged with its execution identity — durable state precedes
every externally visible acknowledgement (command/event-model
discipline). Attachment is observation: attach, detach, and reattach
freely with reconnect cursors over the append-oriented event rows;
many read-only observers may follow one execution; a dropped
connection changes nothing about the work. Control actions — cancel,
pause, resume, reprioritize — are explicit, idempotent, authorized
commands; cancellation and timeout propagate to the worker's process
group and finalize observed usage honestly (PRD-051; unknown stays
unknown). Orderly daemon shutdown stops at durable boundaries and
checkpoints; daemon crash recovery replays ownership from storage and
resumes valid checkpoints (PRD-039). **Orphaned workers:** each
worker subprocess is launched with an identity token and, where the
OS supports it, a parent-death mechanism (process groups plus
`PR_SET_PDEATHSIG`-class supervision on Linux) so daemon death
normally takes workers with it. On recovery, a provably dead worker's
rows close honestly with `runner_interrupted`-class reasons (the B13
sweeper lands here). A **surviving** worker may still produce effects
and provider usage, so the new daemon never resumes that stage and
never launches a replacement while the survivor is unadopted: policy
per worker capability is verify-and-adopt (the survivor proves its
launch token and streams to the new owner), wait-for-exit, or
terminate-and-recover; a survivor that cannot be verified, awaited,
or terminated leaves the execution in an explicit
**ambiguous-live-orphan** state requiring operator recovery, and a
late-arriving outcome from a recovering worker is recorded against
its original attempt, never double-counted. These daemon and worker
identities and states are also the evidence this PRD supplies to
PRD-064's owner-liveness contract: process-start identity, nonce, and
claim generation prove an owner provably dead; a surviving or
unverifiable worker maps to the ambiguous liveness state, so its
reservations are never released as though dead. Completion emits a
notification event any adapter can consume.

## Local transport

A Unix-domain socket in the per-user runtime directory carries a
versioned request/response-plus-event-stream protocol. Peer
credentials restrict connections to the same local user; there is no
network listener. Same-user peer identity is only the outer gate:
request authority comes from the session model below, because
harnesses, tool subprocesses, and local models run as the same OS
user. Every request carries a request id; mutating
submissions carry idempotency keys; event subscriptions carry resume
cursors. Version negotiation happens at connect; a stale client is
refused with the upgrade remedy. Discovery is the claim record and
socket path in the runtime directory. The dashboard's localhost
TCP remains read-only presentation.

## Ownership claim and fallback

Mutation authority is one atomic claim, unifying the PRD-039
exclusive-ownership mechanism with the daemon: the claim is an
atomically created runtime-directory record (the `worker_lock`
lineage) whose holder is the only process permitted to mutate. A PID
alone is not identity — PIDs are reused — so the claim record carries
**installation identity, a random owner nonce, the owner pid plus its
process-start identity (or equivalent platform evidence), boot or
session identity where available, the socket path, the protocol
version, and a monotonically increasing claim generation**. A live
process at the claimed pid proves ownership only by echoing the
nonce over the socket handshake; matching pid with mismatched
start-identity or nonce is a reused PID, not the owner. The
daemon acquires the claim **before** binding its socket and releases
it **after** an orderly shutdown reaches a durable boundary and
closes the socket, so the claim's lifetime covers the socket's.

A CLI that needs to mutate resolves ownership deterministically —
**a failed socket connection alone never authorizes fallback**:

- **No claim record** — the daemon is authoritatively absent. The CLI
  attempts the atomic claim itself; on success it runs the identical
  services in-process as the owner. Two CLIs racing here are resolved
  by the atomic create: one wins, the other observes a live owner.
- **Claim held by a live process** — an owner exists. The CLI
  connects and health-checks the advertised socket: healthy and
  version-compatible means submit through the daemon. Unreachable,
  unresponsive past the health timeout, unhealthy, still starting
  (claim held, socket not yet bound), socket permission failure, or
  protocol-version mismatch all mean the same thing: a live owner
  that cannot be used. The CLI **fails closed** with a diagnostic
  naming the owner pid, the observed state, and the exact recovery
  instructions (wait for startup, inspect daemon status and logs,
  upgrade the stale side, or perform an explicit operator recovery
  action). It never starts a competing orchestrator.
- **Claim disproven stale** — the pid is gone, or a process exists at
  that pid whose start identity or nonce does not match (PID reuse: a
  live unrelated process never blocks recovery and is never treated
  as the owner). Recovery is an atomic compare-and-swap on the exact
  stale record that bumps the claim generation — one winner under
  concurrency; the new owner removes the stale socket, runs PRD-039
  crash recovery to durable state, resolves surviving workers (below),
  and only then mutates. Daemon crash is exactly this path;
  simultaneous daemon and CLI startup is the ordinary race, decided
  by the atomic create either way. A live process that matches the
  claim identity but cannot be contacted is a live owner (fail
  closed, above), never a stealable claim.

Read-only inspection needs no claim: where the repository's query
contracts permit direct reads of persisted state, the CLI may serve
them from a safely opened read-only view, labeling results as
possibly stale relative to a running owner (the query model's `Stale`
state, never silently fresh).

## Authority model

Distinct authority classes, never interchangeable: operator (human,
via CLI/tray actions), repository-declared configuration (untrusted
until approved — PRD-036/049), approved configuration snapshots,
agent (a worker's capability-scoped session), observer (read-only
attachment), provider inference credentials, billing credentials
(PRD-052/054 — never in worker environments), and delivery authority
(PRD-033/048). Worker subprocesses receive only the environment and
capabilities their work requires.

**Request authentication by client class.** Every daemon request is
authorized by an unforgeable, daemon-minted session credential bound
to a client class — operator CLI, read-only observer, tray client,
MCP adapter, worker/agent capability session, or internal daemon
component — never by peer uid alone. Operator sessions bootstrap from
an operator credential file readable only by the user and outside
every worker sandbox path; observer sessions carry read-only scope;
adapter and executor components hold their credentials host-side and
issue constrained requests on the model's behalf — a model-controlled
subprocess is never handed a reusable daemon credential, and a
same-user process connecting bare obtains no operator power and no
unrelated-project visibility. Capability tokens and references stay
out of prompts, model-visible environments, tool output, logs, and
accounting rows; worker sandboxes additionally deny the socket path
and credential files as defense in depth, not as the authorization
mechanism. MCP sessions are minted per
(project, execution, attempt, worker) with an explicit authority set:

| Agent may | Agent may never |
|---|---|
| inspect its assigned project, execution, and workflow state | inspect or affect unrelated projects |
| read its warrant and remaining reservation | increase its own warrant or approve its own request |
| report progress and submit evidence | alter provider or billing credentials |
| request another capability or worker | change attribution, policy, or its own tool grants |
| read its relevant accounting labels | erase or rewrite accounting or audit history |

An agent request for more capability, budget, or a different worker
becomes a pending human gate on the PRD-035 surface. No model-facing
interface is an approval path for its own escalation.

## Migration

Exactly one mutating orchestrator exists at any moment; storage stays
the single source of truth throughout.

1. **Extract.** Move routing, policy, warrant, transition, and query
   logic out of CLI command handlers into the application services;
   the CLI calls them in-process. Behavior and pinned outputs are
   unchanged.
2. **Host.** The daemon hosts the same services behind the socket;
   the CLI resolves ownership through the claim protocol above —
   submitting to a healthy owner, failing closed on an unusable live
   owner, and mutating in-process only as the successful claimant of
   an authoritatively absent daemon. Claim and lock are one
   mechanism: the daemon and an in-process orchestrator can never
   both mutate.
3. **Own.** Detached execution, per-project queues, multi-project
   scheduling, orphan sweeping. The PRD-034 supervisor shifts from
   running per-repository drive sessions to keeping the daemon alive;
   `worker run` becomes a submission.
4. **Scope.** MCP re-homes onto the socket as a capability-scoped
   adapter, ending its direct database access.

Existing records (projects, executions, checkpoints, accounting)
migrate or remain readable as-is; every phase leaves current CLI
workflows working; a machine that never starts the daemon keeps
today's behavior indefinitely.

## Tray and server compatibility

A later tray client needs only what the boundary already serves:
projects, queue/run/blocked/failed/completed state, current stage,
worker, provider, model, elapsed time, token usage with
estimated/reconciled cost labels (PRD-051/053/055), warrants and
reservations, billing freshness, pending approvals, control actions,
and notification/evidence links — all over the same socket with
operator authority. No tray framework, widgets, graphs, REST
endpoints, or layouts are specified here (the dormant wave-one tray
feature flag stays dormant). The future optional Familiar Server
keeps only its seams: globally unique installation, project,
execution, and event identities; serializable append-oriented events;
schema versions; lossless export; explicit authority and provenance;
domain logic separated from persistence and transport. It is never a
dependency for local execution.

## Test strategy

Deterministic and offline: fake agents and temporary databases drive
submission/ack idempotency, detach/reattach cursor replay, observer
isolation, per-project and global ceiling enforcement, pause and
archival semantics, foreground-only session teardown, daemon restart
and crash recovery (no repeated stage, honest orphan closure),
same-user socket refusal of foreign peers and stale versions,
ownership races (simultaneous daemon/CLI startup, two concurrent CLI
fallback attempts, stale claim and stale socket recovery, claim held
with socket unbound, health-check timeout against a live owner,
permission failure, version mismatch — each ending with exactly one
owner or a fail-closed diagnostic by exact message), ownership
identity fixtures (PID reuse, stale claim with a live unrelated PID,
daemon death with a dead worker, daemon death with a surviving
worker, failed worker termination, and a worker outcome arriving
during recovery — none resuming a stage or launching a replacement
while a survivor is unadopted), persistence fixtures (submission
transaction failure acknowledging nothing, and recovery where
control-plane and project-local state disagree), an authority fixture
where a same-user malicious subprocess connects directly and is
denied operator actions and unrelated project access, MCP
capability refusals by exact diagnostic, and structural tests
asserting CLI/MCP layers contain no routing or policy implementation.

## Assumptions (recorded 2026-08-30)

- The daemon becoming single writer is compatible with SQLite and the
  existing storage layer; in-process fallback keeps the current
  busy-timeout discipline until phase 3 completes.
- PRD-034's supervisor machinery (launchd/systemd) is reused to keep
  the daemon resident; its per-repository unit shape is superseded in
  phase 3 and recorded as such rather than deleted.
- PRD-053/055 need not be implemented first: ProjectId uses PRD-051's
  minimal issuance, and ceilings enforce through PRD-064 reservations
  (a dependency) with PRD-024 warrant semantics preserved.
