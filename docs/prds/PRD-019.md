# PRD-019: Planner — Design Documents to an Approved PRD Batch

**Status:** Ready for implementation
**Date:** 2026-08-04
**Depends on:** PRD-011, PRD-013, PRD-017, PRD-030, PRD-031, PRD-039
**Architectural direction:** Stewardship Over Control; Determinism Before Intelligence; Trust Is Earned Through Verification
**Delivery boundary:** Independently mergeable PRD-batch generation with a deterministic validation gate and a human batch-approval step

## Objective

Add `familiar-ai plan`: given one or more design documents, use a configured coding agent to draft a dependency-ordered batch of bounded PRDs; validate every draft deterministically against the same closed contracts the backlog enforces; write drafts to a proposal area invisible to backlog discovery; and admit them to the executable backlog only through an explicit human batch approval.

The model drafts; deterministic code judges. A generated PRD that does not parse under the PRD-013 Expected Files grammar, does not carry the required sections, or breaks the dependency graph never reaches the backlog — it is reported as a planner failure, not patched by heuristics.

## Motivation

The planner is the north star's highest-leverage unbuilt organ: decomposition quality determines everything downstream, and the human gate moves from reviewing code to reviewing decomposition. The role has an existence proof — design intent has repeatedly been turned into machine-valid, dependency-ordered PRDs by hand this wave. This PRD productizes that process with the same doctrine as review: LLM output is untrusted material that must survive deterministic validation, and authority to execute comes only from an explicit human approval recorded durably.

## Proposal Area and Approval Model

Backlog discovery reads only the top level of `docs/prds/`; subdirectories are invisible to it (the existing `done/` behavior). The planner therefore writes drafts to `docs/prds/proposed/<batch-id>/PRD-NNN.md`. Approval is file movement plus a durable record:

- `familiar-ai plan <design-doc>...` — generate, validate, write the proposal batch, print a one-screen batch summary (per-PRD title, declared dependencies, Expected Files size) for human review.
- `familiar-ai plan approve <batch-id> --actor human:<identity>` — deterministically re-validate every proposed PRD (content may have been hand-edited during review — that is expected and welcome), verify the batch's numbers are still unclaimed, move the files into `docs/prds/`, and record the approval with actor and per-file content hashes.
- `familiar-ai plan reject <batch-id> --actor human:<identity> --reason <text>` — record the rejection and delete the proposal directory.

Nothing in `proposed/` is ever selected, claimed, or executed. Approval is the only path in, and it re-validates at approval time so review edits cannot smuggle an invalid contract past the gate.

## Generation and Validation

Generation uses one configured agent — a `[planner]` entry with the same shape and validation as the PRD-014 `[agents]` entries — invoked with the design documents and the numbering/grammar/section rules in its prompt. The agent's output is parsed as PRD files and then judged; the planner never edits a draft to make it pass.

Deterministic admission gate, all fail-closed, per draft and per batch:

1. Filename `PRD-NNN.md` with the next unused numbers (checked against `docs/prds/` and `proposed/`).
2. Required sections present: Objective, Scope, Non-goals, Acceptance Criteria, Test Strategy, Expected Files, Definition of Done; a `Depends on:` line naming only existing or in-batch PRDs.
3. The Expected Files section parses under the exact PRD-013 grammar.
4. The batch's dependency graph, unioned with the existing backlog, passes the existing graph validation (no cycles, no unknown references).
5. Bounded size: configured ceilings on PRDs per batch and bytes per PRD.

Any failure reports the draft, line, and rule, retains the raw agent output as an artifact for inspection, and produces no proposal files for the failing batch.

## Non-goals

This PRD does not:

- let an LLM approve, admit, renumber, or edit anything — every authority action is human or deterministic code;
- execute, claim, or schedule PRDs (the approved batch is ordinary backlog for `run`/`drive`);
- attach or enforce budget warrants (the driver's warrant from PRD-017 remains the execution ceiling);
- modify backlog discovery, admission, claim, completion, or recovery semantics;
- summarize or rewrite design documents, maintain them, or check them into any new location;
- add multi-repository planning, replanning of failed runs, or incremental batch editing commands beyond approve/reject; or
- modify prior PRDs, architecture documents, ADRs, contracts, or philosophy.

## Acceptance Criteria

1. `plan` drafts a batch from design documents via the configured planner agent and writes it only under `docs/prds/proposed/<batch-id>/`, which backlog discovery, `next`, `run`, and `drive` provably never see.
2. Every proposed PRD passed the deterministic gate: valid next-unused numbering, required sections, a PRD-013-valid Expected Files contract, and a batch dependency graph that validates against the existing backlog.
3. A draft failing any rule fails the batch with the exact draft, line, and rule named; raw agent output is retained as an artifact; no proposal files are written for a failed batch.
4. `plan approve` re-validates every file at approval time, moves the batch into `docs/prds/`, and durably records batch id, actor, timestamp, and per-file content hashes; approved PRDs are immediately ordinary backlog entries.
5. `plan reject` records actor and reason durably and removes the proposal.
6. Approval requires an explicit `human:` actor exactly as PRD-012 recovery does; there is no non-human spelling.
7. The planner agent entry is validated with the same fail-closed rules as PRD-014 agent entries; planner usage is recorded in execution history with the existing honest accounting (unknown stays unknown).
8. Hand-editing a proposed PRD before approval is supported: approval judges current file content, not generation-time content.
9. All tests use fake planner agents emitting fixture drafts (valid, invalid-grammar, bad-numbering, cyclic); no test invokes a real model or network.
10. Formatting, focused Clippy, focused tests, and the full workspace suite pass, with demonstrably pre-existing failures reported separately with exact evidence; the change is confined to the expected files and independently mergeable.

## Test Strategy

- Gate unit tests per rule: numbering collisions (including against `proposed/`), missing sections, grammar violations (line and rule named), unknown and cyclic dependencies, size ceilings.
- Fake-agent batches: a valid batch lands in `proposed/` with a pinned summary; each invalid fixture fails with its exact diagnostic and retains the raw artifact.
- Discovery invisibility: with a populated `proposed/`, `next` and `drive` selection are byte-identical to an empty one.
- Approval: re-validation catches a hand-edit that breaks the grammar; a clean approve moves files, records hashes/actor, and the batch becomes selectable; reject records and removes; non-`human:` actors are refused.
- Storage round-trip for batch records; migration coverage.

## Expected Files

The implementation is expected to modify or add only:

- `crates/familiar-ai-daemon/src/plan.rs` — generation orchestration, the deterministic gate, approval/rejection, with unit tests
- `crates/familiar-ai-daemon/src/lib.rs` — module export
- `crates/familiar-ai-daemon/src/bin/familiar-ai.rs` — `plan`, `plan approve`, `plan reject` subcommands
- `crates/familiar-ai-core/src/config.rs` — typed `[planner]` configuration and validation
- `config/default.toml` — documented defaults
- `crates/familiar-ai-storage/migrations/` — the next unused additive migration for batch proposals and approvals
- `crates/familiar-ai-storage/src/` — migration registration and the batch repository
- `crates/familiar-ai-storage/tests/` — migration and round-trip coverage
- `crates/familiar-ai-daemon/tests/` — planner integration coverage

No new crate or third-party dependency is expected. Changes outside this list require explicit pull-request justification. In particular, `familiar-ai-review` (whose Expected Files parser is consumed, not changed) and backlog domain code are not expected to change.

## Definition of Done

PRD-019 is done when design documents go in, a validated dependency-ordered batch lands in the proposal area with a reviewable one-screen summary, nothing executes without an explicit recorded human approval that re-validates every file, every planner failure names its draft, line, and rule with the raw output retained — and an approved batch is indistinguishable from hand-written backlog to everything downstream.
