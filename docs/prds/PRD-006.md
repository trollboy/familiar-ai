# PRD-006: Context Compiler v1

**Status:** Ready for implementation  
**Date:** 2026-08-03  
**Architectural direction:** Context Is Precious; Determinism Before Intelligence  
**Delivery boundary:** Independently mergeable extraction of deterministic execution context compilation

## Objective

Replace the ad hoc repository, PRD, and document-context construction in the `familiar run` path with a deterministic `ContextCompiler` that accepts a repository and PRD as input and produces a structured `ExecutionContext`.

`ExecutionContext` records the canonical repository and worktree identities, current Git commit when available, validated PRD, every directly included document, the exact reason each document was included, and deterministic token estimates. It becomes the canonical prepared context input for future execution work.

The existing run pipeline remains responsible for rendering the unchanged execution prompt, invoking the existing `CodingAgent`, streaming output, and recording execution history. Context compilation performs no execution and introduces no functional change to `familiar run`.

## Motivation

Familiar owns context compilation as a permanent stewardship responsibility. The current implementation in `crates/familiar-daemon/src/run.rs` performs that responsibility indirectly through private functions that resolve Git state, validate the PRD, scan its text for selected references, read documents, and immediately concatenate those values into a prompt string.

That arrangement has three problems:

1. The result is an opaque string rather than an inspectable context artifact.
2. Inclusion decisions and repository provenance are not represented explicitly, so callers cannot explain or test why a document was present.
3. Context discovery, prompt rendering, and execution orchestration are coupled even though they have distinct responsibilities.

Context Compiler v1 creates the smallest useful deterministic boundary. It preserves the repository as truth, makes inclusion reproducible, and gives future execution work a structured canonical input without prematurely implementing budgets, reduction, semantic retrieval, task packages, agent-specific rendering, or execution supervision.

## Scope

This PRD includes:

1. A focused context-compilation module or crate exposing `ContextCompiler`, `ContextRequest`, `ExecutionContext`, repository metadata, document records, inclusion reasons, token estimates, and categorized compilation errors.
2. Deterministic resolution of the supplied repository/worktree and PRD using canonical filesystem and Git observations.
3. Validation that the PRD is a regular UTF-8 Markdown file contained beneath the selected worktree's `docs/prds` directory.
4. Deterministic discovery of directly referenced ADRs, contracts, and supporting documents from the PRD source only.
5. Canonical repository-relative document identities, exact source content, document kind, inclusion reason, and deterministic ordering.
6. Recording of the canonical worktree path, canonical Git common-directory identity, and optional current `HEAD` commit.
7. Deterministic token estimates for each included document and for the complete context content represented by v1.
8. Refactoring the existing run pipeline to compile an `ExecutionContext` before rendering the execution prompt.
9. Preservation of the existing prompt bytes, fixed execution constraints, direct ADR/contract presentation, working directory, history, pricing, output, failure, and CLI behavior.
10. Focused unit and integration tests for compilation, provenance, inclusion, ordering, estimation, error handling, and unchanged run behavior.

### Separation of responsibilities

The `ContextCompiler` owns:

- canonicalizing and validating the requested worktree and PRD;
- resolving the Git common-directory repository identity and optional `HEAD`;
- reading the PRD as authoritative source;
- discovering allowed direct document references from the PRD;
- validating and reading referenced documents;
- assigning document kinds and explicit inclusion reasons;
- producing deterministic document ordering; and
- calculating deterministic token estimates.

The existing run orchestration continues to own:

- loading configuration and opening execution history;
- applying the fixed execution constraints;
- rendering the current execution prompt from `ExecutionContext` without changing its bytes;
- creating and finalizing execution-history records;
- invoking the existing `CodingAgent` abstraction;
- streaming output and propagating execution status; and
- applying current duration, missing-value, total-token, and pricing rules.

## Non-goals

This PRD does not:

- invoke an LLM for any purpose;
- summarize, rewrite, interpret, rank, or infer meaning from documents;
- create or consume embeddings;
- add vector, semantic, fuzzy, or model-assisted search;
- add model or coding-agent routing, selection, capabilities, or configuration;
- execute a coding agent, command, test, build, formatter, or verification step;
- change `CodingAgent`, `ExecutionRequest`, `ExecutionResult`, `AgentExecutionError`, or `CodexAgent` semantics;
- change the existing execution prompt template, fixed constraints, headings, document content, whitespace, or ordering for inputs supported today;
- implement token budgets, token reduction, truncation, omission, compression, or document substitution;
- add recursive or transitive reference traversal;
- scan arbitrary repository source files for relevance;
- use stored summaries, decisions, findings, handoffs, session rollups, or repository indexes;
- persist context artifacts or add a database schema or migration;
- add hashes, immutable artifact storage, task contracts, capability profiles, warrants, policy, review, or later target-state context-package features;
- modify MCP, daemon IPC, dashboard, history, usage, or CLI presentation; or
- modify philosophy, architecture documents, ADRs, contracts, or prior PRDs.

## Architecture

The implementation introduces a deterministic compilation boundary before prompt rendering:

```text
familiar run <prd-path>
          |
          v
ContextCompiler
  - validate worktree and PRD
  - resolve repository and Git metadata
  - discover direct references
  - read authoritative documents
  - record inclusion reasons
  - estimate tokens
          |
          v
ExecutionContext
  - repository metadata
  - PRD document
  - ordered referenced documents
  - provenance and token estimates
          |
          v
existing execution-prompt renderer
          |
          v
existing run history + CodingAgent execution
```

Compilation is a pure read-and-observe stage except for invoking read-only Git commands. Given identical filesystem content, canonical paths, and Git state, it must produce an equal `ExecutionContext`.

`ExecutionContext` is agent-neutral and contains no executable name, model, provider, process arguments, output sink, execution result, history identifier, price, or routing decision. It describes the context selected for execution; it does not authorize or perform execution.

The preferred implementation is a small `familiar-context` workspace crate. A separate crate provides a stable public contract and prevents context compilation from depending on daemon orchestration, storage, agent adapters, MCP, or LLM subsystems. If repository evidence demonstrates that a crate would add no useful boundary, an equivalently focused public module under `familiar-daemon` is acceptable, but its dependency direction and public semantics must remain the same.

## Public Types

Exact Rust module paths and field naming may follow repository conventions, but the public semantic contract must be equivalent to:

```rust
pub struct ContextCompiler {
    // Stateless in v1, or contains only deterministic collaborators.
}

impl ContextCompiler {
    pub fn compile(
        &self,
        request: ContextRequest<'_>,
    ) -> Result<ExecutionContext, ContextCompilationError>;
}

pub struct ContextRequest<'a> {
    pub repository: &'a std::path::Path,
    pub prd: &'a std::path::Path,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ExecutionContext {
    pub repository: RepositoryContext,
    pub prd: ContextDocument,
    pub documents: Vec<ContextDocument>,
    pub estimated_tokens: u64,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct RepositoryContext {
    pub repository: std::path::PathBuf,
    pub worktree: std::path::PathBuf,
    pub git_commit: Option<String>,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ContextDocument {
    pub path: String,
    pub kind: DocumentKind,
    pub content: String,
    pub inclusion: InclusionReason,
    pub estimated_tokens: u64,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum DocumentKind {
    Prd,
    Adr,
    Contract,
    Supporting,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum InclusionReason {
    RequestedPrd,
    DirectReference { referenced_by: String },
}
```

The concrete API may use validated newtypes for repository-relative paths or token counts. It must preserve the following semantics:

- `repository` is the canonicalized Git common-directory identity currently recorded by execution history.
- `worktree` is the canonicalized Git worktree root in which execution will occur.
- `git_commit` is the exact trimmed output of `git rev-parse --verify HEAD` when that command succeeds and returns a non-empty value; otherwise it is `None`, preserving current behavior.
- `prd.path` and every referenced document path use `/`-separated, canonical repository-relative identities.
- `prd.inclusion` is always `RequestedPrd`.
- Every referenced document records `DirectReference` and identifies the PRD path as `referenced_by`.
- `documents` excludes the PRD itself and contains each included referenced path exactly once.
- `documents` has a stable lexical ordering by canonical repository-relative path, preserving the current `BTreeSet` ordering for existing ADR and contract references.
- `estimated_tokens` uses checked arithmetic and cannot silently wrap.

`ContextCompilationError` must distinguish at minimum:

- invalid or unavailable repository/worktree input;
- failed Git metadata queries needed to identify the worktree or common directory;
- empty, missing, non-file, non-Markdown, or out-of-scope PRD input;
- unreadable or non-UTF-8 PRD content;
- unresolved, escaping, non-file, non-Markdown, or unreadable direct references; and
- token-estimate or aggregate arithmetic overflow.

Errors must identify the affected path or Git operation and retain their underlying source where one exists. They must not contain prompt-rendering, agent, provider, storage, or execution concerns.

## Data Flow

1. The unchanged CLI receives `familiar run <prd-path>` and the run pipeline identifies the current directory as it does today.
2. Run constructs `ContextRequest` with that repository/worktree input and the supplied PRD path.
3. `ContextCompiler` asks Git for `--show-toplevel`, canonicalizes the resulting worktree, resolves `--git-common-dir` to the canonical repository identity, and observes optional `HEAD` with `rev-parse --verify HEAD`.
4. The compiler resolves the supplied PRD path, validates containment beneath `<worktree>/docs/prds`, validates a `.md` regular file, reads it as UTF-8, and creates the required PRD document record.
5. The compiler scans only the PRD's exact source text for syntactically eligible direct repository-relative document references.
6. Candidate references are normalized only through filesystem canonicalization and repository-relative identity conversion; no semantic interpretation is performed.
7. Each unique reference is validated against its allowed documentation root, read exactly once, classified, assigned an explicit inclusion reason, and inserted in lexical path order.
8. The compiler estimates each document independently and computes the checked aggregate estimate.
9. The compiler returns `ExecutionContext` without rendering a prompt, mutating state, or executing an agent.
10. The run pipeline renders the existing prompt from the structured context using the unchanged template and fixed constraints, then performs the existing history and agent-execution flow.

No prompt, context, source content, metadata, or estimate is newly persisted in v1.

## Inclusion Rules

Inclusion must be deterministic and explainable.

### Required PRD

The supplied PRD is always included exactly once with:

- `DocumentKind::Prd`; and
- `InclusionReason::RequestedPrd`.

The PRD must be contained beneath the selected worktree's canonical `docs/prds` directory, must be a regular file, must have the exact lowercase `.md` extension, and must be readable as UTF-8. These rules preserve current validation semantics.

### Direct references

Only literal repository-relative Markdown paths present in the PRD source are eligible. The compiler does not follow references found inside referenced documents.

Eligible paths are divided into these kinds and allowed roots:

| Literal prefix | Required containment root | Kind |
|---|---|---|
| `docs/adr/` | `<worktree>/docs/adr` | `Adr` |
| `docs/contracts/` | `<worktree>/docs/contracts` | `Contract` |
| `docs/supporting/` | `<worktree>/docs/supporting` | `Supporting` |

Supporting-document discovery is intentionally limited to the explicit `docs/supporting/` namespace in v1. This prevents broad `docs/` scanning, accidental inclusion of architecture or prior PRDs, and changes caused merely by prose mentioning another document. Additional supporting namespaces require a later explicit contract.

For each prefix, scanning uses the same deterministic literal-path grammar as the current run implementation: after the prefix, ASCII alphanumeric characters plus `/`, `-`, `_`, and `.` remain part of the candidate; trailing sentence periods are removed; and only candidates ending in `.md` are considered.

Each candidate must canonicalize to a regular file beneath its corresponding allowed root. Symlink or traversal escape is rejected. An eligible literal that cannot be resolved or validated fails compilation rather than being silently omitted.

Duplicate mentions of the same canonical repository-relative path produce one `ContextDocument`. Its inclusion reason remains `DirectReference` to the requested PRD because v1 has exactly one discovery source. Distinct paths are sorted lexically by their `/`-separated repository-relative identity.

No file is included because of filename similarity, keywords, directory proximity, Git history, stored metadata, summaries, embeddings, model output, or references in another included document.

### Prompt compatibility

The existing prompt renderer consumes the PRD and ordered documents from `ExecutionContext`. For the currently supported ADR and contract inputs, its emitted bytes must remain identical, including headings, blank lines, source bytes, final newlines, and lexical ordering. The compiler does not own the fixed execution constraints or any prompt prose.

The new supporting-document kind uses the same existing `## Directly referenced document: <path>` rendering form when such a document is explicitly referenced. No other prompt section or wording changes are permitted.

## Token Estimation Strategy

Context Compiler v1 reuses the repository's existing deterministic estimator in `familiar-tokens`: Unicode scalar-value count divided by four, rounded up.

Equivalent behavior is:

```rust
estimated_tokens = content.chars().count().div_ceil(4)
```

Rules:

1. Estimation is performed over each document's exact `content` field only.
2. The PRD estimate and every referenced-document estimate are recorded independently.
3. `ExecutionContext.estimated_tokens` is the checked sum of the PRD estimate and all referenced-document estimates.
4. Prompt template text, fixed execution constraints, headings, separators, repository metadata, and agent protocol overhead are not included in the v1 context estimate because they are not document context.
5. Counts are converted to the public integer type using checked conversion. Conversion or aggregation overflow returns a categorized compilation error.
6. No tokenizer, model-specific encoding, network service, cache, sampling, truncation, or correction factor is introduced.
7. Empty content estimates to zero. UTF-8 multibyte encoding does not increase the count beyond the number of Unicode scalar values, matching `familiar_tokens::estimate_tokens`.

The estimate is an explicit deterministic approximation, not a claim about provider billing tokens or model context-window consumption. Execution history continues to record only observations reported by the executing agent and its pricing semantics remain unchanged.

## Acceptance Criteria

1. A public deterministic `ContextCompiler` accepts a repository and PRD input and returns a structured `ExecutionContext`.
2. `ExecutionContext` contains canonical repository identity, canonical worktree, optional current Git commit, required PRD, ordered referenced documents, explicit inclusion reasons, per-document estimates, and a checked aggregate estimate.
3. The PRD is validated with the same containment, regular-file, lowercase `.md`, canonicalization, and UTF-8 behavior currently enforced by `familiar run`.
4. Repository identity, worktree, and optional `HEAD` observations match the current run-history values for the same Git state, including linked-worktree behavior and unavailable `HEAD` behavior.
5. Direct ADR and contract discovery preserves the current literal grammar, containment protection, failure semantics, deduplication, and lexical ordering.
6. Direct supporting documents are recognized only beneath `docs/supporting/` and use the same literal grammar, canonical containment, deduplication, and ordering rules.
7. Every included document has exactly one inspectable kind and inclusion reason; no included document has an inferred or unspecified reason.
8. Discovery examines only the supplied PRD source. References inside ADRs, contracts, or supporting documents are not followed.
9. No LLM, summarizer, embedding, vector index, semantic search, inference backend, model router, or network service is called or added as a dependency.
10. Token estimates exactly match `familiar_tokens::estimate_tokens` for ASCII, Unicode, empty, and boundary-length fixtures.
11. The aggregate estimate includes all and only document-content estimates and fails safely on checked conversion or addition overflow.
12. The compiler performs no truncation, reduction, omission for budget, ranking, summarization, prompt rendering, process execution, database mutation, or execution-history mutation.
13. The run orchestration obtains repository metadata, PRD content, and referenced documents from `ExecutionContext` rather than maintaining a second discovery or resolution implementation.
14. The run orchestration remains dependent only on structured context and the existing agent execution boundary during their respective stages; the context compiler does not depend on `familiar-agent` or storage.
15. Existing prompt fixtures are byte-for-byte unchanged for all currently supported ADR and contract inputs.
16. `familiar run`, `familiar history`, and `familiar usage` syntax, help, stdout, stderr, exit status, streaming, history, metrics, missing-value, timing, and pricing behavior are unchanged.
17. Existing fake-Codex integration tests pass without functional expectation changes.
18. No schema, migration, configuration, MCP, daemon-runtime, architecture, ADR, contract, philosophy, or prior-PRD change is introduced.
19. Production code contains no agent routing, execution, token reduction, semantic retrieval, or later-roadmap context features.
20. The change is one independently mergeable context-compilation extraction.

## Test Strategy

### Context compiler unit tests

- Compile the same repository state twice and assert equal `ExecutionContext` values.
- Assert PRD kind, source content, repository-relative path, inclusion reason, and token estimate.
- Assert ADR, contract, and supporting-document classification and `DirectReference` provenance.
- Assert duplicate references are included once and documents are ordered lexically across kinds.
- Assert references inside an included document are not followed.
- Assert unknown paths, bare filenames, absolute paths, non-Markdown paths, and other `docs/` namespaces are not discovered.
- Assert syntactically eligible missing references fail with their exact path identified.
- Assert canonical containment rejects `..`, symlink escape, wrong-root classification, and paths outside the worktree.
- Assert empty, missing, directory, uppercase-extension, out-of-tree, unreadable, and non-UTF-8 PRDs fail in the correct category.
- Assert unreadable, directory, non-UTF-8, and escaping referenced documents fail in the correct category.
- Assert ASCII, Unicode, empty, exact-boundary, and multi-document estimates match `familiar_tokens::estimate_tokens`.
- Assert checked aggregate overflow behavior through a focused estimator boundary or injectable deterministic test fixture without allocating an impractically large document.

### Git and repository boundary tests

- Use temporary Git repositories and linked worktrees; never depend on a developer's repository or global Git configuration.
- Assert canonical worktree and Git common-directory identities match Git observations.
- Assert `HEAD` is recorded exactly when available and remains `None` for the same currently tolerated unavailable-commit cases.
- Assert a non-repository input and failures of required Git identity queries return categorized errors.
- Assert repository-relative identities always use `/` separators.

### Run compatibility tests

- Preserve existing prompt-construction fixtures and compare the complete rendered prompt before and after the extraction byte for byte.
- Preserve fake-agent orchestration tests and assert the agent receives the same worktree and prompt.
- Preserve fake-Codex end-to-end tests for exact arguments, stdin, stdout, stderr, live flush, exit status, history, usage, metrics, and pricing.
- Add a focused supporting-document fixture proving explicit inclusion and the unchanged directly referenced document rendering form.
- Assert compilation failure occurs before agent execution and does not create an execution-history row, matching current pre-history validation behavior.

### Verification commands

Implementation must run:

- `cargo fmt --all -- --check`;
- focused context compiler and token-estimation unit tests;
- focused run prompt, pricing, and fake-agent tests;
- the fake-Codex CLI integration suite;
- Clippy with warnings denied for the new crate and affected targets; and
- an attempted workspace test suite, with pre-existing or unrelated failures distinguished from implementation failures.

Test expectation changes are prohibited except for module paths, public type names, dependency injection, and new supporting-document fixtures. Existing prompt snapshots, prompt bytes, arguments, output, history values, pricing values, and exit-status expectations must not change.

## Definition of Done

PRD-006 is done when:

1. `ContextCompiler` deterministically produces the canonical `ExecutionContext` for one validated repository/worktree and PRD.
2. The result records repository identity, worktree, optional Git commit, authoritative PRD content, all eligible direct documents, document kinds, exact inclusion reasons, per-document estimates, and checked aggregate estimated tokens.
3. Direct discovery is limited to literal ADR, contract, and `docs/supporting/` references in the PRD, with deterministic validation, deduplication, ordering, and no transitive traversal.
4. Token estimates reuse the existing deterministic character-based estimator and are clearly separate from execution-observed billing usage.
5. The existing run pipeline renders the same prompt and remains solely responsible for agent execution, streaming, history, metrics, pricing, failures, and exit propagation.
6. No LLM, summarization, embedding, vector search, semantic search, routing, reduction, truncation, execution, persistence, or later context-package feature is introduced.
7. Focused compiler, repository, prompt, fake-agent, and fake-Codex tests pass without functional expectation changes.
8. Formatting and focused Clippy pass, and the workspace suite is attempted with unrelated failures reported separately.
9. No database, configuration, MCP, architecture, ADR, contract, philosophy, prior PRD, or unrelated subsystem is changed.
10. The implementation is independently mergeable as one behavior-preserving deterministic context-compilation extraction.
