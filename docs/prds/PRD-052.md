# PRD-052: Authoritative Anthropic Organization Cost Collection

## Objective

Give Familiar its first authoritative billing source: Anthropic
organization accounts collected through the Admin cost-report API into
the PRD-051 ledger as provider-authoritative observations — multiple
organizations, independent cursors, exact money handling, and BYO-Auth
discipline — while individual accounts and foreign clouds fail closed
to honest local-estimate coverage.

## Design

**A billing source is a provider.** PRD-047's kind-tagged provider
entries gain `kind = "billing"`; no competing abstraction. The entry
carries an auth descriptor referencing an externally managed credential
(`env: ANTHROPIC_ADMIN_KEY`, an OAuth session the operator maintains) —
never a value. Configuration flows through the PRD-047 machinery:
probe-before-persist, comment-preserving TOML, actor/UTC provenance,
one decision row per mutation with before/after hashes.

    familiar-ai config provider add org-main --kind billing \
        --auth env:ANTHROPIC_ADMIN_KEY
    Added org-main (billing) — organization "Acme" (org_…7f2) via
    /v1/organizations/me.
    org-main: credential lacks organization authority — individual API
    accounts have no Admin API; view billing in the Claude Console, or
    supply an organization Admin key. Nothing added.

    familiar-ai billing status            # cached; staleness + remedy
    familiar-ai billing collect [org-main] [--month 2026-08]   # network

**Organization identity is discovered, not declared.** Each credential
resolves to exactly one organization via `GET /v1/organizations/me`;
the discovered id is the source's identity. A second source resolving
to an already-bound organization is rejected before persistence — the
double-count guard. Multiple distinct organizations for one operator
are first-class: independent credentials, cursors, workspaces, and
failure states.

**Deterministic collection.** Windows are UTC and half-open, aligned to
the API's daily buckets (`GET /v1/organizations/cost_report`,
RFC 3339 `starting_at`/`ending_at`, `group_by` workspace and
description, `has_more`/`next_page`). A window is complete only after
pagination finishes; partial pages retain the prior complete snapshot
and record a failed attempt. Rows are append-only, deduplicated by
(source, dimensions, bucket); re-collection is idempotent. The `amount`
string is parsed with exact decimal arithmetic — the verbatim string is
retained, the normalized value is integer microusd rounded half-to-even
— and credits, adjustments, and non-token charges keep their provider
classification. Provider-authoritative rows are subject to reporting
delay and never claim completeness for the current day.

**Security.** Collection runs in a narrowly scoped host-side component
with read-only authority: it can query billing endpoints and nothing
else — no model execution, configuration, merge, or delivery power. The
admin credential is resolved at call time from its external reference
and is scrubbed from every spawned agent/model process environment; an
Anthropic Admin key must never be inherited by a Claude Code
subprocess. Threats designed against: malicious repository content
declaring billing config (inert without PRD-049 approval and
machine-local binding), log/report leakage (references only, value
redaction tested), credential confusion between organizations (identity
re-verified against the bound org id on every collection), and
double-counting (duplicate-binding rejection plus row dedup).

**Foreign billing systems.** Bedrock, Vertex/Agent Platform, Microsoft
Foundry, and future brokers are declared as recognized `external-billing`
modes behind the same collector interface, but no cloud SDK enters the
workspace and no collector for them is implemented here. Configuring
one fails closed naming its status: local-estimate-only coverage until
a dedicated PRD authorizes a collector.

## Scope

- `kind = "billing"` provider entries with mode, auth descriptor, and
  discovered organization identity; probe implementation over
  `/v1/organizations/me`; duplicate-organization rejection.
- The collector component, collection cursors and window state, raw
  provider observation rows feeding the PRD-051 ledger as
  `authoritative-report` mode facts.
- `billing status` (cached, staleness-labeled) and `billing collect`
  (explicit network) verbs; `config provider list` shows billing
  sources with mode, organization, authority state, last successful
  collection, and coverage window.
- Exact remediation strings for the closed failure set: no Admin API
  (individual account), missing credential reference, expired
  credential, insufficient role.
- Contract text in docs/contracts/providers.md for the billing kind,
  collection semantics, and the unsupported-mode vocabulary.

## Assumptions (recorded at specification time, 2026-08-30)

- The Admin API surface is as documented at specification time: one
  organization per credential, daily buckets, string amounts, cursor
  pagination. If bucket granularity or grouping evolves, collection
  gains capability without schema breakage because raw responses are
  retained verbatim.
- Anthropic reports amounts in USD; currency is nonetheless persisted
  per row so a future non-USD report cannot be silently misread.
- HTTP goes through the workspace's existing `reqwest` dependency; no
  new client stack and no cloud SDKs.
